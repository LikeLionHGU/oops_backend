# OoPs?! 보안·운영 정책

> 기준 브랜치: `minwook` · 기준일: 2026-10-06

이 문서는 현재 구현된 보호 장치와 아직 보완해야 하는 항목을 나누어 기록한다. 구현하지 않은 기능을 “보안이 적용되었다”고 설명하지 않는 것을 원칙으로 한다.

## 1. 데이터 흐름과 보호해야 할 대상

```text
사용자 영상
  → Spring Boot 업로드 API
  → 원본 파일 저장
  → Python STT/OCR
  → OpenAI·뉴스 검색(선택)
  → 분석 결과·리포트 저장
  → 사용자에게 결과 제공
```

보호 대상은 원본 영상, STT 대본, OCR 결과, 분석 리포트, 외부 API 키, 사용자별 영상 접근 권한이다. 특히 영상과 대본에는 인물·대화·개인정보가 포함될 수 있으므로, “데모 데이터”라고 가정하고 로그나 외부 API로 무제한 복사해서는 안 된다.

서비스의 판단 대상은 영상 속 발언·행동·화면 문구이지, 사람의 출신 지역·정치 성향·커뮤니티 이용 여부 같은 정체성이 아니다. 모델이 이런 정보를 추정하거나 저장하지 않도록 입력과 출력 스키마를 제한해야 한다.

### 신뢰 경계

```text
브라우저·외부 클라이언트
  ↓ HTTPS / CORS / 요청 제한
Nginx·Spring Boot API
  ├─ DB·로컬 저장소
  ├─ Python 분석 서버
  └─ OpenAI·뉴스 검색
```

경계가 바뀔 때마다 보호 방식도 달라진다. CORS는 브라우저의 출처 제한일 뿐 사용자 인증이 아니며, IP 요청 제한은 영상 소유권 확인이나 외부 API 비용 상한을 대신하지 않는다. 특히 Python 분석 서버는 `filePath`와 OCR `frameDir`을 요청으로 받으므로, 외부에 공개되면 임의 파일 읽기·쓰기 경로로 악용될 수 있다. 이 서버는 반드시 내부 네트워크에서만 접근 가능해야 한다.

## 2. 현재 적용된 보호 장치

### 네트워크와 API

- 외부 요청은 Nginx를 거쳐 Spring Boot API로 들어오는 구조다.
- Python 분석 서버는 외부 클라이언트가 직접 호출하는 공개 API가 아니라 내부 분석 서버로 사용한다.
- CORS는 허용된 프론트엔드 Origin 목록을 설정으로 관리한다.
- 업로드·YouTube 등록·재시도 API에 IP 기준 요청 제한을 적용했다.
- 응답의 `X-Request-Id`와 서버 로그의 추적 ID를 연결해 장애를 추적한다.
- `/health`는 Spring Boot 자체뿐 아니라 Python 분석 서버와 저장소 상태도 확인한다.

현재 요청 제한은 Spring 인스턴스 내부 메모리에 저장하는 고정 윈도우 방식이며, 인증 전까지 업로드·재시도를 IP 기준으로 제한한다. 따라서 여러 대로 늘리면 인스턴스마다 한도가 따로 적용되고, Python·뉴스·OpenAI 호출 자체는 제한하지 않는다. `X-Forwarded-For`와 `X-Real-IP`는 신뢰하는 프록시가 덮어쓰는 환경에서만 사용해야 하며, Spring을 직접 인터넷에 노출한 상태에서 임의 헤더를 믿으면 제한을 우회할 수 있다.

`allowCredentials(true)`인 CORS 설정은 실제 프론트 Origin만 운영 설정에 넣어야 한다. CORS 허용 목록에 도메인을 추가하는 것만으로 영상 접근 권한이 생기지는 않으며, 인증 도입 후에는 모든 영상·리포트·프레임 API에서 소유권 검사를 별도로 수행해야 한다.

### 파일 업로드와 저장

- 업로드 크기와 허용 확장자를 제한한다.
- 저장 파일명은 사용자 입력 파일명을 그대로 경로로 사용하지 않고 서버가 생성한 ID를 기준으로 만든다.
- 경로 순회 공격을 막기 위해 저장 경로가 설정된 저장소 내부인지 확인한다.
- 원본 파일은 설정한 보관 시간이 지나면 자동 삭제할 수 있다. 현재 기본값은 기존 데모 동작을 보존하기 위해 자동 삭제하지 않는 설정이다.
- 전체 산출물도 별도의 보관 기간 설정으로 정리할 수 있다.

현재 업로드 검사는 500MB 크기와 `mp4`·`mov`·`avi` 확장자를 확인하고, 분석 서버의 `ffprobe`로 영상 길이를 확인하는 수준이다. 확장자와 실제 파일 형식이 일치하는지, 악성 코덱·압축 폭탄·재생기 취약점이 없는지까지 검증하는 것은 아니다. 공개 운영에서는 MIME·파일 시그니처·코덱·해상도·길이를 함께 검사하고, 필요하면 격리 영역에서 재인코딩한 파일만 분석해야 한다.

### 비밀정보

- OpenAI·Naver 등 API 키는 코드에 하드코딩하지 않고 환경변수 또는 운영 설정으로 주입한다.
- `.env`와 실제 키 파일은 Git에 커밋하지 않는다.
- 키가 노출되었다고 판단되면 저장소에서 문자열만 지우는 것으로 끝내지 말고 해당 키를 폐기·재발급해야 한다.

## 3. 현재 남아 있는 보안 공백

다음 항목은 아직 제품 수준으로 완료되었다고 볼 수 없다.

1. 사용자 인증과 영상 소유권 검사가 완성되지 않았다. `videoId`를 아는 사용자가 다른 영상에 접근할 수 있는지 반드시 점검해야 한다.
2. 로컬 H2와 로컬 디스크 중심이라 서버 관리자나 호스트 접근 권한이 있는 사람은 원본 파일에 접근할 수 있다.
3. 저장 데이터의 암호화, 백업 암호화, 키 관리 방식은 운영 인프라에서 별도로 확정해야 한다.
4. Python 내부 API에 애플리케이션 간 별도 인증 토큰이 없다면, 포트·보안 그룹·localhost 바인딩으로 외부 노출을 막아야 한다.
5. 파일 내용의 확장자 위조 검사, 악성 파일 검사, 업로드 후 안전한 재인코딩은 추가 검토가 필요하다.
6. 중앙 로그 보관, 감사 로그, 관리자 접근 이력, 침해 탐지 알림이 아직 운영 정책으로 정리되어 있지 않다.

7. 영상 URL 등록은 현재 입력값이 비어 있지 않은지만 검증한다. 허용할 호스트를 YouTube 등으로 제한하고, 리다이렉트·다운로드 크기·다운로드 시간도 제한해야 서버가 임의 외부 URL의 다운로드 대행자가 되지 않는다.
8. 스트리밍·프레임·대본·OCR 원문·리포트 API가 `videoId`만으로 동작하므로 인증을 붙이기 전에는 ID를 아는 사람이 다른 영상 자료를 조회할 수 있는지 공개 운영을 해서는 안 된다.
9. Python 분석 API에는 현재 애플리케이션 간 인증이 없고, `filePath`·`frameDir`을 요청 본문으로 받는다. 네트워크 차단만으로 끝내지 말고 내부 토큰, 허용 경로 검증, 요청 크기·시간 제한을 함께 적용해야 한다.

따라서 외부 발표에서는 “암호화되어 누구도 볼 수 없다”처럼 현재 구현을 넘어서는 표현을 피하고, 처리 목적·보관 기간·접근 주체를 사실대로 설명해야 한다.

### 우선순위별 보안 공백

| 우선순위 | 공백 | 우선 조치 |
|---|---|---|
| P0 | Python 내부 API 외부 노출 가능성 | localhost·보안 그룹·프록시 ACL로 차단하고 내부 인증 추가 |
| P0 | `videoId` 기반 무권한 조회 가능성 | 인증 주체와 영상 소유권을 모든 영상 API에서 검사 |
| P0 | 운영 Origin·비밀정보 설정 오류 | 실제 프론트 도메인만 허용하고 키를 Secret 주입으로 전환 |
| P1 | 확장자만 믿는 업로드 검사 | 파일 시그니처·ffprobe 결과·코덱·재인코딩 정책 추가 |
| P1 | IP 기준 인메모리 제한 | 인증 사용자·IP·작업 비용 기준을 분리하고 다중 인스턴스 정책 수립 |
| P2 | 감사 로그·중앙 알림 부재 | 관리자 접근, 원본 조회, 키 변경, 삭제 이벤트를 별도 기록 |

### 외부 AI·검색 서비스로 보내는 정보

외부 AI나 뉴스 검색을 사용할 때는 영상 전체와 원문 대화를 무조건 보내지 않고, 필요한 후보 구간·최소한의 문맥·검색에 필요한 Entity만 선별하는 방향이 적합하다. 외부 서비스에서 반환한 검색 결과도 사실 확정이 아니라 참고 근거이므로 출처와 기준일을 저장하고, 결과가 없다는 이유만으로 위험이 없다고 판단하지 않는다.

사용자 피드백을 품질 개선 데이터로 사용할 때는 원본 영상과 검수 라벨의 보관 목적을 분리하고, 불필요한 개인정보를 제거한 뒤 평가셋에 편입한다. 이 정책은 현재 구현된 기능이 아니라 운영 전 확정해야 할 데이터 거버넌스 항목이다.

## 4. 사고가 발생했을 때의 초안 대응 순서

아래는 운영 환경에 적용하기 전에 담당자와 확정해야 하는 기본 순서다.

### API 키가 노출된 경우

1. 노출된 키를 즉시 비활성화하고 새 키를 발급한다.
2. 해당 키를 사용하는 서버의 환경변수를 교체하고 재배포한다.
3. 사용량·과금·호출 기록과 노출 시점을 확인한다.
4. 로그와 배포 기록을 보존한다. 원인을 조사하기 전 로그를 삭제하거나 덮어쓰지 않는다.
5. 영향받은 외부 서비스와 팀에 사실, 영향 범위, 조치 결과를 공유한다.
6. 저장소·CI 로그·메시지에 같은 키가 남아 있는지 검색하고 재발 방지 조치를 기록한다.

비용이 빠르게 증가하는 경우에는 키 차단과 함께 새 업로드·재시도·대량 분석 작업을 먼저 제한한다. 키를 교체했더라도 이미 접수된 작업이 계속 외부 API를 호출할 수 있으므로, 진행 중 작업과 예약된 재시도를 함께 확인해야 한다.

### 영상 또는 리포트가 노출된 경우

1. 문제 API, 파일 경로, 다운로드 기능을 우선 차단한다.
2. 어떤 영상 ID와 사용자가 영향을 받았는지 접근 로그로 확인한다.
3. 관련 요청 로그, 서버 상태, 배포 버전을 별도로 보존한다.
4. 노출된 파일의 공개 경로를 제거하고 필요한 경우 원본을 격리·삭제한다.
5. 영향받은 사용자에게 범위와 조치를 안내한다.
6. 원인이 권한 검사인지, URL 노출인지, 서버 설정인지 분류하고 재발 방지 테스트를 추가한다.

### Python 분석 서버 또는 외부 AI 장애

1. Health API와 애플리케이션 로그로 장애 범위를 확인한다.
2. 새 분석 요청의 유입을 제한하고, 진행 중 작업이 무한 대기하지 않게 실패 또는 재시도 상태로 전환한다.
3. Python 프로세스, 외부 API 상태, 디스크 용량, 메모리 사용량을 순서대로 확인한다.
4. 일시적 오류만 재시도하고, 잘못된 파일·한도 초과·인증 실패는 별도 안내한다.
5. 복구 후 대표 영상으로 STT·OCR·리포트 생성까지 실제 검증한다.
6. 장애 시간, 영향받은 작업, 원인, 재발 방지책을 기록한다.

## 5. 운영 전 보안 체크리스트

- [ ] 모든 영상 API에 인증과 소유권 검사가 적용되었는가?
- [ ] Python 포트가 인터넷에 직접 노출되지 않는가?
- [ ] API 키가 Git, CI 로그, 애플리케이션 로그에 없는가?
- [ ] 업로드 파일의 크기·확장자·실제 형식을 모두 검사하는가?
- [ ] 원본 영상과 STT 대본의 보관 기간을 사용자에게 설명할 수 있는가?
- [ ] 저장소와 백업의 암호화 및 접근 권한을 확인했는가?
- [ ] 요청 제한과 비용 상한이 있는가?
- [ ] 장애·키 노출·영상 노출 대응 담당자와 연락 순서가 정해졌는가?
- [ ] 로그에 원본 영상 내용과 개인정보가 과도하게 남지 않는가?
- [ ] 대표 영상으로 권한 없는 접근과 만료 파일 접근을 테스트했는가?

### 테스트해야 할 최소 공격 시나리오

- 로그인한 사용자 A가 사용자 B의 `videoId`로 스트림·프레임·리포트·대본을 조회할 수 없는가?
- Python의 `/probe`, `/transcribe`, `/ocr`에 외부에서 직접 접근할 수 없는가?
- `filePath=../../...` 또는 저장소 밖 `frameDir`을 보내도 파일을 읽거나 쓸 수 없는가?
- `X-Forwarded-For`를 바꿔도 IP 제한을 무제한으로 우회할 수 없는가?
- 확장자만 `mp4`인 비영상 파일과 과도하게 긴 영상을 거부하는가?
- 삭제·보관 만료 후 DB 결과와 원본·프레임 파일이 서로 어긋나지 않는가?
- OpenAI 키가 없는 로그, 오류 응답, 디버깅 API에 원문 키가 노출되지 않는가?

## 6. 적용 우선순위

추가 비용 없이 먼저 할 일은 Python 외부 노출 확인, 운영 Origin 고정, 로그 민감정보 점검, 내부 API 경로 검증, 권한 없는 접근 테스트, 사고 대응 담당자 지정이다. 인증·소유권 검사는 공개 운영 전에 반드시 마쳐야 한다. 이후 사용자와 영상이 늘어나면 S3의 비공개 버킷과 만료형 URL, 운영 DB 권한 분리, Secret Manager, 중앙 로그·알림을 도입한다.
