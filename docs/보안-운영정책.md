# OoPs?! 보안·운영 정책

> 기준: `minwook` 작업 트리 · 최신 확인: 2026-10-08 · 로그인·개인 데이터는 설계 단계

이 문서는 현재 구현된 보호 장치와 아직 보완해야 하는 항목을 나누어 기록한다. 구현하지 않은 기능을 “보안이 적용되었다”고 설명하지 않는 것을 원칙으로 한다.

## 최신 추가 경계: 진단과 외부 도구

- 진단 조회에는 local 프로필·명시적 loopback 서버 바인딩·loopback 접속 주소 검사를 구현했다. Forwarded/X-Forwarded-For/X-Forwarded-Host가 있으면 차단한다. 기존 진단의 사용자 인증·소유권 검사는 여전히 없으므로 터널/공개 프록시로 노출하지 않는다. 기본 프로필 자체가 local이라는 점도 배포 전에 점검한다.
- 일반 진단은 최근 20영상/1시간 메모리 자료지만 유효 이유·대상에 민감정보가 포함될 수 있다. 별도 기본 OFF인 request-traces는 실제 텍스트 최초 검증의 원문·파싱 응답(거절 전 응답 포함)을 보관한다. local/loopback 바인딩/32자 이상 별도 토큰 조건이며 조회에 X-Review-Trace-Token을 요구한다. 키·HTTP 헤더는 저장하지 않고 영상당 256KiB/32요청·20영상·1시간 한도·삭제 커밋 정리를 적용한다. 기록 파일 내보내기는 자동 만료되지 않으므로 공유/Git 포함을 금지하고 별도 폐기한다. [활성화와 기록 범위](성공-버전-회귀-비교.md#로컬-실제-요청-기록--구현-새-영상-검증-대기)를 따른다.
- PostHog는 미연동이다. 이벤트에 영상/대본/OCR/후보 인용/파일명/원본 URL/이메일/키를 보내지 않는다. 허용 속성 목록만 쓰고 세션 리플레이는 영상·캡처·대본·리포트 영역을 차단한다. DOM 마스킹과 이벤트/URL/네트워크 수집 제한은 별도로 검증해야 한다.
- HyperFrames는 미도입이다. 후속 렌더링은 신뢰된 템플릿만 쓰며 사용자/LLM의 임의 HTML·JavaScript를 실행하지 않는다. 별도 워커에서 네트워크/파일 접근·자원 사용·시간을 제한하고 원본 덮어쓰기 없이 파생본을 보관한다.
- 개인정보 처리·동의·보관/삭제·수집 지역·프로젝트 접근 정책을 팀이 정한 뒤 외부 수집을 활성화한다. 이번에는 계정 생성/외부 데이터 전송/운영 보안 설정 변경을 하지 않았다. 상세 설계와 공식 자료는 [도구 검토](main-minwook-비교-및-도구-적용-검토.md)를 따른다.

## 1. 데이터 흐름과 보호해야 할 대상

```text
사용자 영상
  → Spring Boot 업로드 API
  → 원본 파일 저장
  → Python STT/OCR
  → OpenAI·뉴스 검색(선택)
  → 분석 결과·리포트 저장
  → 사용자에게 결과 제공
```

보호 대상은 원본 영상, STT 대본, OCR 결과, 분석 리포트, 외부 API 키, 사용자별 영상 접근 권한이다. 특히 영상과 대본에는 인물·대화·개인정보가 포함될 수 있으므로, “데모 데이터”라고 가정하고 로그나 외부 API로 무제한 복사해서는 안 된다.

서비스의 판단 대상은 영상 속 발언·행동·화면 문구이지, 사람의 출신 지역·정치 성향·커뮤니티 이용 여부 같은 정체성이 아니다. 모델이 이런 정보를 추정하거나 저장하지 않도록 입력과 출력 스키마를 제한해야 한다.

### 신뢰 경계

```text
브라우저·외부 클라이언트
  ↓ HTTPS / CORS / 요청 제한
Nginx·Spring Boot API
  ├─ DB·로컬 저장소
  ├─ Python 분석 서버
  └─ OpenAI·뉴스 검색
```

경계가 바뀔 때마다 보호 방식도 달라진다. CORS는 브라우저의 출처 제한일 뿐 사용자 인증이 아니며, IP 요청 제한은 영상 소유권 확인이나 외부 API 비용 상한을 대신하지 않는다. 특히 Python 분석 서버는 `filePath`와 OCR `frameDir`을 요청으로 받으므로, 외부에 공개되면 임의 파일 읽기·쓰기 경로로 악용될 수 있다. 이 서버는 반드시 내부 네트워크에서만 접근 가능해야 한다.

## 2. 현재 적용된 보호 장치

### 네트워크와 API

- 외부 요청은 Nginx를 거쳐 Spring Boot API로 들어오는 구조다.
- Python 분석 서버는 외부 클라이언트가 직접 호출하는 공개 API가 아니라 내부 분석 서버로 사용한다.
- CORS는 허용된 프론트엔드 Origin 목록을 설정으로 관리한다.
- 업로드·YouTube 등록·재시도 API에 IP 기준 요청 제한을 적용했다.
- 응답의 `X-Request-Id`와 서버 로그의 추적 ID를 연결해 장애를 추적한다.
- `/health`는 Spring Boot 자체뿐 아니라 Python 분석 서버와 저장소 상태도 확인한다.

현재 요청 제한은 Spring 인스턴스 내부 메모리에 저장하는 고정 윈도우 방식이며, 인증 전까지 업로드·재시도를 IP 기준으로 제한한다. 따라서 여러 대로 늘리면 인스턴스마다 한도가 따로 적용되고, Python·뉴스·OpenAI 호출 자체는 제한하지 않는다. `X-Forwarded-For`와 `X-Real-IP`는 신뢰하는 프록시가 덮어쓰는 환경에서만 사용해야 하며, Spring을 직접 인터넷에 노출한 상태에서 임의 헤더를 믿으면 제한을 우회할 수 있다.

`allowCredentials(true)`인 CORS 설정은 실제 프론트 Origin만 운영 설정에 넣어야 한다. CORS 허용 목록에 도메인을 추가하는 것만으로 영상 접근 권한이 생기지는 않으며, 인증 도입 후에는 모든 영상·리포트·프레임 API에서 소유권 검사를 별도로 수행해야 한다.

### 파일 업로드와 저장

- 업로드 크기와 허용 확장자를 제한한다.
- 저장 파일명은 사용자 입력 파일명을 그대로 경로로 사용하지 않고 서버가 생성한 ID를 기준으로 만든다.
- 경로 순회 공격을 막기 위해 저장 경로가 설정된 저장소 내부인지 확인한다.
- 원본 파일은 `source-retention-hours` 기준으로 정리한다. 저장소 기본값은 24시간이며 완료·실패 영상의 원본만 삭제한다. 0으로 설정하면 원본 자동 정리를 끈다. 대본·리포트·프레임은 별도 정책 대상이다.
- 전체 산출물은 별도의 `retention-days` 기준으로 정리한다. 기본값 0은 전체 자동 정리를 끈다. AWS의 실제 주입 값은 배포 환경에서 확인하며, 원본 만료 후 영상 재생·재분석 가능 여부를 사용자 안내와 맞춘다.

현재 업로드 검사는 500MB 크기와 `mp4`·`mov`·`avi` 확장자를 확인하고, 분석 서버의 `ffprobe`로 영상 길이를 확인하는 수준이다. 확장자와 실제 파일 형식이 일치하는지, 악성 코덱·압축 폭탄·재생기 취약점이 없는지까지 검증하는 것은 아니다. 공개 운영에서는 MIME·파일 시그니처·코덱·해상도·길이를 함께 검사하고, 필요하면 격리 영역에서 재인코딩한 파일만 분석해야 한다.

### 비밀정보

- OpenAI·Naver 등 API 키는 코드에 하드코딩하지 않고 환경변수 또는 운영 설정으로 주입한다.
- `.env`와 실제 키 파일은 Git에 커밋하지 않는다.
- 키가 노출되었다고 판단되면 저장소에서 문자열만 지우는 것으로 끝내지 말고 해당 키를 폐기·재발급해야 한다.

## 3. 현재 남아 있는 보안 공백

다음 항목은 아직 제품 수준으로 완료되었다고 볼 수 없다.

1. 사용자 인증과 영상 소유권 검사가 완성되지 않았다. `videoId`를 아는 사용자가 다른 영상에 접근할 수 있는지 반드시 점검해야 한다.
2. 로컬 H2와 로컬 디스크 중심이라 서버 관리자나 호스트 접근 권한이 있는 사람은 원본 파일에 접근할 수 있다.
3. 저장 데이터의 암호화, 백업 암호화, 키 관리 방식은 운영 인프라에서 별도로 확정해야 한다.
4. Python 내부 API에 애플리케이션 간 별도 인증 토큰이 없다면, 포트·보안 그룹·localhost 바인딩으로 외부 노출을 막아야 한다.
5. 파일 내용의 확장자 위조 검사, 악성 파일 검사, 업로드 후 안전한 재인코딩은 추가 검토가 필요하다.
6. 중앙 로그 보관, 감사 로그, 관리자 접근 이력, 침해 탐지 알림이 아직 운영 정책으로 정리되어 있지 않다.

7. 영상 URL 등록은 현재 HTTPS YouTube 도메인만 허용한다. yt-dlp가 리다이렉트를 따라갈 수 있으므로, 외부 공개 전에 리다이렉트·다운로드 크기·다운로드 시간 제한도 점검해야 서버가 다운로드 대행자가 되지 않는다.
8. 스트리밍·프레임·대본·OCR 원문·리포트 API가 `videoId`만으로 동작하므로 인증을 붙이기 전에는 ID를 아는 사람이 다른 영상 자료를 조회할 수 있는지 공개 운영을 해서는 안 된다.
9. Python 분석 API에는 현재 애플리케이션 간 인증이 없고, `filePath`·`frameDir`을 요청 본문으로 받는다. 허용 저장소의 `videos/` 원본과 `frames/` 경로만 사용하도록 제한했지만, 내부 토큰과 요청 크기·시간 제한도 적용해야 한다.
10. 저장소의 기본 설정은 `local` 프로필을 활성화하고, 이 프로필은 H2 콘솔을 켠다. AWS에서 실제로 어떤 프로필과 설정을 주입하는지는 저장소만으로 확인할 수 없으므로 배포 환경에서 확인해야 한다.

따라서 외부 발표에서는 “암호화되어 누구도 볼 수 없다”처럼 현재 구현을 넘어서는 표현을 피하고, 처리 목적·보관 기간·접근 주체를 사실대로 설명해야 한다.

### 우선순위별 보안 공백

| 우선순위 | 공백 | 우선 조치 |
|---|---|---|
| P0 | Python 내부 API 외부 노출 가능성 | localhost·보안 그룹·프록시 ACL로 차단하고 내부 인증 추가 |
| P0 | `videoId` 기반 무권한 조회 가능성 | 인증 주체와 영상 소유권을 모든 영상 API에서 검사 |
| P0 | 운영 Origin·비밀정보 설정 오류 | 실제 프론트 도메인만 허용하고 키를 Secret 주입으로 전환 |
| P1 | 확장자만 믿는 업로드 검사 | 파일 시그니처·ffprobe 결과·코덱·재인코딩 정책 추가 |
| P1 | IP 기준 인메모리 제한 | 인증 사용자·IP·작업 비용 기준을 분리하고 다중 인스턴스 정책 수립 |
| P2 | 감사 로그·중앙 알림 부재 | 관리자 접근, 원본 조회, 키 변경, 삭제 이벤트를 별도 기록 |

### 외부 AI·검색 서비스로 보내는 정보

현재 Python STT는 영상 전체의 오디오를 분할한 뒤 OpenAI 음성 인식 API로 전송한다. Spring의 텍스트·맥락 분석도 STT/OCR에서 얻은 문장과 문맥을 OpenAI에 보낼 수 있다. 따라서 현재 데이터 흐름을 “후보 구간만 외부로 전송한다”고 설명하면 안 된다. 향후에는 STT 결과를 포함해 분석 단계별 전송 범위와 보관 정책을 명시하고, 맥락 판단에 필요한 최소 구간만 전송하는 방안을 검토한다. 뉴스 검색 결과는 사실 확정이 아니라 참고 근거이므로 출처와 기준일을 저장하고, 결과가 없다는 이유만으로 위험이 없다고 판단하지 않는다.

사용자 피드백을 품질 개선 데이터로 사용할 때는 원본 영상과 검수 라벨의 보관 목적을 분리하고, 불필요한 개인정보를 제거한 뒤 평가셋에 편입한다. 이 정책은 현재 구현된 기능이 아니라 운영 전 확정해야 할 데이터 거버넌스 항목이다.

## 4. 사고가 발생했을 때의 초안 대응 순서

아래는 운영 환경에 적용하기 전에 담당자와 확정해야 하는 기본 순서다.

### API 키가 노출된 경우

1. 노출된 키를 즉시 비활성화하고 새 키를 발급한다.
2. 해당 키를 사용하는 서버의 환경변수를 교체하고 재배포한다.
3. 사용량·과금·호출 기록과 노출 시점을 확인한다.
4. 로그와 배포 기록을 보존한다. 원인을 조사하기 전 로그를 삭제하거나 덮어쓰지 않는다.
5. 영향받은 외부 서비스와 팀에 사실, 영향 범위, 조치 결과를 공유한다.
6. 저장소·CI 로그·메시지에 같은 키가 남아 있는지 검색하고 재발 방지 조치를 기록한다.

비용이 빠르게 증가하는 경우에는 키 차단과 함께 새 업로드·재시도·대량 분석 작업을 먼저 제한한다. 키를 교체했더라도 이미 접수된 작업이 계속 외부 API를 호출할 수 있으므로, 진행 중 작업과 예약된 재시도를 함께 확인해야 한다.

### 영상 또는 리포트가 노출된 경우

1. 문제 API, 파일 경로, 다운로드 기능을 우선 차단한다.
2. 어떤 영상 ID와 사용자가 영향을 받았는지 접근 로그로 확인한다.
3. 관련 요청 로그, 서버 상태, 배포 버전을 별도로 보존한다.
4. 노출된 파일의 공개 경로를 제거하고 필요한 경우 원본을 격리·삭제한다.
5. 영향받은 사용자에게 범위와 조치를 안내한다.
6. 원인이 권한 검사인지, URL 노출인지, 서버 설정인지 분류하고 재발 방지 테스트를 추가한다.

### Python 분석 서버 또는 외부 AI 장애

1. Health API와 애플리케이션 로그로 장애 범위를 확인한다.
2. 새 분석 요청의 유입을 제한하고, 진행 중 작업이 무한 대기하지 않게 실패 또는 재시도 상태로 전환한다.

4. 일시적 오류만 재시도하고, 잘못된 파일·한도 초과·인증 실패는 별도 안내한다.
5. 복구 후 대표 영상으로 STT·OCR·리포트 생성까지 실제 검증한다.
6. 장애 시간, 영향받은 작업, 원인, 재발 방지책을 기록한다.

## 7. 로그인과 개인별 데이터 설계안

이 절은 **설계이며 아직 구현하지 않았다.** 현재 Spring Boot 4.0.5에는 Spring Security·OAuth2·Spring Session 의존성이 없고, 영상에 사용자 소유자도 없다. 기존 AWS 배포와 Spring/Python 분리를 유지하는 안이다. Rails 마이그레이션이나 편집·포즈 분석은 이 작업의 선행조건이 아니다.

### 7.1 사용자별 DB가 아니라 사용자별 소유권

현재 규모에서는 하나의 운영 DB에 회원과 영상을 함께 저장하고 `video.owner_id`로 구분한다. 사용자마다 물리 DB를 만들면 스키마 변경·백업·연결 관리가 복잡해진다. 기업별 전용 DB는 계약상 격리가 실제로 필요한 단계에서 별도로 검토한다.

```text
app_user
  ├─ user_identity: 소셜 로그인 연결
  ├─ 세션 / 약관·동의 기록
  └─ video.owner_id: 개인 영상
       ├─ AnalysisJob: 분석 작업
       ├─ STT / OCR / 프레임
       ├─ 리포트 / 탐지 결과 / 분석 범위
       └─ 검수 행동: 확인·수정·무시
```

영상·프레임 파일 자체는 DB에 넣지 않고 기존 파일 저장소에 두며, DB에는 `storageKey`와 메타데이터를 저장한다. 사용자별 폴더는 정리 수단이지 권한 검사를 대체하지 않는다. 나중에 팀 계정이 필요하면 `workspace`·`workspace_member`를 추가하고 영상 소유권을 워크스페이스로 확장한다.

### 7.2 DB에 넣을 데이터와 단계

아래 테이블명과 필드는 제안이다. 실제 마이그레이션에서는 기존 JPA 테이블명과 FK를 확인한다.

| 단계 | 테이블·대상 | 주요 데이터 | 저장 목적·주의점 |
|---|---|---|---|
| 1차 | `app_user` 신규 | 내부 ID, 표시 이름, 선택적 이메일·인증 여부, 계정 상태, 가입·최근 로그인 시각, `auth_version`, 탈퇴 요청 시각 | 회원 관리. 전화번호·생년월일·주소는 수집하지 않음 |
| 1차 | `user_identity` 신규 | 회원 FK, provider, issuer, subject, 연결·로그인 시각 | 소셜 계정 연결. `(provider, issuer, subject)` 유일 제약. 이메일을 계정 식별자로 쓰지 않음 |
| 1차 | Spring Session 관리 테이블 | 세션 ID, principal, 생성·접근·만료 시각, 최소 인증 속성 | 로그인 유지. 원문 OAuth 토큰·프로필 전체는 세션에 불필요하게 저장하지 않음 |
| 1차 | `user_consent` 신규 | 회원 FK, 목적, 문서 버전, 동의·철회 시각 | 약관 수락·개인정보 안내 확인과 선택 동의를 목적별로 구분 |
| 1차 | 기존 `video` 확장 | `owner_id`, 기존 파일명·형식·저장 키·업로드 시각 | 내 영상 목록. `(owner_id, created_at, id)` 인덱스와 FK 추가 |
| 1차 | 기존 결과 테이블 | 대본, OCR 영역·역할, 프레임 경로, 위험 구간·이유, 리포트, coverage | 영상 FK를 통해 권한 상속. 자식에 소유자를 중복 저장하지 않음 |
| 1차 | 기존 `ReviewAction` 확장 | 행동한 회원 FK, 기존 finding·video FK, 선택·메모 | 누가 판단했는지 기록. 현재 최신 선택 갱신 구조는 완전한 변경 이력이 아님 |
| 1차 | `audit_event` 신규 | 행위자, 사건 유형, 대상 ID, 성공 여부, request ID, 시각 | 접근 거부·계정 변경·삭제·관리자 접근 추적. 대본·토큰·영상 내용은 로그에 넣지 않음 |
| 2차 | 기존 `AnalysisJob` 확장 | 요청자, 모델·프롬프트·사전 버전, 입력 hash, 설정, 처리 시간·사용량 | 기존 job을 분석 실행 단위로 활용. 별도 중복 job 체계는 만들지 않음 |
| 2차 | 결과의 실행별 연결 | `analysis_job_id`, 실행별 리포트·finding·대본·OCR·coverage | 재분석 전후 비교. 현재 video 단위 덮어쓰기에서 별도 마이그레이션 필요 |
| 2차 | 검수 이벤트 / 사용량 원장 | 회원·실행·finding·행동 시각 / 단계·시도·실측 사용량·멱등 키 | append-only 검수 이력과 중복 과금·한도 차감 방지 |

비밀번호 직접 가입은 1차 범위에서 제외한다. 회원별 OpenAI API 키도 저장하지 않는다. 소셜 로그인만 한다면 provider access/refresh token의 장기 보관은 필요하지 않으며, framework의 authorized-client 저장 정책도 명시적으로 제한한다.

중간 AI 평가를 저장하는 2차 단계에서도 근거·판단·버전을 저장하지, 화자의 출신 지역이나 커뮤니티 이용 여부를 추정해 회원 정보로 저장하지 않는다. 개인 업로드를 서비스 개선 데이터셋으로 자동 편입하지 않는다.

### 7.3 로그인 규칙 제안

1. **소셜 로그인 한 종류부터 시작한다.** 제안 기본값은 Google OIDC이며, 카카오가 주 고객에게 더 적합하면 구현 전에 변경한다. 제공자는 아직 확정되지 않았다. 자체 이메일·비밀번호 방식은 인증 메일·재설정·비밀번호 보호까지 별도 범위로 잡는다.
2. 서버의 OAuth authorization code 흐름을 사용하고 Spring Security에서 `state`, OIDC `nonce`, 서명·issuer·audience·만료를 검증한다. PKCE도 provider 지원과 설정을 확인해 적용한다. callback·로그인 후 이동 URL은 허용 목록으로 제한한다.
3. 처음 연결한 계정은 약관 수락과 개인정보·외부 AI 처리 안내를 거쳐 `ACTIVE`가 된다. 초기 상태는 `ONBOARDING`이며 프로필·동의 API만 허용한다. 선택적 마케팅·데이터셋 활용 동의는 서비스 이용 동의와 분리한다. 필요한 법적 근거·문구는 출시 전에 별도 확인한다.
4. 재로그인은 동일 소셜 subject의 기존 회원으로 연결한다. 이메일이 같다는 이유로 다른 provider 계정을 자동 합치지 않는다. 향후 계정 연결은 양쪽 계정 재인증 후에만 허용한다.
5. 닉네임은 중복 가능하게 하고 길이·출력 escaping을 검증한다. 본인 식별은 닉네임이 아닌 내부 회원 ID로 한다.
6. `SUSPENDED`, `DELETION_PENDING`, `DELETED`는 새 분석과 개인 자료 접근을 허용하지 않는다. 정지 사유 문의처럼 별도로 지정한 계정 안내 API만 예외로 둔다.
7. 비로그인 사용자는 소개 화면과 공개 동의를 받은 별도 데모만 볼 수 있다. 개인 영상 업로드·URL 분석·조회는 로그인 후에만 허용한다. 운영자가 일반 회원 영상 전체를 자동 열람하는 권한도 기본으로 부여하지 않는다.

Google은 이메일이 아닌 `sub`를 계정 식별자로 사용할 것을 명시한다. [Google OIDC 문서](https://developers.google.com/identity/openid-connect/openid-connect)

### 7.4 로그인 유지: 서버 세션을 우선

웹 서비스 MVP에는 JWT를 브라우저 저장소에 넣는 방식보다 **서버 세션 + HttpOnly 쿠키**를 우선 제안한다. 로그아웃·정지 시 서버에서 세션을 끊기 쉽고, 영상 `<video>`·프레임 `<img>`·WebSocket도 동일 출처 쿠키를 이용할 수 있다. 모바일 앱·외부 API 고객이 생기면 토큰 인증을 별도 설계한다.

기존 MySQL에 Spring Session JDBC 테이블을 추가하면 새 Redis 서비스 없이 로그인 상태를 공유할 수 있다. 프레임워크 제공 DB별 스키마와 만료 세션 정리를 사용하고 Boot 관리 버전에 맞춘다. 세션 저장으로 DB 부하는 늘어나므로 규모가 커지면 Redis 전환을 검토한다. [Spring Session JDBC](https://docs.spring.io/spring-session/reference/configuration/jdbc.html)

운영 기본안은 다음과 같다. 시간 값은 표준의 의무가 아니라 **우리 서비스의 제안값**이다.

- HTTPS, host-only 세션 쿠키, `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`. 운영에서는 `__Host-` 접두사 검토. 로컬 개발 설정은 분리한다.
- 30분 유휴 만료·로그인 후 절대 24시간 만료. 절대 만료는 별도 검사를 구현하며, 백그라운드 상태 폴링이 세션을 무한 연장하지 않게 한다. 자동 로그인은 1차에서 제외한다.
- 로그인 시 세션 ID 교체. 로그아웃은 CSRF 보호된 POST로 현재 세션 무효화. 전체 기기 로그아웃·정지·탈퇴는 사용자 세션 모두 무효화하고 `auth_version` 갱신.
- 매 요청마다 계정 상태·인증 버전을 확인한다. 오래된 세션에 저장된 권한만 믿지 않는다. 탈퇴·로그인 수단 변경에는 최근 재인증을 요구한다.
- 쿠키 인증의 POST/PUT/PATCH/DELETE에는 CSRF 토큰 검증. `SameSite`·CORS만으로 대신하지 않는다. 로그인·로그아웃 후 프론트의 CSRF 토큰 갱신 흐름도 포함한다.
- Nginx에서 프론트와 `/api`, `/ws`를 동일 출처로 제공하는 구성을 우선한다. 실제 frontend/API 출처가 다르면 credential CORS·쿠키 전달·브라우저 제약을 별도로 검증한다. 무조건 `SameSite=None`으로 풀지 않는다.

쿠키 속성과 세션 교체·만료는 [OWASP 세션 관리 지침](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), CSRF 구현은 [Spring Security CSRF 문서](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)를 기준으로 검증한다.

### 7.5 로그인보다 중요한 영상 권한 규칙

현재 `/history`, 상태·리포트·대본·화면 텍스트 조회, 재시도·취소·삭제, 검수 기록·완료, `/stream`, `/frames/{frameId}` 모두 소유권 검사 대상이다. 프레임 API는 현재 frame-video 연결은 확인하지만 로그인한 소유자는 확인하지 않는다.

- 업로드의 소유자는 인증 principal에서 정한다. 요청의 `userId`·`ownerId`는 신뢰하지 않는다.
- 개인 요청은 서비스 계층의 소유자 조건 조회(`id AND owner_id`)를 거친다. 목록도 페이지네이션과 owner 조건을 동시에 적용한다. 분석 worker용 내부 조회와 사용자 조회를 분리한다.
- finding·frame·review action은 소유 영상에 속하는지도 확인한다. 내가 소유한 videoId에 다른 사람의 frameId를 넣어도 실패해야 한다.
- 미로그인은 `401`, 로그인했지만 없는/남의 영상은 동일한 `404`, CSRF 거부는 `403`. API는 JSON 오류를 반환하고 로그인 시작 경로만 명시적으로 redirect한다.
- 스트림 Range·HEAD, 프레임 요청도 인증한다. 개인 응답은 초기에는 `Cache-Control: private, no-store`로 하고 기존 프레임 1시간 캐시 정책을 재검토한다. 업로드 폴더를 Nginx 정적 경로로 공개하지 않는다.
- WebSocket handshake 인증만으로 충분하지 않다. 현재 `/topic/videos/{videoId}/progress`의 SUBSCRIBE도 영상 소유권을 검사하고 불필요한 SEND·임의 topic 구독을 거부한다. 로그아웃·만료 시 연결을 종료한다. 안전한 구독 검사를 완료하지 못하면 인증된 상태 폴링만 우선 제공한다.
- Python은 인터넷에 공개하지 않는다. Spring이 확인한 작업 ID·영상 정보만 내부 요청으로 넘기고 Python이 브라우저 세션을 검증하게 만들지 않는다.
- metrics·관리 기능·운영 H2 console은 별도 제한한다. 공개 health 응답은 최소한의 생존 정보만 제공한다.

### 7.6 분석 작업·탈퇴·보관 정책

비동기 실행 전에 영상 소유자와 job을 DB에 저장한다. worker는 HTTP 스레드의 SecurityContext에 의존하지 않고 DB의 job→video→owner를 사용한다. 일반 로그아웃·세션 만료는 진행 중 분석을 취소하지 않는다.

계정 정지·탈퇴 시 새 작업을 막고 대기 작업을 취소한다. 실행 중 작업은 외부 AI 호출 전과 결과 저장 전에 계정·삭제 상태를 확인한다. 이미 전송된 외부 요청은 회수할 수 없다는 한계를 설명한다. 늦게 반환된 결과가 삭제된 영상을 되살리지 못하도록 한다.

탈퇴는 `DELETION_PENDING`으로 즉시 접근을 차단한 뒤, 재시도 가능한 삭제 작업으로 원본·프레임·중간 파일·결과·소셜 연결을 정리한다. 감사 로그의 최소 보관 범위와 백업 만료는 별도 정책으로 고지한다. 단일 DB cascade만으로 디스크 파일 삭제를 완료했다고 간주하지 않는다.

로그인 도입이 무기한 영상 보관을 의미하지는 않는다. 현재 기본값은 원본 24시간 보관·전체 산출물 만료 비활성(0)이므로, 실제 운영 설정과 결과 보관 기간을 구현 전에 결정해야 한다. 원본이 만료되어도 대본·리포트가 남는지, 재분석이 불가능한지 화면에서 구분한다.

개인 사용량 제한은 계정 기준으로, 전체 분석 동시성은 서버 자원 기준으로 각각 관리한다. 사용자마다 Python 프로세스나 thread pool을 하나씩 만드는 구조가 아니다. 동시 작업 수·영상 길이·파일 크기·월 분석 시간의 수치는 실제 비용과 테스트로 정하고 동시 요청에도 원자적으로 적용한다. 소셜 계정을 여러 개 만들 수 있으므로 회원 한도만으로 남용 방지가 끝나는 것도 아니다. 로그인 시도 제한은 별도 보안 정책이며 기존 업로드 IP 제한의 켜짐 여부와 구분한다.

### 7.7 API와 구현 순서

신규 API 초안은 `GET /api/v1/auth/me`, `GET /api/v1/auth/csrf`, `POST /api/v1/auth/logout`, `POST /api/v1/auth/logout-all`, `PATCH /api/v1/me`, `DELETE /api/v1/me`다. OAuth 시작·callback은 Spring Security의 provider 경로를 사용한다. 가입 확정·동의 API는 별도로 정의한다. 기존 영상 API는 가능한 한 유지하되 인증·소유권 계약을 추가한다.

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 1 | 제공자·운영 출처·약관·보관 정책 결정, 회원·identity·세션 스키마 작성 | provider console의 callback 설정과 프론트 협업 범위 확정 |
| 2 | Spring Security·OAuth2·JDBC 세션, 로그인·로그아웃·가입 확정 구현 | 계정 중복·정지·만료·CSRF·재인증 테스트 통과 |
| 3 | 모든 영상 API와 작업·미디어·WebSocket 권한 적용 | 사용자 A/B 간 조회·변경·구독이 전부 격리됨 |
| 4 | 기존 영상 이관·프론트 연동·운영 전 검증 | 소유자 없는 자료가 공개되지 않고 로그인부터 결과 확인까지 동작 |
| 5 | 실행별 이력·검수 이벤트·실측 사용량 원장 | 재분석 비교와 개인 한도를 중복 기록 없이 제공 |

2·3·4는 함께 검증해 배포한다. 로그인 화면만 추가하고 영상 ID 조회가 공개된 상태는 완료가 아니다. 외부 유료 인증 플랫폼은 필수가 아니지만, DB 저장·백업·트래픽 운영 비용까지 0이 된다는 의미도 아니다.

기존 영상은 소유자를 알 수 없으므로 첫 가입자에게 일괄 귀속하거나 이메일·파일명으로 추측하지 않는다. nullable `owner_id` 추가 → 기존 자료 비공개 격리 → 팀이 확인한 귀속만 이관 → 정리 후 필요한 NOT NULL 제약 순으로 진행한다. 격리 자료의 삭제는 별도 승인을 받는다. 이관 중에도 `owner_id IS NULL`을 공개 접근 예외로 두지 않는다.

롤백해도 인증 없는 기존 API를 다시 공개하지 않는다. 보호 장치를 유지할 수 없다면 개인 데이터 경로를 일시 차단한다. 운영 DB 변경은 백업과 별도 마이그레이션으로 수행한다.

### 7.8 필수 검증 시나리오

- A가 B의 영상 ID로 모든 조회·취소·삭제·검수 API를 호출하면 실패하는가? A의 영상에 B의 frame/finding ID를 섞어도 실패하는가?
- 미로그인·만료·로그아웃한 쿠키의 stream Range/HEAD, 프레임, WebSocket 구독이 차단되는가? 저장소 직접 URL로 우회할 수 없는가?
- 잘못된 OAuth state/nonce·issuer·audience·만료 토큰을 거부하는가? 동일 이메일의 다른 소셜 계정을 자동 합치지 않는가?
- CSRF 토큰 없이 상태 변경이 불가능한가? 허용하지 않은 Origin과 임의 redirect를 차단하는가?
- 정지·탈퇴 후 오래된 세션과 WebSocket이 계속 살아 있지 않은가? 분석 도중 삭제해도 늦은 결과가 다시 저장되지 않는가?
- owner 없는 기존 자료가 목록·리포트·파일·진행률 어느 경로로도 공개되지 않는가?
- 동시에 여러 업로드·재시도가 들어와도 개인 한도를 초과하거나 사용량이 중복 기록되지 않는가?

**구현 전 확정할 선택:** Google/카카오 등 첫 로그인 제공자, 실제 프론트·API 도메인, 결과 보관 기간, 개인 분석 한도. 이 설계 추가만으로 로그인이나 권한 보호가 활성화되지는 않는다.
