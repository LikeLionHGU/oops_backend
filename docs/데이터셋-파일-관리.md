# 논란 사례집 파일 관리와 런타임 갱신

2026-10-15 · minwook · 현재 실행 절차. 이전 설명은 [과거 파일 관리 기록](archive/데이터셋-파일-관리-20261014-이전.md)에 보존했다.

현재 로컬 입력/출력은 B 맥락 분리 후 32사건·38발언/예시·6기준, 버전
2026-10-15-life-choice-boundary-v1-patterns-4다. build --write/--verify와 실제 Java 참고 배선을
검사했지만 모델 성능 비교·서버 재시작·AWS 배포는 하지 않았다. 아래 37개 이관 결과는 당시 이력이다.

## 현재 입력과 출력

```text
datasets/controversy/
  incidents/*.json              사건별 입력, incident-2
  definitions/build.json        공통 판단 기준·생성 설정·기존 순서
  research/source-snapshots/    사건에 연결된 출처 발췌
  guidelines/runtime.json       생성 결과, Spring이 읽는 파일
  guidelines/build-manifest.json 입력/출력 해시·버전·건수
  legacy/pre-incident-build/    이전 카드·계획·목록·패턴/예시 파일
  legacy/runtime-history/       교체 전 런타임, 원본 해시로 식별
```

사례 편집은 사건 파일, 공통 기준 편집은 definitions/build.json에서 한다. runtime은 직접 편집하지 않는다.
연구 후보·검수 원장·평가 자료는 자동으로 분석 입력에 포함되지 않는다. 사건의 legacyCard와
legacyDictionaryCard는 현재 스키마와 컴파일러가 읽는 호환 필드라 삭제하면 안 된다.

## 추가·갱신·확인

저장소 루트에서 다음을 실행한다.

```sh
# 현재 입력으로 생성 가능성·ID 계약·기한·크기 검사. 쓰기 없음.
python3 tools/build_incident_dataset.py
# 검사 후 이전 runtime 보관, runtime과 manifest 갱신.
python3 tools/build_incident_dataset.py --write
# 입력에서 재생성한 내용과 저장 출력 및 manifest 일치 확인.
python3 tools/build_incident_dataset.py --verify
```

사건 추가 도구의 --apply는 사건 저장과 생성 가능성 검사까지만 수행한다. 위 --write를 실행해야
분석용 결과를 갱신한다. 새 메커니즘은 definitions/build.json에 정의한 뒤 사건에서 연결한다.
잘못된 ID·미등록 메커니즘·중복·필수 필드 오류는 생성 단계에서 거절한다.

manifest에는 모든 입력 파일의 SHA-256, runtimeSha256, sourceBundleSha256,
contextDictionarySha256, 버전, 사건/예시/기준 수를 기록한다. 입력이 변경된 채 이전 출력이 남으면
verify가 실패한다. 문구 버전을 유지해도 해시로 내용 변경을 구분할 수 있다.

검증한 결과만 runtime 파일로 원자 교체한다. runtime과 manifest의 교체를 하나의 트랜잭션으로
묶지는 않으며 두 파일 사이 중단은 verify가 감지한다. 다시 --write하면 일관된 쌍을 생성한다.
직전 runtime은 legacy/runtime-history에 원본 바이트 그대로 보관한다. 이는 로컬 복구 사본이고
외부 백업은 아니다. 데이터를 복구할 때 해당 버전의 사건 입력·공통 정의도 함께 복구해야 한다.

## 서버 반영

Spring은 시작 시 사전을 메모리에 읽는다. 빌드 뒤 Spring을 재시작하고 시작 로그를 확인한다.

```text
[context-dictionary] state=READY_WORKING_REFERENCE ... version=... sourceSha256=... examples=38
```

로그의 version/sourceSha256/examples를 manifest의 version/sourceBundleSha256/examples와 대조한다.
이것은 서버 로드 확인이며 관련 예시의 실제 선택 확인과는 다르다. 요청별 SelectionTrace로
선택된 예시와 제외 family를 확인한다. 기본 위치는 oops-backend 실행 디렉터리 기준
file:../datasets/controversy/guidelines/runtime.json이다. 다른 배치에서는 REVIEW_GUIDELINES_LOCATION을
절대 경로로 지정한다. Python 분석 서버는 이 파일을 읽지 않는다.

## 이번 이관에서 확인한 결과

이관 당시 32사건·37발언과 기존 runtime 37예시의 ID가 모두 대응했다. 공통 정의를 복구하면서
기존 메커니즘별 예시 순서를 유지해 이전 runtime과 재생성 내용의 동치를 확인했다.
과거 파일 8개(이전 README 포함)는 legacy/pre-incident-build에 이동하고 해시 목록을 남겼다.
이동 후에도 신규 build/verify가 통과한다. 현재 README는 새 경로 안내로 교체했다.

실제 Java 로드 검사에서 사례 ID의 # 구분자가 구형 ID 검증에 거절되는 문제가 확인됐다.
사례 ID만 사건#발언 형식을 허용하며 family/메커니즘 ID의 검증은 유지한다.
참고 스키마를 바꾸거나 판단 기준·사례 설명을 바꾼 작업은 아니다.

구형 CLI는 공통 정의가 있는 현재 데이터셋에서 신규 빌드 명령을 안내하며 중단한다.
compile 함수는 신규 빌드와 과거 회귀 시험이 재사용하므로 유지한다. 과거 명령을 현재 운영
절차로 사용하지 않는다. 기존 댓글 수집본은 삭제하지 않았으며 별도 보관·기한 기록을 따른다.

datasets와 uploads는 Git 제외다. 새 체크아웃·AWS에는 데이터가 자동 전달되지 않으므로 현재
입력·연결된 스냅샷·runtime·manifest를 별도 공유하고 검증한다. 생성 성공이 사람 검수·운영 적격·
학습 권한이나 논란 탐지 정확도를 승인하지 않는다.
