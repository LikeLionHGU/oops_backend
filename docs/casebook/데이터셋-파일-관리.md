## 단일 검수 입력 도구 — 2026-10-24

`tools/casebook_intake.py`는 검수 입력JSON 하나를 기존 source/unit/relation 계약으로 투영하는 로컬CLI다. 새 스키마의 웹관리자·자동학습·외부 수집기가 아니다. [예시 입력](../../tools/templates/casebook-intake.example.json)은 실제 자료가 아닌 작성 틀이므로 0해시·가상경로를 원본/승인 기록으로 교체해야 한다.

### 작업 종류와 승인

| action | 쓰는 내용 | 사전 반영 |
|---|---|---|
| ADD | 출처 스냅샷·맥락 단위·검색 관계3개JSON과 검수 접수 기록 | 승인 계획 적용 시 기존 빌더로 생성·검증 |
| UPDATE | 기존 개발 단위의 작성 해석·경계·검색 설명·대조와 관계 설명 | 출처·원문ID·역할·판단·식별자·메커니즘·라우팅 키는 변경 금지 |
| HOLD | 원음 등 부족 정보와 승인 기록을 `review-intakes/`에 보존 | runtime 변경·Java 검색 감사 없음 |

사용자는 원문/필요 문맥,판단,이유,경계를 검수하고 개발자가 입력을 작성한다. `approval`은 기존 사용자 검수JSON의 path/sha256/eventIds를 참조한다. 해당 review의 decision·scope·명시 응답과anchor가 선택 원문에 있어야 한다. 해시 검사는 저장 기록과의 일치 검사이지 실제 사람의 신원·권한·판단 타당성을 인증하는 것은 아니다. `humanVerified=false`·학습 허가 없음인 개발 참고 상태를 유지한다.

`source`는 원문스냅샷 path/sha256/format/kind/videoId를 지정한다. 지원 format은 `RESULT_TRANSCRIPT`(transcript 배열),`API_TRANSCRIPT`(data 배열),`TIMED_SEGMENTS`(segments 배열)다. 각 선택 항목에는 index/id/role만 쓰고 text·시간을 복사해 입력하지 않는다. 도구가 원문에서 가져와 전사·시간·순서를 보존한다. sourceGroupId는 같은 원영상/재편집본의 묶음을 유지한다. 실제 원음 독립 확인이나 사용자 보충 정보를 새 영상의 사실로 승격하지 않는다.

긴 문맥 지원 후 PASS는 최대11줄(승인 설명을 더해flow12개),검토/보류는 최대12줄,각 원문350자 제한이 있다. 컴파일러·v6/v7 로더·관계sourceIds·오프라인 검색 감사가 같은 상한을 따른다. 구형 스키마flow8개 제한은 유지한다. 넘으면 임의로 줄이거나 잘라 통과시키지 않고 거절한다. 전체 파일1MiB·검색 입력 예산은 늘리지 않았으며 긴 사례가 예산에 안 들어가면 검색에서 제외될 수 있다. 개별 회수 검사를 수행한다.

`interpretation`, `boundary`, `retrievalText`, `relation.situation/target/linkage`가 작성할 핵심 설명이다. UPDATE는 기존unit 바이트해시인 `expectedUnitSha256`도 필요하다. PASS/검토 대상의 라벨 변경·원문 재선정은 이 UPDATE에 숨겨 넣을 수 없다. `normalContrasts`를 생략한 UPDATE는 기존 대조를 유지한다. 합성을 쓰면 SYNTHETIC_DEVELOPMENT_CONTROL로 명시하고 자동 생성하지 않는다. 현행 compiler 때문에 REVIEW_REQUIRED에는 명시적인 대조1개 이상이 필요하다.

`relatedUnitIds`는 기존 runtime에 존재하는 사례ID만 받는다. 연결은 접수 이력에 보관되는 관리용 관계이며 새 runtime 지식그래프·자동 판정 규칙은 아니다. 표면3gram 기반 기존 사례 제안도 출력하지만 운영 검색기의 의미 검색/추천 승인으로 사용하지 않는다. 모든 항목을 신규 사례로 만들지 말고 기존 경계를 보강할지 먼저 검토한다.

### 사용 순서

검수 입력은 Git 제외 `datasets/controversy/` 아래에 보관한다. 저장소 루트에서:

```bash
# 1. 쓰기 없는 계획: 변경 파일·필드·전후 해시·사례 수·기존 사례 제안
python3 tools/casebook_intake.py datasets/controversy/research/intake.json

# 2. 선택: 실제 Java 로컬 검색 회수까지 검사하고 새 비공개 미리보기 폴더에 보관
export JAVA_HOME=/opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk/Contents/Home
export PATH="$JAVA_HOME/bin:$PATH"
python3 tools/casebook_intake.py datasets/controversy/research/intake.json \
  --check-retrieval \
  --output /Users/im_inwook/dev/oops_backend/datasets/controversy/experiments/intake-preview-새이름

# 3. 사람이 위 계획을 검토·승인한 뒤 출력 planSha256을 넣어 적용
python3 tools/casebook_intake.py datasets/controversy/research/intake.json \
  --apply --expected-plan-sha 검토한_64자리_해시

# 4. 완료 후 확인. 서버 반영은 별도 Spring 재시작·로드 해시 확인
python3 tools/build_incident_dataset.py --verify
```

일반 미리보기는 정본 쓰기0회다. `--output`을 요청한 경우에만 experiments 아래 새 폴더에 plan/summary/runtime/query를0600 권한으로 저장하며 기존 경로는 덮어쓰지 않는다. 콘솔에는 원문·검수 응답·API키를 출력하지 않는다. 후보 runtime·변경 전후 내용은 비공개 plan에서 확인한다. 내용이 같은 UPDATE는 미리보기 가능하지만 NO_CHANGE로 적용을 거절한다.

ADD/UPDATE 적용은 **실제 Java 검색 감사를 통과해야 한다.** 고정된 `casebookIntakeAudit` Gradle task를 `--offline`으로 실행하고 기대ID의 회수와 입력/후보 runtime 해시를 확인한다. JDK17·Gradle 의존성이 로컬에 준비되지 않으면 적용 전에 중단하며 자동 다운로드나 우회 적용을 하지 않는다. OpenAI/Groq키는 필요 없고 이 감사 자식 프로세스에도 전송하지 않는다. HOLD는 검수 기록만 남기므로 검색 대상이 없다.

계획 해시는 입력·정본/실행사전·출처/승인·도구/빌더/검색 코드에 묶인다. 바뀌면 다시 미리보기·승인을 받아야 한다. 출력과 사례JSON은 정본을 먼저 직접 수정해 맞추지 않는다. 적용 성공 시 `review-intakes/{planSha256}.json`에 승인 참조·변경 전파일·기존/새 runtime 해시·검색 결과를 남긴다. 이전 runtime도 기존 runtime-history 정책으로 보존한다.

### 검증 범위와 실패 처리

적용은 협력적 `.casebook-intake.lock`을 사용하고 적용 전 입력을 재확인한다. 실패하면 이 도구가 쓴 것으로 확인되는 파일만 복원하고,다른 편집자가 바꾼 파일은 덮어쓰지 않고 ROLLBACK_CONFLICT로 중단한다. 기존 standalone 빌더·수동 편집은 이 lock을 공유하지 않으므로 적용 중에는 다른 정본 편집/빌드를 하지 않는다. 강제종료로 남은 lock은 소유 프로세스를 확인한 뒤 수동 처리한다. 여러 파일의 OS 차원 원자 트랜잭션이나 전원 장애 자동복구까지 보장하지 않는다.

출처/원문/승인·정본 빌드와 해당 발췌의 로컬 검색 회수까지 무료 검사한다. 다른 사례 전체의 검색 회귀·원음 확인·의미 정확도·유료 구안/신안 비교·운영 서버 반영은 자동 수행하지 않는다. 출시 묶음에서는 기존 승인 검색 회귀와 필요할 때의 모델 비교를 별도로 진행한다.

버전1은 **시간 정보가 있는 승인된 개발 경계**의 ADD/UPDATE와 정보부족 보존만 지원한다. 시간 없는 뉴스 인용에 임의시각을 붙이지 않는다. 실제 사건 원장은 기존 `add_incident.py` 경로,OCR 출처·legacy 단위의 재구조화·독립 평가셋·판단 라벨 변경은 별도 검수로 둔다. 이 도구가 평가자료를 학습/운영 참고로 자동 승격하지 않는다.

## 기존 정본 디렉터리

```text
datasets/controversy/
  incidents/*.json              사건별 입력, incident-2
  definitions/build.json        공통 판단 기준·생성 설정·기존 순서

  context-units/*.json          작성한 맥락 참조 단위
  context-relations/*.json      역할별 검색 관계 프로필
  context-sources/*.json        참조 단위의 원문·기원·해시
```

사례 편집은 사건 파일, 공통 기준 편집은 definitions/build.json에서 한다. v7의 참조 단위·관계 프로필은 해당 정본 입력을 편집한다. runtime은 직접 편집하지 않는다. 빌드는 사건 원장에서 v4 기반을 메모리에 만든 뒤 참조 단위·검색 키·관계 프로필을 결합해 v7을 생성한다. 이전 실험 runtime이나 생성된 미리보기를 입력으로 복사하지 않는다.
연구 후보·검수 원장·평가 자료는 자동으로 분석 입력에 포함되지 않는다. 사건의 legacyCard와
legacyDictionaryCard는 현재 스키마와 컴파일러가 읽는 호환 필드라 삭제하면 안 된다.

## 추가·갱신·확인

저장소 루트에서 다음을 실행한다.

```sh
# 현재 입력으로 생성 가능성·ID 계약·기한·크기 검사. 쓰기 없음.
python3 tools/build_incident_dataset.py
# 검사 후 이전 runtime 보관, runtime과 manifest 갱신.
python3 tools/build_incident_dataset.py --write
# 입력에서 재생성한 내용과 저장 출력 및 manifest 일치 확인.
python3 tools/build_incident_dataset.py --verify
```

사건 추가 도구의 --apply는 사건 저장과 생성 가능성 검사까지만 수행한다. 위 --write를 실행해야
분석용 결과를 갱신한다. 새 메커니즘은 definitions/build.json에 정의한 뒤 사건에서 연결한다.
잘못된 ID·미등록 메커니즘·중복·필수 필드 오류는 생성 단계에서 거절한다.

manifest에는 모든 입력 파일의 SHA-256, runtimeSha256, sourceBundleSha256,
contextDictionarySha256, 버전, 사건/예시/기준 수를 기록한다. 입력이 변경된 채 이전 출력이 남으면
verify가 실패한다. 문구 버전을 유지해도 해시로 내용 변경을 구분할 수 있다.

검증한 결과만 runtime 파일로 원자 교체한다. runtime과 manifest의 교체를 하나의 트랜잭션으로
묶지는 않으며 두 파일 사이 중단은 verify가 감지한다. 다시 --write하면 일관된 쌍을 생성한다.
직전 runtime은 legacy/runtime-history에 원본 바이트 그대로 보관한다. 이는 로컬 복구 사본이고
외부 백업은 아니다. 데이터를 복구할 때 해당 버전의 사건 입력·공통 정의도 함께 복구해야 한다.

## 서버 반영

Spring은 시작 시 사전을 메모리에 읽는다. 빌드 뒤 Spring을 재시작하고 시작 로그를 확인한다.

```text
[context-dictionary] state=READY_WORKING_REFERENCE ... version=2026-10-15-context-relations-v1 ... examples=39
```

로그의 version/sourceSha256/examples를 manifest의 version/sourceBundleSha256/examples와 대조한다.
이것은 서버 로드 확인이며 관련 예시의 실제 선택 확인과는 다르다. 요청별 SelectionTrace로
선택된 예시와 제외 family를 확인한다. 기본 위치는 oops-backend 실행 디렉터리 기준
file:../datasets/controversy/guidelines/runtime.json이다. 다른 배치에서는 REVIEW_GUIDELINES_LOCATION을
절대 경로로 지정한다. Python 분석 서버는 이 파일을 읽지 않는다.

## 이번 이관에서 확인한 결과

이관 당시 32사건·37발언과 기존 runtime 37예시의 ID가 모두 대응했다. 공통 정의를 복구하면서
기존 메커니즘별 예시 순서를 유지해 이전 runtime과 재생성 내용의 동치를 확인했다.
과거 파일 8개(이전 README 포함)는 legacy/pre-incident-build에 이동하고 해시 목록을 남겼다.
이동 후에도 신규 build/verify가 통과한다. 현재 README는 새 경로 안내로 교체했다.

실제 Java 로드 검사에서 사례 ID의 # 구분자가 구형 ID 검증에 거절되는 문제가 확인됐다.
사례 ID만 사건#발언 형식을 허용하며 family/메커니즘 ID의 검증은 유지한다.
참고 스키마를 바꾸거나 판단 기준·사례 설명을 바꾼 작업은 아니다.

구형 CLI는 공통 정의가 있는 현재 데이터셋에서 신규 빌드 명령을 안내하며 중단한다.
compile 함수는 신규 빌드와 과거 회귀 시험이 재사용하므로 유지한다. 과거 명령을 현재 운영
절차로 사용하지 않는다. 기존 댓글 수집본은 삭제하지 않았으며 별도 보관·기한 기록을 따른다.

datasets와 uploads는 Git 제외다. 새 체크아웃·AWS에는 데이터가 자동 전달되지 않으므로 현재
입력·연결된 스냅샷·runtime·manifest를 별도 공유하고 검증한다. 생성 성공이 사람 검수·운영 적격·
학습 권한이나 논란 탐지 정확도를 승인하지 않는다.
