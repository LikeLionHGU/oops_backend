### 현재 상태 — 2026-10-14

10/14 코드 갱신: 신규 generate/add의 레거시 파일 의존을 `definitions/build.json`으로 분리했다. 같은 compile 함수의 합성 입력 결과와 직렬화 동치를 확인했고, 정의 누락 시 자동 fallback은 없다. 아래 템플릿 의존 설명은 분리 전 상태다. 현재 원본 6사건이 비어 실자료 재검증/구형 CLI 아카이브는 보류했다. 사건·승인·runtime은 자동 변경하지 않았다.

사건 → 발언 → 복수 메커니즘 구조를 채택했다. 스키마·변환/emit·신규 빌드·기사-only 추가 도구가 존재한다. 기본 미리보기와 사용자 확인 후 apply를 구분하며 apply는 생성 가능성 검사까지이고 runtime 저장/비교는 별도다. 새 빌드의 공통 정의는 definitions/build.json으로 독립했고 사건은 incidents에서 읽는다. 컴파일러 아카이브 완료로 표시하지 않는다.

짜깁기 중심 평가는 동결하고 풀영상·다른 사건·정상 대조를 재구축한다. §9 메커니즘 라우팅은 설계이며 운영 구현/전이 성능은 미검증이다. 기존 메커니즘을 보강하는 후보를 먼저 사용자에게 공유한다. 기사/댓글을 같은 사건의 평가 원문으로 바꾸거나 도구 실행만으로 승인·학습 사용을 승격하지 않는다.

아래 '코드/스키마를 아직 바꾸지 않았다', '승인 후 아직 안 함'은 최초 설계 당시 상태다. §4 JSON은 현재 입력 예제가 아니며, 실제 형식은 mechanismIds 배열과 legacy 호환 필드를 포함한다.

### 1. 왜 바꾸나 — 당시 구조의 문제

현재 한 사건의 자료가 4개 파일에 쪼개져 서로를 참조한다.

```
drafts/cards.json                     사건·카드·evidence.sources 정의
guidelines/plan.json                  mechanism -> sourceCaseIds 역매핑
research/context-dictionary-plan.json card별 topicTags + documents(기사 발췌)
research/source-snapshots/*.txt       기사 발췌 원문(발췌만, sha256으로 무결성)
```

확인된 구체적 문제:

1. **네이밍이 "사건-카테고리" 혼종.** `pisik-B / pisik-C / pisik-D`에서 B/C/D는 사실
   카테고리(지역 생활 비하 / 리뷰 속 모욕 / 신체 훼손 비유)인데 사건 이름(pisik)에 붙어 있다.
   `pisik-B`가 "사건의 B번째 카드"인지 "지역비하 카테고리"인지 불명확하다.
2. **1 사건 : N 논란이 표현되지 않는다.** 영양 영상 하나에 지역비하·신체비유에 더해
   뉴스에서 확인된 발언(공무원 발령, 똥물 등)이 더 있는데, B/C/D 3칸에는 더 담을 자리가 없다.
3. **pisik 카드만 `evidence.sources`가 비어 있다.** sgbg/workman/chim 등은 기사 소스가 등록됐으나
   피식대학(개발 벤치마크)만 비어, 기사 발췌를 사전 documents에 넣으려다 컴파일러의
   `SOURCE_DOCUMENT_REFERENCE_REQUIRED`/`SOURCE_ORIGIN_MAPPING_INVALID`로 막혔다.
4. **벤치마크 클립과 사건 전체의 혼동.** 저장 STT 창(v1.mp4, 롯데리아 대화 22~61초)에는
   기사가 가장 강하게 지목한 발언("공무원 발령", "매일 이것만", "똥물")이 없다. 그런데 사건 라벨은
   영상 전체 기준이라, "B 미탐"이 모델 실패인지 클립 누락인지 구조가 구분하지 못한다.

### 2. 목표 — 3층 분리

사건(무엇이 올라왔나) / 발언근거(어느 발언이 문제인가) / 메커니즘(왜 논란이 되는가)을 분리한다.

```
① 사건 Incident        영상/업로드 1개 = 사건 1개
     │ 1:N
② 발언근거 Statement    사건 안의 개별 논란 발언 + 출처(기사 발췌 / STT 전사 구간)
     │ N:M (발언근거의 mechanismIds 배열이 복수 메커니즘을 참조)
③ 메커니즘 Mechanism    사건을 가로질러 공유되는 "왜 논란인가"의 범용 조건
                       = 전이 학습/참조의 단위
```

- **전이의 단위는 메커니즘**이다. "지역 생활 비하(local-life-devaluation)"가 여러 사건에 쌓이면,
  그것이 다른 미공개 영상에서 재현되는지 평가한다. 사건명/지역명/브랜드명은 전이 조건에 넣지 않는다.
- **발언근거가 사건과 메커니즘을 잇는 다리**다. 각 발언근거는 (a) 어느 사건의 어느 구간/기사 발췌인지,
  (b) 어느 메커니즘인지, (c) 출처 종류(STT 전사 / 기사 서술 / 댓글 반응)를 명시한다.

### 3. 네이밍 규칙

| 층 | 규칙 | 예 |
|---|---|---|
| 사건 Incident | `{channel}-{topic}-{yyyymmdd}` (게시일 기준) | `pisik-yeongyang-20240511` |
| 메커니즘 Mechanism | 의미 기반 영문 kebab-case | `local-life-devaluation`, `graphic-body-metaphor` |
| 발언근거 Statement | `{incidentId}#s{seq}` | `pisik-yeongyang-20240511#s1` |

- `familyId`는 이미 `{channel}-{topic}-{date}` 형태이므로 **사건 id로 승격**한다(중복 개념 제거).
- `pisik-B / pisik-C / pisik-D`는 **폐기**한다. "B"는 발언근거의 `mechanismId: local-life-devaluation`로 표현한다.
- 메커니즘 id는 지금 쓰는 값(`local-life-devaluation`, `constraint-mockery`, `graphic-body-metaphor`,
  `symbolic-association`, `publication-context`, `group-inferiority`, `concern-dismissal`,
  `third-party-harm-dismissal`)을 그대로 승계한다. 네이밍이 이미 의미 기반이라 바꿀 필요 없다.

### 4. 과거 스키마 초안 — 현재 JSON 입력 형식 아님

```jsonc
{
  "id": "pisik-yeongyang-20240511#s2",
  "incidentId": "pisik-yeongyang-20240511",
  "mechanismId": "local-life-devaluation",
  "sourceKind": "NEWS_BODY",            // STT_TRANSCRIPT | NEWS_BODY | AUDIENCE_REACTION
  "statementKind": "AUTHOR_INTERPRETATION", // 전사면 SOURCE_UTTERANCE, 기사면 AUTHOR_INTERPRETATION 등
  "snapshot": "research/source-snapshots/dailian-pisik-...-extract.txt",
  "sha256": "...",                      // 발췌만 저장, 무결성 보장
  "excerpt": "공무원인데 여기 발령 받으면 여기까지 하겠다 ...",
  "whyControversial": "그 지역에 사는 것 자체를 기피·형벌처럼 취급.", // 근거 한 줄
  "source": { "publisher": "데일리안", "url": "...", "publishedDate": "2024-05-25", "retrievedOn": "2026-10-13" },
  "transcriptWindowMs": null,           // STT 출처일 때만 [start,end]
  "evaluationUse": "REFERENCE_ONLY_SAME_FAMILY_EXCLUDED" // ① 참조만, ② 같은 family 평가 입력 금지
}
```

핵심 규칙(기존 원칙 승계):
- **① 참조용 / ② 평가 입력 금지 분리.** 기사·댓글(사후 자료)은 참조 사례(①)로 쓰되,
  같은 사건(family) 영상의 게시 전 탐지 평가(②)에는 입력·정답으로 넣지 않는다. family 제외로 강제.
- **발췌만 저장.** 기사 전문을 저장하지 않는다. 발췌 텍스트 파일 + sha256로 무결성만 보장한다
  (`SHORT_EXTRACT_NOT_FULL_ARTICLE`).
- **출처 종류를 섞지 않는다.** STT 전사(원발언)와 기사 서술(기자 해석)과 댓글(수용 반응)을
  `sourceKind`로 구분한다. 기사 서술을 원발언 전사로 승격하지 않는다.
- **벤치마크 클립 ≠ 사건.** 사건은 영상 전체이고, 평가에 쓰는 클립(v1.mp4)은 그 일부다.
  발언근거에 `transcriptWindowMs`가 있으면 "이 발언이 어느 클립에 포함되는지"를 추적할 수 있어,
  B 미탐이 모델 실패인지 클립 누락인지 구분된다.

### 8. 2026-10-13 세션 추가 결론 — 벤치마크 폐기·정리·규모 분석

#### 8.1 짜깁기(쇼츠) 벤치마크는 무효
- 지금까지 리뷰한 v1.mp4(90초)는 **논란 영상의 쇼츠 짜깁기**이며, 기사가 가장 강하게 지목한 비하 발언
  ("공무원인데 여기 발령 받으면", "이것만 매일 먹으면", "강이 똥물")이 **담겨 있지 않다**.
- 따라서 `pisik-B/C/D` 벤치마크 위에서 돌린 B 미탐은 모델 실패로 단정할 수 없고,
  그 위에 쌓인 `evaluation/v1`의 B 회귀 결과들은 **결론을 쓸 수 없다**(입력이 불완전).
- 방향: 짜깁기 벤치마크는 동결, **유튜브 풀영상(기사가 짚은 발언이 실제 담긴 클립)으로 벤치마크를 재구축**한다.
  기사로 논란 발언·맥락을 먼저 짚고, 그 발언이 담긴 풀영상을 입력으로 쓴다.

#### 8.2 기사·위키의 올바른 사용 (철칙 재해석)
"게시 전 평가에 사후 자료를 넣지 않는다"는 철칙은 **②평가 입력만** 막는다. **①참조 사례 설명**에는
기사·위키가 당연히 들어간다(그게 서비스의 핵심 — 이전 사례를 먹여 전이시키는 구조). 구분:
- ① 참조 사례 설명의 근거 = 기사/위키 OK. 사례집·사전에 발췌로 저장(발췌만, sha256 무결성).
- ② 그 사건 자신(같은 family)의 게시 전 탐지 평가 입력 = 금지. `family 제외`로 강제(이미 코드에 있음).
- 적용 완료: 데일리안 기사 발췌(B/D)를 사전 → runtime.json까지 전파함(코드 변경 0, 유료 0).

#### 8.3 실험 산물 정리 (2026-10-13 실행)
- `tools/*.py` 82개 중 **9개만 live**(생성 체인 6 + 유틸 3: evaluate_analysis_run, collect_youtube_comments,
  review_dataset). 나머지 73 스크립트 + 65 테스트(짜깁기 B 실험)를 `tools/archive-shorts-experiments/`로 git mv.
- live 3단계 파이프라인 --verify green, 남은 95 테스트 통과. 삭제가 아니라 아카이브(이력 보존).
- `evaluation/v1`(62개 디렉토리)은 아직 그대로. 같은 방식으로 아카이브 대상.

#### 8.4 수백 사건 규모 — 비용 계산
- **빌드는 O(N) 전체 재검증**(`for incident in catalog`). 증분 없음. 수십까지는 공짜, 100+에서 느려짐 →
  재구축 시 **사건=파일 하나 + 사건별 해시로 증분 빌드** 가능하게 만든다.
- **런타임은 이미 검색(retrieval) 기반**: `ContextExampleSelector.rank` → `maxExamples=2`로 프롬프트엔 2개만.
  **사례가 수백이어도 프롬프트는 안 터진다**(top-2 고정). "사례 많아서 프롬프트 커짐" 걱정은 틀림.
- 사람 비용: 지금은 사건 추가 시 draft + plan 3개를 4곳에서 수정. 수백 규모에선 지옥 →
  **사건=파일 하나**로 통합해 사람 비용 O(1)로.

#### 8.5 검색 품질 — 수백 규모의 진짜 벽
- `ContextExampleSelector.rank`는 **TF-IDF 유사 어휘(3-codepoint n-gram) 검색**. 의미 임베딩 아님.
  주석 명시: "Local lexical routing only. Similarity is NOT a risk score or semantic proof."
- 성능: 선형 스캔이지만 수천까지 ms. **속도는 수백에서 병목 아니다 — 최적화 투자 불필요.**
- 품질 한계: **같은 메커니즘이라도 소재(단어)가 다르면 못 끌어온다**(hits<3 탈락). 영양="롯데리아/산나물",
  다른 지역비하="스타벅스/시골"이면 어휘가 안 겹쳐 매칭 실패. **메커니즘 전이 목표와 충돌.**
- 장점: 3-글자 n-gram이라 한글 조사·활용에는 강건(먹는다/먹었다/먹고 → "먹" 조각 공유).

#### 8.6 수백 대비 투자 순서 (권고)
1. **메커니즘 필터를 어휘검색 위에 얹기** — 입력을 먼저 메커니즘으로 분류 → 그 메커니즘의 사례만 후보.
   소재가 달라도 메커니즘이 같으면 끌려옴. 사례에 `mechanismId`가 이미 있어 가장 싸고 효과 큼.
2. **측정 후 부족하면 의미 임베딩** — 사례 텍스트 임베딩 + 벡터 검색(수백~수천은 brute-force cosine도 ms).
   로컬 `qwen3-embedding` 모델이 이미 있음. 인프라 추가 비용은 그때 평가.
3. **속도 최적화는 하지 않는다** — 선형 스캔이 충분. 품질(1→2)에만 투자.

#### 8.7 cards/dictionary/runtime 3단계는 왜 있나 (단순화 방향)
- 3단계는 재포맷이 아니라 **서로 다른 입력(plan 3개)을 합류**시키는 과정이고, 해시로 묶여 "소스 안 바꾸고
  실행본만 손대기"를 막는다. runtime.json은 Java가 `review-guidelines-1~5` 버전 분기로 읽어 강결합.
- 지금 규모(6사건)에선 **과잉 복잡성**이지만, 단계를 합치는 건 틀린 접근(입력이 흩어진 게 문제).
- 단순화 방향: (B, 지금 가능) 3단계를 순서 실행+검증하는 오케스트레이터 1개로 "3번 컴파일" 번거로움 제거.
  (A, 재구축 시) 사건=파일 하나로 입력 통합 → 중간 산출물은 build/ 캐시로 숨김, runtime 스키마는 유지(Java 변경 0).

### 9. 메커니즘 필터 설계 — LLM 1-pass 분류 (방식 2 확정)

> 상태: 설계 확정, 구현 보류(풀영상 벤치마크 필요). 코드·유료 변경 아직 0.

#### 9.1 왜 필요한가 (한 줄)
현재 사례 검색(`ContextExampleSelector.rank`)은 어휘(글자 n-gram)라 **"같은 메커니즘·다른 소재"를 못 끌어온다**
(롯데리아↔스타벅스, 산나물↔라면). 메커니즘 전이가 목표인데 어휘만으론 전이가 안 된다.
해법: 입력을 **먼저 메커니즘으로 분류**해, 소재와 무관하게 그 메커니즘의 사례를 후보로 올린다.

#### 9.2 왜 방식 2 (어휘 필터·임베딩이 아니라)
- 방식 1(어휘 필터): 결국 글자 기반이라 근본 한계 그대로. 반쪽. → 기각.
- **방식 2(LLM 1-pass 분류): 의미 기반이라 소재 달라도 메커니즘을 잡음. 최소 비용(분류 1회).** → 채택.
- 방식 3(임베딩): 가장 강력하나 인프라 추가. 수백 규모 전엔 과잉. 방식 2 측정 후 부족하면 그때.

#### 9.3 메커니즘 목록 (2026-10-13 당시 8개 설계, 구형 guidelines/plan.json)
- `local-life-devaluation` 지역 생활·선택지 비하 (pisik-B, pisik-C)
- `graphic-body-metaphor` 신체 훼손 비유 (pisik-D)
- `constraint-mockery` 상대의 의무·제약을 편의와 대비해 조롱 (sgbg)
- `group-inferiority` 개인→집단 속성 확대·집단 열등화 (jang)
- `concern-dismissal` 문제 제기를 호불호·무지로 환원해 무시 (chim)
- `third-party-harm-dismissal` 제3자 피해를 대신 용서·축소 (kwak)
- `symbolic-association` 숫자·발음·배치 조합이 비하와 연결 (workman)
- `publication-context` 피해 사건 주목 시기에 희화화 + 게시 시점 (sgbg-timing)
- (메커니즘은 고정 분류 체계가 아니다. 사건이 쌓이며 분화·병합된다.)

#### 9.3a 메커니즘 입도 기준 — 대분류로 가지 않는다 (2026-10-13 확정)

**메커니즘은 분류학(taxonomy)이 아니라 검색 클러스터(routing key)다.** 유일한 기능은
"같은 메커니즘의 과거 사례를 검색 후보로 끌어오기"(§9.1)이므로, 입도는 "이 사례들을 한 묶음으로
검색해 섞어 보여줬을 때 서로의 판단에 실제로 도움이 되는가"로 정한다.

- **대분류(소수의 넓은 축)로 가면 안 된다.** `target-treatment` 하나로 합치면 지역비하 영상에
  신체훼손 비유 사례까지 후보로 끌려와 노이즈가 된다. 검색 라우팅의 목적(§9.1) 자체가 무력화되고
  어휘검색보다 나을 게 없어진다.
- **사건마다 고유 메커니즘(과도한 세분류)도 안 된다.** 메커니즘당 사례가 자기 자신뿐이면 끌어올
  사례가 없어 전이가 불가능하다 — 메커니즘의 존재 이유가 사라진다.
- **적정 입도 = "다른 사건인데 같은 메커니즘으로 묶으면 한쪽이 다른 쪽 판단에 실제로 도움 되는" 수준.**
- **메커니즘은 소재가 아니라 '연결 구조'로 정의한다.** "지역/음식/스포츠"(소재)가 아니라
  "부재→대체생활 폄하", "수행 직접 조롱"(구조)으로. 소재로 나누면 전이가 깨진다(롯데리아↔스타벅스 교훈).

**새 메커니즘을 만드는 기준:** "앞으로 이 유형 사례가 **여러 개 쌓일 것 같은가?**"
- 쌓일 것 같다 → 새 메커니즘 가치 있음(전이 클러스터가 된다).
- 이 사건 하나뿐일 것 같다 → 기존 중 가장 가까운 데 넣거나, 안 맞으면 **그 사례를 넣지 않는다.**
- 억지로 안 맞는 사례를 새 메커니즘으로 만들면 '전이 안 되는 싱글턴'만 늘어 분포가 나빠진다.

#### 9.3b 분포 점검 결과 (2026-10-13) — 지금 필요한 건 새 메커니즘이 아니라 사례다

현재 8메커니즘 / 6사건 / 9사례. **메커니즘(8)이 사례(9)와 거의 같다.**
- 복수 사례(전이 가능): `local-life-devaluation`(2) **1개뿐**.
- 싱글턴(1사례, 전이 불가): 나머지 **7개**.

결론: 7/8이 싱글턴이라 §9가 노린 "소재 달라도 메커니즘으로 사례 검색"이 **지금은 거의 작동하지 않는다.**
문제는 메커니즘이 모자란 게 아니라 **각 메커니즘에 사례가 모자란 것**이다. 따라서 당분간 전략은:
- **새 메커니즘(9번째)을 만들지 않는다.** 기존 7개 싱글턴에 2번째·3번째 사례를 채워 전이 클러스터로 승격시킨다.
- 새 사례는 "기존 싱글턴 메커니즘을 채우는가"를 우선 기준으로 선별한다. 기존 어디에도 안 맞는 사례는
  새 메커니즘을 늘리기보다 보류한다(분포 악화 방지).

#### 9.4 흐름
```
분석 진입(발언 전체 확보 후, 사례 검색 전):
  1. LLM 1-pass 분류: 입력 발언 → 위 8개 중 "후보 메커니즘" 복수 선택 (0~N개)
     - 복수 허용(한 영상에 여러 메커니즘 가능). 확신 없으면 넓게.
     - 출력은 메커니즘 id 배열만. 판정(REVIEW/PASS)은 하지 않는다 — 라우팅 전용.
  2. select()에 분류 결과 전달:
     - selector.rank 결과 중 해당 mechanismId 사례에 강한 가산점(어휘 점수는 보조로 유지).
     - 같은 메커니즘 내에서 소재까지 겹치면 더 상위.
  3. maxExamples=2 그대로 → 프롬프트 안 터짐.
```

#### 9.5 분류 프롬프트 초안 (라우팅 전용, 판정 아님)
```
# 메커니즘 후보 분류 (라우팅 전용)
입력은 시간 정보가 붙은 발언 전사다. 이 영상에 어떤 '논란 메커니즘'의 후보가 보이는지
아래 목록에서 고른다. 이것은 검토 후보 라우팅일 뿐, 논란 여부·유죄를 판정하지 않는다.
확신이 없으면 넓게 고른다. 해당 없으면 빈 배열.
소재(가게·음식·지역 이름)가 아니라 '연결 구조'로 판단한다:
  예) '여기엔 X가 없어 → 대신 Y로 때워야 → 그런 삶' 연결은 local-life-devaluation.
     소재가 롯데리아든 스타벅스든, 산나물이든 라면이든 같은 메커니즘이다.
메커니즘: [위 8개 id와 각 condition 한 줄]
JSON: {"mechanismCandidates": ["id", ...]}
```

#### 9.6 구현 지점 (풀영상 재구축 때)
- `ReviewGuidelineLibrary.select(...)`에 `mechanismCandidates` 인자 추가.
- 분류 1-pass는 `CandidateReviewEngine.run` 진입부 또는 `SpeechReviewAnalyzer.analyze` 앞에서 1회.
- `ContextExampleSelector.rank`에 메커니즘 가산점 로직 추가(어휘 점수 유지).
- 비용: 분석당 모델 호출 +1 (짧은 분류, 저렴). family 제외 규칙은 그대로.

#### 9.7 검증 조건 (풀영상 벤치마크 필요)
- 짜깁기 벤치마크로는 전이 측정 불가. **풀영상 + 다른 소재 대조 영상**이 있어야 "소재 다른데 메커니즘으로
  끌어왔는가"를 측정할 수 있다.
- 성공 기준: pisik 지역비하 사례를 넣고, 소재가 다른 지역비하 영상에서 `local-life-devaluation` 사례가
  검색 후보로 올라오는가(어휘로는 안 올라오던 것). 반대로 무관한 영상엔 안 올라오는가(오탐).
- 분류 자체의 오탐/미탐도 측정: 분류가 과하면 엉뚱한 사례, 부족하면 전이 실패.

### 10. 핵심 요건 — 기사만으로 사례 성립 허용 (reaction optional)

> 2026-10-13 측정으로 확정된 재구축 핵심 요건. 구현은 재구축 때.

#### 10.1 측정으로 드러난 문제
"알려진 사례를 사전에 많이 넣기"를 지금 구조로 시도한 결과:
- 사례(case) 1건 추가 = **6개 입력 파일 수정 + 3단계 재컴파일**.
- 그리고 **각 사례는 실제 수집된 댓글(reaction)이 사실상 전제**다. `controversy_cards.convert()`가
  `row = original[(videoId, commentId)]` 로 수집 댓글과 대조하고 `EXCERPT_NOT_IN_ORIGINAL`을 검사한다.
  현재 9개 사례 전부 reaction 2~6개를 갖고 있고 reaction 0개 사례는 없다.
- 즉 **"기사로 사례를 넣자"가 실제로는 "그 사건 댓글을 YouTube API로 매번 수집해야 한다"**를 의미한다.
  기사 발췌는 보조 문서(documents)일 뿐, 사례 본체가 댓글 반응에 묶여 있다.

#### 10.2 핵심 요건: reaction 없이 기사 발췌만으로 사례가 성립해야 한다
수백 사건을 쌓으려면, 사건마다 댓글 수집을 강제하면 안 된다. 재구축 스키마는 다음을 만족한다:
- **사례의 최소 성립 조건 = (알려진 논란 지점 + 기사/위키 근거 발췌)**. 댓글 반응은 **선택(optional)**.
- 댓글이 있으면 보강 자료로 붙이되, 없어도 사례가 유효하다.
- 기사 발췌는 지금처럼 발췌만 저장(sha256 무결성, SHORT_EXTRACT_NOT_FULL_ARTICLE).

#### 10.3 정확히 무엇을 완화하나 (막연한 "스키마 변경" 아님)
현재 코드에서 reaction을 사실상 필수로 만드는 지점:
- `convert()` 39~42줄: reaction마다 수집 댓글 대조(`original[...]`, `EXCERPT_NOT_IN_ORIGINAL`).
- `build_bundle` 195줄: `CLASSIFICATION_PLAN_COVERAGE_MISMATCH` — plan의 reaction 집합과 실제가 정확히 일치해야.
- 참고: `validate_bundle`은 reactions가 **비어도 거부하지 않는다**(하드 제약 아님). 즉 간접 제약이다.

완화 방향:
- 사례 입력에서 **reactions를 0개 허용**(이미 validate_bundle은 통과). draft/plan 작성 관행만 바꾸면 된다.
- `reasonHypotheses`/`reasonSupportReactionIds`는 reaction 없으면 빈 배열(코드상 이미 reactions 기반 comprehension이라 자동).
- 대신 **기사 발췌(documents)가 사례의 근거 역할**을 하도록, 사례 성립 검증을 "reaction 존재"가 아니라
  "knownPoint + 최소 1개 근거(reaction 또는 article document)"로 재정의한다.

#### 10.4 ②평가 입력 금지 원칙과의 관계
- 기사 발췌로 사례를 성립시키되, 그 사례는 **참조용(①)**이다. 같은 family 영상의 게시 전 평가(②) 입력엔 안 쓴다.
- 즉 "기사만으로 사례 성립"은 참조 사례를 늘리는 것이지, 평가 치팅을 여는 게 아니다. family 제외는 그대로.

#### 10.5 사건=파일 하나(방안 A)와 묶어서
reaction optional + 사건=파일 하나를 함께 적용하면, 사례 추가가:
```
incidents/{incident-id}.json 하나 작성:
  { knownPoint, mechanismIds, articleDocuments[발췌+sha256],
    reactions[] (선택, 비어도 됨), topicTags }
  → build.py 1회 → runtime.json
```
사례 1건 = 파일 1개 + 빌드 1회. 댓글 수집 없이 기사만으로 가능. 수백 규모에서 사람 비용 O(1).

#### 10.6 검증
- 기사만(reaction 0) 사례가 cards → dictionary → runtime 전 단계를 통과하는지.
- 그 사례가 런타임 검색(메커니즘 필터, 섹션 9)에서 후보로 선택되는지.
- 댓글 있는 기존 사례와 혼재해도 깨지지 않는지(하위호환).

#### 10.7 실증 결과 (2026-10-13, 더미 사건 전 체인 테스트)
reaction 0개·기사만 더미 사건(`test-schema-check`)을 catalog/draft/plan 6곳에 주입해 전 체인을 돌린 결과
(테스트 후 전부 원복, live 체인 녹색 확인):

- **reaction 0개는 한 번도 안 걸렸다.** `validate_bundle`은 빈 reactions를 허용한다. "기사만 사례 성립"은
  스키마상 가능 — reaction 제약은 가짜 장벽이었다.
- **진짜 장벽은 catalog ↔ cards.json 상호 정합성 검증이다:**
  1. `UNKNOWN_COLLECTION` — catalog incident가 `collectionId`를 **필수 참조**한다(reaction 0개여도).
     댓글 없는 사건은 가짜 collection 참조를 넣어야 통과하는 부자연스러움.
  2. `COMMON_CATALOG_CASE_MISMATCH` — catalog의 case 집합이 **저장된 drafts/cards.json**과 정확히 일치해야 한다
     (`review_dataset_catalog.validate_private`).
  3. **닭-달걀 순환:** `build_bundle`은 cards.json을 생성하기 **전에** `validate_private`로 **옛 cards.json**과
     새 catalog의 일치를 **먼저 요구**한다(controversy_cards.py:186). catalog를 바꾸면 cards를 바꿔야 하고,
     cards를 바꾸려면 옛 cards가 새 catalog와 맞아야 하는 순환.

#### 10.8 그래서 add_incident 도구가 해결해야 할 것 (실증 기반)
"reaction optional"만으론 부족하다. 사건=파일 하나(`add_incident.py`)는 다음을 함께 해결해야 한다:
- **collectionId를 optional로** (또는 `no-collection` 센티넬 허용) — 댓글 수집 없는 기사-only 사건 지원.
- **catalog · drafts/cards.json · 3개 plan을 원자적으로 함께 생성** — 순환 검증을 한 번에 만족시킨다.
  (현재는 사람이 6곳을 수동으로, 순서까지 맞춰 고쳐야 통과.)
- 생성 후 전 체인(cards → dictionary → runtime) `--verify` 녹색을 자동 확인.
- 실패 시 원자적 롤백(부분 반영 금지).

이 도구가 있어야 §10의 "사건=파일 하나 + 기사만 + 빌드 1회"가 실제로 성립한다. 없으면 catalog/cards
순환 때문에 사람이 수동으로 못 넣는다(이번 더미 테스트가 그 벽을 실증).

```sh
# 유효한 기존 공통 정의가 있는 데이터셋에서 1회만 명시적으로 실행. 기존 정의 덮어쓰기 금지.
python tools/incidents_migration.py --emit-definition --dataset-root /path/to/dataset

python tools/build_incident_dataset.py --dataset-root /path/to/dataset --verify
```

| 항목 | 확인한 구현 | 남은 경계 |
|---|---|---|
| 사건 입력 | incident-2 스키마·변환/emit·기사-only 추가 도구 존재 | 아래 목표 JSONC를 그대로 입력하지 않음 |

사용 순서는 **후보 공유·확인 → add_incident 미리보기 → apply → 별도 build write → verify**다. write는 로컬 runtime 변경이므로 반영 목적과 검수 상태를 확인한 뒤 실행한다. 이번 문서 갱신에서는 생성/쓰기 명령을 실행하지 않았다. 6단계 컴파일러 아카이브는 완료로 표시하지 않는다.

### 1. 지금 왜 못 쓰는가 — 측정으로 확인된 3대 결함

(근거: `논란맥락사전-구조-재설계.md` §10.7 더미 사건 전체인 테스트)

| A | **catalog ↔ cards.json 닭-달걀 순환.** 빌드가 cards 생성 *전에* 옛 cards와 새 catalog 일치를 먼저 요구 | `controversy_cards.build_bundle` → `validate_private` | 설계 결함(제거) |

| C | **입력 6파일 분산** — 사건 1건 = catalog + cards + plan 3개 + collection 을 사람이 순서 맞춰 수동 수정 | 전반 | 근본 원인(통합) |

3단계 컴파일(cards→dictionary→runtime) **자체는 유지**한다. 이는 재포맷이 아니라 서로 다른 입력을
합류시키고 해시로 무결성을 지키는 안전장치다(§8.7). 문제는 단계 수가 아니라 **입력이 흩어진 것**이다.

### 2. 목표 의미 구조 — 사건 = 파일 하나

아래 JSONC는 설계 당시 의미 구조이며 현재 incident-2 유효 입력 예제가 아니다. 실제 스키마는 catalogMeta와 statement별 legacy 호환 필드를 요구한다. 파일 생성은 add_incident 최소 스펙/미리보기를 따른다. 기사와 STT 출처 필드는 종류별로 분리하고 설명 필드를 동시에 채워 출처를 혼합하지 않는다.

경로: `datasets/controversy/incidents/{incidentId}.json`
사건 id 규칙: `{channel}-{topic}-{yyyymmdd}` (게시일 기준). 예 `pisik-yeongyang-20240511`.

```jsonc
{

  "incidentId": "pisik-yeongyang-20240511",

  // 승인 게이트 — 전부 false 로 생성. 사람만 승격한다.
  "status": "UNREVIEWED_DRAFT",
  "humanApproved": false,
  "runtimeEligible": false,
  "trainingUseAuthorized": false,

  "split": "DEVELOPMENT",
  "topicTags": ["지역", "음식"],              // 검색 주제(위험 라벨 아님)

  // 사건 안의 개별 논란 발언 = 발언근거(statement). 1:N.
  "statements": [
    {
      "id": "pisik-yeongyang-20240511#s1",
      "mechanismIds": ["local-life-devaluation"], // §9 메커니즘 전이 단위. 배열 — 한 발언이
                                                  // 둘 이상에 걸릴 수 있다(예: 지역비하+조롱).

      "article": {                               // sourceKind=NEWS_BODY 일 때
        "publisher": "데일리안", "url": "https://...",

  // 적용 경계·정상 대조. 반론/가상 예문은 정상 영상으로 계산하지 않는다.
  "boundaries": ["부재·욕구·대체는 정상 설명에도 있다. ..."],
  "normalControlCases": [],

    "migratedFrom": ["catalog.json", "drafts/cards.json#pisik-B", "guidelines/plan.json"],
    "legacySha256": "..."
```

#### 2.1 스키마가 결함을 어떻게 없애나
- **C 해소:** 사건의 catalog 항목·카드·mechanism 매핑·topicTags·기사 출처가 **한 파일 안**에 있다.
  교차 참조할 다른 입력 파일이 없으므로 A(순환)가 **구조적으로 발생 불가**.
- **B 해소:** `reactions` 가 선택이고 `collectionId` 가 사라진다. 댓글 없는 사건은 `reactions: []`.
  댓글이 있으면 `AUDIENCE_REACTION` sourceKind 또는 `reactions[]` 에 보강으로만 붙인다.
- **메커니즘 전이(§9) 준비:** `statements[].mechanismIds` 가 사건 안에 직접 있어, mechanism→statement
  역매핑을 별도 `plan.json` 없이 빌드가 수집한다. 배열이므로 한 발언이 복수 메커니즘(지역비하+조롱 등)에
  걸리는 경우를 단일→배열 마이그레이션 없이 처음부터 표현한다(수백 규모에서 반드시 발생).

### 3. 빌드 재구성 — 생성 ↔ 검증 분리 (A 순환 제거의 핵심)

현재: `build_bundle` 하나가 "옛 출력 검증 → 새 출력 생성"을 섞어 순환을 만든다.
확정: **두 함수로 쪼갠다.**

```
build.py --write      incidents/*.json  (입력만 읽음)
                        → build/cards.json → build/context-dictionary.json → guidelines/runtime.json
                      생성 단계는 기존 출력을 절대 읽지 않는다. 순환 불가.

build.py --verify     guidelines/runtime.json (출력만 읽음)
                        → 스키마·해시·mechanism 커버리지·family 제외 검증
                      검증 단계는 입력을 생성하지 않는다.
```

- 중간 산출물(`cards.json`, `context-dictionary.json`)은 `build/` 캐시로 숨긴다. 사람이 손대지 않는다.
- `runtime.json` **출력 스키마는 그대로**. Java `ReviewGuidelineLibrary`(review-guidelines-1~5) 변경 0.
- `catalog.json` 은 **생성물로 강등**(사건 목록은 `incidents/*.json` 글롭으로 자동 집계). 더 이상 수기 입력 아님.

### 4. 마이그레이션 — 되돌릴 수 있는 7단계

각 단계는 독립 커밋. 어느 단계든 `git revert` 로 되돌아간다. **사람 승인·런타임 편입·학습 사용은 전 과정 0 유지.**

1. **스키마 고정 커밋** — Git 에 올리는 것은 `tools/schemas/incident-2.schema.json`(소비자가 tools/ 의
   Python 데이터셋 도구이므로 그 트리에 배치; Java 런타임과 무관)과 이 문서뿐. 실제 `incidents/*.json`
   데이터는 `/datasets/` 아래 로컬 생성물로 Git 제외. 코드 영향 0.
2. **신규 빌드 경로 추가(병행)** — `build_incident_dataset.py` 신설. 기존 3개 컴파일러는 **그대로 둔다**.
   새 빌드가 기존과 **동일한 runtime.json 을 생성**하는지 바이트 비교 테스트부터 통과시킨다(동작 동치 증명).
3. **기존 6사건 변환** — `catalog + cards + plan 3개` → `incidents/{6개}.json`. 변환 스크립트는 1회용,
   결과를 사람이 눈으로 확인. 변환 후 새 빌드 산출 runtime.json == 기존 runtime.json(바이트 동일) 검증.
4. **생성↔검증 분리 적용** — §3. `--write`/`--verify` 분리. 순환 검증 제거.
5. **collectionId optional / reactions optional** — B 제거. **완료(2026-10-13).** 새 빌드 경로는
   catalog `UNKNOWN_COLLECTION` 을 안 타고, compile 은 빈 reactions 를 받아낸다. 실증 과정에서 드러난
   진짜 장벽은 `reassemble` 이 '원본에 없는 새 사건'을 cards/gplan 에 반영하지 못한 버그였고(2단계는
   기존 6사건 그대로라 안 드러남), 이를 "원본 순서 먼저 + 새 사건 뒤에" 로 고쳐 기사-only 신규 사건이
   전 체인을 통과함을 회귀 테스트로 고정했다.
6. **기존 3개 컴파일러 아카이브** — 새 경로가 동치임이 증명된 뒤에만 `tools/archive-*/` 로 이동(삭제 아님).
   Java·runtime 스키마는 이 단계에서도 불변.
7. **그 위에 `add_incident.py`** — "incidents/{id}.json 하나 작성 → build --write → build --verify".
   저장 규칙(사례 추가 전 **후보를 사용자에게 공유**)을 도구에 내장: 기본 dry-run, `--apply` 로만 기록.

#### 4.1 동치 증명이 안전의 핵심
2·3단계의 "새 빌드 == 기존 runtime.json 바이트 동일"이 **마이그레이션 전체의 안전핀**이다.
이게 통과해야 "구조만 바꿨고 판정 동작은 안 바꿨다"가 증명된다. 통과 전에는 기존 경로를 지우지 않는다.

### 6. 결정 기록 (2026-10-13 세션)

#### 확정된 결정
1. **사건 id = 사건 식별자, 카테고리 아님.** id 는 내부 큐레이션/빌드용 라벨이며 **사이트·모델 응답에
   노출되지 않는다**(런타임은 `mechanismIds`/`context`만 모델에 전달, 사건 id 는 로컬 진단 전용). 따라서
   기준은 "사람이 읽어 알아보기 쉬움 + 유일 + 불변"뿐이다. 카테고리(왜 논란인가)는 가변 해석이라
   id 가 아니라 발언의 `mechanismIds` 속성으로 분류한다. 식별과 분류를 분리한다.
2. **메커니즘은 배열(`mechanismIds`).** 한 발언이 복수 메커니즘(지역비하+조롱 등)에 걸리는 경우를
   처음부터 표현한다. 최소 1개, 빈 배열 금지. 단일→배열 후행 마이그레이션 회피.
3. **메커니즘은 사건에 종속되지 않는 독립 식별자.** 발언이 메커니즘을 "가리키고", 같은 메커니즘이
   여러 사건을 가로질러 축적된다(§9 전이 학습의 단위). 메커니즘을 사건 안에 폴더처럼 가두지 않는다.
4. **동치 증명을 머지 게이트로 삼는다** — "새 빌드 == 기존 runtime.json 바이트 동일"이 마이그레이션
   안전핀. 통과 전 기존 경로를 삭제하지 않는다.

#### 추가 확정 (2026-10-13, 사실 확인 후)

5. **기존 6사건 id = familyId 그대로 승격.** id 는 내부 라벨이고 이미 읽기 쉬우며(`pisik-yeongyang`),
   재명명 이득이 없고 2단계 동치 증명(runtime.json 바이트 동일)에도 유리하다. 날짜 없는 기존 건은
   그대로 둔다. 같은 채널의 다른 영상이 실제로 추가될 때 그 **신규 건에만** 구분자(날짜 등)를 붙인다
   (지금 없는 문제를 미리 풀지 않는다).
6. **datasets 전체 Git 제외 유지 — `incidents/*.json` 포함.**
   **사실 정정:** 앞 초안이 "drafts/cards 는 Git 추적 중"이라 적었으나 **오류다.** `.gitignore` 28줄
   `/datasets/` 로 **catalog·cards·plan·기사 발췌 txt 전부 추적되지 않는다**(실측 `git ls-files datasets/`=0,
   확립된 운영 원칙 "데이터셋·원응답·키는 Git에 올리지 않는다"와 일치). 따라서:
   - `incidents/*.json` 도 `/datasets/` 아래이므로 **Git 제외**. 코드 저장소와 분리된 로컬 데이터.
   - 기사 발췌(`research/source-snapshots/*-extract.txt`)의 Git 제외는 저장소 공개를 줄이는 조치다.
     자료 이용·학습·재배포 권한을 보장하지 않는다. 발췌 범위·출처·권한 검토는 별도이며 해시는 무결성만 확인한다.
   - 설계·코드·문서(`docs/`, `tools/`, `oops-backend/src`)만 Git 추적. 이번 문서가 그 예.

#### 여전히 열린 것
없음. 1단계(스키마 고정)는 **완료** — `tools/schemas/incident-2.schema.json` 생성·커밋.

### 아래 이력의 해석

2026-10-16 후속으로 [로컬 구조화 검색 보완](맥락사전-구조화검색-보완.md)을 v7 기본 ON에 연결했다. 원장·고정 검색 view·판단 context를 바꾸지 않고, 별도 코드 리소스의 개념 조합으로 기존 문자 검색을 보완한다. 성적 사생활 질문·집단 전체 평가 2개 프로필만 지원하며, 의미 검색·최종 분류가 아니다. `STRUCTURED_CONTEXT_SEARCH_ENABLED=false`로 이전 결과를 재현한다. 최대 개수·글자·제외 사건 조건은 그대로다.

아래 1절 이후의 기본 v4·v6 미리보기·최대 2예시 설명은 당시 구현 경과다. 현재 기본 v7·최대 3예시는 위 상태를 따른다. 과거의 시험 조건을 바꾸지 않기 위해 기존 절을 보존한다.

### 2. 왜 저장 단위를 나눴나

38예시 중37개는 한 문단 flow, 원문 구간은1개 항목, 명시적 비판 가설은2개뿐이었다.

빌드는 통과하므로 미연결보다는 내용·검색 단위가 병목이다. 요약을 자동으로 원문으로 복원하지 않는다.

| 새 단위 필드 | 역할 |
|---|---|
| parentCaseId / familyId | 연구 원장의 발언·사건으로 돌아가는 연결 |
| source | 로컬 정본 원문·해시·출처 종류 |
| utteranceIds / roles | 원문 ID·상황/평가 역할. 역할별로 재정렬하지 않고 실제 순서를 유지 |
| interpretation / boundary | 작성한 비판 연결과 한계. 전사와 분리 |
| normalContrasts | 합성 개발 대조임을 표시. 실제 정상 영상·독립 정답 승인과 구별 |

완전한 분류 목록이 아니며 싱글턴의 한계도 남는다. 같은 사건의4단위를 독립 사건4개로 세지 않는다.

### 4. 실제 분석 연결과 필터의 안전 경계

- 기본v4: 발견 배치 → 어휘 사례 선택 → 후보 발견 → 배치 참고 고정 → 검증/복구. 기존 동작 유지.
- 명시적v6: 발견 배치 → 후보 발견 → 검증된 후보의 원문 근거로 단위 참고를 한 번 선택 → snapshot 고정 → 검증/복구.
- 검증할 때마다 참고를 바꾸거나 원문 창을 확대하지 않는다. 기존 승인 사례 참고도 함께 보존한다.
- 세부 routingKeys 힌트를 받으면 해당 단위를 어휘 겹침 없이도 우선 후보로 올릴 수 있다.
  다른 어휘 후보를 제거하는 하드 필터는 아니다. 미지/빈 힌트는 어휘 검색으로 돌아가고 빈 원문은 예시를 만들지 않는다.
- family 제외·채널·최대2예시·예시 전체3000자·전체payload6000자 제한은 유지한다.
- **생산 코드 경로에 선택적 자동 분류를 연결했다.** v6와 활성화 설정을 함께 선택하면 발견 배치별 키를 공급한다.
  기본v4·비활성 설정에서는 추가 호출이 없다. 구현과 실제 모델의 분류 성능 검증은 구별한다.
- normalContrasts는 합성 대조라는 지침을 v6에만 붙이고 현재 영상 근거나 정상 판정을 대신하지 못하게 한다.

### 7. 후속 완료: LLM 자동 분류의 실제 분석 연결

`ContextMechanismRouter`를 Spring 컴포넌트로 추가하고 `SpeechReviewAnalyzer.runCandidates`에서
`CandidateReviewEngine`에 주입했다. 별도 실험 실행기에만 있는 기능이 아니다.

```text
STT 원문 → 발견 배치
             ↓ 선택적 LLM 검색 키 분류 {key, segmentIds}
           사례 검색: 키 일치 우선 + 기존 어휘 후보 유지
             ↓ 후보 발견·원문 근거 검증
           후보 근거 ID와 겹치는 키만 전달해 사례를 한 번 선택
             ↓ 참고 payload·원문 snapshot 고정
           기존 검증/제한된 계약 복구 → 카드
```

분류는 key/segmentIds만 반환하며 REVIEW/PASS·점수·인물 의도·수정 전사를 반환하지 않는다.
JSON 모드가 의미와 스키마까지 보장한다고 가정하지 않고, 허용 키·실제 원문 ID·중복·개수·null을 서버에서 검증한다.
기존 API/모델을 유지하는 선택이며 [OpenAI 구조화 출력 안내](https://developers.openai.com/api/docs/guides/structured-outputs)를 참고했다.
프롬프트와 응답 계약은 `ContextMechanismRouter.java`의 PROMPT/Response/Route가 정본이다.

- registry의 schemaVersion/keys만 읽고 실제 로드한 v6의 SPEECH 사례·family 제외 조건과 교집합을 낸다.
  과거 registry의 classificationImplemented 같은 작성 시점 메타데이터는 실행 스위치가 아니다.
- 배치 전체에 키가 있어도 후보가 인용한 원문 ID와 겹치지 않으면 그 키를 후보 검증에 넘기지 않는다.
  다만 ID 겹침은 구조적 경계일 뿐, 모델의 의미 분류 정확도를 보증하지 않는다.
- 빈 응답·거부·타임아웃·HTTP 실패·잘못된 키/ID·입력 상한·호출 상한은 어휘 검색으로 돌아간다.
  분류 실패를 PASS나 최종 분석 실패로 바꾸지 않는다. 본 검증의 실패 상태는 그대로 보존한다.
- 영상당 세션을 새로 만들고 기본 최대12배치만 호출한다. 배치당1시도, 자동 재시도/복구0회,
  출력 최대1024 completion tokens다. 초과 배치도 발견·검증은 계속한다. HTTP timeout은 기존 클라이언트 설정을 공유한다.
- 원문 최대36줄/20,000 codepoints, 키 정의 최대32개/파일32KiB, 응답 최대4키·키당1~12 ID다.
  코드포인트 제한은 토큰 제한이 아니며, 호출/출력 상한도 달러 단위 청구액 보장 한도가 아니다.
- 실제 호출 usage는 기존 영상 합계에 포함한다. `candidatePipeline.mechanismRouting`에 배치별 revision,
  상태·키·원문 ID·입력 SHA·시간·attempted를 남기고 원문·설명·provider 오류 본문은 넣지 않는다.
  attempted는 호출 helper 진입 여부이며 실제 과금 성공 건수와 다르다.
- DISABLED / REQUIRES_V6 / NO_ROUTABLE_KEYS / INVALID_REGISTRY 등은 무호출 상태다.
  ROUTED / EMPTY / NO_RESPONSE / INVALID_RESPONSE / REQUEST_FAILED는 실제 호출 경로의 결과다.
  기존 후보 진단에는 참고 SHA가 남아 어떤 검색 결과로 검증했는지도 대조할 수 있다.

#### 활성화 경계

기본값 OFF이며 기본v4 파일을 교체하지 않았다. 아래는 **유료 테스트 승인 후 새 Spring 프로세스를 시작할 때**
사용할 설정 예시다. 연결 구현 당시 export·재시작·실자료 전송은 없었다.
후속 비교는 별도 실행기로 승인된 텍스트만 전송했으며 실제 서버는 재시작하지 않았다.

```sh
export REVIEW_GUIDELINES_LOCATION=file:/Users/im_inwook/dev/oops_backend/datasets/controversy/experiments/context-unit-upgrade-20261015/runtime.json
export CONTEXT_MECHANISM_ROUTING_ENABLED=true
export CONTEXT_MECHANISM_ROUTING_MAX_CALLS=12
```

registry는 기본 상대 경로를 쓰므로 Spring 실행 디렉터리가 oops-backend가 아니라면
`CONTEXT_MECHANISM_ROUTING_LOCATION=file:/Users/im_inwook/dev/oops_backend/datasets/controversy/definitions/context-routing.json`도 지정한다.
비활성화하려면 ENABLED=false로 새 프로세스를 시작한다. 기존 v4 경로까지 복구하려면
REVIEW_GUIDELINES_LOCATION도 원래 guidelines/runtime.json으로 돌린다. 환경변수만 바꿔도 이미 켜진 서버가 갱신되지는 않는다.

#### 검증과 남은 일

mock으로 실제 analyzer→router→검색→후보별 선택→검증/복구 연결, 후보 간 키 격리,
분류 실패/비활성 시 기존 후보 snapshot·판정 보존, 긴 영상의 상한 뒤 발견 계속,
옵션 호출 실패와 필수 분석 실패의 분리, 토큰 합계 포함·단일 HTTP 시도를 확인했다.
판단 POLICY·출력 validator·기본runtime·사례 내용은 수정하지 않았다. 새 API 호출/추가비용0이다.

후속으로 동일v6 자동분류 OFF/ON16회를 실행했고 [결과](../experiments/맥락-자동분류-OFF-ON-비교.md)에 분류·검색·판정을 분리 기록했다.
v4→v6 저장 구조 효과와 자동분류 효과를 한 번에 묶어 개선으로 주장하지 않는다.
우선순위 충돌의 무료 수정도 완료했다. 수정 후 추가 유료 시험은 새 승인 뒤 별도로 수행한다.

최종 무료 검증: Java733개 통과(실패/오류/skip0), Python129개 통과/기존 선택적6skip,
기본 사전 빌드 --verify 통과(runtime SHA 불변), git diff --check 통과다.
자동분류 mock9개와 선택적 API 클라이언트2개를 추가했다. 이 수치는 연결 구현 당시 기록이며 실모델 비교/추가 테스트는 후속 문서를 우선한다.
