## 2. 과탐 제어의 판단 경계

### 사건 속 행위와 현재 화자의 행위를 구분

- ‘그들이 피해자에게 이런 역할을 요구했다’는 보고를 ‘화자가 피해자에게 그 역할을 요구한다’로 바꾸지 않는다.
- ‘오펜무가 뭐예요?’에 대한 질문형 뜻풀이를 현재 상대에게 한 질문으로 자동 변환하지 않는다.
- 자기 공개 제안, 타인에게 공개 요구, 동의 없는 공개는 다르다. 실제 노출·화자·의도는 전사만 보고 만들지 않는다.
- 인용·보도·농담·교육도 면책은 아니다. 인용을 빌미로 현재 상대를 공격하거나 피해자를 조롱하거나 비공개 정보를 재노출하는 별도 근거가 있으면 검토한다.

과거 행위 관계 필드·상황 우선·가설 중립화 실험이 충분히 개선하지 못했다. 새 필드나 에이전트를 더 붙이면 해결된다고 하지 않는다. 먼저81/86의 실제 요청에서 원문·후보 가설·선택 사례·판단 이유가 어느 지점에서 달라지는지 본다. 기록이 없으면 내부 입력을 추측하지 않는다.

### 경고 목적을 분리

| 목적 | 필요한 근거 | 목표 발행 경로 |
| --- | --- | --- |
| 논란 맥락 검토 | 원문으로 설명되는 모욕·대상화·조롱·집단 확대 | 기본 검토 카드 |
| 표현 수위 검토 | 구체적 신체 훼손 비유 등 표현 자체의 별도 이유 | 표현 자체 카드. 공격 대상을 만들지 않음 |
| 민감 소재 안내 | 성폭력 등 소재의 언급/설명이나 독립 문제 행위 근거 없음 | 별도 안내·선택 표시. 기본 논란 카드로 자동 승격하지 않음 |
| 단어 사용 사실 | 욕설·논쟁 표현의 실제 출현 | 기존 expressionOccurrences. 정상 뜻과 논란 의미를 동일시하지 않음 |
| 정보 부족 | 필수 전사/문맥 누락 | 보류·커버리지. PASS나 논란으로 집계하지 않음 |

이는 목표 설계이며 민감 소재 안내의 새 API/프론트는 미구현이다. SEXUAL/SENSITIVE_TOPIC이라는 category만 보고 일괄 숨기지 않는다. ‘기쁨조’ 표현에 수위 검토가 필요하더라도 고발 서술을 피해자에 대한 직접 대상화로 설명하지 않는다.

후보는 넓게 살펴보되 발행에는 구체적인 구별 근거가 있어야 한다. 단어가 민감하다·단정적이다·누군가는 불쾌할 수 있다만으로 경고하지 않는다. 집단 일반화는 실제 평가 범위가 개별 행위자에서 집단 전체로 확대됐는지 확인한다. ‘관련 측근’과 ‘모든 구성원’을 바꾸지 않고 정치 성향과 무관하게 같은 기준을 쓴다.

점수 임계치 일괄 상향은 우선 채택하지 않는다. 현행 점수는 검증된 논란 확률이 아니며 높은 점수의 역할 혼동도 해결하지 못한다. 서버 형식 검증만으로 의미 정확도가 보장되지 않는 한계도 남는다.

## 3. 개발·시험 순서와 종료 기준

1. **검수 단위 고정:**81 고발3구간과 같은 표현의 PASS 구간,86 뜻풀이/자기 제안을 분리한다.85의3후보는 정상 검수 후보로 둔다. 기존 승인 보존, 새 전사로 자동 확장 금지, 미승인 항목은 DRAFT다.
2. **입력 추적:** 뜻풀이 질문·고발 문맥이 실제 모델 입력에 들어갔는지, 선택 사전이 무엇을 강조했는지 확인한다. 누락이면 전달 문제, 제공됐는데 오해했다면 판단 문제로 다룬다.
3. **한 원인만 수정:** 우선 ‘설명된 행위를 현재 화자에게 귀속’하는 오류를 목표로 한다. 프롬프트·사전·검색·규칙을 동시에 바꾸거나81/86 단어를 화이트리스트로 만들지 않는다.
4. **무료 회귀 먼저:** 서버 계약·원문 보존·평가 라벨 누출·fusion을 확인한다. 프롬프트/입력이 바뀌면 옛 응답을 억지로 매칭해 새 판단 효과로 쓰지 않는다.
5. **작은 실제 비교:** 승인된 핵심 실패2단위＋가까운 실제 검토2단위를 구안/수정안 각2회, 최대16분석 실행부터 고려한다. HTTP 수·비용은 별도 산정하고 새 승인 후 호출한다. 효과가 없으면 확대하지 않고 폐기/재설계한다.
6. **유망한 수정만 통합 시험:** 승인된 정상·검토 사례의 다른 유형을 망가뜨리지 않는지 확인한 뒤 채택/폐기하고 기준선을 동결한다. 운영 기본 ON·배포는 별도 결정이다.

시험 전에 목표 역할 혼동0건, 승인 직접 모욕/요구의 누락 증가0건, 계약 실패/미평가 증가0건 같은 소표본 채택 문턱을 정한다. 이를 달성해도 범용 정확도 입증은 아니다. 한 가족의 여러 발언/반복을 독립 영상으로 세지 않는다. 실제 검토2단위가 확보되지 않으면 실제인 것처럼 합성으로 채우지 않는다. 사람 불일치는 기록/조정하고 결과에 맞춰 정답을 바꾸지 않는다.

과탐·미탐·원문 없는 대상/행위 귀속·중복·형식 실패·보류/예산 제외·시간/사용량을 나눠 기록한다. 미평가를 PASS로 세지 않는다. 모든 경고를 검수하기 전에는 precision 등 성능 수치를 발표하지 않는다.

## 4. 새 영상 확인은 계속하되 작게

첫 묶음은 새 원영상4~6개를 제안한다: 정상 인터뷰/농담1~2개, 사건 설명/교육1~2개, 실제 직접 모욕/요구/집단 확대가 확인되는 영상1~2개. 사람은 모델 결과를 보기 전에 발언과 필요한 문맥을 적는다. 모르는 것은 탐색 자료로 두며 라벨을 만들지 않는다.

제작자 발언과 영상이 설명하는 타인의 행위를 구분한다. 긴 전체 운영 시험과 짧은 경계 발췌 시험은 별도다. 잘랐다면 뜻 질문·사건 설명을 보존하고 FULL_VIDEO로 표시하지 않는다. 같은 원영상/뉴스/재편집본은 같은 가족이다. 같은 오류가 반복되면 영상 추가 대신 원인을 수정한다.

새 독립 영상은 해당 사례를 사전에 넣기 전에 평가한다. 문제를 보고 수정에 사용했다면 이후에는 개발 자료이며 새 독립 시험으로 재사용하지 않는다. 이번 계획에서는 링크 조사·다운로드·유료 분석을 하지 않았다.

## 5. 사전 확장

### 현재 사전과 우선순위

로컬 `datasets/controversy/guidelines/runtime.json`은 v7·6기준·39참고·32가족이다. `context.normalContrasts`는5개이고 status=WORKING_REFERENCE_NOT_VALIDATED, humanValidated=false다. 검수된 정답32사건이나 학습 데이터39건이라고 부르지 않는다.

기존 사례에 **언제 적용하지 않는지**를 먼저 보강한다. 그러나 정상 대조가 이미 있는86도 실패하므로 데이터 추가만으로 해결된다고 보지는 않는다.

확장 단위는 다음 묶음이다.

- **검토 사례:** 누가 누구에게 무엇을 했고 어떤 연결이 문제인지, 원문/출처.
- **실제 정상 대조:** 유사 소재지만 뜻풀이·고발·자기 설명·일반 리뷰라 다른 현재 행위가 되는 경우.
- **가까운 검토 대조:** 같은 소재라도 실제 상대에게 요구하거나 인용으로 공격하는 등 바뀐 조건.
- **경계 설명:** 적용 조건/적용 금지 범위/부족한 정보. 합성은 실제 관측과 구분.

정상 대조는 반론 댓글로 논란을 취소하는 것이 아니라 **현재 발화 행위가 다른 경우의 경계**다. 댓글은 실제 비판 이유·감정·특수 의미의 보강 자료이고 다수결 정답·원발언·확정 사실이 아니다. 반론은 참고 이력으로 보존하며 기존 비판 근거를 자동 취소하지 않는다.

### 1차 품질 파일럿

성적 대상화/사생활 요구, 비판적 인용, 집단 일반화/정치 비판, 음식 리뷰/지역 선택지의4경계 묶음을 고른다. 각각 검토1개＋실제 정상1개를 점검해 최대8단위로 시작한다. 독립8사건을 뜻하지 않는다. 기존 참고를 보강할 수 있으면 새 사건/상위 유형을 늘리지 않는다. 정상 실제 대조가 없으면 합성으로 위장하지 않는다.

81 발언들을 곧바로 새 양성 사례로 추가하지 않는다.86을 일괄 면책 규칙으로 만들거나85 영상 전체를 무조건 PASS로 만들지도 않는다. 사건별 검수·라벨과 범용 패턴의 적용 경계는 별개로 관리한다.

### 저장·검색·승격

기존3층 구조를 유지한다: 사건 원장(출처·원문·댓글·검수 이력) → 짧은 범용 패턴 → 검색용 사례/대조. runtime에 댓글 전체·긴 사건 해설을 넣지 않는다. 제안 필드를 현행 스키마 필드처럼 추가하지 않고 먼저 기존 normalContrasts와 원장 검수 구조를 이용할 수 있는지 확인한다.

원영상이 없으면 공식 뉴스에서 실제 발언이 재생/인용된 부분을 출처를 명시해 사용한다. 기자 해설·원발언·댓글은 구분하고 없는 앞뒤 대화·원영상 시간·화자 행동을 복원하지 않는다. 수집·재이용 조건·개인정보·보관 기간도 확인한다.

**후보 공유/검수 → 원장 반영 → runtime 프리뷰 → 스키마·출처·해시·검색 점검 → 과탐/미탐 비교 → 채택 후 write/verify → 서버 반영 확인**으로 운영한다. 빌드 성공은 의미 검수 성공이 아니다. 기본 v7과 복구본을 보존하고 runtime 자동 덮어쓰기는 하지 않는다. 코드 push만으로 Git 제외 사전이 AWS에 반영되지 않는다.

사전/평가 자료는 원영상·뉴스·재편집본의 가족 단위로 분리한다. v1은 사전 포함 개발 점검으로 유지하고 독립 성능에 합산하지 않는다. 파인튜닝·벡터DB·대량 댓글 수집은 경계 품질 확인 후의 선택지이지 당장 필수는 아니다.

## 6. 바로 할 일과 보류

**먼저:**81·86 실패 단위/85 정상 후보 검수 자료 정리 → 기존 승인과 새 전사 대응 → 실제 입력의 문맥·사전 연결 점검 →4경계 묶음 정상 대조 누락 감사.

**사용자 결정 필요:** 미승인 단위 판단, 새 영상 선택, 실제 비교의 새 예산/텍스트 전송. 과거 승인 예산은 재사용하지 않는다.
