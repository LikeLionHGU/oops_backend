# 맥락 중심 검수 사례 자산 — 2026-10-23

후속: [1차 정비·무료 검증 보고](../experiments/검색-진단과-운영연결-기록.md#record-5)에서 43개 품질 목록과 대표 메커니즘 6조건·경계 링크·실제 검색 검사까지 수행했다. 아래 대표 1건은 시작 단계 이력이며 운영 미연결 상태는 유지한다.

## 방향

단어가 같은 사례를 찾는 사전이 아니라, 어떤 상황·관계에서 검토 이유가 성립하는지 비교하는 사례집으로 정비한다. 원문은 삭제하지 않고 증빙층으로 분리한다. 현재 입력의 근거는 항상 현재 입력에서 찾아야 한다.

## 구현 완료와 미완료

- 완료: `tools/build_context_assets.py`의 오프라인 미리보기 빌드, 구조 검증, 출처 해시 검증, 증빙/참고/검색 표현 분리, 대표 사례 1건 생성.
- 대표 사례: 사용자 승인 PASS인 과거 모욕의 피해 경험 인용. 구조화한 설명은 개발자 작성 초안이며 추가 사용자 승인·독립 정답·학습 권한을 뜻하지 않는다.
- 미완료: Spring 검색/판단 경로 연결, 기존 43개 전환, 실제/합성 대조의 별도 관계 모델, 의미 검색, 성능 비교. 기존 runtime은 변경하지 않았다.
- 공용 프롬프트 변경·유료 호출·서버 재시작 없음. 특허성 검증이나 정확도 향상을 주장하지 않는다.

## 세 가지 투영

| 출력 | 목적 | 내용 |
| --- | --- | --- |
| evidence.json | 추적·재검수 | 원문·시간·출처 해시·기존 개발 판단 |
| reference.json | 향후 모델 참고 초안 | 상황·대상·관측 관계·메커니즘·성립 조건·불충분 조건·정상 경계·미확인 정보 |
| search.json | 향후 검색 인덱스 초안 | 상황·대상·메커니즘·관계 설명. 원문 문자열을 자동 연결하지 않음 |

관측 관계에도 증빙 ID를 붙인다. 관계 설명은 작성한 해석이므로 원문 사실과 동일시하지 않는다. `requiredConditions`는 코드가 강제하는 판정 규칙이 아니라 해석 비교용 명시적 조건이다. 문자열만으로 의미의 진실성을 검증할 수는 없다.

기존 단위 정본은 원문 ID와 원문 출처를 유지한다. 새 프로필은 정본의 canonical SHA-256에 결합되어 정본이 변경되면 재검토 전 빌드가 중단된다. 이는 단위 변경을 탐지할 뿐 모든 판단 기준 변경을 자동 추적하는 완성된 배포 시스템은 아니다.

출력은 별도 private 미리보기이며 Java runtime 계약이 아니다. 기존 `normalContrasts`나 기존 판단을 모델 참고에 그대로 복사하지 않는다. 실제/합성 대조는 다음 단계에서 출처와 승인 상태를 보존하는 독립 링크로 추가한다.

## 대표 파일과 재현

Git 제외 정본: `datasets/controversy/context-assets/victim-quotation.json`

```bash
/opt/anaconda3/envs/oops-analysis/bin/python tools/build_context_assets.py \
  --profile context-assets/victim-quotation.json \
  --output /Users/im_inwook/dev/oops_backend/datasets/controversy/experiments/context-assets-victim-preview-20261023
```

출력 경로가 이미 있으면 덮어쓰지 않는다. 재현 시 experiments 아래 새 경로를 지정한다. manifest에는 프로필·생성기·기존 runtime과 각 출력의 canonical 해시를 남긴다. 참고 문자열이 의미상 원문을 재현하지 않는지는 사람 검수가 필요하다. 코드가 보장하는 것은 원문 필드의 자동 삽입 방지이지 자동 익명화가 아니다.

이번 대표 참고는 직렬화 기준 1,023 code point다. 토큰 수·비용 절감·성능 향상 측정값은 아니다.

## 검증

- Python tools 회귀: 160 passed, 6 skipped, 27 subtests passed. 이후 소규모 검증 보강은 같은 명령으로 재검증한다.
- 새 계약 테스트: 원문/기존 라벨 분리, 결정적 출력, 원본 입력 불변, 미승인 상태 유지, 빈 경계·외부 근거 ID·알 수 없는 필드·변조된 출처/정본 해시 거부.
- 기존 사건 빌드 `--verify`: 43참고·6기준, runtime SHA `6f330d24cd557197f66a9d8b0f9f7bc80c02dfea7bd83da61f526c08a2f94d1b` 유지.
- Java 코드는 변경하지 않았으며 이번 작업에서 Gradle 테스트를 실행하지 않았다.

## 다음 순서

1. 대표 프로필의 관측 관계와 판단 조건을 검수한다. 기존 PASS 승인을 구조화 설명 전체의 승인으로 확대하지 않는다.
2. 실제·합성 대조 링크, 검수자별 이견, 정책 버전을 설계한다.
3. 기존 43개 품질 목록을 만들고 이전 요약형 35개를 순차 정제한다. 삭제·이름 변경하지 않는다.
4. 검수된 프로필에서 실행용 새 계약을 만들고 검색 회수·요청 보존·원문 누출 여부를 무료 검증한다.
5. 실제 비교는 새 승인 뒤 사례 자산만 교체해 진행한다. 공용 프롬프트·모델 변경 효과를 섞지 않는다.
