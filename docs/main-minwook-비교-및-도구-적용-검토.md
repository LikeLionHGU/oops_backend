**우리 코드는 main의 단순 상위 버전이 아니다.** main도 별도로 운영/재생/호출 제어를 보강했다. 아래 비교는 최종 파일 상태 차이이며, 모든 삭제를 이번 개발에서 의도적으로 없앤 기능으로 해석하지 않는다. 미커밋 신규 파일은 `git diff main`만으로는 나오지 않아 직접 함께 확인했다. AWS가 이 main 커밋을 실제 실행 중인지는 확인하지 않았다.

핵심 방향은 **‘단어가 걸렸으니 경고’에서 ‘대화·대상·원문 근거를 확인하고 왜 다시 볼지 설명’으로 바꾸는 것**이다. 다만 실제 정확도가 높아졌다는 결론은 아직 낼 수 없다.

## 3. 현재 좋아진 점과 아직 해결되지 않은 점

좋아진 것은 **검토 범위와 실패 원인을 관측할 수 있는 구조**다. ID 9에서는 구간 53개 모두 유효 판정됐고 묶음 5개 중 4개 유효, 1개 계약 탈락이었다. 그러나 지역 음식 흐름 B는 연결을 인정해도 PASS였고, 이전에 있던 D의 ‘할머니 살’ 비유 카드가 사라졌다. 최종 카드는 C 메뉴 평가 1개, 시간은 ID 8의 126.2초에서 142.6초로 증가했다.

따라서 “main보다 정확도가 높다”, “묶음 분석으로 논란을 충분히 잡는다”는 표현은 아직 사용하지 않는다. main에 같은 영상·조건으로 분석한 비교 결과도 없다. v1은 반복 개발 자료이며 독립 테스트셋이 아니다. [ID별 실험 기록](AI-분석-실험-기록.md)을 실제 결과의 기준으로 사용한다.

다음은 불쾌한 신체 비유와 실제 인물/집단 모욕을 구별하는 탐지 기준, B의 브랜드/지역 음식/주민 대상 해석, 정상 대조 사례, 묶음 계약 오류 세분화를 우선한다. 단어 하드코딩이나 증거 검증 완화로 결과를 맞추지 않는다.

## 5. 추가 요청: HyperFrame은 어떻게 적용할 수 있는가

### 도구 확인

이번 조사는 **HeyGen의 HyperFrames**를 대상으로 한다. 정확한 멘토 추천 링크가 다른 제품이면 다시 대조해야 한다. HTML/CSS·미디어·시간 제어 애니메이션을 영상으로 렌더링하는 오픈소스이며, 분석 모델이나 논란 탐지기는 아니다. 저장소의 현재 라이선스는 Apache-2.0, CLI 요구사항은 Node.js 22+와 FFmpeg다. [공식 저장소](https://github.com/heygen-com/hyperframes), [LICENSE](https://github.com/heygen-com/hyperframes/blob/main/LICENSE).

공식 엔진은 브라우저에서 프레임을 캡처해 인코딩하며 상위 CLI/producer가 렌더 파이프라인을 담당한다. 합성 영상 미리보기용 player도 제공한다. 우리 서비스에서의 적용은 아래 설계 제안이며 기존 편집툴 프로젝트를 자동 가져오거나 OCR에서 진짜 자막만 뽑아준다는 뜻은 아니다. [엔진 문서](https://hyperframes.heygen.com/packages/engine), [합성 구조](https://hyperframes.heygen.com/concepts/compositions), [player 문서](https://hyperframes.heygen.com/packages/player).

### 추천 적용 범위: 검수 → 사람이 승인한 수정안의 미리보기

| 단계 | 우리 서비스의 작업 | 도구 필요성/상태 |
|---|---|---|
| 지금 | 위험 후보·원문·타임스탬프·앞뒤 문맥 제공 | 기존 기능. HyperFrames 불필요 |
| 먼저 검토 | 편집자에게 수정 제안/구간 목록을 JSON·CSV 등으로 전달 | 간단한 export는 자체 구현 가능, 특정 편집툴 호환은 별도 검증 |
| 후속 작은 실험 | 승인된 한 구간에 안내/대체 자막을 겹친 짧은 미리보기 | HyperFrames 합성/렌더 후보. 아직 PoC 미실행 |
| 나중 | 삭제/음소거/블러/자막 교체를 승인 후 파생본으로 출력 | 트림·음성 동기화·효과별 별도 검증 필요. 단순 컷/음소거는 FFmpeg만으로 가능한지 먼저 비교 |

이미 영상에 구워진 자막은 별도 SRT를 고치는 것만으로 교체되지 않는다. 원본 편집 프로젝트나 별도 마스킹/재합성이 필요하다. OCR 선별 문제는 `ScreenTextClassifier` 개선과 향후 SRT/VTT 업로드·출처 검증으로 해결해야 하며 HyperFrames 도입만으로 해결됐다고 설명하지 않는다.

백엔드 연결 제안:

1. 사람 승인 전후를 구분한 `EditProposal`과 `RenderJob`을 향후 설계한다. sourceVideoId/analysisRunId/근거 findingId/원본 구간/작업 유형/승인자/템플릿 버전/출력 assetId가 필요하다. 현재 DB에는 이 기능이 없다.
2. Spring은 권한·원본 존재·시간 범위·승인 상태를 검사하고 작업 상태만 관리한다. Node 렌더 워커는 기존 분석 Executor와 분리하고 처음에는 동시성 1로 제한한다. 기존 AWS 배포를 유지할 수 있으며 Rails/Railway 전환은 선행조건이 아니다.
3. 워커는 허용 템플릿과 검증된 asset 참조만 받는다. 임의 HTML/JS·외부 URL·사용자 파일 경로를 실행하지 않고 네트워크/파일 접근, CPU/메모리/실행시간/출력 길이를 제한한다.
4. 원본을 덮어쓰지 않고 파생본·원본 시간 매핑·작업 이력을 보존한다. 원본 보관 만료 시 렌더 불가를 안내하거나 동의한 별도 보관 정책을 설계한다. 자동 재렌더/무제한 재시도는 하지 않는다.
5. 검증은 10~30초 샘플부터 시작한다. 음성/화면 싱크·자막 시간·프레임 정확도·파일 크기·실패/취소·원본 만료·비인가 asset 접근을 확인하고 렌더 시간/메모리를 측정한다.

라이브러리의 렌더당 사용료가 없어도 CPU·저장·전송·운영비는 발생한다. 일단 로컬 PoC만 검토하고 Lambda/추가 서버를 자동 도입하지 않는다. 지금은 편집 기능을 보류한다는 사용자 결정을 유지한다.

## 6. 추가 요청: PostHog는 어떻게 적용할 수 있는가

### 목적과 역할

사용자가 확인한 도구명은 **PostHog**다. 제품 이벤트와 세션 리플레이로 사용 흐름을 관찰하는 도구이며 논란 판단의 정답을 만들거나 STT/OCR를 대신하는 도구가 아니다. 우리에게는 ‘업로드가 어려운가, 분석 대기 중 떠나는가, 리포트를 실제 검수에 쓰는가’를 확인하는 데 적합하다. [공식 문서](https://posthog.com/docs), [세션 리플레이](https://posthog.com/docs/session-replay).

먼저 **내용 없는 명시적 이벤트**, 이후 동의한 제한적 리플레이를 추천한다. 프론트 코드는 이 백엔드 저장소에 없으므로 DOM 계측·마스킹·사용자 인터랙션은 프론트 담당자가 별도로 구현해야 한다. Spring만 수정해서 실제 화면 리플레이를 얻을 수는 없다.

### 이벤트 계약 제안 — 아직 미구현

| 이벤트 | 기록 주체·시점 | 확인할 질문 |
|---|---|---|
| `upload_started` | 프론트가 업로드를 시작할 때 | 업로드를 시도한 사람이 얼마나 되는가 |
| `upload_accepted` | Spring 파일/작업 생성 커밋 후 | 시작 대비 실제 접수에 성공했는가 |
| `analysis_started` | Spring 작업 실행이 확정될 때 | 대기열에서 얼마나 기다렸는가 |
| `analysis_completed` / `analysis_failed` / `analysis_cancelled` | Spring 최종 상태 커밋 후, 상태 변경당 1회 | 완료율·부분 분석·지연·실패/취소율은 얼마인가 |
| `report_opened` | 프론트에서 리포트 화면을 실제 열었을 때 | 결과를 보기도 전에 떠나는가 |
| `candidate_opened` | 프론트에서 후보를 선택했을 때 | 어느 유형의 후보를 확인하는가 |
| `review_action_saved` | Spring 검수 액션 커밋 후 | 확인/수정/보류/불필요 판단을 얼마나 남기는가 |

허용 속성은 환경, 익명화가 아니라 **가명화된** 테스트 사용자/세션 식별자, 랜덤 run 상관 ID, 영상 길이 구간, 큐/처리 시간, 결과 개수, coverage 상태, 제한된 에러 코드, 검수 액션 enum 정도로 시작한다. 숫자 DB videoId/jobId를 그대로 전송할 필요는 없다. 인증 전 서버 작업과 브라우저 세션을 연결하려면 동의/식별 토큰의 전달·검증 계약을 따로 설계하고 임의 사용자 ID를 신뢰하지 않는다.

파일명·영상·원본 URL·프레임·STT/OCR·인용·후보 reason/target·이메일·키·자유입력 피드백은 보내지 않는다. 이벤트 종류/속성을 허용 목록으로 제한한다. 이후 로그인 도입 시 내부 ID의 외부 식별 매핑과 로그아웃 reset, 동의 철회/삭제 절차를 설계한다.

### 백엔드 연결과 실패 정책

- `ProductAnalytics` 인터페이스와 기본 no-op 구현을 두고 PostHog 전송을 어댑터로 격리하는 방안을 추천한다. 현재 main/minwook 모두 이 어댑터가 없다.
- 상태 저장과 외부 전송을 같은 트랜잭션에 넣지 않는다. 커밋 후 제한된 별도 전송 큐에 보내고 timeout·최대 재시도·중복 제거를 둔다. 분석/업로드를 계측 실패 때문에 실패시키지 않는다.
- 메모리 전송은 종료 시 이벤트를 잃을 수 있다. 초기 실험에는 손실을 문서화하고, 정확한 완료율/결제 통계가 필요해지면 DB outbox와 소비자 중복 방지를 도입한다. 분석 status 폴링마다 완료 이벤트를 반복 전송하지 않는다.
- 서버 HTTP capture/batch 연동을 후보로 검토한다. 오래된 `PostHog/posthog-java` 저장소는 archived여서 그 패키지를 무조건 추가하지 않는다. 실제 구현 때 공식 권장 라이브러리/지원 JDK/전송 형식을 다시 확인하고 버전을 고정한다. [수집 API](https://posthog.com/docs/api/capture), [기존 Java 저장소 상태](https://github.com/PostHog/posthog-java).
- 인입용 project token과 관리용 personal API key를 구별한다. 관리 키는 프론트에 넣지 않는다. 동의 여부와 환경별 enabled 설정을 검사하고, local/test는 기본 외부 전송을 끈다.

### 리플레이 보안과 비용

입력 필드 마스킹만으로 안전하지 않다. PostHog 공식 웹 문서는 일반 DOM 텍스트가 기본 마스킹 대상이 아니라고 설명하며 전체 텍스트 마스킹과 `ph-no-capture` 영역 차단을 제공한다. 영상/캡처/대본/리포트/계정 영역을 차단하고 URL 쿼리·네트워크 payload·콘솔 로그·자동 이벤트도 별도로 점검한다. 마스킹은 custom event에 직접 넣은 원문을 제거해주지 않는다. [공식 웹 개인정보 제어](https://github.com/PostHog/posthog.com/blob/master/contents/docs/session-replay/_snippets/web-privacy.mdx).

초기에는 autocapture와 리플레이를 끄고 허용 이벤트만 검증한다. 그 다음 동의한 내부 사용자 일부 세션에서만 리플레이를 켜고, 실제 수집 payload와 재생 화면에 민감정보가 없는지 확인한다. 보관/삭제·수집 지역·프로젝트 접근 정책을 승인한 뒤 고객 테스트에 사용한다. 웹 동의/UI 구현과 서버 동의 계약이 필요하다.

조사 시 공식 가격 페이지는 월 제품 이벤트 **1M**, 리플레이 **5K** 무료 제공량을 표시했다. 이는 프로젝트 설정/초과 수집 비용까지 항상 무료라는 뜻은 아니다. 예산·샘플링·수집 상한/차단 정책을 설정하고 계약 시 재확인한다. 셀프호스팅도 운영 자원이 필요하므로 무과금의 자동 대안으로 보지 않는다. [공식 가격](https://posthog.com/pricing).

### 완료 조건과 개발자별 분담

| 담당 | 우선 할 일 | 완료 조건 |
|---|---|---|
| 백엔드 | 이벤트 enum/허용 속성/no-op 어댑터, 커밋 후 발생, 제한된 비동기 전송 설계 | 원문/키 없음, 장애 격리, 재시도/중복/동의/disabled 테스트 |
| 프론트 | 업로드·리포트·후보 인터랙션 이벤트, 익명 세션 연결, 수집 동의 | 전환 흐름 연결 가능, 원문 없는 payload, 동의 철회 반영 |
| 프론트·보안 담당 | 리플레이 차단 영역과 URL/네트워크/콘솔 점검 | 민감 화면 비노출을 실제 payload/재생으로 검증 |
| 기획/팀 | 무료 테스트 고객과 인터뷰, 지표 정의/접근·보관 정책 | 업로드→완료→열람→검수 전환 및 이탈 이유를 설명 가능 |
| 편집 PoC 담당(후속) | HyperFrames 짧은 샘플/자원·동기화 측정 | 승인된 수정만 파생본에 반영, 원본/시간 매핑 보존 |

`NOT_USEFUL` 액션은 고객의 유용성 피드백이지 자동 오탐 정답이 아니다. 완료 전환율과 독립 평가의 탐지 정밀도/재현율은 분리한다. 자동 모델 교체/실험으로 사용자별 판정이 바뀌도록 하는 기능은 지금 넣지 않는다.

## 7. 팀에 전달할 짧은 요약

“main은 기존 배포·재생·호출 제어 기능을 보존해야 하는 기준선이고, minwook은 원문 근거와 대화 맥락을 검증하며 실패 이유를 볼 수 있도록 분석 경로를 개편하고 있습니다. 아직 탐지 정확도 개선은 검증되지 않아 정상/위험 사례 평가가 먼저입니다. PostHog는 내용 없는 이벤트 계측부터 고객 사용 흐름 검증에 연결할 수 있습니다. HyperFrames는 추후 승인된 수정안의 미리보기·렌더링용으로 검토하되 편집 기능은 현재 보류합니다.”

이번 작업은 문서 갱신과 코드/공식 자료 조회만 수행했다. 프레임워크·모델·DB·서버를 변경하지 않았고 병합, 커밋/푸시, 배포, 도구 설치/계정 생성, 사용자 데이터 전송, 유료 분석/렌더를 실행하지 않았다.
