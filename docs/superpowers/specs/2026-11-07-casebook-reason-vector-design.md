# 사례집 비판 이유 벡터 검색 — 설계

작성 2026-11-07. 상태: 초안, 사용자 검토 대기.

## 의도

사례집(`datasets/controversy/incidents/`, 32사건·38발언)은 실제로 논란이 된 발언과 그 비판 이유를 모은 자료다. 지금 서비스는 이 사례집을 문자·키워드 겹침(`ContextExampleSelector`)으로 찾아 판정 모델에 참고로 붙인다. 표현이 다르면 같은 종류의 논란을 찾지 못한다.

이번 작업은 사례집의 **비판 이유**를 벡터로 저장하고, 새 발언도 **비판받는다면 그 이유**로 바꿔 의미가 비슷한 과거 논란을 찾는 것이다. 평가는 원영상이 없어도 되는 실제 논란 사례로 한다. 무엇이 왜 비판받았는지가 기사·나무위키·댓글에 남아 있으므로, AI가 만든 라벨이 아닌 외부 기록을 정답으로 쓸 수 있다.

배경: J1([J1-판정품질-기준선-설계.md](../../experiments/J1-판정품질-기준선-설계.md))은 논란이 없는 일상 영상을 써서, 제품이 겨냥하는 "실제로 논란이 될 발언"과 다른 것을 쟀다. 사용자는 실제 논란 사례 중심의 평가를 원한다.

## 목표

1. 사례집 발언마다 비판 이유 문장을 하나씩 만든다. 형식은 "누구를/무엇을, 어떤 방식으로, 왜 문제인가"이다.
2. 비판 이유 문장을 `BAAI/bge-m3`로 벡터화해 저장한다. 원래 인용과 출처, `mechanismIds`, `familyId`를 함께 둔다.
3. 새 발언도 AI가 비판 이유 문장으로 바꾼 뒤 벡터로 비교해 비슷한 과거 논란을 찾는다.
4. 사례 하나를 시험할 때 그 사건(family) 전체를 저장소에서 빼고 평가한다.

## 성공 기준

평가 입력은 사례집 각 발언의 기사 인용 문장이다(`knownPoint.text`, `boundaries`의 발언 원문). 원영상은 쓰지 않는다.

1. **찾기:** 같은 사건을 뺀 상태에서 상위 3개 안에 같은 `mechanismIds`를 가진 다른 사건이 있는 비율. 같은 질문에 현재 키워드 검색(`ContextExampleSelector`)도 돌려 비교한다. 벡터 검색이 키워드 검색보다 분명히 높아야 성공이다.
2. **판정:** 같은 인용 문장에 대해 서비스가 REVIEW_REQUIRED를 내는 비율을 세 조건으로 비교한다. (a) 참고 사례 없음, (b) 키워드 검색 참고, (c) 벡터 검색 참고. (c)가 가장 높아야 한다.
3. **오탐:** J1 무작위 층(평범한 발언, 기준 NO_RISK)에 같은 세 조건을 적용했을 때 (c)의 REVIEW_REQUIRED가 (a)보다 늘지 않아야 한다.

## 하지 않는 것

- 사례집 확장(`research/catalog-100-judged-20261014.csv`의 100건 활용). 다음 단계로 미룬다.
- STT 개선. 별도 작업이다.
- 운영 기본값 변경. 결과가 좋아도 이번에는 실험 경로에서만 쓴다.
- 벡터 DB 도입. 38건이라 파일 하나와 메모리 내 코사인 유사도로 충분하다.

## 실패로 보는 것

- 같은 사건의 다른 발언이 저장소에 남아 정답을 미리 보여 주는 경우(누설).
- 판정이 늘었는데 평범한 발언의 오탐도 같이 늘어난 경우. 이건 탐지 개선이 아니다.
- 결과를 보고 비판 이유 문장이나 기준을 고친 뒤 같은 사례로 다시 재는 경우.

## 제약

- 유료 호출은 사용자가 직접 실행한다. 비용 상한과 동의 토큰은 기존 실험 절차(`ContextExperimentTrial`)를 따른다.
- 임베딩은 로컬 `bge-m3`로 무료 실행한다. `tools/embed_segments.py`가 이미 이 모델을 받고 해시를 고정한다. 디스크 여유가 약 11GB이므로 새 모델은 받지 않는다.
- 사례집 항목은 모두 `UNREVIEWED_DRAFT`이고 `humanApproved: false`이다. 결과는 "검수 전 사례집 기준"이라고 적는다.
- 38발언이 비판 유형 6개(`group-generalization`, `harmful-glorification`, `insult-mockery`, `privacy-exposure`, `sexual-objectification`, `victim-mockery-dismissal`)에 고르지 않게 나뉜다. 결과는 방향 확인용이며 통계적 결론이 아니다.
- 규칙(비판 이유 문장, 질의 지시문, 상위 k, 평가 입력)은 실행 전에 해시로 동결한다.

## 사용자가 정한 것

- 벡터로 비교하는 대상은 발언 원문이 아니라 **비판 이유**다.
- 새 발언도 AI가 먼저 "비판받는다면 이유는 이것"으로 바꾼 뒤 비교한다.
- 정답은 기사·나무위키·댓글에 남은 "무엇이 왜 비판받았나"다.
- 사례집 비판 이유 문장은 AI가 초안을 쓰고 사용자가 채팅에서 가볍게 확인한다(J1 오류 분류와 같은 방식).
- **참고 사례는 후보 발견 단계에 붙인다.** 발견 호출 전에 발언 묶음마다 별도 AI 호출로 비판 이유를 쓰고, 그 이유로 찾은 사례를 발견 요청의 참고로 넣는다. J1에서 놓친 RISK 26건 중 23건이 후보로 뽑히지 않았으므로(NO_CANDIDATE) 발견 단계를 직접 겨냥한다. 묶음마다 호출이 하나 늘어나는 비용을 감수한다.
- **조건의 참고 방식은 발견과 검증 두 단계에 모두 적용한다(2026-11-08 사용자 확정).** 벡터 조건은 발견 단계에서 고른 참고가 검증까지 그대로 가고, 키워드 조건은 두 단계 모두 키워드로 고르며, 참고 없음 조건은 두 단계 모두 참고가 없다. 구현 리뷰에서 v7 runtime이 검증 단계에서 키워드로 다시 고르며 같은 사건 예시를 섞는 문제가 드러나 이렇게 정했다. 결과는 발견 단계만의 효과가 아니라 참고 선택 방식 전체의 효과로 읽는다.

## Claude가 정한 것(사용자 확인 대상)

- **평가 입력 형태:** 발언 하나의 기사 인용 문장들을 세그먼트로 하는 작은 전사문을 만들어 서비스에 넣는다. 대상은 그 세그먼트 전부다. 원영상 맥락이 없다는 점을 결과에 적는다.
- **찾기 분모:** `harmful-glorification`, `privacy-exposure`는 사건이 1개뿐이라 같은 사건을 빼면 맞힐 대상이 없다. 이 두 유형의 발언은 찾기 분모에서 빼고 판정 평가에만 쓴다.
- **우연 기준선:** `group-generalization`은 31사건 중 17사건이라 무작위로 3개를 골라도 자주 맞는다. 유형별로 무작위 선택의 기대 적중률을 함께 보고하고, 벡터·키워드 결과를 그 위에서 읽는다.
- **"분명히 높다"의 뜻:** 표본이 작아 유의성 검정은 하지 않는다. 유형별 적중 수와 우연 기준선을 나란히 보고하고, 벡터가 키워드와 우연 기준선을 모두 넘는지로 방향을 판단한다.
- **반복:** 판정은 J1처럼 조건마다 3회 반복한다. 참고 사례 수 상한은 운영 설정(`guidelines-example-max-cases: 3`)과 같게 둔다.

## 구현자 판단으로 둔 것

- 발견 전 비판 이유 호출의 출력 형식. 묶음의 발언마다 이유 문장 0~1개(비판받을 여지가 없으면 비움)를 받고, 이유가 있는 발언만 검색한다. 묶음 단위로 찾은 사례는 합쳐서 상한 3개로 자른다. 판정 조건 (b) 키워드 검색은 기존 `reference()` 경로를 그대로 쓴다.
- 비판 이유 문장 초안 생성 모델과 지시문. 서비스 판정 모델(`gpt-6-luna`)과 다른 모델을 쓰면 같은 모델끼리 맞추는 효과를 줄일 수 있다.
- 저장 형식(JSON 파일 하나, 벡터 정규화 포함), 파일 위치(`datasets/controversy/` 아래 gitignore 경로).
- Java 쪽 연결 방식. 기존 `ReviewGuidelineLibrary.select`와 같은 `Selection`(프롬프트 + trace)을 돌려주는 새 선택기로 만들면 기존 판정 경로를 바꾸지 않고 붙일 수 있다.
- 사건 제외는 기존 `guidelines-excluded-families` 설정 또는 선택기 인자로 한다.
