## 개정 23: 규칙만이 아니라 사례의 연결 과정도 전달

ID 30은 최종 카드 0개지만 검토가 PARTIAL이었다. 기준집은 적용됐고 B 후보 2개는 발견됐으나 대상 근거 계약에 실패했다. C/D는 탐색 결과가 확보되지 않았으며 정상 PASS가 아니다. 따라서 기준집 누락·STT 문제로 단정하지 않는다. 응답 검증 실패와 참고 자료의 설명력은 별도 개선 과제다.

기존 8개 맥락 조건에 `referenceContexts`를 추가했다. 공통 카드에서 다음 자료를 직접 가져와 조건과 함께 탐색·검증에 전달한다.

- `flow`: 원문 구간에 연결된 작성자 해석 전체. 원문이 없는 사건은 보도 기반 알려진 논란 포인트로 대체하되 발화 순서를 만들지 않는다.
- `criticismHypotheses`: 내용에 관한 비판이며 특정 표현/흐름에 매핑된 가설 중 카드 순서상 첫 1개. 빈도·중요도 순위가 아니며 전체 비판 요약도 아니다. 사건 전체 반응, 반론, 사후 대응은 제외한다.
- `coverage`, `missingContext`: 발췌 전사인지 보도 맥락뿐인지, 아직 확인하지 않은 사실을 함께 전달한다. 자료 한계는 토큰 절약을 이유로 삭제하지 않는다.

예를 들어 B의 지역 지칭→매장 부재→욕구와 대체 음식 이야기→가정식 추억이라는 다른 해석→뒤의 '못 먹기 때문에 조합한다'는 연결을 보존한다. C의 메뉴 평가→제공 방식에 관한 발언은 별도 비교 자료다. 둘을 합쳐 하나의 후보를 두 건 탐지로 집계하지 않는다. 현재 B 댓글은 롯데리아 대화를 직접 지목하지 않았다는 한계도 함께 제공한다.

모델은 **공통 조건 + 사례의 연결 과정 + 정상 해석 경계**를 현재 원문과 비교한다. 과거 사례는 현재 영상의 근거가 아니며 TARGET/CONTEXT 원문 인용 검증은 그대로 유지한다. 사건 ID·댓글 원문·기사 URL·정답 라벨은 모델에 보내지 않는다. 원사례는 여전히 미검수이며 이 변경은 승인·파인튜닝이 아니다. [OpenAI 공식 지침](https://developers.openai.com/api/docs/guides/prompt-engineering)의 참고 맥락 분리 방식을 확인해 적용했다.

새 런타임 계약은 `review-guidelines-2`다. 조건별 연결 사례가 빠지거나 출처가 다르면 거부한다. 기존 v1 파일도 호환되지만 비교 자료 수는 0이다. 진단의 `referenceContextCount`로 실제 전달 수를 확인한다. 현재 SPEECH는 7조건/8비교 자료/5,163 code point, CAPTION은 8조건/9비교 자료/5,874 code point다. 기존 6,000 한도와 추가 모델 호출 없는 구조를 유지하되 입력량은 늘었다. 실제 청구 토큰이나 비용 증가율은 아직 측정하지 않았다.

기준집을 로컬에서 재생성했고 실제 Java 로더에서 READY 및 비교 자료 8개를 확인했다. Java 테스트 410개, 도구 Python 테스트 85개 통과. 저장된 **이전 응답**의 근거 계약 감사는 수행했지만 새 프롬프트로 모델을 호출한 결과가 아니다. 새 영상·유료 실행·서버 재시작·운영 배포는 하지 않았다. Spring 재시작 후 새 분석에서 개정 23/기준 버전 2를 확인하고 B/C/D 재현과 별도 정상 리뷰를 평가해야 한다.

사례 추가 시 공통 카드의 흐름/댓글 매핑을 보강하고 조건의 `sourceCaseIds`를 갱신한 후 재컴파일하면 비교 자료도 함께 갱신된다. 한도 초과 시 임의로 자료를 잘라 내거나 기본 한도를 늘리지 않고 명시적으로 압축·선별 계획을 재검토한다. ID 30의 실패 응답 진단 및 제한 재시도는 이번 참고 구조 변경에 포함하지 않았다.

## 개정 22에서 바뀐 점

사례를 저장만 하거나 새 사건 세 개만 전달하던 방식에서, **현재 6사건·9카드 전체의 맥락 조건을 압축한 기준집을 실제 분석에 참고시키는 방식**으로 바꿨다. 피식대학 B/C/D도 포함한다. 원댓글·사건별 직접 인용·기대 정답은 기준집 입력에서 제외한다. 파인튜닝이나 모델의 영구 학습이 아니라 매 요청에 제공하는 참고 자료다.

원사례의 사람 검수·권한·범용성 확인이 끝난 것은 아니다. `WORKING_REFERENCE_NOT_VALIDATED`라는 작업 상태로 구별하며 원사례의 미승인 상태를 그대로 둔다. 사람 승인 사례만 받는 기존 `ReviewCaseLibrary`의 문턱도 낮추지 않는다. 사용자의 명시적인 요청으로 별도 `ReviewGuidelineLibrary` 경로에서 맥락 조건을 참고시키는 것이다.

## 실제 분석 연결

발언: STT → 기존 배치/문맥 창 → **압축 기준 참고 후보 탐색** → **같은 기준 참고 + 현재 원문 근거 검증** → 기존 카드 발행 검증.

화면: 기존 OCR 선별 → **화면 조건까지 포함한 기준 참고** → 현재 OCR 원문 근거 검증. STT로 OCR을 복원하거나 간판·메뉴판을 편집자의 평가로 바꾸지 않는다. 화면이 없어도 텍스트 분석은 실행한다.

기준집은 기존 요청 안에 넣으므로 추가 에이전트·검색·임베딩·모델 호출을 만들지 않는다. 대신 요청 토큰은 늘어난다. 현재 발언 기준은 7개, 압축 JSON은 Java 직렬화 기준 2,432 code point다. 화면 경로는 문화적 연상 조건까지 8개다. 요청별 기준 JSON 한도는 6,000 code point이며 실제 토큰 한도나 비용 불변을 뜻하지 않는다. 전체 파일은 16조건까지 허용하지만 한도를 넘으면 일부를 몰래 자르지 않고 적용 실패로 알린다.

분석 진단의 `candidatePipeline.guidelineReference`에는 기준집 버전·소스 해시·적용 조건 ID·상태가 남는다. 파일 미제공·만료·잘못된 구조·예산 초과 시 기본 원문 검수는 유지하고 리포트 경고에 기준집 미적용을 표시한다. 기능을 명시적으로 끈 경우에는 이 경고를 만들지 않는다.

현재 원문 인용과 참고 조건의 구분은 [OpenAI 공식 프롬프트 지침](https://developers.openai.com/api/docs/guides/prompt-engineering)을 확인해 설계했다. OpenAI Docs 스킬은 이 분리와 대조 실험의 경계를 확인하는 데 사용했다. 기존 출력 계약과 Luna 모델은 유지했다.

## 파일과 앞으로의 보강 절차

원본·댓글·카드·기준집 파일은 모두 Git 제외다. 공개 저장소에는 도구·가상 테스트·사용 설명만 둔다.

```text
datasets/controversy/
  drafts/cards.json           원사례와 댓글 연결 초안
  guidelines/plan.json        조건별 출처 카드 연결·압축 문장
  guidelines/runtime.json     실제 분석에서 읽는 컴파일 결과
  experiments/               전사 대조 및 근거 계약 감사 기록
```

앞으로 사례를 추가할 때마다 다음을 함께 수행한다.

1. 알려진 논란 포인트와 확보한 원문/보도 인용을 구분한다.
2. 실제 비판 반응을 맥락 포인트에 매핑하고 사건 전체 반응·시점·사후 대응을 분리한다.
3. 공통 카드와 분류 계획·현재 상태 목록을 갱신한다.
4. `guidelines/plan.json`에서 **기존 조건의 출처 카드를 추가하고 적용 경계를 보강**한다. 정말 다른 연결 방식일 때만 조건을 신설한다. 문장만 비슷하다고 자동 연결하지 않는다.
5. 조건 버전을 올리고 아래 컴파일/검사를 실행한다. 새 카드가 어떤 조건에도 연결되지 않았으면 `NEW_CARDS_REQUIRE_EXPLICIT_MECHANISM_MAPPING`으로 실패한다.
6. 같은 영상의 연결 확인과 별도 사건/정상 리뷰의 범용성 확인을 구분해 기록한다. 조건 변경이 과탐지를 늘리지 않는지도 확인한다.
7. 갱신한 기준집 파일을 분석 서버에 제공하고 Spring을 재시작한다. 기준은 시작 시 로드하므로 파일만 바꿔도 실행 중인 서버가 자동 학습·갱신되는 것은 아니다.

```sh
python3 tools/controversy_cards.py --bundle datasets/controversy/drafts/cards.json
python3 tools/build_review_guidelines.py           # 준비 검사만, 모델 호출 없음
python3 tools/build_review_guidelines.py --write   # 기준집을 원자적으로 갱신, 모델 호출 없음
python3 -m unittest discover -s tools/tests -q
```

컴파일러는 원본·발췌·보관 기한·분류 계획과 공통 카드가 일치하는지 먼저 검사한다. 조건마다 출처 카드와 소스 번들 SHA-256을 남기지만 모델에는 사건 ID·댓글·기사 URL을 보내지 않는다. 인간의 의미 검수나 사용 권한 확인을 자동 통과시키지는 않는다. 갱신은 안전한 임시 파일 교체를 사용하며 원사례를 덮어쓰지 않는다.

기준집의 현재 갱신/삭제 점검 기한은 원수집본 중 가장 이른 **2026-11-08 11:01:53 UTC**를 따른다. 파생 기준·백업도 함께 점검하며 파일 재생성으로 기한을 연장하지 않는다. Java는 실행 중에도 요청 시 만료 여부를 확인한다. 출처를 제거하거나 갱신할 때 원사례·조건 출처 연결·기준집을 함께 다시 검사한다.

## 로컬 및 운영 적용

`oops-backend` 폴더에서 Spring을 실행할 때 기본 위치는 `file:../datasets/controversy/guidelines/runtime.json`이다. 이 작업에서 로컬 파일을 생성하고 실제 Java 로더의 `READY_WORKING_REFERENCE`를 확인했다. 실행 중인 Spring에는 재시작 후 적용된다.

운영 배포는 이번에 하지 않았다. 데이터가 Git 제외이므로 코드만 배포하면 기준집 파일은 전달되지 않는다. 별도 배포 파일로 제공하고 다음 설정을 사용한다.

- `REVIEW_GUIDELINES_LOCATION=file:/절대경로/runtime.json`
- `REVIEW_GUIDELINES_ENABLED=true` (기본값; false는 롤백/비교)

기존 API 키나 댓글 원본을 기준집 배포 파일에 넣지 않는다. 파일 경로는 로컬 `file:`/`classpath:`만 허용하고 외부 호스트의 파일은 거부한다.
