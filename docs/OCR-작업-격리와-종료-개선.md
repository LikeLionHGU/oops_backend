## 근거와 범위

[106·107 단독 재측정](101번-OCR-단독-재측정.md)에서도 약10분 OCR 단계 뒤 결과 수신 실패가 반복됐다. Spring이 완료된 뒤 Python에서 Paddle 추론이 계속됐고 RSS는 약7.4GiB까지 증가했다. 시간 제한과 작업 종료 전달의 구조적 문제는 코드로 확인했지만, 각 실행의 상세 HTTP 예외를 확보하지 않아 과거 실패 원인·메모리 누수를 확정하지 않는다.

이번에는 같은 조건의 유료 반복 대신 실행 경로를 수정했다. 프롬프트·사례집·STT 모델·프레임 간격·프레임 수 상한·원본PTS·OCR 텍스트 필터·영역 좌표·추적 계약은 변경하지 않았다. 새 실영상의 OCR 성공·속도·최대 RSS 감소는 아직 미검증이다.

## 구현

### 1. OCR 요청별 프로세스

`app/ocr_jobs.py`가 요청마다 `python -m app.ocr_worker`를 시작하고, 다운로드·프레임 추출·Paddle 초기화·인식을 그 안에서 수행한다. 완료 응답은 작업 전용 임시 JSON으로 받는다. 모델 로그와 결과 JSON을 stdout에 섞지 않으며, 대량 이미지나 모델 객체를 부모 프로세스로 보내지 않는다.

- 종료·실패·시간 초과·HTTP 연결 종료·ASGI 작업 취소의 모든 경로에서 자식 프로세스를 회수한다.
- macOS/Linux에서는 작업용 새 세션 전체를 종료해 실행 중인 ffmpeg 등 하위 프로세스도 남기지 않는다. Windows 분기는 직접 자식 종료만 제공하며 하위 트리 보장은 이번 검증 범위가 아니다.
- 회수 이후에만 작업 임시 디렉터리를 지운다. 원본 업로드와 외부에 보존한 프레임은 임의 삭제하지 않는다. 실패 중 일부 저장된 프레임도 정상 완료 산출물처럼 사용하지 않는다.
- 실패를 빈 `items`의 정상 결과로 바꾸지 않는다. HTTP504 `OCR_TIMEOUT`, HTTP503 `OCR_BUSY`/`OCR_WORKER_FAILED`, 연결 종료499를 구분한다.
- 프로세스당 OCR 동시 실행은1개다. 두 번째 요청은503으로 거절하며 몰래 대기열에 쌓지 않는다. 이 제한은 **uvicorn 프로세스별**이므로 로컬에서는 기본 단일 worker를 사용한다. 여러 `--workers`를 띄우면 전역1개 보장은 없다.

한 요청의 Paddle/native 할당이 다음 요청까지 같은 서버 프로세스에 계속 남는 것을 작업 프로세스 수명으로 끊는다. 단일 작업 중 RSS를 OS 하드 제한한 것은 아니며, 최대 메모리 개선 폭은 별도 실측해야 한다.

### 2. OCR 메모리·관측

- health는 Paddle 모델을 초기화하지 않고 설치 의존성만 확인한다. `ocrAvailabilityCheck=DEPENDENCIES_ONLY_NOT_MODEL_READY`를 추가해 모델 로딩·작업 성공 보증과 구별한다.
- health의 `ocrBusy`는 현재 서버 프로세스의 OCR 슬롯 상태, `ocrJobIsolation`은 `SUBPROCESS_PER_JOB`이다. 모델 설치가 돼 있어도 가중치·네이티브 초기화 실패는 실제 작업에서 발생할 수 있다.
- 인식 배치는 `OCR_REC_BATCH_NUM=1`을 기본으로 둔다. 실제 설치 PaddleOCR2.9.1과 [공식 소스의 rec_batch_num 옵션](https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/v2.9.1/tools/infer/utility.py)을 확인했다. 해당 옵션은 인식 묶음 크기이며 프레임을 버리거나 탐지 기준을 바꾸는 설정이 아니다. 수치·성능 동등성이 완전히 보장된다는 뜻은 아니다.
- `[ocr-job] started/reaped/deadline/disconnected`에 pid·경과 시간을 기록하고, 인식 중에는25성공 프레임마다 `[ocr-progress]`를 남긴다. 원문·API 키를 새 로그에 추가하지 않는다.

### 3. 대기시간 정렬

| 실행 설정 | Python OCR 전체 작업 제한 | Spring 분석 서버 읽기 제한 |
|---|---:|---:|
| 기본 | 540초(9분) | 기존10분 유지 |
| 명시적 local | 1200초(20분) | 25분 |

Python 제한에는 미디어 다운로드·모델 시작·프레임 처리까지 포함한다. `OCR_TIMEOUT_SEC`으로1~3600초 범위에서 명시 재정의할 수 있지만 Spring 제한보다 여유 있게 짧아야 한다. 제한을 늘리기만 한 것이 아니라 연결 종료 감지와 프로세스 종료도 함께 구현했다. ASGI 이벤트 루프가 감지한 연결 종료를 기준으로 하며 프록시가 즉시 연결 종료를 전달하지 않는 환경까지 보장하지는 않는다.

Spring은 HTTP504의 `OCR_TIMEOUT` 설명을 유지한다. 전송 예외의 원인 체인에서 연결 실패는 `WORKER_CONNECTION_FAILED`, 응답 시간 초과는 `WORKER_READ_TIMEOUT`으로 구별한다. 리포트의 기존 상위 경고 코드 `OCR_UNAVAILABLE`은 호환성을 위해 유지하며 구체적 이유는 메시지에 포함한다.

## 반영 방법과 남은 검증

현재 사용자가 켜둔 서버는 자동 재시작하지 않았다. **Spring과 Python 모두 재시작해야 적용된다.** Spring은 `--spring.profiles.active=local`, Python은 실행할 때 `ANALYSIS_PROFILE=local`을 명시해야 위 로컬 대기시간이 맞는다. Python은 `oops-analysis` 디렉터리에서 기존 전용 환경으로 실행한다. 단일 uvicorn worker를 유지한다.

재시작 후 `/health`의 새 필드를 확인하고, 다음 실영상 재측정은 별도 예산·전송 승인을 받아 한 편만 실행한다. 확인할 것은 OCR 결과 수신·시간·최대/종료 후RSS·`ocrBusy` 해제·카드 변화다. 기존101·106·107 결과와 사전 기록은 보존한다. 이번 코드 수정만으로 그 실행들이 성공으로 바뀌거나 OCR이 최종 탐지를 개선했다고 주장하지 않는다.

강제 OS 종료나 부모 프로세스 SIGKILL처럼 정리 코드 자체가 실행되지 않는 상황의 고아 프로세스 방지까지 이번에 구현한 것은 아니다. 새 프로세스는 일반 성공·오류·ASGI 취소·연결 종료·제한시간 경로를 대상으로 검증했다. 다중 uvicorn worker의 전역 admission·일반 작업큐 전환도 이번 범위 밖이다.
