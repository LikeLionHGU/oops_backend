# 논란 사례 구조 — 확정 스키마 & 마이그레이션 계획 (1단계)

> 상태: **구현 확정안** (사람 최종 승인 대기) · 작성 2026-10-13 · 브랜치 minwook
> 선행 문서: `논란맥락사전-구조-재설계.md`(§2~5 설계 토론, §8~10 측정·요건)
> 이 문서의 목적: 그 설계 토론을 **구현 가능한 단일 스키마 + 되돌릴 수 있는 단계별 마이그레이션**으로
> 확정한다. runtime.json 출력 스키마와 Java(`ReviewGuidelineLibrary`)는 **바꾸지 않는다**(변경 0).
> 입력 쪽만 재구성한다.

---

## 0. 한 문장 요약

한 사건의 자료가 **6개 파일에 쪼개져 순환 참조**하는 현재 구조를, **사건 = 파일 하나
(`incidents/{incidentId}.json`)** 로 통합하고, 빌드를 **"생성(입력만 읽음) ↔ 검증(출력만 읽음)"**
으로 분리해 catalog↔cards 순환을 제거한다. runtime 출력과 Java는 그대로 둔다.

---

## 1. 지금 왜 못 쓰는가 — 측정으로 확인된 3대 결함

(근거: `논란맥락사전-구조-재설계.md` §10.7 더미 사건 전체인 테스트)

| # | 결함 | 코드 지점 | 성격 |
|---|---|---|---|
| A | **catalog ↔ cards.json 닭-달걀 순환.** 빌드가 cards 생성 *전에* 옛 cards와 새 catalog 일치를 먼저 요구 | `controversy_cards.build_bundle` → `validate_private` | 설계 결함(제거) |
| B | **collectionId 필수** — 댓글 없는 기사-only 사건도 가짜 collection 참조 필요 | `review_dataset_catalog.validate` `UNKNOWN_COLLECTION` | 과거 워크플로 잔재(제거) |
| C | **입력 6파일 분산** — 사건 1건 = catalog + cards + plan 3개 + collection 을 사람이 순서 맞춰 수동 수정 | 전반 | 근본 원인(통합) |

3단계 컴파일(cards→dictionary→runtime) **자체는 유지**한다. 이는 재포맷이 아니라 서로 다른 입력을
합류시키고 해시로 무결성을 지키는 안전장치다(§8.7). 문제는 단계 수가 아니라 **입력이 흩어진 것**이다.

## 2. 확정 스키마 — 사건 = 파일 하나

경로: `datasets/controversy/incidents/{incidentId}.json`
사건 id 규칙: `{channel}-{topic}-{yyyymmdd}` (게시일 기준). 예 `pisik-yeongyang-20240511`.

```jsonc
{
  "schemaVersion": "incident-2",
  "incidentId": "pisik-yeongyang-20240511",

  // 승인 게이트 — 전부 false 로 생성. 사람만 승격한다.
  "status": "UNREVIEWED_DRAFT",
  "humanApproved": false,
  "runtimeEligible": false,
  "trainingUseAuthorized": false,

  "split": "DEVELOPMENT",
  "topicTags": ["지역", "음식"],              // 검색 주제(위험 라벨 아님)

  // 사건 안의 개별 논란 발언 = 발언근거(statement). 1:N.
  "statements": [
    {
      "id": "pisik-yeongyang-20240511#s1",
      "mechanismId": "local-life-devaluation",   // §9 메커니즘 전이 단위
      "sourceKind": "STT_TRANSCRIPT",            // STT_TRANSCRIPT | NEWS_BODY | AUDIENCE_REACTION
      "statementKind": "SOURCE_UTTERANCE",       // SOURCE_UTTERANCE | AUTHOR_INTERPRETATION
      "excerpt": "이것만 매일 먹으면 햄버거가 천상의 맛일 것",
      "whyControversial": "지역 음식을 '매일 이것만' 처지로 그려 식생활을 낮게 취급.",

      // 출처 종류별로 하나만 채운다 (상호 배타)
      "article": {                               // sourceKind=NEWS_BODY 일 때
        "publisher": "데일리안", "url": "https://...",
        "publishedDate": "2024-05-25", "retrievedOn": "2026-10-13",
        "snapshot": "research/source-snapshots/dailian-...-extract.txt",
        "sha256": "..."                          // 발췌만 저장, 전문 금지(SHORT_EXTRACT_NOT_FULL_ARTICLE)
      },
      "transcriptWindowMs": [20500, 24000],      // sourceKind=STT_TRANSCRIPT 일 때만

      // 참조 전용 — 같은 family 평가 입력 금지 (치팅 차단). 코드 family 제외 그대로.
      "evaluationUse": "REFERENCE_ONLY_SAME_FAMILY_EXCLUDED"
    }
  ],

  // 댓글 반응은 선택(optional). 비어도 사건 성립 (§10.2).
  "reactions": [],

  // 적용 경계·정상 대조. 반론/가상 예문은 정상 영상으로 계산하지 않는다.
  "boundaries": ["부재·욕구·대체는 정상 설명에도 있다. ..."],
  "normalControlCases": [],

  "missingContext": ["저장 STT의 제한된 창. 원음·화자·억양 미확인. ..."],

  "provenance": {                                // 마이그레이션 추적용
    "migratedFrom": ["catalog.json", "drafts/cards.json#pisik-B", "guidelines/plan.json"],
    "legacySha256": "..."
  }
}
```

### 2.1 스키마가 결함을 어떻게 없애나
- **C 해소:** 사건의 catalog 항목·카드·mechanism 매핑·topicTags·기사 출처가 **한 파일 안**에 있다.
  교차 참조할 다른 입력 파일이 없으므로 A(순환)가 **구조적으로 발생 불가**.
- **B 해소:** `reactions` 가 선택이고 `collectionId` 가 사라진다. 댓글 없는 사건은 `reactions: []`.
  댓글이 있으면 `AUDIENCE_REACTION` sourceKind 또는 `reactions[]` 에 보강으로만 붙인다.
- **메커니즘 전이(§9) 준비:** `statements[].mechanismId` 가 사건 안에 직접 있어, mechanism→statement
  역매핑을 별도 `plan.json` 없이 빌드가 수집한다.

## 3. 빌드 재구성 — 생성 ↔ 검증 분리 (A 순환 제거의 핵심)

현재: `build_bundle` 하나가 "옛 출력 검증 → 새 출력 생성"을 섞어 순환을 만든다.
확정: **두 함수로 쪼갠다.**

```
build.py --write      incidents/*.json  (입력만 읽음)
                        → build/cards.json → build/context-dictionary.json → guidelines/runtime.json
                      생성 단계는 기존 출력을 절대 읽지 않는다. 순환 불가.

build.py --verify     guidelines/runtime.json (출력만 읽음)
                        → 스키마·해시·mechanism 커버리지·family 제외 검증
                      검증 단계는 입력을 생성하지 않는다.
```

- 중간 산출물(`cards.json`, `context-dictionary.json`)은 `build/` 캐시로 숨긴다. 사람이 손대지 않는다.
- `runtime.json` **출력 스키마는 그대로**. Java `ReviewGuidelineLibrary`(review-guidelines-1~5) 변경 0.
- `catalog.json` 은 **생성물로 강등**(사건 목록은 `incidents/*.json` 글롭으로 자동 집계). 더 이상 수기 입력 아님.

## 4. 마이그레이션 — 되돌릴 수 있는 7단계

각 단계는 독립 커밋. 어느 단계든 `git revert` 로 되돌아간다. **사람 승인·런타임 편입·학습 사용은 전 과정 0 유지.**

1. **스키마 고정 커밋** — `incidents/` 디렉토리 + `templates/incident-2.schema.json` + 이 문서. 코드 영향 0.
2. **신규 빌드 경로 추가(병행)** — `build_incident_dataset.py` 신설. 기존 3개 컴파일러는 **그대로 둔다**.
   새 빌드가 기존과 **동일한 runtime.json 을 생성**하는지 바이트 비교 테스트부터 통과시킨다(동작 동치 증명).
3. **기존 6사건 변환** — `catalog + cards + plan 3개` → `incidents/{6개}.json`. 변환 스크립트는 1회용,
   결과를 사람이 눈으로 확인. 변환 후 새 빌드 산출 runtime.json == 기존 runtime.json(바이트 동일) 검증.
4. **생성↔검증 분리 적용** — §3. `--write`/`--verify` 분리. 순환 검증 제거.
5. **collectionId optional / reactions optional** — B 제거. 기사-only 더미 사건으로 전 체인 녹색 확인.
6. **기존 3개 컴파일러 아카이브** — 새 경로가 동치임이 증명된 뒤에만 `tools/archive-*/` 로 이동(삭제 아님).
   Java·runtime 스키마는 이 단계에서도 불변.
7. **그 위에 `add_incident.py`** — "incidents/{id}.json 하나 작성 → build --write → build --verify".
   저장 규칙(사례 추가 전 **후보를 사용자에게 공유**)을 도구에 내장: 기본 dry-run, `--apply` 로만 기록.

### 4.1 동치 증명이 안전의 핵심
2·3단계의 "새 빌드 == 기존 runtime.json 바이트 동일"이 **마이그레이션 전체의 안전핀**이다.
이게 통과해야 "구조만 바꿨고 판정 동작은 안 바꿨다"가 증명된다. 통과 전에는 기존 경로를 지우지 않는다.

## 5. 범위 밖 (이번에 하지 않음)

- **§9 메커니즘 필터의 Java 구현**은 별개 작업이다. 이번은 데이터에 `mechanismId` 를 **담는 자리**까지만.
  라우팅 로직(`ContextExampleSelector` 가산점, 분류 1-pass)은 풀영상 벤치마크 후.
- **런타임 편입·학습 승격·사람 승인**은 0건 유지. 스키마의 승인 게이트는 전부 false 로 생성.
- **기사·댓글 사용 범위**(저작권·개인정보)는 기존 보안 운영정책과 매체 약관을 따른다. 발췌만 저장.
- **새 사건 추가**는 이 구조가 선 뒤(7단계) `add_incident.py` 로. 그 전에는 추가하지 않는다.

## 6. 결정이 필요한 지점 (사람 승인)

1. 사건 id 규칙 `{channel}-{topic}-{yyyymmdd}` 확정 여부 (기존 `familyId` 를 id 로 승격).
2. `incidents/` 를 Git 추적할지 — drafts/cards 는 추적 중. 발췌 snapshot(기사)은 저작권상 발췌만.
3. 2단계 "동치 증명"을 머지 게이트로 삼을지(권장: 예).

승인되면 1단계(스키마 고정 커밋)부터 시작한다. 이 문서는 코드·데이터를 아직 바꾸지 않았다.
