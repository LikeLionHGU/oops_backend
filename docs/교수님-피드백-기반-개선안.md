# 교수님 피드백 기반 OoPs?! 개선안

> 정리일: 2026-10-06 · 목적: 멘토링에서 받은 사업·기술 피드백을 검증 가능한 제품 개선 과제로 전환

## 핵심 요약

교수님 피드백의 핵심은 “GPT API를 쓴다”는 사실 자체가 아니라, 현재 설명만으로는 OoPs?!만의 기술적 차별성과 실제 구현 능력이 증명되지 않는다는 점이다. 투자자는 아이디어나 장기 계획만이 아니라, 작동하는 제품·고객 문제·팀의 실행 역량·투자금 사용 계획을 확인하려 한다.

따라서 당장의 목표를 “AI 기술을 고도화하겠다”는 선언으로 두지 않는다. 영상 검수에서 우리가 직접 해결하는 기술 문제를 좁히고, 기존 모델을 사용하는 부분과 우리 팀이 설계·검증하는 부분을 구분한 뒤, 작동하는 프로토타입과 비교 결과로 증명한다. 기술 차별성 외에 실제 고객과 배포·영업 역량이 경쟁력이 될 가능성도 함께 검증한다.

## 1. 피드백을 실행 과제로 해석하기

| 교수님 피드백 | OoPs?!에 대한 의미 | 대응 방향 |
|---|---|---|
| 투자 계획서의 틀만으로는 판단하기 어렵고, 구체적인 아이템·자료가 필요하다 | 현재는 실제 결과와 운영 근거보다 계획 설명의 비중이 큼 | 투자 문서보다 먼저 작동하는 프로토타입, 대표 사례, 사용 흐름을 준비 |
| Whisper·GPT API를 호출하는 것만으로는 기술력이 드러나지 않는다 | 외부 모델이 수행하는 기능과 우리 팀이 만드는 고유한 부분이 불분명함 | 외부 모델 사용을 숨기지 말고, 우리만의 검수 기준·데이터·증거 연결·품질 개선 능력을 분리해 설명 |
| “기술 고도화”가 무엇인지 분명하지 않다 | 투자자가 기대하는 성과와 팀이 생각하는 목표가 다를 수 있음 | 투자 검토자에게 기대하는 구체적 기술·제품 마일스톤을 직접 확인 |
| 제품이 실제로 되는지 확인할 수 있는 프로토타입이 중요하다 | 컨셉 영상·설명서만으로는 입력부터 결과까지의 실현 가능성을 판단하기 어려움 | 영상 업로드부터 시점·원문 근거가 있는 결과까지 한 번에 시연 |
| 투자금이 왜 필요한지, 어디에 쓸지 구체적이어야 한다 | “서비스를 끝까지 만들고 싶다”만으로는 투자 판단에 필요한 계획이 부족함 | 필요한 금액, 집행 항목, 기간, 그 돈으로 달성할 검증 결과를 연결 |
| 고객 확보·유통 역량도 경쟁력이 될 수 있다 | 기술만이 유일한 방어력은 아니며 고객 접근 경로가 강점일 수도 있음 | 크리에이터·제작사별 문제와 도입 의사를 인터뷰로 검증 |
| 특정 성과를 투자 조건으로 삼는 투자자도 있다 | 투자자가 무엇을 증명하면 투자할지 사전에 합의할 수 있음 | 투자자의 판단 기준·마일스톤·검토 시점을 질문하고 기록 |

## 2. 우리가 주장할 수 있는 기술과 아직 증명되지 않은 것

### 현재 정직하게 설명할 수 있는 범위

- Whisper 계열 STT, OCR, OpenAI API 등 외부 구성요소를 사용한다.
- Spring Boot가 분석 과정을 조율하고, Python 분석 서버가 영상의 음성·화면 텍스트를 추출한다.
- 사전·규칙·프롬프트·결과 병합을 통해 검토 후보와 근거를 만드는 구조를 개발하고 있다.
- 서비스 목표는 최종 판결이 아니라, 제작자가 다시 볼 영상 구간을 근거와 함께 찾도록 돕는 것이다.

이는 구현 현황이지 아직 투자자가 인정할 만한 성능 우위의 증거는 아니다. “우리만의 AI 모델”, “논란을 정확히 예측한다”, “사람보다 더 잘 찾아낸다”는 표현은 검증하기 전까지 사용하지 않는다.

### 검증할 기술 차별성 가설

OoPs?!의 차별성 후보는 범용 생성 모델 자체보다 영상 검수에 특화된 다음 결합에 있다.

1. **영상 맥락에 맞는 후보 선택**: 단어가 등장했다는 이유만으로 경고하지 않고, 발화·화면·시간대의 문맥을 함께 검토한다.
2. **검증 가능한 근거**: 실제 STT/OCR 원문과 타임스탬프에 결과를 연결하고, 원문에 없는 근거는 결과에서 걸러낸다.
3. **제작자 관점의 과탐지 조절**: 일반 비평·사투리·인용과 실제 검토 필요 사례를 분리하고, 불확실하거나 부분 분석된 범위를 숨기지 않는다.
4. **영상 검수 작업 흐름**: 긴 영상을 처음부터 다시 보지 않아도 후보 구간과 이유를 검토하고, 사람이 결과를 수정할 수 있게 한다.
5. **검수 데이터와 개선 절차**: 제작자가 유용/불필요로 판정한 사례를 동의·보관 정책 안에서 축적해 사전·프롬프트·평가셋을 개선한다.

이들은 현재 확정된 해자(moat)가 아니라 검증 가설이다. 데이터가 적거나 반복 사용과 품질 개선으로 이어지지 않으면 지속 가능한 차별성이 아닐 수 있다. 모델 API를 쓰는 것이 곧 사업성이 없다는 뜻은 아니지만, 외부 모델 위에 어떤 재현 가능한 제품 역량을 쌓는지 보여줘야 한다.

## 3. 우선순위별 개선안

### P0 — 작동하는 프로토타입과 품질 기준 만들기

- 대표 영상 또는 사용 허가를 받은 짧은 영상으로 업로드 → STT/OCR → 분석 → 타임라인 결과 확인까지 시연한다.
- 결과마다 영상 시점, 원문 인용, 검토 이유, 분석 범위와 미처리 경고를 보여준다.
- 분석이 맞는지 사람이 판정한 소규모 사례를 만든다. 먼저 약 20개 구간으로 판정 기준을 맞추고, 이후 다양한 유형으로 확장한다. 현재 [AI 검수 사례 초안](AI-검수-사례-초안.md)은 합의된 정답이 아니므로 사람의 검토를 거친다.
- 같은 사례에서 기준선(단순 키워드/기본 프롬프트)과 현재 파이프라인을 비교한다.
- 적어도 아래 지표를 기록한다.

| 지표 | 투자자·고객에게 보여주는 것 |
|---|---|
| 유용 판정 비율(정밀도) | 표시한 후보 중 사람이 실제로 다시 볼 가치가 있다고 판단한 비율 |
| 중요 사례 탐지율(재현율) | 사람이 중요하다고 합의한 사례 중 서비스가 찾은 비율 |
| 영상당 불필요 알림 수 | 과탐지로 검수 흐름을 방해하는 정도 |
| 원문·타임스탬프 연결 정확도 | 결과가 실제 영상 구간에서 확인 가능한 정도 |
| 처리시간·실패율 | 시연을 넘어 반복 사용 가능한지 |
| 영상당 추론 호출 수·비용 | 고객당 운영 비용과 가격 설계 가능성 |

초기 표본으로 성능을 과장하지 않는다. 유형별 사례 수, 실패·미처리 건, 평가셋 구성과 한계를 함께 공개한다. 품질 목표치는 기준선을 측정한 다음 정한다.

### P1 — 기술 구현 범위와 제품 가치를 분리해 설명하기

투자 설명과 기술 소개에는 다음 구분을 일관되게 쓴다.

| 구분 | 설명 예시 |
|---|---|
| 외부 구성요소 | STT/OCR/LLM은 상용 API·오픈소스 모델을 활용 |
| 우리 팀의 구현 | 영상 분석 파이프라인, 맥락 후보 선별, 근거·시점 연결, 분석 범위·실패 처리, 검수 UI/흐름 |
| 아직 연구·검증 중 | 논란 맥락 판별 정확도, 제작자별 기준 개인화, 피드백 기반 품질 개선 |
| 성과로 증명할 것 | 기준선 대비 오탐·미탐·검수시간·비용이 어떻게 바뀌었는지 |

“AI가 논란을 예측한다”보다 “긴 영상에서 사람이 검토할 구간을 근거와 함께 좁혀주는 보조 도구”처럼 현재 기능과 맞는 표현을 사용한다.

### P1 — 고객 문제와 도입 가능성 검증하기

연예인·대형 제작사만을 고객으로 미리 고정하지 않는다. 크리에이터, MCN, 영상 제작사, 기업 홍보팀 등 후보군별로 실제 게시 전 검수 과정과 문제를 확인한다.

- 최근 영상 검수에서 놓친 문제나 수정에 시간이 많이 든 사례가 있었는지 묻는다.
- 현재 누가 어떤 도구·체크리스트로 검수하고, 어떤 단계에서 시간이 드는지 확인한다.
- 업로드 가능한 영상 유형·길이·민감정보·보관 조건을 확인한다.
- 결과가 어느 수준이어야 사람이 써볼지, 과탐지와 미탐지 중 어떤 실패가 더 큰 비용인지 묻는다.
- 무료 체험 의향만이 아니라 반복 사용, 도입 담당자, 지불 의사와 구매 절차를 확인한다.

인터뷰 결과는 “잠재 고객이 많다”는 주장 대신 대상군별 인터뷰 수, 반복해서 나온 문제, 파일럿 의향, 다음 행동으로 정리한다. 실제 인터뷰 전에 고객 수요가 확인됐다고 발표하지 않는다.

### P2 — 투자자와 기대 마일스톤을 먼저 맞추기

후속 멘토링에서 투자 검토자에게 다음을 구체적으로 질문한다.

- 현재 서비스에서 투자를 검토하려면 우선 어떤 가설이 증명되어야 하는가?
- 기술 완성도, 정확도, 실제 사용자, 파일럿 계약 중 어떤 증거를 가장 중요하게 보는가?
- 어느 정도의 표본과 기간이면 그 증거를 판단할 수 있는가?
- 특정 목표를 달성하면 투자 검토를 진행한다는 합의가 가능한가? 가능하다면 목표·판정 방식·시점을 무엇으로 할 것인가?
- 후속 검토 때 원하는 자료는 무엇이며, 투자금의 규모와 사용 계획 중 어떤 형식이 필요한가?

구두 조언을 투자 약속으로 해석하지 않는다. 목표·평가 방식·검토 시점을 문서로 되짚어 오해를 줄인다.

## 4. 투자 계획서 구성 방향

초기 문서는 완성된 투자 자료가 아니라 가설 검증 계획으로 표시한다. 프로토타입과 고객 검증 결과가 생기면 아래 순서로 구체화한다.

1. 고객과 반복적으로 발생하는 검수 문제
2. 현재 대안과 그 대안이 충분하지 않은 이유
3. 제품 시연: 입력부터 근거가 있는 결과까지
4. 기술 구성: 외부 기술과 자체 구현의 경계
5. 품질·비용·처리시간 비교 결과와 평가 한계
6. 목표 고객, 도입 흐름, 파일럿·사용자 증거
7. 경쟁 대안과 차별화 가설
8. 팀의 역할과 현재 역량, 부족한 역량
9. 투자 요청액, 항목별 사용 계획, 기간, 달성할 마일스톤
10. 주요 위험, 개인정보·영상 보관 정책, 실패 시 계획

투자금 사용은 “개발비” 한 줄로 묶지 않는다. 예를 들어 데이터 라벨링, 사용자 파일럿, 필요한 개발 인력·외부 비용, 보안·법률 검토처럼 실제 견적과 기간을 확인해 구분한다. 지금 확정되지 않은 금액이나 성과는 만들어 넣지 않는다.

## 5. 진행 순서와 완료 조건

| 순서 | 작업 | 완료 조건 |
|---|---|---|
| 1 | 기술 주장과 현재 구현 경계 정리 | 외부 모델·자체 구현·미검증 가설을 한 장에서 구분 |
| 2 | 영상 검수 프로토타입 시연 준비 | 대표 영상에서 입력부터 원문·타임스탬프가 있는 결과까지 재현 가능 |
| 3 | 소규모 평가셋과 기준선 측정 | 사람 합의 사례, 오탐·미탐·비용·시간이 함께 기록됨 |
| 4 | 고객 인터뷰 및 파일럿 후보 확인 | 대상군별 문제·검수 흐름·도입 장벽·지불 의사 기록 |
| 5 | 투자자 마일스톤 확인 | 투자 검토자가 원하는 증거와 판정 시점을 확인하고 기록 |
| 6 | 투자 계획서와 요청안 작성 | 제품·고객 근거, 필요한 금액, 사용처, 기간, 검증 목표가 연결됨 |

우선 1~3단계를 비용이 거의 들지 않는 범위에서 진행한다. 평가 사례의 라벨링이나 실제 외부 모델 비교에 인력·API 비용이 들 수 있으므로 범위와 예산을 정한 뒤 실행한다. 기술 품질만으로 고객 수요가 증명되지는 않으며, 고객 인터뷰와 파일럿을 별도 검증으로 취급한다.
