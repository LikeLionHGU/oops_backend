# 메커니즘 후보 생성 · 무료 그림자 실행

2026-10-20 · minwook · 운영 미연결. 기존 검색·AI 탐색·검증·병합·리포트 결과는 변경하지 않는다.

## 목적과 이전 실험에서 가져온 경계

기존 StructuredContextSearch는 관련 참고를 고르는 검색 전용이며 두 프로필만 지원한다. 이번 MechanismCandidateShadow는 별도 순수 함수로, 검토할 원문 신호를 확보하는 첫 단계다. AI를 대체하는 판정기가 아니다.

이전 자동분류 시험에서는 같은 발견 입력·참고에서도 후보 결과가 달랐다. 구조화 검색은 관련 사례 회수를 개선했지만 정상 경계 비교에서 최종 판단 우위를 증명하지 못했다. 따라서 이번에는 사전·프롬프트를 바꾸지 않고 후보 생성만 관찰한다. 과거 순위·슬롯 비교는 후보 생성 효과의 근거로 사용하지 않는다.

## 구현 계약

- 개정: `2026-10-20-surface-candidate-shadow-1`.
- 세 규칙: 신체 부위+훼손 동작 표면 표현, 가치 부정+선택 조건 표현, 집단+범위+평가 표현.
- 출력: mechanismId, RULE_SHADOW 출처, 규칙 개정, anchorId, 적중 구간 ID·문자 위치·원문 부분 문자열, 연결 구간 ID.
- 문자 위치는 Java UTF-16 offset이며 시간 정렬이나 단어 단위 타임스탬프가 아니다. 원문은 정규화·교정하지 않는다.
- SPEECH만 사용하며 화면 글자·사전 설명·AI 가설은 입력 신호에 포함하지 않는다.
- 최대 8개 연속 음성 구간·전체 20초·인접 구간 공백 3초 이하. 이 값은 초기 감사 예산이며 대화 경계·같은 화자를 보증하지 않는다. 신호 등장 순서의 의미 관계도 판정하지 않는다.
- 같은 메커니즘·anchor의 중복은 가장 짧은 구간 수의 연결 하나로 정리한다. 다른 대안 근거 전체를 보존하는 기능은 아직 없다.
- 입력 최대 10,000음성 구간·구간당 24,000 UTF-16 문자, 출력 최대 1,000후보. 초과 후보 수와 20초 초과 구간 수를 따로 보고한다. 긴 단일 구간은 현재 검사하지 않으며 PASS로 해석하지 않는다.
- 인용·정상 설명도 후보로 남을 수 있다. 후보는 경고가 아니며 결과에 PASS/REVIEW·위험 점수·비판 가설을 생성하지 않는다.

규칙은 초기 코드 정의다. 사건명·브랜드·피식대학 ID는 조건에 넣지 않았다. 지역 비하·은근한 반어·모든 방언·동의어를 포괄하지 않으며, 메뉴라는 대상 자체의 의미 확인이나 신체 비유 여부도 확정하지 않는다. 문자열 신호를 실제 의미 관계로 승격하면 안 된다.

## 오프라인 실행

Spring 디렉터리에서 저장된 transcript API 응답(`success:true`, `data:[{startMs,endMs,text}]`)을 읽는다. 출력은 stdout이며 원본 파일·DB를 수정하지 않는다. 원문 일부가 포함되므로 출력도 비공개 연구 자료로 취급한다.

```sh
./gradlew --offline mechanismShadowAudit \
  -PmechanismShadowInput=../datasets/controversy/experiments/v1-current-pipeline-restart-20261018/transcript.json
```

입력 파일 SHA256을 출력한다. stt-index ID는 해당 스냅샷 배열 순번이며 DB 식별자나 다른 전사의 같은 ID와 동일성을 보장하지 않는다. 네트워크·Spring·모델·DB 호출은 없다.

저장 plan의 `conditions[]` 또는 `cases[]` 안에 `id/raw`가 있어도 같은 도구로 감사할 수 있다. 이 경우 저장 raw ID를 유지한다. `labelStatus`는 결과의 출처 설명으로만 복사하고 규칙에는 전달하지 않는다. 기존 정답·후보 가설·사전·provider 응답도 규칙 입력에서 제외한다. 출력은 입력 SHA와 `audits[]`이며, 각 항목에 개정·후보·제외 수를 기록한다. 중복 case ID와 빈 raw는 거절한다.

저장71번 전사 재생에서는 메뉴34→35 연결과 신체 표현37의 2후보를 생성했다. 메뉴는 `의미가 없`과 `주는대로`, 신체는 `살을 뜯`의 실제 위치를 보존했다. 이는 78번의 새 요청 재현이나 최종 카드 탐지 성공이 아니다. 단일 기존 전사와 합성 경계 테스트만으로 범용 후보 회수율을 주장하지 않는다.

무료 전체 Java 테스트 1,046개 통과·실패/오류0. 신규8개는 반복 결과 동일성, 원문 offset, 일반 리뷰, 긴 공백, 정상 인용도 후보로 유지, 음식 복합어/화면 글자 제외, 독립 메커니즘, 짧은 연결 선택·중복, 긴 단일 구간 제외를 확인했다. 제공자 호출0이며 운영 서버 재시작·사전 변경·DB 변경은 없다.

## 후속: 규칙·AI 합집합 공통 계약과 문맥·예산 계획

`CandidateUnionShadow`는 별도 순수 계획기이며 기존 `CandidateReviewEngine.run()`에 호출을 추가하지 않았다. 서버 설정이나 새 API로 켜지는 기능이 아니며, 실제 AI 후보를 읽는 운영 adapter도 아직 없다. 이번 검증은 합성 입력의 무료 계약 테스트다.

### 공통 후보

- 원문 전체 `ReviewInput`의 SHA256을 고정한다. AI 입력 후보의 해시가 다르면 거절하며, ID만 같다는 이유로 다른 전사에서 재사용하지 않는다. raw text·시간·ID·채널이 해시 범위에 들어간다.
- RULE/AI 출처, 원래 sourceId·개정 정보, anchor, 검토 축, 원문 evidenceIds를 분리 보관한다. RULE은 기존 세 규칙을 같은 입력에서 직접 실행하며 offset 신호도 보존한다.
- 규칙의 축 매핑은 검증 경로용 힌트다. 신체 표면 신호는 EXPRESSION_CONTENT, 나머지는 TARGET_TREATMENT이며 최종 유형·논란 판정은 아니다.
- AI 입력은 sourceId·해시·축·원문 근거 ID만 받는다. 가설·비판 이유·PASS/REVIEW·사전 설명은 공통 계획기가 생성하거나 요구하지 않는다. AI 소스 개정은 현재 `CALLER_SUPPLIED_UNVERIFIED_AI_CANDIDATE` 표기이며 실제 요청/모델 검증을 마쳤다는 뜻이 아니다.
- 사전 검색이 0개이거나 AI 후보가 비어 있어도 규칙 후보를 지우지 않는다. 참고 선택은 이 계획기에 포함하지 않았다.
- 같은 AI sourceId와 동일 입력의 재전달만 중복 제거한다. 같은 sourceId에 다른 내용은 거절한다. RULE과 AI 또는 서로 다른 AI sourceId는 같은 anchor/근거라도 자동으로 의미 병합하지 않는다. 서로 다른 쟁점을 유지하는 대신 중복 검증 비용은 남으며 실제 쟁점 병합은 후속 과제다.

### 원문 창

근거 첫 줄부터 마지막 줄 사이의 음성 원문도 포함한다. 중간 줄을 생략해 대화를 압축하거나, 근거 사이 간격을 실제 침묵으로 오해하지 않는다. 기존 `CandidateContextWindow.extend`를 사용해 앞뒤 원문을 보충한다. 인용 역할이나 신체 표현을 PRIMARY로 새로 승격하지 않는다.

원문 창은 최대60초·48구간·6,000 codepoints, 구간 간 공백5초를 검사한다. 실제 확장 결과에도 같은 제한을 재검사하며, 근거를 잘라 맞추지 않는다. 규칙 신호의 20초/3초 조합 예산과 검증 문맥의 60초/5초 예산은 다른 목적이다. 같은 화자·주제·동의·억양을 추론하지 않는다.

### 예산 배분

anchor의 절대 시각을 1분 버킷으로 묶고, 각 활성 버킷에서 한 건씩 순환 선택한다. 버킷 안에서는 시간순 후보를 RULE/AI 출처별로 나눈 뒤 번갈아 배치한다. 위험 점수나 특정 사건 우선순위는 없다. 예산0도 허용하며 전체를 미평가로 남긴다.

- READY: 이번 계획에서 검증 대상으로 예약됨. 검증 완료나 경고가 아니다.
- BUDGET_SKIPPED: 검증 예산 밖. PASS로 계산하지 않는다.
- CONTEXT_INVALID: 원문 창이 제약을 만족하지 못함. 유효 후보의 예산을 소비하지 않으며 원래 근거를 보존한다.

버킷 수보다 예산이 작으면 앞 버킷이 우선하므로 모든 후반 구간의 기회를 보장하지 않는다. 버킷 내 첫 슬롯은 RULE이므로 예산1에서는 출처 균형도 보장하지 않는다. 초기 재현 가능한 휴리스틱이며 최적 배분 검증은 아니다. 입력 AI 최대1,000개·계획 예산 최대1,000은 도구 안전 한도일 뿐 운영 비용 상한이 아니다. 규칙 감사에서 후보 잘림/긴 단일 구간이 있으면 불완전한 커버리지를 조용히 계획하지 않고 중단한다.

### 운영 연결 전 남은 작업

현재 검증 요청의 `hypothesisNotEvidence`와 `proposedEvidence`는 AI 제안을 전제로 한다. 규칙 후보에 가짜 비판 가설을 넣어 이 계약을 우회하지 않는다. 다음은 원래 AI 제안의 출처를 유지하는 adapter와, 가설 없는 규칙 후보의 검증 요청·허용 원문 계약을 분리하는 것이다. 기존 판단 기준·근거 validator는 완화하지 않는다. 그 뒤 저장 응답 무료 재현을 거치고, 실제 모델 비교는 새 승인 범위에서 수행한다.

이번에는 운영 탐색·검색·판단 프롬프트·검증·병합·DB·서버를 변경하지 않았고 API 호출0이다. 합집합 규칙의 실제 영상 정확도나 검증 비용 절감을 증명한 단계는 아니다.

무료 전체 Java 테스트1,063개 통과·실패/오류0. 추가10개는 AI 빈 응답에서도 규칙 보존, 앞뒤 원문, 출처별 쟁점 보존·정확한 중복만 제거, 스냅샷 변경 차단, 허구 ID·출처 충돌 거절, 시간 버킷 배분, 예산0·결과 재현, 부적합 창의 예산 비소비, 근거 사이 원문 유지, 버킷 내 두 출처 선택을 확인했다.

## 후속: 가설 없는 규칙 후보의 검증 연결부

`MechanismVerificationBridge`는 검증 요청 준비와 저장/모의 응답의 검증기 재생을 제공한다. 클라이언트·Spring bean·HTTP 호출·자동 복구·결과 발행 기능은 없으며 **운영 run 경로에는 여전히 미연결**이다. 앞 절의 공통 계약 다음 단계이며 실제 모델 판단 성공으로 취급하지 않는다.

### 입력·참고·출력 계약

- 합집합 계획의 원문 해시·개정을 확인하고 같은 입력에서 규칙 후보/원문 창을 재구성해 비교한다. 위조 신호·허용 창·중복 규칙 출처를 거절한다. READY인 RULE만 요청으로 만들며 BUDGET_SKIPPED/CONTEXT_INVALID는 요청하지 않는다.
- 규칙 근거는 전체 원문 줄로 채우되 `Proposal.reason=null`을 유지한다. 기존 AI 탐색의 이유 필수 검사/탐색 복구를 통과한 것으로 위장하지 않고 별도 진입점을 사용한다.
- 실제 요청 JSON에는 `hypothesisNotEvidence`·reason·사전 정답을 넣지 않는다. RULE 출처·신호 위치·실제 원문·허용 구간과 proposedEvidence를 보낸다. 신호의 PRIMARY/TARGET/CONTEXT 역할을 규칙에서 확정하지 않는다.
- 기존 POLICY와 검증 출력 계약을 유지하고, 후보 소개 문장만 규칙 신호로 바꾼 뒤 가설 없는 입력 계약을 덧붙인다. 원문 표면 적중은 대상 관계나 잘못을 입증하지 않는다고 명시한다. 기존 소개 문장이 바뀌면 조용히 치환 실패하지 않고 준비를 중단한다. 운영 프롬프트 자체는 수정하지 않았다.
- 기존 사전 선택기로 후보 근거와 주변 원문에 맞는 참고를 한 번 고르고 system 문자열·참고 SHA256·선택 trace를 동결한다. 참고가 없어도 준비할 수 있으며, 응답 검사 중 다시 검색하지 않는다. 규칙 ID를 LLM 라우터의 판정 키로 자동 변환하지 않는다.
- 한 요청에 규칙 후보 하나만 준비한다. 기존 VerificationResult DTO를 사용하며 미요청 이해 기록/판단 근거 실험 필드는 거절한다. 이번에는 새 strict schema나 새 모델 설정을 도입하지 않았다.
- 응답은 정확히 한 candidateId여야 하며 원문 해시가 바뀌면 재사용하지 않는다. `SourceUnderstandingContract.validate`의 기존 비실험 경로를 통해 대상·대조 해석·근거·출력 상한·발행 조건을 그대로 검사한다. PASS/REVIEW를 자동 생성하거나 검증 실패를 PASS로 바꾸지 않는다.
- `retainAi` adapter는 AI 후보의 원래 Proposal·가설·sourceRelations·허용 raw를 별도 객체로 그대로 보존한다. 공통 계획이 넓힌 문맥을 AI 요청에 자동 적용하지 않는다. 현재 운영 AI 검증 요청은 바꾸지 않았다.

[OpenAI 공식 Structured Outputs 문서](https://developers.openai.com/api/docs/guides/structured-outputs)에 따라 형식 준수와 의미 정확도는 별개로 본다. 공식 문서 확인이 해당 요청의 실모델 호환성·품질 시험을 대신하지 않는다.
