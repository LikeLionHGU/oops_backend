# 표현 자체 탐지와 선택 필터

> 2026-10-10 · STT 표현 탐지·DB·리포트 API 구현 완료. 프론트 필터, OCR 표현 목록, 카드 연결 ID는 후속 작업이다. 운영 배포·실영상 정확도 검증은 수행하지 않았다.

## 1. 맥락 검수와 표현 등장은 다르다

### 2026-10-18 설계 보강: 논란 근거와 내용 수위의 분리

아래는 R01 재검토에 따른 **설계안**이다. 기존 표현 API는 구현돼 있지만, 내용 수위 분류·저장·필터는 아직 구현하지 않았다. 현재 판단 프롬프트·점수·응답 스키마·운영 기본값을 변경하지 않는다.

| 구분 | 답하는 질문 | 필요한 근거 | 결과 취급 |
|---|---|---|---|
| 맥락 검토 | 이번 발화·흐름을 왜 다시 확인해야 하나? | 실제 요청·폄하·위협 등과 정상 해석을 구별하는 구체적 원문 연결 | 근거가 검증되면 기존 검토 카드 |
| 표현 적중 | 등록한 표현이 전사에 등장했나? | 사전 표기·원문 위치 | 기존 별도 표현 목록, 논란 확정 아님 |
| 내용 수위 안내 | 제작자가 선택적으로 확인하고 싶은 소재·묘사가 있나? | 실제 언급과 소재 분류, 뜻풀이/인용/실제 행위의 구분 | 향후 선택형 안내, 기본 논란 카드·점수에 합산하지 않음 |

내용 수위 안내는 ‘문제없는 말’이나 ‘문제인 말’의 별칭이 아니다. 성적·사적 소재가 등장했다는 관찰과 그것이 이번 맥락에서 왜 위험한지에 대한 판단을 분리한다. 대상 없는 구체적인 신체 훼손 비유처럼 표현 자체에 독립적인 검토 이유가 있다면 맥락 검토에 남길 수 있다. 수위 안내로 보내기 위해 기존 검토 근거를 버리지 않는다.

#### R01에 적용한 설계 예시

- 165→166: 약어 뜻 질문에 답함. 실제 청자에게 속옷 색을 요구했다는 근거로 쓰지 않는다.
- 소재 안내 초안: ‘속옷 관련 사적 소재 언급’, 사용 방식 ‘뜻풀이’. 이는 새로운 논란 라벨이나 법적·연령 등급이 아니다.
- 현재 경고 이유의 ‘사적인 질문 내용 자체’만으로는 별도 모욕·강요·정보 노출을 입증한 것으로 세지 않는다. 독립적인 검토 이유가 있으면 별도로 평가한다.
- 뒤의 자기 설명·제안은 별도 쟁점이다. 166의 소재 안내에 합쳐 실제 노출·상대 요구·피해를 만들어내지 않는다.

#### 판단 및 연결 원칙

1. 원문과 발화 기능을 먼저 보존한다. 뜻풀이/인용도 자동 PASS가 아니며 소재 등장도 자동 경고가 아니다.
2. 검토 카드는 무엇을 어떻게 문제 삼는지 독립적인 근거가 있어야 한다. 단지 ‘성적/사적 내용’이라는 설명뿐이면 내용 관찰과 검토 근거를 구분해 재검수한다.
3. 내용 수위 안내와 맥락 검토는 상호 배타적이지 않다. 실제 사적 요구는 맥락 검토와 소재 안내가 함께 존재할 수 있다. 안내 필터를 꺼도 검증된 검토 카드를 숨기지 않는다.
4. 기본 화면에서 선택 안내를 숨기는 것은 프론트 제안이다. 현재 UI가 구현됐다고 표시하지 않는다. 표현 적중과 새 내용 수위는 탐지 방식도 달라 기존 expressionOccurrences에 임의로 섞지 않는다.
5. 추후 결과에는 원문 ID·시간·소재·사용 방식·등장 근거·분류 출처/버전을 남긴다. API 필드명·DB 구조는 별도 구현 검토 후 확정한다. 기존 API와 호환되는 선택적 확장을 우선한다.
6. 추가 LLM 호출을 바로 붙이지 않는다. 기존 출력으로 충분한지 먼저 확인하고, 문장만으로 분류하기 어려운 경우를 구분한다. 현재 저장 응답의 EXPRESSION_CONTENT를 내용 수위로 자동 전환하지 않는다.

#### 검수 후 고정할 대조표

| 대조 종류 | 확인할 경계 | 현재 승인 상태 |
|---|---|---|
| R01 뜻풀이 | 소재 언급과 실제 질문을 구별 | 기존 맥락 PASS 승인 유지, 새 소재 라벨은 설계 초안 |
| R05 뜻풀이·R06 비판적 인용 | 같은 단어라도 현재 상대 요청으로 바꾸지 않음 | 기존 PASS 승인 유지, 새 소재 분류 미승인 |
| R04 실제 요청·R08 요청 후 중단 | 뜻풀이로 면책하지 않되 지속 강요로 확대하지 않음 | 기존 검토 승인 유지, 새 소재 분류 미승인 |
| 독립적 표현 문제가 있는 인용 | 뜻풀이·인용이라는 형식만으로 면책하지 않음 | 새 대사 선정·사람 검수 필요 |

다음 구현의 선행 조건은 새 소재 범주와 대조 예시의 검수다. 현재5조건은 독해 경계와 기존 판단용 승인이지 새로운 내용 수위 분류의 정답셋이 아니다. 독해·기존 판단 일치·근거 타당성·형식은 계속 따로 집계한다. 이번 설계 작업에서는 원응답·정답·맥락 사전·운영 코드를 수정하지 않았고 추가 모델 호출도 없다.

| 트랙 | 반환하는 것 | 기본 카드/점수 |
|---|---|---|
| 맥락 검수 | 실제 원문·대상·대화 연결에 근거가 있는 검토 이유 | 기존 events·summary·위험 점수 |
| 선택 표현 | 등록된 욕설·논쟁 표현의 전사 등장 사실 | 별도 expressionOccurrences, 기본 카드와 점수에서 제외 |

표현 상태는 `EXPRESSION_DETECTED`다. 재미·인용·일상 용례에서도 등장은 유지하지만, 혐오·차별·악의·특정 커뮤니티 소속이나 실제 논란을 확정하지 않는다. 맥락 검수의 PASS가 표현 목록을 지우지는 않는다. 맥락으로 검증된 위협·차별 카드는 표현 필터와 무관하게 기존 events에 남는다.

## 2. 현재 사전과 매칭

### 완료: 합성4조건 기준선12회 결과

2026-10-18 사용자가 새 추정 상한 $0.10과 합성 텍스트 전송을 승인해 아래 동결 계획 그대로12회를 실행했다. 프롬프트 수정·독해 기록·사전·정답·검토 메모·소재 라벨 없이 기존 test 전용 판단 계약으로 평가했다. 재시도·자동 복구·추가 호출 없이 종료했다.

| 조건 | 승인 판단 | 판단 일치 | 계약 통과 | 일치＋계약 통과 |
|---|---|---:|---:|---:|
| A01 추억 표현 | PASS | 3/3 | 3/3 | 3/3 |

이 작은 합성 개발 대조에서는 단어 등장만 보고 동일하게 경고하지 않았고, 비유를 받아들이는 흐름과 사용하지 말자는 흐름을 구별했다. A02는 세 번 모두 EXPRESSION_CONTENT, A04는 TARGET_EVALUATION으로 설명했다. **R01·실영상·운영 파이프라인 개선이나 범용 정확도 증명은 아니다.** 기존/수정 프롬프트의 비교도 아니다.

#### 근거 재검토 메모 — 사용자 승인과 구분

개발 보조자가 저장12응답의 이유·대조 설명·근거 ID를 확인했다. 핵심적인 비유 동조/비판적 수정/발언자 모욕 구분은 이유에 드러나지만, 다음을 따로 보존한다.

- A03의 function 선언은 SELF_OFFER 1회, DIRECT_REQUEST_TO_LISTENER 2회다. “바꾸죠”를 청자에게 하는 제안으로 보는 것은 사적인 정보 요구와 다르며, 세 응답 모두 이를 문제 요구로 경고하지 않았다. 이 enum은 새 사용자 정답으로 승인되지 않았으므로 오류율로 자동 채점하지 않는다.
- A01-1은 화자가 앞줄을 말한 뒤 추억을 설명했다고 서술한다. 원문에 화자 ID가 없으므로 동일 화자의 연속 발화까지 확인된 사실로 인정하지 않는다. 추억이라는 해석과 화자 귀속은 별도다.
- A04-3은 “그 말을 한 사람”을 앞줄 표현처럼 설명했지만 실제로는 s1에 있는 지칭이다. 핵심 대상 연결은 유지돼도 위치 설명은 부정확하다. 판단 라벨 일치를 근거 설명 무오류로 확대하지 않는다.
- A01-3은 s1만 evidenceIds에 넣고 대조 설명에서는 s0의 추억 연결도 사용했다. s1 단독으로도 PASS 이유를 설명하지만, 앞줄을 활용했다는 사실과 인용 ID의 충분성은 별도 점검 대상으로 남긴다.

자동 집계의 reasonValidity는 계속 PENDING_HUMAN_REVIEW이며 위 메모를 새 사용자 근거 승인으로 취급하지 않는다. 현재 test 계약은 발행 승인을 하지 않는다. 소재 안내 라벨은 미승인·미전송·미평가 그대로다.

#### 비용과 보존

- 호출12회. 입력24,558토큰(캐시22,222), 출력2,423토큰. 응답 소요시간 합계36,947ms.

- 결과는 비공개 `datasets/controversy/experiments/context-contrast-baseline-results-20261018/`에 저장했다. 원본12 HTTP 응답과 파싱된 결과·모델명·발행 비승인 상태를 대조했다. 원문·응답은 보정하거나 재호출하지 않았다.
- 결과 SHA-256: `83da438f2dc9f6823a065216f677617e3b61f4b674233ee1c878faa28e2f6b9e`.

- 운영 프롬프트·카드·사전·배포는 바꾸지 않았다. 이 시험의 승인은12회에서 종료한다.

다음은 이 단순한 대조에서는 구분 가능한데 R01 전체 문맥에서는 판단이 흔들리는 이유를 보자는 것이다. R01과 합성 대조의 문맥 길이·초점·독립 경고 이유 차이를 먼저 무료로 점검하고, 필요할 때만 한 요인씩 새 유료 시험을 설계한다. 이 결과를 이유로 인용 자동 PASS나 새 선택 필터를 바로 운영에 넣지 않는다.

### 실행 전 이력: 합성4조건 기준선12회 계획

프롬프트 수정 전 기준선을 확보한다. A01~A04를 각각3회, 총12회로 준비하며 비교안이나 자동 복구 호출은 없다. `ContextContrastPlan`은 요청 생성만 가능하고 네트워크 실행·키 읽기 기능이 없다. `contextContrastPlan` 작업으로 비공개 계획 파일을 생성한다. 이전 $0.50 승인은 종료된35회 시험의 승인이고 이번 시험에 재사용하지 않는다.

- 모델/계약: GPT-6 Luna, reasoning none, 기존 `SourceFirstJudgmentContract`와 strict 스키마 그대로. 원문만 제공하며 독해 기록·사전·과거 가설은 제외한다.
- 입력: 승인된 합성 대화2줄과 ID, 마지막 발화 `s1`을 중립 초점으로 고정한다. 순서용 시간0~2000ms는 합성 값이며 영상 정렬 시간이 아니다. 표기된 시간으로 실제 영상 위치나 정밀도를 평가하지 않는다.
- 정답·검토 메모·소재 라벨은 전송하지 않는다. 승인된 맥락 정답은 로컬 계획의 별도 메타데이터로만 보존한다. 반복마다 조건 순서를 회전하되 프롬프트·원문은 동일하다.
- 채점: 승인 맥락 판단 일치, 계약 통과, 두 조건을 함께 충족한 수를 각각 집계한다. 이해·근거 타당성은 이유를 원문과 대조해 별도로 검토한다. 새 기능 enum은 사용자 정답으로 승인되지 않았으므로 독해 정확도 점수를 자동 계산하지 않는다.
- 근거 점검: A02의 비유 채택, A03의 비판·수정, A04의 사람 모욕이라는 연결을 보존했는지 본다. 승인 정답과 다르다는 이유만으로 독해 오류로 부르지 않는다.
- 실패 처리: 원응답을 먼저 저장하고 형식 실패·거절·미완료를 PASS로 바꾸지 않는다. 12회 이내, 재시도·자동 복구 없이 종료한다. 실제 실행기는 별도 승인 뒤 연결한다.

#### 평가 및 구현 진입 조건

- 맥락 판단과 소재 안내를 각각 승인한다. 예를 들어 A03 PASS에 동의해도 소재 안내까지 승인된 것으로 처리하지 않는다.
- A02는 인용·뜻풀이 자동 면책 방지, A03은 인용 내용만 보고 경고하는 오류 방지, A04는 선택 필터가 실제 모욕 경고를 숨기는 문제를 점검한다.
- 기존5조건은 기존 맥락 평가만 유지한다. 새4조건은 승인된 개발용 맥락 대조로 사용할 수 있지만 아직 모델 시험을 실행하지 않아 성능 수치는 없다. 모든 소재 안내 라벨은 미승인으로, 해당 축의 점수 분모에서 제외한다. 개발 대조 승인을 범용 사전 승격·독립 평가셋 승인으로 확대하지 않는다.
- 후속 구현 완료: `oops-backend/src/test/resources/evals/context-content-contrasts-v1.json`에 합성4조건의 원문·버전·축별 승인 상태·검토 메모를 고정했다. `ContextContentContrastTest`는 승인된 대사/판단의 정확 보존, 미승인 안내의 정답 제외, 추후 입력 준비 시 라벨/메모/소재 초안 배제와 원본 복사 보호를 확인한다. 테스트용 합성 fixture이므로 비공개 실영상·댓글 데이터셋과 분리해 Git에 포함한다. 실데이터나 기존 응답은 옮기지 않았다.
- 이번 단계는 합성4조건의 맥락 판단 승인 이력을 문서에 반영했다. 기존 정답 변경·모델 호출·런타임 연결·새 API 구현은 없다. 이전 유료 시험 예산을 재사용하지 않는다.

위 JSON은 운영 사전이 아니며 모델 runner에도 아직 연결하지 않았다. 무료 전체 회귀1,023개 실패0(새 테스트3개 포함), 문서 차이 공백 검사 통과다. 무료 테스트는 보관·입력 경계 검증이지 모델이 네 조건을 맞혔다는 결과가 아니다. 다음 실제 비교는 입력/프롬프트/비교 축을 동결하고 별도 예산·전송 승인을 받은 뒤 진행한다.

- 사전: `oops-backend/src/main/resources/expression-dictionary.json`.
- 버전: `2026-10-10-user-watchlist-1`, 98개 표기. 사용자 목록에 기존 욕설 표기와 드릉드릉을 함께 등록했다.
- 분류: `PROFANITY` / `DISPUTED_EXPRESSION`. 등록 근거는 사용자 지정 확인 목록이며 학술적·사회적 의미 검수가 완료된 혐오어 목록이 아니다.
- `민주화·홍어·7시·주먹·코르셋·초딩` 등의 정상 용법 가능성을 commonUsageNote에 보존한다. 이런 표현을 정상 문장에서 발견해도 논란 카드로 발행하지 않는다.
- `~노` 단독 제외는 유지한다. 지역명·브랜드명·군대·선거·19금·칼로·내돈내산 자체를 키워드 위험 카드로 만들던 경로는 제거했다.
- 원문 정확 표기와 단어 경계, 제한된 조사/어미 목록으로 매칭한다. 부분 문자열·퍼지 매칭·추측 교정·공백/Unicode 정규화는 하지 않는다. `시발점·새끼손가락·민주화운동`처럼 이어진 일반 단어는 현재 경계 정책에서 제외한다.
- 같은 위치에 짧은/긴 표기가 겹치면 긴 표기 하나를 기록한다. 반복 등장은 각 위치를 보존한다.
- 새 표기를 추가할 때 개별 ID를 유지하고 별칭·정상 부분 문자열·인용·조사 결합 테스트를 보강한다. 사전 수정은 재빌드/재시작 후 적용한다.

이 사전은 LLM 프롬프트에 통째로 삽입하지 않는다. 로컬 매칭의 추가 AI 호출은 0회이며 전체 영상 분석이 무료라는 뜻은 아니다.

## 3. 실제 파이프라인과 저장

STT 원장 저장 → ExpressionService.replace → OCR 및 기존 맥락 검수 → 결과와 완료 상태를 함께 커밋 → 리포트 조회.

`expression_occurrence` 테이블은 영상 참조, 개별 표현 ID, 분류, 적중 문자열, STT segmentId, 구간 시간, 원문 UTF-16 위치, 사전 버전, 정상 용법 주석을 저장한다. 재분석에서는 기존 적중을 교체하고 영상 삭제에서는 함께 삭제한다. 기존 결과가 남은 리포트를 소급 재분석하지 않는다.

STT가 확보되면 AI 검토가 스킵/실패해도 완료된 파이프라인의 표현 목록은 저장될 수 있다. 하지만 전체 결과 트랜잭션이 실패/취소되면 표현 행도 롤백한다. STT 자체가 실패하면 `EXPRESSION_SCAN=FAILED`로 표시하고, 옛 리포트에 이 단계가 없으면 `NOT_ANALYZED`다. 둘을 정상 0건으로 해석하지 않는다.

시간은 단어 정렬 시간이 아니라 STT 구간 시간이다. 원음 대조 없이 실제 발화를 보증하지 않는다. OCR 표현 목록은 아직 수집하지 않으며 OCR의 맥락 검토·개인정보 검사는 유지한다.

## 4. 리포트 API와 프론트 연결

기존 `GET /api/v1/videos/{id}/report`에 다음 필드를 추가했다. 예시는 가상 ID이며 실제 저장 결과에 맞게 반환된다.

```json
{
  "expressionDetectionStatus": "SUCCESS",
  "expressionOccurrences": [{
    "id": "101",
    "expressionId": "dictionary-entry-id",
    "category": "DISPUTED_EXPRESSION",
    "status": "EXPRESSION_DETECTED",
    "matchedText": "허버허버",
    "sourceType": "STT",
    "segmentId": "stt-12",
    "startMs": 12000,
    "endMs": 15000,
    "timePrecision": "SEGMENT",
    "startOffset": 3,
    "endOffset": 7,
    "offsetUnit": "UTF16",
    "dictionaryVersion": "2026-10-10-user-watchlist-1",
    "commonUsageNote": "일상 용례·농담·인용 가능."
  }]
}
```

`expressionDetectionStatus`는 분석 수행 상태(SUCCESS/FAILED/NOT_ANALYZED 등)이며 각 적중의 상태와 다르다. 프론트는 category별 욕설 보기/논쟁 표현 보기 버튼을 나중에 연결하면 된다. 기본 OFF는 제안값이지 구현된 UI나 저장된 계정 설정이 아니다. 필터를 바꿔도 재분석/API 모델 호출은 필요 없다. 기존 events/summary/reviewSummary는 표현 등장 수를 포함하지 않는다.

`relatedEventIds`, OCR 적중, 사용자별 필터 설정은 미구현이다. 같은 시간에 등장했다는 이유만으로 표현과 위험 카드를 자동으로 같은 문제라고 연결하지 않는다.

## 5. 배포와 검증 경계

새 테이블이 필요하다. local/dev의 ddl-auto=update는 생성하지만 다른 운영 정책에서는 [MySQL 수동 마이그레이션 초안](migrations/2026-10-10-expression-occurrences.sql)을 DB 백업·실제 스키마 확인 후 적용해야 한다. 이 작업에서 운영 DB나 서버를 변경하지 않았다. 롤백 시 테이블을 삭제하지 않는다.

정확 매칭·일상 용례·인용·부분 문자열·~노 제외·전체 사전 표기·겹침/반복·구간/원문 위치·별도 집계를 테스트한다. 전체 파이프라인의 표현 저장/롤백과 기존 OCR 프레임 삭제 참조 순서도 메모리 DB로 확인한다. 이러한 계약 테스트를 실제 탐지 정확도나 범용성 검증으로 취급하지 않는다.
