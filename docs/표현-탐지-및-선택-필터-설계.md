# 표현 자체 탐지와 선택 필터 설계

> 2026-10-10 · 사용자 합의 방향을 정리한 설계 · 이번 작업은 문서만 수정한다. 전용 탐지 결과/API/프론트 필터는 아직 구현하지 않았다.

## 1. 두 가지 검수 목적

논란 맥락 사전은 “이 대화의 연결에서 무엇이 문제로 받아들여질 수 있는가”를 찾는다. 별도 표현 사전은 “제작자가 확인할 만한 표현이 실제 전사에 등장했는가”를 찾는다. 표현 등장에는 맥락상 문제라는 증명을 요구하지 않는다. 재미·감탄·인용으로 사용했어도 등장 사실은 유지한다.

| 트랙 | 결정하는 것 | 표시 방식 |
|---|---|---|
| 맥락 검수 | 실제 대상·표현·대화 연결에 구체적인 검토 이유가 있는가 | 기존 검토 필요/보류와 원문 근거 |
| 표현 자체 탐지 | 등록된 욕설·비속어·논쟁 표현이 입력에 있는가 | 별도 표현 목록과 선택 필터 |

제품 내에서 ‘논란 표현’ 목록으로 묶을 수는 있지만 내부 상태는 `EXPRESSION_DETECTED`로 분리한다. 단어 일치만으로 혐오·차별·악의·특정 커뮤니티 소속이나 실제 논란 발생을 확정하지 않는다. 맥락 검수의 PASS도 표현 등장 기록을 없애지 않는다.

## 2. 초기 범위와 사전

- 욕설·비속어: 팀이 검토한 명시적 표현과 검증된 표기 변형.
- 커뮤니티·논쟁 표현: 사용자 지정 시작 후보인 ‘허버허버’, ‘드릉드릉’ 등. 확정 은어/혐오어라는 뜻이 아니라 확인 목록에 등록한 표현이다. 일상 용례가 있어도 등장 자체는 목록에서 확인할 수 있다.
- 제외 유지: 문장 끝 `~노` 단독, 지역명·브랜드명·일반 부정 평가만으로는 등록하지 않는다. 일반 단어 전부를 논쟁 표현으로 확장하지 않는다.

표현 엔트리의 제안 필드: `expressionId`, `canonicalForm`, `aliases`, `category`(`PROFANITY`/`DISPUTED_EXPRESSION`), `matchPolicy`, `commonUsageNote`, `registrationReason`, `sourceReferences`, `reviewedAt`, `version`, `enabled`.

기원·집단 연관성은 확인한 출처 범위에서만 설명한다. 사용자 지정 후보와 검수된 설명을 구분하고, 확인되지 않은 의미를 모델 기억으로 보충하지 않는다. 맥락 사전의 패턴/사례 스키마를 표현 하나마다 복제하지 않는다. 두 사전은 독립적으로 관리하고 필요할 때 표현→관련 맥락 패턴 연결만 추가한다.

## 3. 탐지 방법과 비용

STT 결과 → 별도 표현 사전의 로컬 매칭 → 실제 원문 위치/구간 검증 → 등장 기록 저장을 우선한다. 맥락 분석이 느리거나 실패해도 확보된 STT에서 이 트랙을 수행할 수 있도록 설계한다. STT 자체가 실패하거나 단어를 누락한 경우에는 탐지할 수 없다. 원음 확인 없이 전사에만 있는 표현을 실제 발화로 보증하지 않는다.

초기에는 정확 일치와 검수된 변형만 사용한다. Unicode·공백 정규화에 필요한 원문 위치 대응을 유지하고 단순 부분 문자열로 일반 단어를 욕설 처리하지 않는다. 무제한 오타 교정·유사 발음 추정·조사 제거·퍼지 매칭은 하지 않는다. STT 제공 시간은 보통 구간 단위이므로 단어 단위 시간이 없으면 해당 구간의 시간으로 표시한다.

LLM이나 예시 검색을 표현마다 추가 호출하지 않는다. 사전 크기 증가는 로컬 매칭 비용이지 전체 사전을 프롬프트에 넣는 입력 토큰 증가가 아니다. 이 설계의 추가 모델 호출은 0회이며 전체 분석 비용이 0원이라는 뜻은 아니다.

OCR은 후속으로 선별된 편집 문구에만 같은 트랙을 적용한다. STT와 강제로 연결하지 않고 배경 간판/메뉴판은 기본 대상에서 제외한다. 인식 오류 의심은 별도 표시하고 추측 복원한 단어를 원문 적중으로 저장하지 않는다.

## 4. 백엔드와 프론트 연결 계약 — 제안

기존 `events`와 별도 `expressionOccurrences`를 둔다. 기존 `RiskCategory`와 새 표현 분류의 이름이 같더라도 의미/저장 경로는 구분한다. 제안 필드는 다음과 같다.

```json
{
  "id": "expression-hit-1",
  "expressionId": "disputed-term-example",
  "category": "DISPUTED_EXPRESSION",
  "status": "EXPRESSION_DETECTED",
  "matchedText": "드릉드릉",
  "sourceType": "STT",
  "segmentId": "segment-12",
  "startMs": 12000,
  "endMs": 15000,
  "timePrecision": "SEGMENT",
  "dictionaryVersion": "expression-dictionary-example",
  "relatedEventIds": []
}
```

위 값은 가상 계약 예시다. 실제 API 필드가 아니며 별도 DB를 사용자마다 만드는 설계도 아니다. 기존 영상 소유권 안에서 결과를 저장한다. 같은 표현의 여러 등장 위치는 보존하고, UI에서 표현별 묶음과 펼쳐보기를 제공할 수 있다. 하나의 적중을 여러 분류에서 중복 집계하지 않도록 ID/분류 목록 정책을 구현 전에 확정한다.

프론트 기본값 제안은 **욕설 보기 OFF / 커뮤니티·논쟁 표현 보기 OFF**다. 분석 결과에는 ‘선택 표현 N건 — 보기’ 진입점을 두고 사용자가 켜면 시간·원문·등록 이유를 보여준다. OFF는 화면 숨김이지 분석 중단/삭제/정상 판정이 아니다. 필터를 바꿔도 재분석하거나 LLM을 다시 호출하지 않는다.

표현 목록은 기본 리포트의 위험 점수·맥락 검토 카드 수와 별도 집계한다. 같은 구간에서 위협·차별·성적 모욕 등이 원문/맥락 검증을 통과하면 기존 `events`는 계속 표시하고 `relatedEventIds`로 연결한다. 욕설 필터 OFF가 그런 카드를 숨기거나 위험도를 낮추지 않는다. 필터 설정을 계정에 저장하는 것은 로그인/소유권 구현 이후 별도 작업이다.

## 5. 현재 코드와의 차이

현재 `context-lexicon.json`에는 두 시작 후보가 있지만 `needsContext: true`로 설정되어 있다. `CommunitySlangRules`는 맥락 확인이 필요한 표현을 직접 탐지 결과로 올리지 않고 `ContextLexiconAnalyzer`가 맥락 확인을 담당한다. 기존 `subtitle`/`screen-text` 규칙 안전망과 `PROFANITY` 유형도 존재한다.

따라서 “사전에 있다”와 “새 별도 목록/API/필터가 작동한다”는 다르다. 이번 설계를 적용하려면 표현 등장 수집 경로·저장/DTO·독립 집계·중복 연결을 구현해야 한다. 기존 맥락 사전의 `needsContext`를 모두 false로 바꾸거나 기존 경고 enum으로 적중을 밀어 넣는 방식은 사용하지 않는다. 기존 맥락 분석·증거 검증을 유지한다.

## 6. 구현 순서와 완료 조건

1. 초기 표현 목록과 정확 매칭 정책, 정상 부분 문자열/일상 용례/인용 대조 자료를 검수한다.
2. STT 전용 로컬 탐지와 원문·시간·사전 버전 저장을 구현한다.
3. 기존 리포트와 별도 결과 계약을 추가하고 맥락 카드와 연결한다. 실패/미분석 상태도 명시한다.
4. 서버에서 분리 집계를 검증한 뒤 프론트 선택 필터를 구현한다. 현재는 프론트 구현을 보류한다.
5. 원음 대조로 STT 누락과 사전 매칭 누락을 분리 측정한다. 맥락 검수 과탐지율과 표현 적중률을 섞지 않는다.

완료 기준: 재미/인용/일상 용례라도 등록 표현의 등장은 보존; 일반 단어 부분 문자열 오탐 차단; 필터 변경 시 재호출 없음; 필터 OFF에도 독립적인 위협·차별 카드는 유지; 미분석을 0건/안전으로 표시하지 않음; 원문과 시간의 출처를 확인할 수 있음.
