## 적용 범위

발언 검토의 기본 경로를 교체했다. 이전에는 긴 유형별 지침을 구간 요청과 독립 대화 묶음 요청에서 반복했다. 이제 같은 출처의 원문 배치에서 두 축으로 비판 후보를 탐색하고 후보만 별도 검증한다. 캐릭터별 에이전트·모델 학습·프론트 구현은 없다.

```text
기존 STT/OCR 추출·역할 분류·장르 결정
→ 발언 규칙 검사
→ 발언 후보 탐색: 대상 취급 / 표현·공개 내용
→ 후보 원문 검증: REVIEW_REQUIRED / PASS / UNCERTAIN
→ 기존 사전·화면 규칙/AI 검토·주장 추출/검색·최근 사건 추출/검색
→ 기존 후보 병합·리포트
```

이는 전체 파이프라인의 일괄 교체가 아니다. 사전·사실 주장·최근 사건 추출을 탐색 요청 하나로 통합하거나 후보로만 검색을 라우팅하는 작업은 아직 하지 않았다. OCR도 꺼지지 않았다. SRT 업로드, 편집, 포즈 분석은 추가하지 않았다.

## 탐색

- `CandidateReviewEngine`의 압축된 공통 기준: TARGET_TREATMENT / EXPRESSION_CONTENT. 당사자·비판적 온라인 시청자의 관점을 한 요청에서 사용한다. 실제 여론 재현이나 다수결이 아니다.
- SPEECH 원문만 사용한다. STT 오류를 OCR·기억으로 복원하지 않는다.
- 기존 배치 상한: 평가 원문 20줄/12,000 code point/120초, 겹침 3줄. 같은 출처 주변 문맥 최대 16줄/8,000 code point.
- 읽기 창은 기존 규칙의 30초/32줄/4,000 code point와 5초 간격 제한을 사용한다. 실제 문장·화자·장면 분할이 아니다.
- 원문은 raw에 한 번, 창은 ID 참조로 보낸다. 동일 원문 창은 anchorIds를 묶어 segmentIds 목록을 한 번만 보낸다. 같은 원문이 다른 요청에서 반복되는 것까지 완전히 제거한 것은 아니다.
- 실제 읽은 primary ID, 후보 최대 12개, 필수 정보 부족, 후보 잘림 표시를 반환한다. 초대형 단일 원문은 잘라 교정하지 않고 미확인 처리한다.
- 후보는 anchor·두 축 중 하나·짧은 비판 이유·정확한 원문 인용으로 구성한다. 한 창 밖의 발언이나 원문에 없는 인용은 거부한다.

## 검증

- 유효 후보 최대 4개씩 별도 요청한다. 각 후보의 허용 문맥만 보내며 요청 안의 같은 원문은 중복 제거한다. 후보 이유는 `hypothesisNotEvidence`다.
- 후보 ID별 정확히 하나의 결정을 요구한다. 누락·중복·알 수 없는 후보 ID·다른 anchor·허구 인용·창 밖 인용은 검증 실패다.
- REVIEW_REQUIRED는 실제 표현/대상 연결, 정상 해석과의 차이를 반환한다. 대상 취급 후보와 주요 대상 평가 태그는 TARGET 원문 및 대상 연결이 필수다. 표현 자체에는 공격 대상을 강제하지 않는다.
- 전 결정에서 anchor PRIMARY 인용, 이유, 필드 조합을 검사한다. REVIEW_REQUIRED의 대조 해석은 필수, UNCERTAIN의 필수 누락 정보는 필수다. 점수는 유한 0~1 우선순위이며 기존 유형별 점수 상한을 유지한다.
- JSON 모드를 유지했다. 서버 검증이 인용/구조를 확인할 뿐 의미적 타당성·전사 정확도·실제 여론을 보증하지 않는다. [OpenAI 공식 구조화 출력 지침](https://developers.openai.com/api/docs/guides/structured-outputs)의 JSON 문법/스키마 구분을 참고했다. strict JSON Schema 도입은 이번 변경에 포함하지 않는다.

## 검토 범위와 진단

- `NO_CANDIDATE`: 원문 탐색 완료, 후보 없음. 개별 PASS·영상 안전·진실 보증이 아니다.
- 유효 후보 검증 PASS: 해당 비판 후보는 근거 부족으로 제외했다. 전체 발언의 안전 보증이 아니다.
- 탐색 누락/실패, 허구 후보, 문맥 제한, 후보 잘림, 검증 누락/실패, UNCERTAIN, 검증 예산 초과를 PARTIAL/FAILED 및 coverageNotice로 알린다. 정상적인 다른 후보는 보존한다.
- `candidatePipeline` 로컬 진단에 탐색/검증 호출 수, 탐색 구간 수, 제안·정확 중복·잘못된 제안·검증 PASS·보류·검증 실패·예산 제외·문맥 제한/잘림을 기록한다. 후보 trace는 최대 200개, 구간은 기존처럼 최대 400개다.
- 원문·전체 모델 응답은 진단에 저장하지 않는다. 설명·필수 누락 정보는 길이를 제한한다. 진단은 기존 메모리 임시 저장/루프백 운영 원칙을 유지한다.
- 동일 anchor의 서로 다른 비판은 유지한다. 같은 원문에 관한 PASS와 REVIEW_REQUIRED는 서로 다른 후보에 대한 판단일 수 있어, 기존 구간별 PASS 충돌 규칙과 구분한다. trace의 candidateId로 추적한다.

## 설정 및 이전 방식 비교

```yaml
oops:
  analysis:
    candidate-review-enabled: true
    candidate-review-max-candidates: 24
    dialogue-review-enabled: true
```

새 경로에서는 dialogue-review-enabled와 무관하게 기존 구간/독립 대화 호출을 하지 않는다. candidate-review-enabled=false이면 이전 경로를 사용한다. 검증 후보 상한은 1~200 범위, 기본 24다. 후보가 넘치면 조용히 버리지 않고 부분 분석으로 기록한다. 후보 검증 호출 수는 기본 최대 6회이며 탐색 배치 호출·기존 다른 분석기·전송 계층 재시도는 별도다. 전체 영상 요청이 2회라는 뜻이 아니다.

기존 Java 1·2인자 생성자는 이전 경로 계약 회귀 테스트를 위한 호환 생성자다. Spring 운영 경로는 설정을 받는 4인자 생성자다. 새 경로는 모의 후보/검증 응답 테스트로 별도로 검증한다. 이전 테스트 통과만으로 새 탐지 품질을 증명하지 않는다.

## 프론트 연결점

기존 리포트의 events에 선택 필드 `reviewPerspective`를 추가한다. DB 필드·캐릭터 UI·추가 LLM 호출은 없다. 최종 대표 후보 category로 계산하므로 과거 저장 결과에도 적용된다.

| 값 | 표현 관점 | 분기 예 |
|---|---|---|
| COMMUNITY_CONTEXT | 특수 용어·사건 맥락 | UNFAMILIAR_CONTEXT / SENSITIVE_TOPIC / TIMING_SENSITIVE |
| AFFECTED_PARTY | 대상 취급 | MOCKERY / BELITTLEMENT / 차별 / 성적 대상화 등 |
| EXPRESSION_SAFETY | 표현·정보 노출 | PRIVACY / PROFANITY / VIOLENCE / GRAPHIC_METAPHOR |
| FACT_VERIFICATION | 사실 확인 | FACT_ERROR / MISINFORMATION / UNVERIFIED_CLAIM |

이는 프론트 표현용 힌트이며 실제 탐색 에이전트 신원·투표·확신도·모든 관련 관점의 목록이 아니다. 대표 유형이 바뀌면 힌트도 바뀐다. 미지원 유형은 null(기존 non_null 설정에서 생략)이다. 프론트는 해당 필드를 무시해도 기존 응답을 사용할 수 있다.
