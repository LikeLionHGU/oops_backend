# Groq 전환 후 전사·사례 회수·정상 대조·검증 점검

## 2026-10-25 겹치는 다중 화자 음성 개선 조사

### 결론과 이번 확인 범위

기본Groq를즉시교체하기보다 **입력트랙보존→품질/겹침관측→문제구간만분리·재전사→원문과대안전사병렬보존** 순서가적합하다. 아래기술은공식문서/개발자모델카드/논문조사이며우리한국어팟캐스트에서성능·메모리·시간을실측하거나운영에연결하지않았다. 현재넘어졌다/너무좋다오인식의원인이동시발화였는지도확인하지않았다.

### 서로 다른 세 작업

| 작업 | 해결하는 것 | 해결하지 못하는 것 |
|---|---|---|
| 음성활동/겹침 탐지 | 말소리·동시발화의 위치 후보 | 누가 무엇을 말했는지 복원 |
| 화자 구간화(diarization) | 어느 시점에 어떤 화자가 말했는지 | 섞인 음성에서 빠진 단어 자동 복원 |
| 음성원 분리(separation) | 섞인 신호를 복수 음성 스트림으로 추정 | 원래 음질·단어·화자 식별 보장 |

자연대화의부분겹침을다루는CSS와실제ASR평가의필요성은[Microsoft Research의CSS논문](https://www.microsoft.com/en-us/research/publication/continuous-speech-separation-dataset-and-analysis/)을참고했다. 분리음질지표가좋다고전사정확도가같이좋아진다고볼수없다. 아래우선순위는우리환경에대한설계판단이지논문에서측정된우리서비스순위가아니다.

### 코드에서 확인한 연결 공백

- `oops-analysis/app/media.py:extract_audio`는모노/16kHz/64kbpsMP3를만든다. 별도마이크트랙이있어도이경로에서는그정보를활용하지않는다. 보관원본은유지하고원래분리된트랙이있는지먼저확인할필요가있다. 유튜브스테레오L/R이개인별마이크라는보장은없다.
- `app/stt.py`는Groq구간을start/end/text로정규화하며avg_logprob·compression_ratio·no_speech_prob는그경로에남기지않는다. 선택적화자라벨은기존OpenAI diarize경로에만있고chunk범위를붙인다.
- Java `AnalysisServerClient.TranscribeResponse.Segment`, `TranscriptProvider.TranscriptLine`은start/end/text뿐이다. Python에화자정보를추가해도이계약/DB/분석입력까지이어지지않으면소실된다.
- local `ScriptImportService.validate`는다음start가이전end보다빠르면거절한다. 실제동시발화구간을시간축위에서그대로표현하려면별도lane/겹침계약이필요하다. 이번조사에서이제약을무작정풀지는않았다.
- 138번은14→58구간이돼탐색1→4회·문맥제한4배치가발생했다. STT모델뿐아니라발화단위의세분화에도배치가민감하다. 원자구간을보존하면서읽기용그룹을별도로만들고화자변경/겹침을가로질러문장을합치지않는설계를검토한다.

### 기술 후보와 한계

1. **분리된 녹음 트랙 활용 — 확보 가능하면 우선.** 제작팀의개별마이크스템이있으면각트랙전사후원래공통시간축에놓는실험을한다. 트랙/시간정렬·다른사람목소리누설·편집지연을확인하고,채널번호를곧바로실명으로표시하지않는다. 섞인스테레오를화자별로완벽복원할수있다는주장은아니다.
2. **Groq 유지+품질 관측 — 가장 작은 시작점.** [Groq공식문서](https://console.groq.com/docs/speech-to-text)는verbose_json의avg_logprob·compression_ratio·no_speech_prob를품질디버깅에활용하고낮은신뢰구간에서동시발화/잡음등을확인하도록안내한다. 현재원응답138의문제구절에도이메타데이터가있지만정확도확률로보정된값은아니다. 낮은값·단어불일치·사람지적을재확인후보로만쓰고높은값으로자동정상인증하지않는다. `language=ko`·짧은맥락포함재전사는실험축으로분리할수있지만겹친음성을해체하는기능은아니다. 정답문구를STT힌트에주입해성능향상으로세지않는다.
3. **pyannote Community-1 — 화자/겹침 구간 후보.** [공식모델카드](https://huggingface.co/pyannote/speaker-diarization-community-1)는일반화자구간과exclusive구간을제공한다. exclusive만남기면겹침정보를잃을수있으므로원래화자구간과함께보존한다. 로컬CPU기본실행·GPU선택과사용조건동의/HF토큰이필요하다. 주고받는단어의순서를보완할후보이지ASR오류수정이나개인실명인식기는아니다. 한국어팟캐스트실측없음.
4. **선택 구간 음성 분리 — 실제 동시발화에 더 직접적.** [pyannote ToTaToNet separation-ami-1.0](https://huggingface.co/pyannote/separation-ami-1.0)은5초/16kHz모노입력에서최대3음성분리와구간화를함께출력한다. 장시간녹음은이모델하나로처리되지않아추가화자임베딩·파이프라인이필요하다. [SpeechBrain SepFormer-WHAMR](https://huggingface.co/speechbrain/sepformer-whamr)도분리후각스트림을ASR로넘길후보다. 해당학습데이터밖성능보장은없으며한국어웃음/예능음악/압축음원의성능은별도검증한다. 분리찌꺼기·단어유실·중복·짧은창사이출력화자순서바뀜을검사하고실패시원음으로돌아간다.
5. **WhisperX — 시간 정렬 보조, 겹침 해결책으로 오해하지 않기.** [공식README](https://github.com/m-bain/whisperX)는단어정렬·화자구간기능을제공하지만겹치는음성을잘다루지못한다는한계도명시한다. 단어시각을정교하게만들어도틀린단어의정확성을보증하지않는다.
6. **화자라벨 API — 운영 편의와 겹침 복원을 구분.** [OpenAI공식음성문서](https://developers.openai.com/api/docs/guides/speech-to-text)는diarized_json의speaker/start/end를설명한다. 조사시점문서상gpt-4o-transcribe-diarize는deprecated이며2027-02-26종료예정이라새기본모델로즉시채택하지않는다. 화자라벨지원만으로겹친한국어의단어복원성능을보장할수없다. 계정별실제사용가능성은확인하지않았다.
7. **음악 분리와 화자 분리를 혼동하지 않기.** [Demucs공식저장소](https://github.com/facebookresearch/demucs)는보컬/드럼/베이스/기타반주분리가목적이다. 배경음악억제후보일수있지만대화자A/B를나누는도구로간주하지않는다. 원저장소는아카이브상태다.

### 우리 서비스 적용 순서 제안 — 미구현

1. 원음/기본전사/공급자원응답/사람확인정정은별도보관한다. 화자ID는화자태그의근거/실행범위를붙이고모르면null로둔다. 한국어인식오류·방언·웃음과실제겹침을같은문제로단정하지않는다.
2. native 원자구간과별개로읽기그룹을만든다. 그룹은원문ID/원시각/화자lane/겹침표시를참조하고축어전사를요약문으로바꾸지않는다. 겹치는말을허위시간순으로이어붙이지않는다. 화자필드와중첩시각의Python→DTO→DB→원문창계약을먼저설계한다.
3. 인간검수된짧은한국어대조10~20개(비겹침/겹침,웃음,빠른주고받기)를고정한다. 핵심어CER/WER와중요표현누락·의미반전·화자귀속·시간오차를각각측정하고최종검토카드도본다. 모델출력을정답으로쓰지않는다.
4. Groq기본→품질관측/겹침구간화→문제10~30초만원음·분리음ASR비교의순서로한요인씩확대한다. 전체100분을매번분리하지않는다. 로컬두서버와분리모델을동시에상주시킬메모리는실측해야한다. 필요한짧은구간을단독프로세스로평가하고무음/중복/누락시기존전사를덮어쓰지않는다.

비용은처리오디오분량+분리계산량+후속LLM토큰으로나눠측정한다. 기본전체ASR을보존하고길이T중비율r의문제구간을k개스트림으로추가전사하면추가ASR분량은대략k*r*T다. 예를들어100분중10분을2스트림재전사하면기본100분외추가20분이며,분리연산·최소과금단위·후속토큰은별도다. 이는분량산식이지실제요금/시간견적이아니다. 오픈소스도서버/메모리비용0을뜻하지않는다.

## 범위와 입력 보존

v4(약 627초)·v6(약 900초)를 현재 Python `stt.transcribe`로 전사했다. 기존과 같은 음성 추출, 600초 분할, 언어·프롬프트 힌트 없음, `verbose_json` 구간 시간 요청이다. 기존 OpenAI 대본은 이전 실험의 읽기 전용 스냅샷을 사용했다. 새 대본으로 DB나 기존 리포트를 덮어쓰지 않았다.

후속 비교는 현재 텍스트 후보 엔진과 v7 사전을 사용했다. 자동 키 분류·출처 관계 추가 기능은 OFF, 시각·OCR·최종 카드 병합은 범위 밖이다. 따라서 새 영상 ID의 전체 분석 결과가 아니다. 각 조건 1회여서 결과의 반복 안정성·모델 교체의 순수 인과 효과를 입증하지 않는다. 전사 모델 교체로 문구뿐 아니라 구간 분할과 배치 문맥도 달라졌다.

설정 확인 중 로컬 Python `.env`에 `STT_MODEL=whisper-large-v3ㄹ` 오타가 있어 `whisper-large-v3`로 바로잡았다. 키 값은 출력하거나 수정하지 않았다. `.env`는 Git 제외이며, 이미 실행 중인 서버는 설정을 다시 읽으려면 재시작해야 한다. 이 점검에서 서버를 재시작하지 않았다.

새 v4 대본에는 질문 뒤의 답변·집에서의 생활 습관·보여주겠다는 제안 등 기존에 감탄사로 반복되던 부분의 대화가 복원됐다. 위 표의 감탄사 수는 두 문자열의 정확 일치 집계이며 전체 오류율이 아니다. 다른 감탄사나 반복은 이 집계에 포함되지 않는다. 새 전사에도 줄임말 및 의심스러운 용어가 남아 있어 전체 오류 해결로 보지 않는다.

영상에 표시된 자막은 핵심 질문의 비교 근거다. 별도 청취자가 작성한 완전한 정답 전사는 없으며, WER·방언 정확도는 계산하지 않았다. 새 타임스탬프의 음수·역전·0길이는 0개이고 600초 이후 구간에도 원본 시간 오프셋이 붙었다. 실제 발음에 대한 정밀 정렬 오차는 미측정이다.

## 2. 관련 사례의 실제 회수

사전 파일 SHA256은 `b538b9fd80e3db6e55068552f6b028c57d11ba646520f324a626031f77b85e36`으로 이전 비교와 같다. 39개 예시와 6개 공통 기준을 로드했다. 선택은 현재 기본인 최대 3개·전체 6000자·예시당 3000자이며 어휘 기반 검색이다.

예시 0개여도 공통 기준 6개는 제공됐다. 사전 연결이 끊긴 문제와, 연결된 사전에서 적절한 예시를 선택하지 못하는 문제를 구분한다. 전사 변경만으로 회수 문제가 해결되지 않았다.

## 3. 정상 대조 보강과 실제 판단 비교

정상 대조는 자기 위생 경험, 자발적인 사적 경험, 성적 요구에 대한 비판적 인용, 특정 관계자의 행동 비판, 사망 후 책임 확인의 한계, 피해자 상황 설명의 6개로 보강했다. 관련 예시 ID와 함께 `pipeline-input.json.normalContrastProposals` 및 `summary.json`에 저장했다. 모두 합성 초안이며 사람이 승인한 정답이나 실제 사건 관측이 아니다. 정식 사전에는 승격하지 않았다.

| 실제 발췌 | 기존 전사 경고 수 | Groq 전사 경고 수 | 확인된 차이 |
|---|---:|---:|---|
| v4 위생·비데 대화 | 1 | 0 | 새 대본 후보 2개는 검증에서 PASS. 양쪽 전체 상태는 PARTIAL |
| v4 속옷 질문 | 1 | 1 | 옛 경고의 배설물 연상이 사라지고 실제 속옷 질문·보여주기 제안으로 근거가 달라짐. 양쪽 PARTIAL |
| v6 성적 가해의 비판적 서술 | 3 | 0 | 새 대본은 후보 없이 SUCCESS. 옛 대본은 성적 표현 경고 3개·PARTIAL |
| v6 죽음 표현 주변 | 1 | 0 | 죽음 표현 후보는 양쪽 모두 계약 탈락. 옛 대본의 경고 1개는 다른 집단 비판 문장 |
| v6 집단 전체 표현 주변 | 0 | 0 | 원래 전체 진영 표현을 대표하는 후보가 유지되지 않음. 양쪽 PARTIAL |

경고 수 감소를 정확도 개선으로 등치하지 않는다. 실제 영상 발췌는 독립 정답 승인이 없고, 특히 PARTIAL의 0개는 정상 통과가 아니다.

합성 정상 대조는 4개가 SUCCESS·경고 0개였고, 자발적 사적 경험·사망 후 책임 확인 2개는 FAILED·경고 0개였다. 실패 2개를 정상 통과로 집계하지 않았다.

## 4. 검증 단계 탈락과 쟁점 이동

### 정상 대조의 JSON 계약 실패

실패한 정상 대조 2개는 모두 검토한 ID와 빈 후보 목록을 반환했으나 `truncated`가 `null`이었다. 현재 `validDiscovery`는 이 Boolean을 필수로 요구하므로 해당 응답 전체를 채택하지 않았다. 내용 판단에서 논란으로 판정한 실패가 아니다. 원본 응답은 수정하지 않았고 자동으로 false를 넣지도 않았다.

### 죽음 표현의 대상 연결 실패

새 대본의 “비겁한 죽음으로 도망친 작자”는 발견됐고 모델의 초기·복구 응답 모두 REVIEW_REQUIRED였다. 그러나 `target=박원순`, `targetMention=작자`를 반환하면서 `targetRelation=EXPLICIT`로 표기했다. 현재 계약은 원문 지칭과 식별한 대상명이 다르면 CONTEXTUAL 연결을 요구하므로 초기·복구 모두 `TARGET_MENTION_RELATION`으로 탈락했다. 기존 전사에서는 복구 후 `TARGET_EVIDENCE_REQUIRED`가 남았다.

이는 전사를 다시 하면 없어지는 문제가 아니다. 모델의 대상 연결 표기와 검증 계약 사이의 불일치다. 이 후보가 실제 검토 대상인지에 대한 사람 판단과, JSON·근거 계약 통과 여부는 별도다. 검증을 느슨하게 하거나 모델 출력을 자동 교정하지 않았다.

### 집단 전체 주장에서 다른 평가로 후보 중심 이동

새 전사에는 “좌파진영이 모두”, “좌파진영 전체로부터”가 있다. 발견 응답은 이 구간들을 근거로 포함하면서 대표 anchor를 뒤의 “페미니스트를 자처한 자들” 문장으로 잡았다. 검증은 그 대표 문장을 해당 사건 행위자의 책임 비판으로 읽어 PASS했다. 원래 전체 진영으로 확장하는 표현이 후보의 중심으로 유지되지 않았다는 점을 확인했다. 모델이 해당 원문을 전혀 읽지 않았다는 뜻은 아니다.

속옷 질문의 중첩 배치에도 이미 처리한 anchor가 다음 배치의 primary 밖에 제안되는 `PROPOSAL_ANCHOR_NOT_REVIEWED`가 있었다. 다만 같은 핵심 후보가 다른 배치에서 살아 최종 경고는 발행됐다. 이 탈락을 쟁점 전체의 미탐으로 계산하지 않는다.
