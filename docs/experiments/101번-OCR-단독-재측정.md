## 목적과 조건

앞선5개 롱폼 중101·103·104·105는 OCR 결과를 받지 못했다. 사용자는 메모리 제약을 고려해 앞으로 한 편씩 확인하기로 했고, 우선101번 원본 제미나이 아카데미(16:19)만 새106으로 재측정했다. 다른 영상을 이어서 등록하지 않는다.

사용자는 이번 새 추정 상한 $2.00과 음성의 Groq·추출 텍스트/필요 프레임의 OpenAI 전송을 승인했다. 서비스 분석1회만이며, 실제 청구액 보장 상한이 아니다. 기존 $10 승인을 재사용하지 않는다.

이것은 OCR의 인과 효과만 분리한 OFF/ON 시험이 아니다. 서버 재시작·실행 시점·모델 응답 변동도 다르므로 카드 변화가 OCR 때문이라고 단정하지 않는다. 원음·장면 직접 검수나 새 정답 확정도 아니다.

## 요청 전 확인

- 처음 Python health가 지연됐지만 재확인에서 Spring/Python UP·STT/OCR 가용true를 확인하고 등록했다.
- 새 서버 PID는 Spring19084/Python19087이다. 기존 Python과 다른 새 프로세스였고 초기 관측 CPU는 거의 유휴였다. Spring의 `analysis-` 스레드는 아직 없었다.
- 이력105개에서 PROCESSING은0개였다. 오래된 PENDING13개는 남아 있지만 실제 실행 확인과 구별했고 취소·삭제하지 않았다. 대표84번 상태 API도 분석 미시작이라고 응답했다.
- Python 활성 작업 조회 API는 없다. 따라서 health UP만으로 유휴를 증명하지 않고 새 프로세스·CPU·Spring 스레드 정보를 함께 확인했다.
- 맥 물리 메모리16GiB, `memory_pressure -Q`의 여유 지표62%, 스왑 사용2588.5MiB. 스왑 사용량 자체를 현재 메모리 부족의 확정 근거로 해석하지 않는다.

## 완료 후 Python 잔류 추론 관측

Spring에서 COMPLETED가 된 뒤에도 Python CPU96~100%가 관측됐다. 1초간 읽기 전용 프로세스 샘플에서 `paddle::AnalysisPredictor::ZeroCopyRun`, `paddle::framework::NaiveExecutor::Run`, CPU convolution 실행 스택을 확인했다. 따라서 단순히 메모리만 유지된 상태가 아니라 Paddle 추론이 실제 계속 실행 중이었다. 이 서버의 OCR 경로에서 Paddle을 사용하며, 다른 새 분석 요청은 없었다. 스택에 job ID가 붙어 있는 것은 아니므로 요청 단위 완전 추적과는 구별한다.

그 뒤 CPU0.1%의 유휴 관측으로 바뀌었지만 RSS는 약7.34GiB가 남았다. 모델 캐시·네이티브 할당자·누수 중 무엇인지는 아직 판별하지 않았다. 프로세스를 종료하거나 강제로 메모리를 비우지 않았고, 다른 영상도 등록하지 않았다.

## 결론과 다음 우선순위

1. 한 편씩 처리하는 원칙은 유지한다. 하지만 Spring 완료 뒤15초만 기다리는 것으로 Python OCR 작업 종료까지 보장되지는 않는다.
2. 남은103·104·105 유료 재분석은 진행하지 않는다. 단독106도 OCR 실패였으므로 먼저 로컬 OCR 처리시간·메모리와 요청 종료/취소 전달 경로를 점검해야 한다.
3. OCR 결과를 정상 수신한 조건을 확보한 다음, 같은 원본의 카드·후보·근거를 비교한다. 현재는 OCR 성공 조건 비교 미완료다.

등록1회, 별도 유료 전사·추가 재분석0회. 새 승인 추정 상한$2.00이며 실제 청구액은 API에 없어 미확인이다. 결과·비교·메모리 관측은 비공개 보존하고 문서만커밋한다.

사용자가 다시1회 실행하도록 새 $2.00 추정 상한과 같은 Groq/OpenAI 전송을 별도 승인했다.106의 승인은 재사용하지 않았다. 이 절은107 승인 범위이며 위106 실행을 소급 수정하지 않는다.

요청 전 Spring20252/Python20255의 새 프로세스를 확인했다. 초기 health에서 Spring DEGRADED였다가 재확인에서 모두UP으로 바뀐 뒤 등록했다. Python CPU0.1%·RSS993,472KiB(약0.95GiB), 시스템 여유 지표62%·스왑1947.56MiB, PROCESSING0개·분석 스레드0개였다. 기존 PENDING13개는 변경하지 않았다. 이번 agent는 서버를 재시작하지 않았다.

전사 응답 SHA는101·106과 같은 `9e072e894ba42552fea66cc6447014de7f7ac8916875b3b865a25aa1b3ecb26e`다. 전사 파일이 같아도 후보 가설·선택 근거·검증 입력까지 같다는 뜻은 아니다. 카드1개가 반복됐다는 이유로 안정화나 정답 일치를 선언하지 않으며, OCR이 실패했으므로 OCR 성공 조건 비교도 여전히 미완료다.

### 메모리·완료 후 작업

Python RSS는약0.95→4.4→7.4GiB로 증가했다. 도중783만KiB(약7.47GiB) 관측도 있었고 시스템 여유 지표16~19%, 스왑3172MiB가 관측됐다. 이는 간헐적 수치이며 최대 메모리·누수 확정은 아니다.

Spring 완료 직후 Python CPU99.6%가 남았다. 이후1초 읽기 전용 샘플에서도 `paddle::AnalysisPredictor::ZeroCopyRun`과 `paddle::framework::NaiveExecutor::Run` 실행을 확인했다.106에 이어 Spring 완료와 Python 추론 종료가 일치하지 않는 관측이 반복됐다. 스택에 job ID가 들어 있는 것은 아니며 추가 분석 요청은 없었다. 그 뒤 CPU0.1%로 내려갔지만 RSS7,790,944KiB(약7.43GiB)는 남았다. 유휴 관측과 메모리 누수 확정은 구별한다.

개인 `datasets/controversy/experiments/single-101-repeat-20261022-Fv3Pkd/`에 별도 승인·등록·최종 API5개·비교·메모리 기록을 보존했다. 다른 영상 요청·별도 유료 전사·추가 재시도는0회이며 실제 청구액은 미확인이다. 서버·프롬프트·사전·분석 코드 변경은 하지 않았다. 같은 조건의 추가 유료 재시도보다 OCR 자원 및 요청 시간 제한·작업 종료 전달을 무료 점검하는 우선순위를 유지한다.
