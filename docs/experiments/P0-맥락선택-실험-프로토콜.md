# P0-맥락선택-실험-프로토콜

[비교 실험·측정 기록](README.md)

## 2026-11-06 실험 A 구현 기준 — 유료 호출 0

대상 발언 하나를 판단할 때 어떤 맥락을 함께 주는지가 판정에 미치는 영향을 측정하기 위한 P0 실험 장치다. 이 문서는 설계 v3.18과 이후 확정안을 코드에 반영한 상태를 기록한다. 모든 검증은 mock 모델과 합성 입력으로 했으며 실제 OpenAI 호출, 실제 전사문 벡터 생성, 개발셋·평가셋 실행은 아직 없다. 수치는 탐지 정확도가 아니다.

검증 결과: 전체 Java 1,401건 중 1,400건 통과, 실패·오류 0, 과거 고정 요청 재생 1건 스킵. Python `tools/tests` 전체 통과(스킵 6). 브랜치 `minwook`, 푸시하지 않음.

### 실험 조건

| 조건 | 선택 규칙 | 구현 | 추가 자료 |
|---|---|---|---|

| A2-T | BGE-M3 dense 벡터 코사인 순위, 예산 B 안에서 욕심 선택 | `EmbeddingContextSelector` (`dense-cosine-v1`) | 고정 벡터 파일 |

A0-page와 A0-prod-engine은 운영 `run()`으로 재현하며 이 실행기를 쓰지 않는다. A4-T와 A6-H-T는 사람이 만든 정보를 쓰는 진단 조건이므로 텍스트 전용 운영 조건과 같은 의미로 해석하지 않는다.

모든 선택기는 `ContextSelector.select(target, transcript)`로 `ContextSelection(contextSegmentIds, selectorId, status)`를 반환한다. 결과 ID는 전사문 순서이고 대상을 포함하지 않으며 구간을 자르지 않는다. `selectorId`에는 규칙, 토큰 계산기, B, 라벨·모델·파일 해시가 들어간다.

### 실험용 묶음과 렌더링

- `CandidateReviewEngine.runExperimental`은 primary(판단 대상)와 context(맥락 전용)를 명시한 묶음 하나로 전체 파이프라인을 실행한다. 운영 읽기 페이지의 5초 공백 분리와 재계획을 적용하지 않는다.
- 요청에는 `ExperimentalBatchRendering`(`experimental-batch-v1`)이 붙는다. 각 행은 `batchRole`이 JUDGED 또는 CONTEXT_ONLY이고, 앞에 제공되지 않은 구간이 있으면 `omittedBefore {segments, gapMs}`를 붙인다. 탐색, 검증, 탐색 복구, 검증 복구 모두 같은 렌더링을 쓴다.
- 운영 경로는 rendering이 null이며 요청 바이트가 이전과 같다.
- 예산 B는 공통 렌더러가 만든 CONTEXT_ONLY 행의 JSON을 `jtokkit-1.1.0:o200k_base`로 센 토큰 수다. B와 같으면 통과한다. 저장된 2026-10-18 `gpt-6-luna` 요청 30개(메시지 2개, `json_object`, 5,444~6,735토큰)에서 API `prompt_tokens`가 모두 o200k_base 내용 토큰 + 10(메시지 framing)과 정확히 같았고 cl100k_base와는 약 2,450토큰 차이가 났다(`TokenizerAgreementTest`, 비공개 기록이 없으면 건너뜀). 따라서 B 계산기는 해당 모델의 청구 토큰화와 일치한다고 본다. json_schema 응답 형식의 schema 토큰은 CONTEXT 부분이 아니므로 B에 들어가지 않는다.

### 형식 오류 추적

실험 묶음에서만 다음 코드를 분리한다. 처리 방식은 같다(탐색 전체 무효, 재시도 없음, 대상은 NOT_RETURNED).

| 상황 | 운영 코드 | 실험 코드 |
|---|---|---|
| `reviewedSegmentIds` 또는 `uncertainSegments`에 CONTEXT_ONLY ID | `DISCOVERY_ENVELOPE_INVALID` | `DISCOVERY_CONTEXT_ID_VIOLATION` |
| 제안 `anchorId`가 CONTEXT_ONLY 구간 | `PROPOSAL_ANCHOR_NOT_REVIEWED` | `PROPOSAL_ANCHOR_CONTEXT_ONLY` |
| 묶음 밖의 알 수 없는 ID | `DISCOVERY_ENVELOPE_INVALID` | 그대로 |

실험 실행의 진단에는 `repairUsage(discoveryRepairLimit=1, contractRepairLimit=2, discoveryRepairCalls, verificationRepairCalls, recovered, failed, notAttemptedForBudget)`가 들어간다. 결과별 개수는 trace 200개 제한과 무관하게 센다. 운영 진단 JSON에는 이 필드가 없다.

### A2-T·A3-T 오프라인 계산

Java에서는 모델을 실행하지 않는다. 전사문은 로컬 CPU에서만 처리하며 외부로 보내지 않는다.

| 항목 | A2-T 임베딩 | A3-T 재정렬 |
|---|---|---|
| 모델 | `BAAI/bge-m3` @ `5617a9f61b028005a4858fdac845db406aefb181` (MIT) | `BAAI/bge-reranker-v2-m3` @ `953dc6f6f85a1b2dbfca4c34a2796e7dde08d41e` (Apache-2.0) |
| 받는 파일 | dense sentence-transformers 파일 10개, 약 2.3GB (`pytorch_model.bin`) | 6개, 약 2.29GB (`model.safetensors`) |
| 질의·문서 | 대상 원문 / 각 구간 원문 (`target-raw-text-v1`) | 대상 원문 / 후보 원문, `max_length=1024` |
| 스크립트 | `tools/embed_segments.py` | `tools/rerank_segments.py` |
| 파일 형식 | `segment-embeddings-v1` | `rerank-scores-v1`, `scoreType=raw-logit` |

- 공통 필수 필드: `modelId`, `revision`(40자리 커밋만 허용), `modelArtifactsHash`, `transcriptSha256`, 입력 버전, `generationLibraryVersions`. 벡터 파일은 `vectorDimension`, `vectorDtype=float32`, `normalized=true`, 미리 계산한 `queryVectors`를 추가로 가진다.
- `transcriptSha256`는 전사문 순서대로 `id NUL text NUL`을 이은 SHA-256이다. Java와 Python 테스트가 같은 기준값 `a9a6035d…78c8`을 고정한다.
- 파일 해시(`vectorFileSha256`, `scoreFileSha256`)는 Java가 로드할 때 계산해 선택기 ID에 기록한다.
- A3 후보는 같은 벡터 파일의 A2 Top-K와 정확히 같아야 한다. 점수 파일의 후보 집합, `candidateSource.vectorFileSha256`, K, 전사문이 하나라도 다르면 거부한다. 따라서 A2와 A3의 차이는 재정렬 효과로만 해석한다. K는 개발셋에서 정해 Freeze 1에 고정한다.
- 라이브러리 버전은 `tools/requirements-embed.txt`에 고정했다(torch 2.15.0, transformers 5.22.1, sentence-transformers 6.2.0 등). 가상환경은 저장소 루트 `.venv`다.

합성 한국어 6구간 smoke(실제 모델, 오프라인): 같은 입력 두 번 실행 시 벡터 파일과 점수 파일이 바이트 단위로 같았고 Java 로드와 후보 집합 검사가 모두 통과했다. 일반화 발언을 질의로 넣으면 5분 뒤 철회 발언이 A2·A3 모두 1위였다. 이것은 동작 확인이며 검색 성능 측정이 아니다.

### 실행기와 결과 저장

- `ContextExperimentRunner.run(context, conditionId, selector, targetIds, repeat)`는 대상마다 선택 → `toBatch` 계약 검사 → `runExperimental` → 기록 한 줄 순서로 실행한다. 시각 단계·라우터·사례집은 항상 null이다.
- 선택 상태가 `BUDGET_INFEASIBLE`이면 모델을 호출하지 않고 그 상태로 기록한다.
- 대상마다 `ReviewRequestTraceStore.experimentalSession()`을 새로 연다. 요청 수·바이트 제한이 없고 메모리 debug store에 공개하지 않는다. 운영 session 제한(128요청, 256KB)은 그대로다.
- `ExperimentResultStore`는 실행 ID마다 새 디렉터리에 `manifest.json`과 `results.jsonl`을 한 번만 만든다. 대상 하나가 끝날 때마다 한 줄을 SYNC로 추가한다. 기존 디렉터리, 안전하지 않은 runId, 같은 (조건, 반복, 대상) 중복은 거부한다. 중단 후 이어 하기는 아직 없다.

### 집계

정답 라벨은 이진 `GoldCase(videoId, targetId, RISK|NO_RISK, clusterId)`다. 기존 프로토콜의 3분류 Gold(PASS, REVIEW_REQUIRED, intrinsically UNCERTAIN)와는 별도로 관리하며, 정답 자체가 불확실한 사례를 NO_RISK로 바꾸지 않는다.

| 서버 상태 | 결과 분류 | 주 지표 |
|---|---|---|
| `REVIEW_REQUIRED` | RISK | 정답과 비교 |
| `PASS`, `NO_CANDIDATE` | NO_RISK | 정답과 비교 |
| `UNCERTAIN` | ABSTAIN (모델이 판단 보류) | 오답 |
| `NOT_RETURNED`, `CALL_FAILED`, `REJECTED`, `CONFLICT`, `NOT_SELECTED` | NOT_EVALUATED (유효한 판단 미완료) | 오답 |
| `BUDGET_INFEASIBLE` | BUDGET_INFEASIBLE (필수 맥락이 B 초과) | 분석에 따라 다름 |

- `CONTROLLED`: 사전 등록한 예산 가능 사례만 평가한다. 그 집합 안에서 BUDGET_INFEASIBLE이 나오면 오류로 거부한다. A1~A6-H 통제 비교는 이 분석을 쓴다.
- `OPERATIONAL`: 전체 사례를 평가하고 BUDGET_INFEASIBLE을 실패로 계산한다.
- 반복 실행은 사례별 정답률을 먼저 구한다. 주 지표는 영상·사건 동일 가중(`clusterWeighted`), 보조 지표는 사례 동일 가중(`caseWeighted`)이다.
- 95% 신뢰구간은 군집 단위 percentile bootstrap이며 seed를 고정한다. 조건 비교는 같은 재표본에서 짝지은 차이를 계산한다.
- 함께 보고: `coverage`(RISK 또는 NO_RISK를 반환한 실행 비율), `selectiveAccuracy`(판단을 반환한 실행에서의 정확도, 없으면 null), `abstainRate`, `notEvaluatedRate`, `budgetInfeasibleRate`, `budgetExcludedCases`, 상태별 횟수. coverage와 selective accuracy는 실행 단위 합산이다.
- 정답 라벨이 없는 기록, 일부 사례가 빠진 조건, 중복 Gold는 거부한다.

예산 가능 사례 집합은 `BudgetFeasibleCases.compute`로 Gold 라벨과 고정 전사문만 써서 미리 계산한다. A4-T 입력의 렌더링 토큰 수를 `OracleContextSelector.measure()`로 재며, A4 선택기의 판정과 같은 메서드를 쓴다. 결과 파일(`budget-feasible-v1`)은 한 번만 쓰고 SHA-256을 분석 계획에 기록한다. B를 바꾸면 새로 만든다.

### 개발셋 라벨 양식

`tools/label_packets.py`가 라벨 패킷 생성, 배치 검증, 내보내기를 맡는다. 입력은 manifest(`labelVersion`, 영상별 `videoId`·`clusterId`·`transcriptPath`·`targets`)다.

- `packets`: 역할별 패킷을 새 폴더에 한 번만 쓴다. T1 패킷에는 대상 발화 원문만 있다. T2 패킷에는 전체 고정 전사문과 빈 T2 필드가 있다. 화자·주제 패킷에는 구간만 있고 대상과 위험 라벨은 없다.
- `validate`: 오류를 모두 모아 보고하고 중간에 멈추지 않는다. 파일 단위로는 T2 파일의 `t1FileSha256`이 T1 파일과 같아야 하고(`T1_NOT_FROZEN`), 화자·주제 라벨러는 T1·T2 라벨러와 달라야 하며(`BLINDNESS_VIOLATION`), 화자 라벨은 모든 구간을 덮어야 하고(`SPEAKER_LABELS_INCOMPLETE`), 화자 파일의 `basis`가 `AUDIO_VERIFIED`여야 한다(`SPEAKER_LABELS_NOT_AUDIO_VERIFIED`). 전사문만으로 추정한 화자 라벨(`TRANSCRIPT_INFERRED`)은 개발·디버깅 참고용이며 A6-H Gold가 아니다. 사례 단위로는 ID 유효성, 대상 자기 참조, 맥락 필요성과 맥락 ID의 일관성, 필요성 근거 누락, 위험 근거 누락(`MISSING_RISK_EVIDENCE`), UNCERTAIN과 맥락 필요 충돌을 검사한다. T2 라벨에 `contextDistance`를 직접 적으면 `CONTEXT_DISTANCE_IS_DERIVED` 오류다.
- 주제 라벨은 episode 시작 구간(`episodeStarts`)만 적는다. 그 사이 구간에는 같은 episode가 자동으로 붙어 전체 구간 coverage를 채운다. 주제 라벨러는 위험 Gold를 보지 않고, episode 경계는 거리 계산 전에 확정한다.
- `diagnose`: 화자 라벨 없이 manifest, T1, T2, 주제, A0 파일로 대상별 표(`label-diagnostic-v1`, `diagnosticOnly=true`)를 만든다. 열은 T1 판단, T2 판단, 맥락 필수성, Gold 맥락·근거 ID, A0 상태와 제공 구간 ID, 거리와 `distanceStatus`, export 상태(VALID/EXCLUDED)와 오류다. T1 동결과 주제 라벨러 blind 규칙은 그대로 검사하고 화자 규칙만 건너뛴다. 정식 export가 아니며 실험 입력으로 쓰지 않는다.
- `export`: 파일 단위 오류가 있으면 거부한다. 유효 사례만 `gold-oracle.json`(A4-T 입력), `speakers-a6h.json`(A6-H-T 입력), `gold-cases.json`(이진 GoldCase와 intrinsically UNCERTAIN 분리), `export-report.json`(제외 사례와 입력 SHA-256)으로 한 번만 쓴다.

#### contextDistance (v3.19 확정)

T2 라벨러는 `goldContextSegmentIds`만 지정하고, 주제 라벨러는 episode 경계만 기록한다. `contextDistance`는 export 단계에서 자동으로 만든다. 판정 순서는 다음과 같다.

| 순서 | 조건 | 결과 |
|---|---|---|
| 1 | 맥락 불필요 또는 T2 = UNCERTAIN | null |
| 2 | 모든 결정적 맥락이 현행 A0 planner 입력에 포함 | Near |
| 3 | 2가 아니고 결정적 맥락 중 하나라도 대상과 다른 topic episode | Far-video |
| 4 | 2가 아니고 결정적 맥락이 모두 대상과 같은 topic episode | Far-topic |

- Near를 먼저 판정한다. 다른 episode의 맥락이라도 A0가 모두 제공했다면 Near다. Near/Far는 현행 시스템의 맥락 접근성을 기준으로 한 상대적 구분이다.
- Far-video는 episode 경계를 하나 이상 넘으면 된다. 사이에 다른 episode가 있을 필요는 없다. 동결된 주제 라벨만으로 계산되고 추가 판단이 필요 없다.
- 고정 시간 창(`nearWindowMs`)은 쓰지 않는다(v3.6 결정: Near = 고정 전사문에 `DialogueReadingPage.plan`을 적용했을 때 대상에 실제로 제공되는 구간 집합에 결정적 맥락이 모두 포함되는 경우).
- A0 입력은 `./gradlew a0ProvidedContext -PlabelManifest=<manifest> -Pa0Output=<새 파일>`로 계산한다(`A0ProvidedContext`, 유료 호출 0). 결과 `a0-provided-v1`에는 A0 선택기 ID, manifest·전사문 SHA-256, 대상별 제공 구간 ID가 들어간다. planner의 primary가 아닌 대상은 `NOT_PLANNED`이며 거리를 만들지 않는다(`TARGET_NOT_PLANNED`).
- 이 파일 없이 export하면 거리는 `NOT_COMPUTED`이고 `distanceComputed=false`다. 임의의 시간 창으로 대신하지 않는다. 라벨링은 먼저 진행하고, 거리별 평가용 export는 A0 입력을 계산한 뒤 다시 만든다. manifest·전사문 해시나 대상 집합이 다른 A0 파일은 거부한다.
- 각 사례의 `distanceStatus`는 `COMPUTED`, `NOT_APPLICABLE`, `NOT_COMPUTED`, `TARGET_NOT_PLANNED` 중 하나다. `export-report.json`에 상태별 사례 수(`distanceStatusCounts`)와 거리별 사례 수(`contextDistanceCounts`)를 기록한다.

상태별 처리(Freeze 기준):

| distanceStatus | 처리 |
|---|---|
| COMPUTED | Near/Far 층화 분석 대상 |
| NOT_APPLICABLE | 맥락 거리 분석 대상 아님(맥락 불필요 또는 UNCERTAIN) |
| NOT_COMPUTED | 거리 분석에서 빼고 계산 미완료로 보고 |
| TARGET_NOT_PLANNED | A0 대상 선정 실패로 따로 보고. Far-topic·Far-video로 바꾸지 않는다 |

거리를 계산하지 못한 사례를 조용히 빼거나 Near/Far로 임의 배정하지 않는다.

#### 개발셋 첫 실행 검증 순서

1. 개발셋 manifest와 전사문을 고정한다(영상, 대상 segment ID 집합).
2. `a0ProvidedContext`로 A0 제공 맥락 파일을 만든다.
3. A0 파일을 연결해 라벨 검증과 export를 실행하고 오류를 확인한다.
4. Development Set Audit: 거리별 사례 수와 `TARGET_NOT_PLANNED`·`NOT_COMPUTED` 비율을 보고 개발셋 보강 필요성을 판단한다.

함께 확인할 항목은 A0가 계획한 대상 비율(planner coverage), A0 파일의 구간 ID와 실제 엔진 입력 구간의 일치(context identity), Gold ID·manifest·전사문·A0 파일의 일치(export integrity)다. 구간 ID가 맞아도 실제 모델 입력에서 본문이 잘렸다면 완전한 맥락 제공이 아니므로, 첫 실제 실행에서 표본을 뽑아 입력 본문을 대조한다.

#### 질의 분해 연구 질문과 사전 고정 조건

RQ: 여러 발화가 섞인 STT 구간에서 질의 분해와 후보 통합 전략이 결정적 맥락 회수율을 높이는가.

- H1: 발화 단위 질의 분해는 원문 전체 임베딩보다 결정적 맥락 회수율을 높인다.
- H2: 조각별 후보 보장 방식은 최대 유사도 통합보다 작은 K에서 결정적 맥락 회수율을 높인다.

두 가설 모두 검증 전이다. 비교할 통합 방식은 다음과 같다.

| 방식 | 비교 목적 |
|---|---|
| 최대 유사도(Max similarity) | 현재 기준선 |
| Reciprocal Rank Fusion(RRF) | 조각별 순위를 결합해 점수 규모 차이의 영향을 줄임 |
| 조각별 Top-N 균등 할당 | 한 조각이 후보 전체를 독점하는 현상을 막음 |
| 조각별 후보 합집합 후 A3 재정렬 | 한 조각에서만 검색되는 관련 문서에도 재정렬 기회를 줌 |

신규 Far 도전 세트에서는 결과를 보기 전에 다음을 고정한다.

- STT 구간을 발화별로 나누는 규칙과, 나누지 못할 때의 처리
- 검색 결과 통합 방식과 동점 처리
- 후보 예산 K = 20, 50, 100. 조각별 Top-N은 총 후보 수가 K를 넘지 않도록 예산을 통제한다.
- A3에 전달할 질의 형태
- 성공 기준: 아래 회수 지표와 기준 라벨 일치율

회수 지표는 사례마다 결정적 맥락(`goldContextSegmentIds`) 기준으로 계산한다.

| 지표 | 정의 |
|---|---|
| Recall@K | 상위 K 후보에 든 결정적 맥락 구간 수 / 결정적 맥락 구간 수. 사례별 값을 평균하고, A0 밖 구간만 센 값도 함께 보고한다. |
| All-context Recall@K | 결정적 맥락 구간이 모두 상위 K 후보에 든 사례 수 / 맥락 필수 사례 수. 일부만 회수한 사례는 실패로 센다. |

판정 지표는 기준 라벨이 독립적인 인간 Gold가 아닌 동안 "최종 판정 정확도"라고 부르지 않고 "기준 라벨 일치율"이라고 부른다. 기준 라벨의 출처(AI 초안, 기존 판정 참고 여부)를 함께 적는다.

A0 밖 결정적 맥락이 없는 사례는 "A0 밖만 센 Recall@K"의 분모가 0이다. 이런 사례는 0점이 아니라 N/A로 기록하고 그 지표의 집계에서 뺀다. 뺀 사례 수는 따로 보고한다.

#### 독립 신규 데이터 단계(P0 탐색·개발 단계 종료)

P0 탐색·개발 단계는 여기서 마친다. 이후 신규 데이터는 목적에 따라 두 세트로 나누고, 성능은 세트별로 따로 보고한다. Far 도전 세트를 일반 평가 세트에 섞으면 실제 Far 발생 비율이 왜곡되기 때문이다.

| 데이터셋 | 목적 | 선정 방식 |
|---|---|---|
| 독립 일반 평가 세트 | 실제 영상에서 Far가 얼마나 나오는지 측정 | 검색 결과와 무관하게 영상을 고른다 |
| Far 도전 세트 | A2·A3의 먼 맥락 회수 능력 검증 | 먼 맥락이 필요한 사례를 의도적으로 모은다 |

진행 순서:

1. 영상 선정·동결: 영상 ID, 선정 기준, 전체 STT, 해시를 기록한다.
2. 독립 라벨링: 검색 순위와 기존 개발 판단을 보여 주지 않고 위험 판정과 결정적 맥락을 작성한다.
3. 라벨 검증·동결: 구간 ID와 맥락 필요성을 검증하고 평가 기준을 고정한다.
4. A0·A2·A3 실행: 사전에 고정한 질의 규칙과 같은 후보 예산으로 비교한다.
5. 결과 분석: 두 세트를 나눠 Recall@K, All-context Recall@K, 기준 라벨 일치율, 비용을 보고한다.

핵심 원칙: 검색 결과를 보고 Gold 맥락을 정하지 않는다. 라벨은 검색 실험 전에 동결한다.

#### Far 도전 세트 구축 절차(2026-11-07 확정)

후보는 AI가 추천하고 별도 라벨러가 독립적으로 확인한다. 기존 개발 사례 재사용(과거 검토 사례)은 이미 발견된 문제 유형에 치우치므로 쓰지 않는다.

1. 신규 영상 선정과 STT 동결: P0 개발 영상(124·121·119)과 P1 일반 평가 영상(1001·1002·1003)은 제외한다. 같은 Groq STT 경로(`tools/service_stt_transcript.py`)로 전사문을 동결한다. 선정한 영상은 처음부터 Far 도전 그룹으로 관리한다.
2. 추천 AI의 후보 발굴: 추천 AI에는 전체 전사문만 준다. 원거리 맥락이 필요할 가능성이 있는 `targetSegmentId`, 예상 맥락 ID, 추천 이유를 기록하고 동결한다. A0·A2·A3 결과는 주지 않는다.
3. 독립 라벨링: 추천된 대상으로 manifest를 만들고, 기존 절차대로 T1(v2)·Topic·T2를 수행한다(T1 동결 후 T2). 라벨러에게는 추천 이유, 추천 맥락 ID, 검색 결과를 주지 않고, Far 사례를 찾는 실험이라는 사실도 알리지 않는다. 패킷과 지시문은 일반 세트와 같다.
4. 거리 분류: 동결된 `goldContextSegmentIds`와 Topic 경계로 Near·Far-topic·Far-video를 계산한다. 추천 AI의 예상 맥락 ID와 일치하는지는 채택 기준이 아니다.
5. 세트 확정: 독립 라벨에서 Far로 판정된 사례만 도전 세트에 넣는다. Near, 맥락 불필요, 판정 불가 사례도 지우지 않고 추천 결과 기록에 남긴다.

사전 고정 조건:

| 항목 | 규칙 |
|---|---|
| 추천 예산 | 1차는 신규 영상 3개, 영상당 최대 20개 후보 |
| 중단 기준 | 정해진 예산까지만 평가하고 확보된 Far 수를 그대로 보고한다. 목표 개수를 채우려고 기준을 완화하지 않는다 |
| 도전 세트 사용 | 평가 전에 A2·A3 검색·통합 규칙을 동결하고, 결과를 본 뒤 조정하지 않는다 |

121/349에서 얻은 검색 개선 방법을 도전 세트에서 시험할 수는 있다. 그러나 그 결과를 보고 알고리즘을 다시 고치면 이 도전 세트도 개발 세트가 되고, 독립 평가에는 또 다른 데이터가 필요하다.

결과 보고는 후보 발굴과 검색 회수를 따로 평가한다.

- 후보 발굴: Far 확정률 = 독립 라벨에서 Far로 확인된 후보 수 / 추천한 전체 후보 수. 추천 후보의 적중률이며, 영상 전체에서 Far를 찾아낸 재현율이 아니다.
- 검색 회수: 확정된 Far 사례에 대해 A0 포함 여부, A2 Recall@K, A3 Recall@K, All-context Recall@K, 기준 라벨 일치율을 본다. AI가 만든 Gold는 인간 검증 전까지 잠정 기준 라벨이다.
- 한계: 추천 AI와 라벨러는 같은 모델(`gpt-6-luna`)의 별도 호출이다. 서로의 출력을 보지 않지만 같은 모델의 판단 경향을 공유할 수 있다.

  | 2002/1963 | 페이지 경계 | A0 안 632·807·1552, A0 밖 617·1050·1744 | 1964~1966 |

- 영상 전체 범위, 모든 방식 공통: 미리보기 평균 Recall@20/50/100 = 0.194/0.194/0.411, All-context 0/3·0/3·0/3. 페이지 경계 Recall = 0/0.25/0.5, A0 밖만 0/0/0.5, All-context 0/2·0/2·1/2(K=100에서 245만).
- 과거만 쓰는 범위: 미리보기는 정답이 모두 대상 뒤에 있어 회수 0이다(정의상 불가). 페이지 경계는 245의 225가 39위로 K=50부터 들어왔고, 1963은 A0 밖 정답(1964~1966)이 모두 대상 뒤라 회수할 수 없다.
- A3: 같은 K에서 후보 집합이 같아 Recall은 A2와 같다. K=100 후보 안에서 A3 순위는 2002/0의 1875가 2위, 2002/17의 1408이 10위, 2001/4의 1032·1033이 12·10위, 245의 225가 33위였다.
- 관찰:
  - 미리보기: 본편 중 미리보기와 문장이 거의 같은 구간은 상위권(2위, 4위)에 오지만, 라벨러가 함께 고른 앞뒤 구간은 문장이 달라 순위가 낮다. 그래서 구간 단위 Recall은 낮고 All-context는 모두 실패했다. 정답이 여러 구간인 사례에서는 구간 단위 의미 검색만으로는 전체 맥락을 모으기 어렵다.
  - 페이지 경계: 맥락이 대상 바로 옆인데도 의미 유사도로는 600위 이하였다(1963). 짧은 대화 구간은 내용이 대상과 닮지 않아 의미 검색이 바로 옆 구간을 찾지 못한다. 이 유형은 검색보다 A0 페이지 구성(대상 주변 구간을 보장하는 방식)과 관련된 문제로 보인다. 다만 이것은 관찰이며, r1 결과를 보고 규칙이나 A0를 고치지 않는다.
- 결론: 5건 모두에서 A2·A3(r1)는 Far 맥락을 K=20 안에 모두 회수하지 못했다. 질의 분해의 효과는 분리 가능한 대상이 없어 검증되지 않았다. 표본이 5건이라 일반적인 성능 판단은 하지 않는다.

#### r1 결과의 동결된 해석(2026-11-07)

r1 결과와 아래 해석은 여기서 동결한다. 이후 실험에서 이 5건을 다시 쓰면 그 결과는 개발·진단 결과로만 기록한다.

| 검증 항목 | 결과 | 해석 |
|---|---|---|
| 질의 분해 H1 | 분해된 대상 0/5 | Not evaluated (0 eligible cases) |
| 통합 방식 H2 | 모든 방식이 같은 결과 | Not evaluated (0 eligible cases) |
| A2 후보 회수 | 일부 맥락 회수 | 유형에 따라 다름 |
| A3 재정렬 | 일부 정답 순위 상승 | 후보 회수 자체는 바꾸지 못함(같은 K에서 같은 후보 집합) |
| 전체 맥락 회수(K=100) | 미리보기 0/3, 페이지 경계 1/2 | 부분 회수와 완전 회수가 다름 |

H1·H2는 지지도 기각도 하지 않는다. 대상이 가설을 평가할 조건(분해 가능한 질의)을 갖추지 못했다. 문장부호 기반 분해 규칙은 이 도전 세트에서 한 번도 작동하지 않았다.

Far는 하나의 문제가 아니다. 원인과 해결 방법이 다를 수 있으므로 앞으로 Far 결과는 아래 유형으로 나눠 보고한다.

| 유형 | 내용 | 이번 사례 | 후속 연구 후보 |
|---|---|---|---|
| A. 미리보기·본편 반복 | 먼 본편에서 비슷한 문장을 찾는 문제. 그 문장을 찾아도 앞뒤 대화까지 확보되지는 않는다 | 3건 | 대표 발언 검색 후 그 위치의 주변 구간 확장 |
| B. A0 페이지 경계 | 맥락은 가깝지만 입력 페이지가 끊겨 빠짐. 의미 검색이 꼭 필요한 문제인지부터 구별해야 한다 | 2건 | 페이지 중첩, 인접 구간 보장, 경계 주변 확장 |
| C. 실제 원거리 대화 참조 | 한참 전에 언급한 사람·사건·발언을 나중에 다시 가리킴. 원래 연구의 핵심 문제 | 0건 | 성능을 판단할 근거 없음 |

A3는 두 질문으로 나눠 평가한다. 후보 회수는 A2가 필요한 맥락을 후보 집합에 넣었는지, 상위 노출은 A3가 제한된 입력 예산 안에서 그 맥락을 앞쪽에 두었는지다.

사후 분석(r1에 없던 지표, 독립 평가 지표 아님): K=100 후보를 A3로 재정렬한 뒤 상위 5·10·20개 안의 정답 구간 비율을 같은 순위의 A2와 비교했다(Q0, 영상 전체 범위).

| 사례 | 후보 회수(@100) | A2 → A3 @5 | @10 | @20 |
|---|---|---|---|---|
| 2001/4 미리보기 | 0.40 | 0 → 0 | 0 → 0.20 | 0 → 0.40 |
| 2002/0 미리보기 | 0.33 | 0.33 → 0.33 | 0.33 → 0.33 | 0.33 → 0.33 |
| 2002/17 미리보기 | 0.50 | 0.25 → 0 | 0.25 → 0.25 | 0.25 → 0.25 |
| 2002/1963 페이지 경계 | 0 | 0 → 0 | 0 → 0 | 0 → 0 |
| 2003/245 페이지 경계 | 1.00 | 0 → 0 | 0 → 0 | 0 → 0 |

과거만 쓰는 범위에서는 245의 225만 A3 상위 20 안에 들었다(A2는 39위). A3가 일부 사례에서 정답을 앞으로 올렸지만(2001/4), 오히려 내린 사례도 있다(2002/17 @5). 상위 노출 지표(재정렬 후 Recall@5·10·20)를 독립 평가에 쓰려면 다음 실험 전에 규칙에 넣어 동결한다.

#### 다음 연구 질문: R2-A와 R2-B(2026-11-07 정의, 세부 규칙은 실행 전 동결)

Far 도전 세트를 그대로 넓히기보다 연구 목표에 따라 두 갈래로 나눈다.

| 실험 | 연구 질문 | 비교 |
|---|---|---|
| R2-A 구조적 맥락 회수 | 의미 검색 없이 인접 구간 확장만으로 페이지 경계 누락(유형 B)과 미리보기의 주변 맥락(유형 A의 확장 단계)을 해결할 수 있는가 | 기존 A0 vs 페이지 중첩·인접 구간 보장·경계 주변 확장 |
| R2-B 원거리 의미 검색 | 분해 질의와 후보 통합이 실제 원거리 대화 참조(유형 C) 회수에 도움이 되는가 | Q0 vs 분해 질의 4가지 통합 방식 |

- R2-B에는 질의 분해가 실제로 일어나는 사례와, 이전 대화의 특정 정보를 참조하는 사례가 필요하다. 새 데이터에서 이 특성을 확인하는 선정 규칙과 추천 예산을 미리 고정한다. 분해 규칙이 문장부호에만 의존하면 이번처럼 0건이 될 수 있으므로, 분해 규칙 자체도 실행 전에 다시 정해 동결한다.
- 이번 5건을 보고 떠올린 개선안(주변 구간 확장, 페이지 중첩 등)을 이 5건에 다시 적용해 볼 수는 있다. 그 결과는 개발·진단 결과로만 기록하고, 독립 성능은 새로 확보한 사례에서 확인한다.
- 두 실험 모두 결과 지표는 후보 회수와 상위 노출을 나눠 보고하고, Far 유형(A·B·C)별로 따로 집계한다.

#### R2-A 구조적 맥락 회수 — 규칙(2026-11-07)

규칙 파일: [r2a-structural-v1.json](retrieval-rules/r2a-structural-v1.json). 첫 작성본(`0c294e24…`)에 아래 처리 규칙 4가지를 더해 동결했다(최종 SHA-256 `425f8b9236a7e179702d2272bb06d81b3e356653b227b8f2e4612ad07238a3a8`). 두 판 모두 새 데이터를 뽑기 전이며, 이후에는 고치지 않는다. 숫자(앞뒤 5구간, 처음·마지막 3개, 확장 10구간, EDGE·INTERIOR 20/10)는 가설 검증을 위한 합리적인 초기 고정값이며 최적값이라는 뜻은 아니다.

배경: A0 페이지(`DialogueReadingPage` 2026-10-25-reading-page-1)는 앞쪽 접두 맥락(최대 10초·1,000자·직전 페이지 primary의 1/4)만 붙이고 뒤쪽 맥락은 붙이지 않는다. 그래서 페이지 끝 근처의 대상은 바로 뒤 발화를 받지 못한다(2002/1963 사례).

| 조건 | 내용 |
|---|---|
| S0 A0 | 현재 A0-T 맥락(대상 페이지의 접두 맥락과 primary 전체에서 대상을 뺀 것) |
| S1 페이지 중첩 | S0 + 접두 규칙을 뒤쪽으로 뒤집은 접미 맥락(페이지 마지막 primary 뒤 구간을 공백 5초 이하, 마지막 primary 끝에서 10초 이하, 1,000자 이하까지) |
| S2 인접 구간 보장 | S0 + 대상 앞뒤 각 5구간(전사문 순서, 공백·페이지와 무관) |
| S3 경계 주변 확장 | 대상이 페이지의 마지막 3개 primary 중 하나면 S0 + 페이지 뒤 10구간, 처음 3개 중 하나면 S0 + 페이지 앞 10구간, 그 밖에는 S0 |

처리 규칙(구현에 따라 결과가 달라지지 않도록 고정):

1. 같은 페이지: S1~S3는 페이지를 다시 나누지 않는다. A0의 페이지 분할, 대상의 페이지, S0 창은 그대로 두고 구간만 더한다.
2. 중복과 순서: S0 창에 이미 있는 구간과 대상은 다시 더하거나 세지 않는다. 최종 맥락은 S0와 추가 구간을 합쳐 원본 STT 순서(ReviewInput 순서)로 놓는다. 영상 시작·끝에서는 있는 구간만 쓴다. S1의 10초·1,000자 제한은 뒤쪽 접미 맥락에만 적용되고 S0의 앞쪽 접두 맥락은 그대로다. S2·S3는 입력 한도 단계 전까지 시간·공백·글자 제한 없이 정한 개수만큼 더한다.
3. 입력 한도: 확장된 창을 `DialogueReadingPage.inputCodePoints`로 재서 24,000 − 256 코드 포인트와 비교한다. 한도 적용 전 포함률(이론값)과 적용 후 포함률을 모두 보고한다. 넘으면 추가 구간을 대상에서 먼 것부터(전사문 순서 거리, 같으면 뒤쪽 구간 먼저) 하나씩 빼고, S0 구간은 빼지 않는다. 실사용 가능한 성공은 한도 적용 후 포함률만 센다. 잘라 낸 사례 수와 뺀 구간도 기록한다.
4. 분모 0: 맥락이 필요 없는 사례(`goldContextSegmentIds=[]`)는 포함률 계산에서 뺀다. S0가 놓친 사례가 없으면 A0 누락 회복률은 0%가 아니라 N/A다. 모든 비율에는 사례 수를 함께 적는다(예: 회복 사례 수 / A0 누락 사례 수).

보고 시 주의: EDGE를 INTERIOR의 두 배로 뽑았으므로 EDGE와 INTERIOR 결과를 먼저 따로 보고한다. 90건 전체 평균은 "경계 과표집 표본의 결과"로 표시하며 운영 환경의 평균 성능으로 제시하지 않는다. A0 누락 회복률은 분모가 작으면 불안정하므로 항상 회복 사례 수 / A0 누락 사례 수와 함께 쓴다.

- 독립 데이터: P0·P1·Far 도전 세트에 쓰지 않은 새 영상 3개를 전사문을 읽기 전에 영상 단위로 고르고, 같은 STT 경로로 동결한다.
- 대상 선정(`r2a-sampling-v1`): A0 페이지의 primary 중 2자 이상인 구간을 후보로 한다. 페이지의 처음 3개·마지막 3개 primary는 EDGE, 나머지는 INTERIOR 층이다. 영상마다 EDGE 20개, INTERIOR 10개를 전사문 SHA에서 정한 시드로 뽑는다. 층의 후보가 모자라면 있는 만큼만 뽑고 부족분을 보고하며, 다른 층에서 채우지 않는다. 뽑은 대상은 바꾸거나 빼지 않는다. 이 선정은 내용을 보지 않지만 페이지 위치로 층을 나누므로, 맥락 필요 비율은 일반 세트와 비교하지 않는다.
- 라벨: `tools/ai_labels.py`(T1 v2·Topic·T2, T2 대상 누락 검사 포함). 라벨러에게 R2-A나 페이지 구조를 알리지 않는다. AI 초안은 잠정 기준 라벨이다.
- 중단 기준: 정한 예산(영상 3개 × 30개)만 평가하고, 맥락 필요·A0 미제공 사례 수를 나온 그대로 보고한다. 목표 개수를 채우려고 기준을 완화하지 않는다.
- 지표: 전체 맥락 포함률(Gold 맥락이 모두 조건의 맥락 안에 든 사례 / 맥락 필요 사례), A0 누락 회복률(S0가 다 담지 못했는데 조건이 다 담은 사례 / S0가 다 담지 못한 사례), 사례별 Gold 포함 비율 평균, 추가 비용(S0 대비 추가 구간 수·글자 수의 평균과 최대, 페이지 입력 한도를 넘는 사례 수). 조건·층·영상·S0 누락의 Far 유형(A·B·C)별로 나눠 보고한다.
- 개발 데이터: 이미 라벨된 맥락 필요 사례(P0 개발 T2 수정본, P1 1001~1003, Far 도전 2001~2003의 Near·Far)에도 조건을 계산한다. 특히 Far 도전 5건은 R2-A 설계에 영향을 주었으므로, 그 결과는 개발·진단 결과로만 기록하고 독립 성능으로 보고하지 않는다.
- 판정 모델에 각 조건의 맥락을 넣어 보는 기준 라벨 일치율은 별도 실행으로 한다.
- 예상: 무작위 P1 대상의 맥락 필요는 3/90이었다. EDGE 층에서도 A0 누락이 적게 나올 수 있으며, 적게 나온 결과도 그대로 유효한 결과다. 영상 1001은 T1 v1·GPT-6 채팅, 영상 1002는 T1 v2·`gpt-6-luna`이므로 T1 관련 지표는 영상별로 따로 본다.

현재 결론: 선정된 21개 발언의 AI T2 수정 라벨 기준으로, 맥락이 필요한 11개 중 A0가 제공하지 못한 사례는 1개였고, 그 사례는 다른 주제 episode의 맥락을 필요로 했다. 표본이 작고 수정 과정에서 기존 판정을 참고했으므로, A0가 충분하다고도 A2·A3가 필요하다고도 결론 내리지 않는다. 독립 신규 데이터에서 A2·A3의 추가 효용을 검증한다.

#### 다음 실험 구성

1. 독립 신규 영상: 기존 세 영상과 겹치지 않는 표본을 고른다. 과거 논란 사례만이 아니라 일반 발언도 넣어 실제 분포를 본다.
2. Far 도전 세트: 무작위 표본과 따로, 앞선 주제나 먼 구간에서 맥락이 결정되는 사례를 모은다. 두 집합의 결과는 섞지 않는다.
3. A0·A2·A3 동일 조건 비교: 같은 대상과 동결된 라벨로 맥락 포함률, Far 회수율, 최종 판정 성능, 토큰 비용, 지연시간을 비교한다.

Far 사례를 많이 찾는 것 자체를 성과로 삼지 않는다. 실제 발언에서 Far가 얼마나 나오는지 재는 일(무작위 표본)과 Far에 대한 검색 성능을 검증하는 일(도전 세트)은 목적이 다르다.

#### STT 오류 처리(라벨링 지침)

- T1·T2 모두 고정 STT 원문을 고치지 않는다.
- 오기 때문에 의미가 불명확하면 추측해 고쳐 쓰지 않고, 불확실성을 판단과 근거에 기록한다. 그리고 STT 문제는 라벨의 `transcriptQualityNote`에 적는다. `diagnose` 표는 이를 `transcriptQuality`(TRANSCRIPT_QUALITY 진단)로 따로 보여 주며, 라벨의 유효성은 바꾸지 않는다.
- 원음을 확인할 수 있게 되어도 기존 Gold를 조용히 바꾸지 않는다. 원음 기반 검토 결과는 별도 기록으로 관리한다.

본 개발셋은 파일럿이 끝난 뒤 서로 다른 원본 영상과 대화 유형으로 따로 확장한다. 맥락 무관 판단, Near, Far-topic, Far-video, 화자 구분이 필요한 사례(A6-H)를 확보하되, 영상 수를 채우는 것보다 결정적 맥락이 필요한 사례와 독립 영상 수를 함께 확보하는 것을 기준으로 한다.

환경 확인이 거의 끝난 것과 Freeze 1이 완료된 것은 다르다. Freeze 1에는 개발셋 기반 파라미터 결정과 안전 빌드 검증이 포함된다. 실험 CLI와 실행 metadata 기록은 구현을 마쳤다(`ContextExperimentTrial`).

- 스냅샷: 저장된 응답은 모두 별칭 `gpt-6-luna`로만 표기되고 `system_fingerprint`가 없어 날짜 스냅샷을 확인할 수 없다. 코드는 `gpt-6-luna-*` 이름을 허용하므로, 날짜 스냅샷을 쓸 수 있으면 spec 모델과 metadata에 고정한다.
