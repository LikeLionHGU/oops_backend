# OoPs?! 서버 아키텍처

> 기준 브랜치: `minwook` · 기준일: 2026-10-06

이 문서는 현재 저장소에 구현된 서버 구조와, 트래픽이 늘어났을 때 확장할 방향을 구분해서 설명한다. 아직 적용하지 않은 인프라는 현재 기능처럼 표현하지 않는다.

## 1. 전체 구조

```text
사용자 브라우저
      │
      ▼
Vercel 프론트엔드
      │ HTTPS
      ▼
Nginx / AWS 진입점
      │
      ▼
Spring Boot API 서버 :8080
  ├─ 영상 업로드·조회·삭제
  ├─ 분석 작업 생성·상태 관리
  ├─ 분석 결과 조합 및 리포트 생성
  ├─ WebSocket 진행률 전송
  └─ Python 분석 서버 호출
          │ 내부 HTTP :8000
          ▼
Python FastAPI 분석 서버
  ├─ Whisper 기반 STT
  ├─ PaddleOCR 기반 화면 텍스트 추출
  └─ 영상·프레임 전처리

Spring Boot ── OpenAI API
Spring Boot ── Google News RSS / Naver News API
```

현재 운영 배포에서는 Spring Boot와 Python 분석 서버가 AWS 환경에서 함께 실행되고, Python 서버는 외부 사용자가 직접 접근하는 API가 아니라 Spring Boot가 내부적으로 호출하는 분석 구성요소로 사용된다. Python 프로세스는 서버 재시작 후 자동으로 실행되도록 운영되고 있지만, 그 프로세스 관리 설정 자체는 이 저장소의 애플리케이션 코드와 별도로 관리된다.

## 2. 서버별 책임

| 구성요소 | 담당 업무 | 현재 저장 위치 또는 연결 대상 |
|---|---|---|
| 프론트엔드 | 영상 선택, 업로드 요청, 진행률 표시, 리포트 표시 | Vercel |
| Spring Boot | 외부 API, 작업 상태, DB 저장, 분석 오케스트레이션 | `oops-backend/` |
| Python FastAPI | 영상에서 STT/OCR 원천 데이터 추출 | `oops-analysis/` |
| H2/JPA | 영상, 작업, STT, OCR, 탐지 결과 저장 | 현재 로컬 파일 DB 중심 |
| 로컬 파일 저장소 | 원본 영상, 프레임, 분석 산출물 저장 | `storage.location` 설정 경로 |
| OpenAI | STT 및 텍스트·맥락 판정 | 외부 API |
| 뉴스 검색 | 논란·사실관계 확인에 사용할 참고자료 수집 | Google News RSS 또는 Naver |
| Nginx | HTTPS 종료 및 Spring Boot로 요청 전달 | 운영 서버 설정 |

## 3. 영상 1개가 처리되는 순서

1. 사용자가 영상 파일과 장르를 전송한다.
2. Spring Boot가 파일 형식·크기·확장자를 확인하고 원본을 저장한다.
3. `Video`와 `AnalysisJob`을 만들고 상태를 `PENDING`으로 둔다.
4. 백그라운드 분석 작업이 시작되면 상태가 `PROCESSING`으로 바뀐다.
5. Spring Boot가 Python 서버에 영상 경로를 전달한다.
6. Python 서버가 Whisper STT와 PaddleOCR을 수행해 타임스탬프가 있는 대본과 화면 텍스트를 반환한다.
7. Spring Boot가 룰 기반 분석, OpenAI 분석, 필요 시 뉴스 검색을 수행한다.
8. 여러 분석기의 결과를 합쳐 리포트와 타임라인을 저장한다.
9. 프론트엔드는 상태 API 또는 WebSocket으로 진행률을 확인하고 완료된 리포트를 조회한다.

작업 상태는 기본적으로 다음과 같다.

```text
PENDING → PROCESSING → COMPLETED
                    └→ FAILED
                    └→ CANCELLED
```

### 현재 작업 실행 방식

현재 `AnalysisJob`은 DB에 저장되지만, 실제 실행 대기열은 Spring Boot 프로세스 안의 `ThreadPoolTaskExecutor`가 관리한다.

```text
DB에 Job 저장
      ↓
커밋 후 @Async 실행 요청
      ↓
메모리 Executor
  ├─ 실행 중: 기본 1~2개
  └─ 대기 중: 기본 최대 50개
```

따라서 `PENDING`은 “실행을 기다리는 상태”를 나타내지만, 별도의 영속 큐에 안전하게 들어갔다는 의미는 아니다. 서버가 종료되거나 Executor가 가득 찬 상황에서는 작업이 지연되거나 재시도 대상이 될 수 있다.

장기적으로는 다음처럼 작업 상태와 실행 대기열을 분리하는 것이 목표다.

```text
DB: 작업 상태와 실행 이력
Queue: 실행 대기·재시도·중복 방지
Worker: 실제 STT/OCR/LLM 처리
```

## 4. 현재 적용된 운영 장치

- 분석은 요청 처리 스레드와 분리된 `analysisExecutor`에서 비동기로 실행한다.
- 분석 Executor의 풀 크기와 큐 크기는 `oops.analysis-executor` 설정으로 조절할 수 있다.
- 영상 업로드·YouTube 등록·재시도 API에 IP 기준 요청 제한을 적용했다.
- `X-Request-Id`를 비동기 분석 로그까지 전파한다.
- `/health`, `/api/v1/health`에서 Spring Boot, Python 분석 서버, 저장소 상태를 확인하며 Python Health 요청은 2초 제한을 둔다.
- 분석 Executor 대기열이 가득 차면 작업을 `FAILED`로 정리하고 재시도 안내를 남긴다.
- 취소 상태를 각 분석 단계 경계에서 확인하고 취소된 분석 결과의 DB 트랜잭션을 롤백한다.
- 원본 영상은 기본 24시간 후 삭제하고, 전체 산출물 정리는 별도 설정으로 관리한다. 전체 정리의 기본값은 꺼짐이다.
- Python OCR이 설치되지 않았거나 OCR 단계가 실패해도 STT 기반 분석까지는 계속 진행할 수 있다.

다만 현재 Executor의 대기열은 메모리 기반이며, 대기열 포화 시 업로드 응답은 접수 상태로 반환된 뒤 상태 조회에서 실패로 바뀔 수 있다. Health 확인은 2초, STT/OCR 요청은 최대 10분으로 분리되어 있고, 실제 미디어 요청 중단은 분석 서버가 응답하거나 timeout될 때까지 기다려야 한다.

## 5. 현재 구조의 한계

현재 구조는 데모와 초기 사용자 규모에는 단순하고 적합하지만, 다음 부분은 대규모 트래픽에서 병목이 될 수 있다.

1. Spring Boot와 Python 분석 서버가 같은 운영 환경의 자원(CPU·메모리·디스크)을 공유한다.
2. 분석 작업 큐와 요청 제한 상태가 메모리에 있어 서버가 여러 대가 되면 상태가 공유되지 않는다.
3. 로컬 디스크와 로컬 H2에 의존하므로 서버 교체·장애·수평 확장에 취약하다.
4. 외부 AI API의 지연과 한도에 분석 처리 시간이 직접 영향을 받는다.
5. 현재 사용자 인증과 영상 소유권 검사가 제품 수준으로 완성되어 있지 않다.
6. Python 분석 서버는 현재 하나의 분석 서비스로 운영되므로 STT와 OCR을 독립적으로 확장하기 어렵다.
7. 분석 전체가 하나의 긴 `@Transactional` 흐름에 묶여 있어, 영상이 오래 걸릴수록 DB 트랜잭션과 커넥션 점유 시간이 길어진다.
8. 현재 취소는 진행 중인 외부 요청을 즉시 끊지 못하므로, STT/OCR/LLM 요청이 반환된 뒤 취소를 반영한다.
9. 서버가 살아 있어도 특정 작업이 외부 API 대기나 Worker 문제로 멈출 수 있어, 작업별 heartbeat와 timeout 감지가 필요하다.

### 5.1. 작업 생명주기 개선안

현재의 단순한 상태 흐름을 운영용으로 확장하면 다음과 같다.

```text
UPLOAD_REQUEST
      ↓
JOB_CREATED
      ↓
QUEUED
      ↓
PROCESSING
      ├─ COMPLETED
      ├─ FAILED
      └─ CANCELLED
```

`PENDING` 하나로 작업 생성 직후, 메모리 큐 대기, 큐에 들어가지 못한 상태를 모두 표현하지 않도록 역할을 나누는 것이 좋다.

각 상태에서 남겨야 하는 정보는 다음과 같다.

| 상태 | 함께 기록할 정보 |
|---|---|
| `JOB_CREATED` | 생성 시각, 영상 ID, 요청 ID |
| `QUEUED` | 큐 등록 시각, 우선순위, 재시도 횟수 |
| `PROCESSING` | 시작 시각, 현재 단계, Worker 식별자, 마지막 heartbeat |
| `COMPLETED` | 완료 시각, 결과 개수, 총 처리시간, 비용 |
| `FAILED` | 실패 단계, 오류 유형, 사용자 안내문, 재시도 가능 여부 |
| `CANCELLED` | 취소 요청 시각, 취소 주체, 실제 중단 시각 |

### 5.2. 장애 상황별 처리

| 상황 | 현재 동작 또는 위험 | 우선 개선 방향 |
|---|---|---|
| Python 서버 종료 | 업로드 또는 분석 시작 시 503이 될 수 있음 | Health 확인은 2초, 분석 요청은 최대 10분 제한 적용 |
| Python 서버가 응답하지 않음 | 실제 분석 요청은 분석 timeout까지 기다릴 수 있음 | 미디어 요청 자체의 취소·중단을 Worker 구조에서 보완 |
| Executor 큐 포화 | 접수 응답 뒤 Job이 `FAILED`로 바뀌고 재시도 안내가 남음 | 큐 용량 지표와 사전 수용 응답 추가 |
| 서버 재시작 | `PENDING`·`PROCESSING` 작업을 실패 처리하고 재시도 안내 | 영속 큐 도입 후 미완료 작업 재등록 검토 |
| OpenAI timeout·rate limit | 일부 분석기가 실패하고 결과가 부분 생성될 수 있음 | 분석기별 재시도 횟수·backoff·최종 실패 사유 저장 |
| 사용자 취소 | 현재 진행 중인 STT/OCR/LLM 요청 자체를 강제로 끊지는 않지만, 요청이 끝난 단계에서 취소를 확인하고 결과 트랜잭션을 롤백함 | 외부 작업 자체를 중단하는 기능은 Worker 분리 후 검토 |
| 작업 무한 대기 | 서버 자체는 정상이어도 작업이 `PROCESSING`에 머무를 수 있음 | heartbeat와 작업별 최대 실행시간 도입 |
| 디스크 부족 | 저장 또는 프레임 생성 실패 가능 | 여유 공간을 Health 지표에 포함하고 업로드 전 상한 확인 |

### 5.3. 긴 트랜잭션을 단계별로 분리

현재 분석 파이프라인은 STT·OCR·외부 API 호출·결과 저장을 하나의 긴 트랜잭션에서 처리한다. 초기에는 동시 분석 수가 작아도 영상 길이가 늘어나면 DB 커넥션 점유와 장애 복구 비용이 커진다.

개선 목표는 다음과 같다.

```text
STT 실행 → STT 결과 저장·커밋
OCR 실행 → OCR 결과 저장·커밋
텍스트 분석 → 후보 저장·커밋
근거 검색 → 참고자료 저장·커밋
최종 집계 → 리포트 저장·커밋
```

이렇게 하면 다음 효과가 있다.

- 특정 단계만 재시도할 수 있다.
- 중간 결과를 재사용할 수 있다.
- 한 단계 실패가 전체 결과를 무조건 롤백시키지 않는다.
- 긴 외부 API 호출 중 DB 트랜잭션을 붙잡지 않는다.

### 5.4. 취소와 재시작의 처리 원칙

취소는 DB의 상태만 바꾸는 것으로 끝나지 않는다. 파이프라인의 각 단계 시작 전과 저장 직전에 취소 여부를 확인해야 한다.

```text
단계 시작 전: 이미 취소되었는가?
외부 API 응답 후: 그 사이 취소되었는가?
결과 저장 전: 아직 완료 처리해도 되는가?
```

최종 완료 처리는 다음 조건을 만족할 때만 허용한다.

```text
현재 Job 상태가 CANCELLED가 아님
현재 Job이 해당 Video의 최신 실행임
현재 단계가 실패하지 않음
```

서버가 재시작된 경우에는 현재 구현처럼 미완료 작업을 실패로 정리할 수 있다. 이후 영속 큐를 도입하면 재시도 가능한 작업만 다시 큐에 넣고, 이미 외부 API를 호출한 단계는 멱등성 키나 결과 해시로 중복 실행을 방지해야 한다.

## 6. 트래픽 증가 시 목표 구조

```text
                 ┌──────────────┐
사용자 ─────────▶│ API 서버 여러 대│
                 └──────┬───────┘
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
      Object Storage   관계형 DB     작업 큐
      원본/프레임      상태/결과      재시도/대기
                                      │
                         ┌────────────┴────────────┐
                         ▼                         ▼
                   STT/OCR Worker              LLM Worker
```

확장 순서는 보통 다음처럼 잡는 것이 현실적이다.

1. 먼저 현재 서버에서 큐 대기시간, 분석시간, CPU·메모리·디스크 사용량을 측정한다.
2. 원본 영상과 프레임을 S3 같은 Object Storage로 옮긴다.
3. H2를 운영용 관계형 DB로 교체하고 작업 상태를 DB에 영속화한다.
4. 분석 요청을 Redis Streams, SQS 등 작업 큐로 분리한다.
5. Python 분석 Worker를 여러 개로 늘리고, 필요하면 STT·OCR·LLM Worker를 분리한다.
6. API 서버와 분석 Worker를 각각 독립적으로 확장한다.

Docker, Kubernetes/EKS, GPU 서버는 위 단계에서 실제 부하와 비용을 확인한 뒤 도입할 대상이다. 지금 당장 도입한다고 해서 분석 품질이나 속도가 자동으로 좋아지는 것은 아니다.

### 대용량 업로드의 목표 처리 방식

현재는 Spring Boot가 Multipart 업로드를 받아 로컬 저장소에 저장한다. 영상이 많아지면 API 서버가 원본 파일을 직접 오래 들고 있지 않도록 다음 구조를 검토한다.

```text
브라우저
  ↓ 직접 업로드용 제한 URL
Object Storage
  ↓ 업로드 완료 이벤트
Analysis Job 생성
  ↓
작업 큐
  ↓
STT / OCR / LLM Worker
```

Object Storage와 제한 URL은 아직 현재 코드에 구현되어 있지 않다. 도입할 때는 파일 업로드 권한, 만료시간, 업로드 완료 여부, 삭제 정책을 함께 설계해야 한다.

### 분석 Worker의 단계 분리

분석을 하나의 긴 요청으로 처리하기보다 다음 Job 단위로 나누면 특정 단계만 재시도하거나 확장하기 쉬워진다.

```text
Preprocess
  ├─ Audio/STT Job
  ├─ OCR Job
  ├─ Text Risk Job
  ├─ Context Search Job
  ├─ Vision Candidate Job
  └─ Final Report Job
```

초기에는 현재 Spring Boot의 분석 파이프라인과 Python 서버를 유지하고, 실제 병목이 확인될 때 Worker를 분리한다. 특히 STT 후보가 있는 구간만 Vision 분석 대상으로 삼으면 전체 프레임을 고비용 모델에 보내는 일을 줄일 수 있다.

## 7. 주요 엔드포인트

| 목적 | 경로 |
|---|---|
| 업로드·등록 | `POST /api/v1/videos` |
| 분석 상태 | `GET /api/v1/videos/{id}/status` |
| 리포트 | `GET /api/v1/videos/{id}/report` |
| 재분석 | `POST /api/v1/videos/{id}/analysis/retry` |
| 진행률 WebSocket 연결 | `/ws` |
| 진행률 STOMP 구독 | `/topic/videos/{id}/progress` |
| 상태 점검 | `GET /health`, `GET /api/v1/health` |

업로드한 원본은 `source-retention-hours` 기준으로 별도 정리한다. 현재 기본값 24시간이며, 완료·실패 상태 영상의 원본 파일만 삭제하고 대본·리포트·OCR 프레임은 남긴다. `retention-days`는 영상 전체와 분석 산출물을 정리하는 별도 설정이며 기본값 0은 전체 정리를 끈다. 정확한 대상과 요청·응답 형식은 [API명세-구현-대조표.md](API명세-구현-대조표.md)를 기준으로 확인한다.

## 8. 확장 여부를 판단하는 지표

서버를 여러 대로 늘리거나 S3·Redis·운영 DB를 도입하는 시점은 사용자 수만으로 정하지 않는다. 다음 지표를 일정 기간 관찰한 뒤 결정한다.

| 지표 | 확장을 검토할 신호 |
|---|---|
| 분석 대기 작업 수 | 10개 이상이 반복적으로 쌓임 |
| 큐 대기시간 | 1분 이상 지속됨 |
| 업로드·상태 조회 p95 | 사용자 체감 지연이 계속 증가함 |
| Python CPU·메모리 | 80% 이상이 반복됨 |
| 저장소 사용량 | 디스크 70% 이상 또는 증가량 예측 불가 |
| 작업 실패율 | 외부 API·Worker 오류가 반복됨 |
| 서버 재시작 후 복구 | 미완료 작업이 자주 실패 처리됨 |
| 영상당 원가 | 사용자 규모에 비해 AI 호출 비용이 커짐 |

최소한 `jobId`, `videoId`, `requestId`, 분석 단계, 시작·종료 시각, 대기시간, 외부 API 실패 횟수는 공통 로그로 남겨야 한다. 그래야 “서버가 느리다”를 업로드 지연, 큐 대기, Python 처리, OpenAI 대기 중 무엇인지 구분할 수 있다.

## 9. 구현 우선순위

### 비용 없이 먼저 할 작업

1. Health 확인용 짧은 timeout과 STT/OCR용 긴 timeout을 분리한다.
2. 분석 각 단계 전후에 취소 여부를 확인하고, 취소된 Job을 완료 처리하지 않게 한다.
3. Executor 큐가 가득 찼을 때 명확한 거절 또는 대기 상태를 반환한다.
4. `PROCESSING` 작업의 마지막 진행 시각을 기록해 멈춘 작업을 감지한다.
5. 분석 전체의 긴 트랜잭션을 단계별 저장 트랜잭션으로 나눈다.
6. 사용자 인증과 영상 소유권 검사를 추가한다.

### 인프라 도입이 필요한 작업

1. 원본 영상과 프레임을 Object Storage로 분리한다.
2. H2를 운영용 관계형 DB로 교체한다.
3. 작업 상태와 실행 대기열을 Redis·SQS 등으로 분리한다.
4. STT·OCR·LLM Worker를 독립적으로 확장한다.
5. 서버가 여러 대가 되면 요청 제한과 중복 방지를 공유 저장소 기반으로 바꾼다.

현재 단계에서 가장 먼저 해결할 문제는 “서버를 여러 대로 늘리는 것”이 아니라, 작업이 생성된 뒤 대기·실행·실패·취소·재시작되는 과정을 잃지 않는 것이다.
