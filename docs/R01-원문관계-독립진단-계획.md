# 원문 관계 독립 진단 계획

기준일: 2026-10-18  
상태: 최신 독립 전제 감사37회까지 완료했다. 형식37/37 통과지만 R01의 잘못된 이유6개 모두에서 실제 질문 전제를 지지했다. 재확인4/6을 핵심 오독 해결로 세지 않는다. 뜻풀이에 맞춘 대조도1/2 불필요한 재확인이 있어 운영 연결은 보류한다. 개정44의 성능 우위가 없다는 이전 결론도 유지한다.

## 왜 별도 진단이 필요한가

최근 48회 비교에서 실제 쟁점 R01-166·R01-178은 두 지침 모두 PASS 0/6이었다. 비교안은 전체 응답 계약 통과도 16/24에서 12/24로 낮아 미채택됐다.

그보다 앞선 `sourceUnderstanding` 실험은 같은 검증 응답에 행위 이해 기록과 최종 판단을 함께 요청했다. 실제 R01 응답은 166을 `DIRECT_REQUEST`로, 178을 `SELF_OFFER`로 기록했지만 두 쟁점 모두 경고를 유지했다. 합성 대조의 일부는 행위 기록이 반복마다 달랐고, 전체 계약 통과는 OFF 24/28·ON 20/28이었다. v1/v2 관계 기록도 같은 판정 호출 안에서 생성됐다. 이 방식은 기록과 판단이 서로 영향을 주는지, 관계 이해가 처음부터 틀렸는지를 분리하지 못한다.

이번 진단은 먼저 **원문 대화에서 발화 기능과 연결만 추출**한다. 이 출력에는 검토/정상 판정을 넣지 않는다. 결과를 사람 승인 관계와 대조하면 원문 이해 오류를 따로 볼 수 있다. 그 다음에야 이 관계 기록이 판정을 돕는지 별도 실험할 수 있다.

## 첫 진단 입력

사용자가 이미 검수한 관계 설명이 분명한 다섯 조건만 점수 대상으로 사용한다.

| 조건 | 입력 범위 | 승인된 관계 기준 |
|---|---|---|
| R01-166 | 실제 대화의 저장 전사 156~187, 32줄 전체 | 165의 뜻 질문에 166이 뜻풀이로 답함. 질문 형태의 문구가 현재 청자에게 실제로 한 사적 질문이라는 근거는 없음 |
| R04 | 합성 대화 2줄 | 현재 청자에게 사적 정보를 묻고 보여 달라고 직접 요청 |
| R05 | 합성 대화 3줄 | 질문 표현의 뜻을 설명하며, 현재 청자에게 그 내용을 묻지 않는다고 명시 |
| R06 | 합성 대화 2줄 | 과거 질문을 인용·언급하고, 따라 하려는 것이 아니라 사생활 질문을 피하자는 취지를 밝힘 |
| R08 | 합성 대화 3줄 | 처음에는 현재 청자에게 직접 요청함. 청자가 거절한 뒤 화자는 주제를 바꿈. 뒤의 중단을 보존하고 지속 요구로 만들지 않음 |

이들은 개발용 승인 기준이지 독립 정답셋이나 블라인드 평가가 아니다. R01-178, R03, R07은 최종 PASS 승인은 있으나 구체적인 행위 관계까지 따로 승인된 것은 아니므로 첫 점수에는 넣지 않는다. 이들을 점수에 포함하려면 관계 해석을 별도로 사람 검수해야 한다.

## 진단 요청

요청에는 선택된 후보, 비판 가설, 맥락 사전, 이전 모델 답변, 정답 라벨, 최종 판단 계약을 넣지 않는다. 입력은 원문 ID·시간·텍스트와 중립적인 초점 발화 ID뿐이다. 초점 ID는 읽을 발화를 지정할 뿐 위험 후보라는 뜻은 아니다. 영상·음성도 보내지 않는다. 모델에는 문제나 위험을 찾으라고 하지 않고, 주어진 대화 안에서 발화가 무엇에 답하고 어떤 행위를 하는지만 묻는다.

첫 v1 요청 지침:

```text
각 초점 발화의 대화상 기능과 원문 안의 연결만 기록한다.
질문형 문구가 뜻풀이·정의·인용의 내용으로 언급된 경우와,
현재 듣는 사람에게 실제 질문이나 행동을 요청한 경우를 구별한다.
화자가 자기 행동을 제안한 경우와 듣는 사람에게 행동·정보를 요구한 경우를 구별한다.
연결은 입력에 있는 원문 ID로만 표시한다. 화자 신원, 의도, 동의,
억양, 표정, 실제 행동은 자료에 없으면 추정하지 않는다.
논란·위험·정상 여부나 도덕 평가를 반환하지 않는다.
구분할 수 없으면 UNCLEAR로 반환한다.
```

설계 응답 형태:

```json
{
  "observations": [
    {
      "anchorId": "입력에 있는 초점 발화 ID",
      "function": "DEFINITION_OR_EXPANSION",
      "links": [
        {"segmentId": "입력에 있는 뜻 질문 ID", "relation": "ANSWERS_MEANING_QUESTION"}
      ],
      "contentUse": "MENTIONED_PHRASE",
      "evidenceIds": ["입력 원문 ID"]
    }
  ]
}
```

위 JSON은 구조 예시다. 실제 v2는 `response_format=json_schema`, `strict=true`로 필수 필드와 허용 enum을 전달한다. JSON mode와 스키마 준수의 차이는 [OpenAI 공식 문서](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=chat)를 따른다. `function`은 뜻풀이/직접 요청/자기 제안/보고·인용/자기 설명/기타/불명을, `contentUse`는 현재 행위/문구 언급/과거 보고/불명을 구분한다. 서버는 anchor 보존과 원문 ID 범위를 추가 검사한다. 형식 통과가 의미 정답을 보장하지는 않으며 기준 대조와 원문 검토를 별도로 기록한다.

## 실행 및 판정 방법

1. 고정된 다섯 입력을 각각 같은 요청으로 세 번 실행한다. 총 15회이며 반복은 모델의 결과 변동을 보는 용도다. 반복 순서는 조건별로 섞어 시간에 따른 변화를 한 조건에 몰지 않는다. 같은 실제 대화의 반복을 독립 사례 수로 세지 않는다.
2. 행위 기능 정확도, 연결 ID·관계 정확도, 언급된 질문을 실제 질문으로 바꾸는 오류, 자기 제안을 청자 요구로 바꾸는 오류, 미제공 화자·의도 추정을 따로 집계한다.
3. JSON/ID 계약 통과율은 의미 일치와 분리한다. 계약 실패나 `UNCLEAR`를 정답으로 바꾸지 않는다.
4. R01-166이 뜻풀이 연결로 안정적으로 읽히지 않으면 판정 프롬프트나 사전을 더 붙이지 않고 원문 관계 추출 오류로 기록한다.
5. 관계 추출이 맞아도 다음 판단 단계가 이를 뒤집는지는 이 시험에서 주장하지 않는다. 그 효과를 보려면 사람 승인된 관계 기록을 고정 입력으로 넣는 별도의 판정 비교가 필요하다.

## 이번 결과가 알려주는 것과 다음 작업

이 고정 대화에서 독립 관계 추출은 R01-166을 뜻풀이로 읽을 수 있었다. 앞선 검증 호출의 오독을 STT 또는 사례 사전 부족만으로 설명할 수 없다는 근거가 생겼다. 다만 검증 요청과 이번 요청은 목표·출력 계약이 다르므로, 어느 입력 요소가 원인인지 단정하는 통제 비교는 아니다. R01-178 자기 제안은 이번 시험 대상에 없었다.

다음 비교는 이번 관계 기록을 고정한 뒤 **최종 판단에 관계 기록을 제공했을 때 R01-166 PASS와 직접 요청 R04/R08 검토가 함께 유지되는지** 확인하는 것이다. 원문·후보·가설·사전·기존 검증기는 같게 두고, 관계 기록 제공 여부만 바꿔야 한다. 뜻풀이 enum 하나로 자동 PASS시키거나 R04의 연결 라벨을 사후 변경하지 않는다. 이번 단계에서는 해당 추가 유료 비교나 운영 연결까지 진행하지 않았다.

다음에는 요청 전제를 더 붙이거나 즉흥 재호출하지 않고, 원문 관계 독해와 최종 이유의 사실 주장을 어떻게 분리·대조할지 설계부터 검토한다. 감사 상태와 설명의 불일치, 원문 정보 부족과 반증의 혼동을 별도 실패로 남긴다. 문자열 기반 강제PASS나 특정 영상 전용 정답 주입은 하지 않는다. 추가 유료 호출은 승인된37회에서 종료했다.

원본 HTTP 응답37개와 저장 JSON 내용·모델명을 모두 무료 대조했고, 저장 응답의 분기를 재실행한 결과도 최초 감사와 일치했다. 코드·스키마·분기·입력 보존 등 전체 무료 회귀1,005개도 실행 전 통과했다. 이것은 의미 검증 성능을 대체하지 않는다. 사례별 이유·전사·응답·동결 계획은 Git에 포함하지 않는다.

## 원문 독해 우선 분리안 — 입력 경계 구현·새 판단 계약은 미완성

2026-10-18 후속은 `SourceFirstReviewBoundary` test 전용 시제품이다. 새 모델 호출이나 운영 분기는 추가하지 않았다. 원문 독해→독해 결과 고정→과거 판단 없이 새 판단이라는 흐름에서 **입력 경계와 출처 결합만** 구현했다. 후속 모델의 판단 계약·실제 리포트 연결은 아직 없다.

1. 독해 입력은 기존 독립 추출기의 `focusId`와 원문 `segments`만 사용한다. 후보 가설·선택 근거·기존 판단 이유·사전·정답은 구조적으로 복사하지 않는다. 원문 ID·텍스트·시간은 보존한다.
2. 독해 결과는 원문 입력·출력 내용·생성 결과 출처의 해시와 결합한다. 복사본을 수정하거나 원문/시간/출처를 바꾸면 검사가 실패한다. 무결성 검사지 모델의 해석이 참이라는 인증은 아니다.
3. 새 판단용 입력은 전체 raw·anchor·고정 독해 결과만 포함한다. 잘못된 과거 가설이나 이유를 그대로 받아 재검토하는 방식이 아니다. 사전도 현재 시제품에서는 제외했으며, 영구 제거를 결정한 것은 아니다. 독해 후 새 판단에서 어떻게 참고할지는 별도 설계 대상이다.
4. 후속 단계가 실제 사용한 기능·용법을 다르게 선언하면, 원문 ID와 짧은 이의 이유를 요구한다. 유효한 이의도 `SOURCE_RECHECK_REQUIRED`로 남길 뿐 독해 결과를 덮어쓰지 않는다. 이의 없이 의미를 바꾼 선언은 `INCOMPLETE_BINDING`이다. 원문 독해 자체가 UNCLEAR여도 재확인이 필요하다.
5. 같은 기능·용법 선언은 `CONSISTENT_DECLARATION`일 뿐이다. 모든 분기는 `publicationAuthorized=false`이고, 뜻풀이·인용이라는 이유로 자동PASS시키지 않는다.

**중요한 미완성 경계:** 이 분기는 선언된 기능·용법과 출처의 일치만 검사한다. 후속 모델이 선언은 뜻풀이로 맞추면서 이유에서는 실제 질문이라고 쓰는 경우까지 탐지하지 못한다. 그 때문에 새 판단 계약과 선언-이유 의미 검증을 완료했다고 표현하지 않으며 운영에 연결하지 않는다. 기존 v1/v2/v3의 형식 검사 문제를 새 필드만으로 해결했다고 주장하지 않는다.

새 독해를 다시 호출하지 않고, 이전 독립 추출 결과의 조건별 **첫 번째 값**으로5개 입력을 준비했다. R04의 OTHER 관계값도 그대로 보존했고 정답에 가까운 반복을 선택하지 않았다. R01은 기존 첫 뜻풀이 추출값을 사용한 것이지 이번에 새로 맞힌 결과가 아니다. 사람 정답·위험 판정은 입력에 넣지 않았다.

- 입력 묶음: `datasets/controversy/experiments/source-first-boundary-inputs-20261018/stage-bundle.json`.
- SHA-256: `49420803861035076abfa68e5dc9a99d4d8cbc1be75aa9ce71e192d0479c05d9`.
- 5개 모두 기존 독해 요청·첫 추출값·원문과 무료 대조 일치. `judgmentState=NOT_RUN`, `judgmentContractImplemented=false`, 새 판단0회·외부 호출0회·추가 사용량 비용0이다.
