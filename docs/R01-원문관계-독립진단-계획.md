## 무료 점검: R01과 합성 대조는 무엇이 다른가

2026-10-18 저장된35회 시험과 후속 합성12회 기준선의 요청·원응답을 로컬에서 대조했다. 새 모델 호출·입력 수정·정답 변경은 없다.

R01 원문만 경고1회는 ACTUAL_REQUEST로 오독했고, 독해 제공 경고1회는 뜻풀이를 보존한 채 EXPRESSION_CONTENT로 경고했다. 두 경고는 각각165·166만 evidenceIds로 제시했다. 175의 자기 설명이나178의 제안을 근거로 옮겨왔다고 주장할 직접 증거는 없다. 긴 뒤 문맥이 모델 내부 판단에 영향을 줬을 가능성은 남지만, 출력만으로 영향 여부를 알 수 없다.

원문만 PASS2회는172·173의 “없을 무” 설명도 뜻풀이 근거로 사용했다. 이것은 별도의 말장난·자기 답변과 연결될 수 있으므로, 166의 원래 약어 풀이를 직접 입증하는 유일 근거처럼 취급하지 않는다. 뜻 질문165→166의 연결과 이후 응답의 관계는 구분해서 검토할 필요가 있다. 이 메모로 기존 사용자 PASS 승인을 바꾸지는 않는다.

### 현재 가설과 아직 증명하지 못한 것

1. **발화 기능 추론:** 실제 R01은 물음표가 붙은 문장의 뜻풀이 사용을 주변 문답에서 읽어야 한다. 직접적인 정상 해설을 넣은 합성 대조보다 오독 가능성이 있다는 가설이다. 단서의 명시성이 원인이라고 실험으로 확정한 것은 아니다.
2. **독립적인 내용 경고 기준:** 뜻풀이를 맞게 읽어도 민감한 내용을 별도 경고할지 흔들린다. 독해만 개선해서 해결되는지와 별개다. 새 소재 안내를 자동 연결해 해결됐다고 볼 수 없다.
3. **초점·문맥 구성:** R01은 초점 뒤에 다른 사적 소재 발화가 있지만 A조건은 마지막을 초점으로 삼았다. 순서·범위 효과는 아직 분리 시험하지 않았다.
4. **반복 변동:** 조건당3회와 서로 다른 소재의 작은 개발 대조라 우연 변동과 일반적 성능 차이를 분리하기 어렵다. ‘짧으면 해결’·‘사전 부족’·‘뒤 문맥 오염’ 중 어느 것도 원인으로 확정하지 않는다.

### 다음 실험을 한다면 — 같은 원문에서 범위만 변경

우선 새 프롬프트·사전·해설을 넣지 않는다. 동일한 R01의 원문만 조건에서 156~187 전체 창과 165~166 최소 문답 창을 비교하는 진단을 고려한다. 초점166·문장·ID·원래 시간·SYSTEM·스키마·모델은 고정하고 문맥 범위만 바꾼다. 독해 기록은 양쪽 제외한다. “이건 뜻풀이” 같은 해설을 원문에 삽입하거나 STT를 교정하지 않는다.

최소 창은 기존 전체 창의 승인 정답을 자동 상속하지 않는다. 사용자에게 두 줄만으로 관계를 판단할 수 있는지 먼저 확인해야 한다. 범위 축소가 필요한 맥락을 지우는 실험일 수 있으므로, 결과를 운영용 자르기 규칙으로 바로 승격하지 않는다. 기능 독해·별도 경고 이유·계약을 각각 비교하며 동일 PASS라는 이유만으로 같은 이해라고 보지 않는다. 아직 해당 새 계획을 동결하거나 유료 실행하지 않았고 예산도 승인받지 않았다.

결론: **현재 확인된 것은 합성 대조에서 명시적 단서를 따라 구별할 수 있다는 점이다. 실제 R01에서 필요한 암묵적 기능 추론과 독립적인 내용 경고의 경계는 별도 검증이 남았다.** 운영 코드·정답·맥락 사전은 그대로 둔다.

## R01 표현 자체 경고의 근거 재검토

2026-10-18 저장 응답 `R01-166-FROZEN_SOURCE-2`를 입력32줄·현행 `ReviewJudgmentPolicy.PROMPT`와 다시 대조했다. 추가 모델 호출은 없다. 아래는 개발 보조자의 검토 의견이며 새 사용자 승인이나 자동 의미 평가 결과가 아니다.

### 응답은 무엇을 이해했고 무엇을 경고했나

응답은 165의 “오펜무가 뭐예요?”에 166이 약어를 풀어 답했다고 설명하고, “실제 청자에게 묻는 문장이 아니라 언급된 표현의 뜻풀이이므로 ACTUAL_REQUEST는 아니다”라고 명시했다. **이 응답에 실제 질문으로 오독했다는 평가는 적용하지 않는다.**

별도 경고의 이유는 “속옷 색을 묻는 구체적 사적 질문 내용 자체가 검토 대상”이라는 것이다. 실제 요구·강요가 있었다는 주장은 하지 않았지만, 내용이 사적이라는 사실 외에 이번 뜻풀이를 검토해야 하는 독립적인 이유는 설명하지 않았다.

| 검토 항목 | 이번 응답의 근거 | 개발 보조자 검토 |
|---|---|---|
| 뜻풀이/실제 요구 구분 | 앞 질문과 뜻풀이 연결, ACTUAL_REQUEST 부정 | 이 구분은 보존됨 |
| 표현 자체의 별도 문제 | 속옷 색이라는 사적 질문 내용 | 민감한 소재의 등장과 구별되는 근거 설명 부족 |
| 구체적 성적 모욕·대상화 등 | 유형에 해당하는 별도 연결을 제시하지 않음 | 없다고 단정하지 않되 응답이 입증한 것으로 세지 않음 |
| 실제 개인정보 노출 | 특정인의 속옷 색을 공개했다는 근거 없음 | 질문 문구의 뜻풀이를 정보 노출로 바꿀 수 없음 |
| 뒤의 자기 설명·제안 | 175·178·179는 입력에 있지만 해당 응답의 근거는165·166 | 별도 제안의 검토 이유로 현재 뜻풀이 경고를 사후 정당화하지 않음 |
| 시청자·노출 장면·억양 | 확인 자료 없음 | 미성년자 시청·실제 노출·불쾌한 표정 등을 추정해 보강하지 않음 |

따라서 이 응답의 현재 상태는 **독해 선언과 이유의 핵심 구분은 일치 / 표현 자체 경고의 독립 근거 설명 부족 / 기존 PASS 기준과 불일치 / 출처 해시 형식 오류 별도**다. “뜻풀이인데 경고했다”는 이유로 오류를 확정하지 않고, 반대로 뜻풀이를 이해했다는 이유로 경고 근거까지 타당하다고 인정하지 않는다. 기존 PASS 승인은 유지한다. 새 근거 타당성 상태 `PENDING_HUMAN_REVIEW`도 사용자 재검수 전에는 바꾸지 않는다.

### 다음 사람 검수에서 확인할 경계

- 뜻풀이를 인정한 상태에서도 이 원문에 독립적인 내용 검토 이유가 있는가? 있다면 어느 표현·연결이 단순한 사적 소재 언급을 넘어서는가?
- 내용 수위를 보고 싶은 제품 요구라면 이를 논란 검토와 같은 기준으로 판단할 것인가, 별도 선택 필터로 제공할 것인가? 아직 어느 방향으로도 구현하거나 승인된 것으로 보지 않는다.
- 실제 요구·피해·모욕이 없는 경우에도 검토할 수 있지만, 무엇이 문제인지 설명 없이 ‘성적/사적 소재이므로’라는 이유만으로 판단하지 않는다. 반대로 인용·뜻풀이도 자동 면책은 아니다.

후속 대조는 동일 소재의 뜻풀이, 실제 상대 요청, 비판적 인용과 별도 표현 문제가 있는 인용을 구별하도록 설계해야 한다. 어떤 대사를 정답으로 삼을지는 검수한 뒤 확정하며 이번에는 새 정답·프롬프트·운영 규칙을 추가하지 않았다.

## 평가 축 분리 — 독해 성공과 판단 기준 불일치는 다르다

2026-10-18 사용자 피드백 반영. 기존35응답과 승인된 PASS 라벨은 수정하지 않고 무료 재집계만 한다. 경고했다는 사실만으로 독해 오류나 잘못된 근거라고 판정하지 않는다.

| 평가 축 | 기록 방법 | 확대 해석하지 않을 것 |
|---|---|---|
| 발화 기능 독해 | 승인된 function/contentUse와 모델 선언의 일치 | 전체 이유·관계·맥락 이해까지 맞았다는 보증 아님 |
| 개발 기준 일치 | 기존 expectedDecision과 응답 decision 대조 | 불일치가 곧 독해 오류·객관적 오판은 아님 |
| 근거 타당성 | 원문 관계 보존, 표현 자체의 독립적 검토 이유, 정상 해석과 구분되는 구체성을 사람 검수 | EXPRESSION_CONTENT라는 이름만으로 타당성 자동 승인하지 않음 |
| 출력 형식·출처 | 기존 계약 검사 결과 그대로 | 형식 실패가 독해 실패는 아니며 형식 통과도 의미 정확성을 보증하지 않음 |

R01 원문만 조건은 독해 선언2/3 일치, 고정 독해 조건은3/3 일치다. 최종 PASS는 양쪽2/3이지만 이 지표 하나로 독해의 진전을 가리지 않는다. 고정 독해에서 경고한1회는 **독해 선언 일치 + 표현 자체 검토 제안 + 기존 PASS 기준 불일치 + 출처 해시 형식 오류**로 각각 기록한다. ‘뜻풀이인데 경고해서 오류’가 아니라, 별도 내용 검토 이유를 승인할지 재검수할 항목이다.

근거 타당성의 자동 채점은 하지 않는다. 기존35응답 모두 새 근거 검수 상태는 `PENDING_HUMAN_REVIEW`다. R01의 표현 자체 검토 제안도 아직 타당/부당 어느 쪽으로 새 승인하지 않았다. 표현 자체 검토를 허용할 때는 어떤 내용 특성과 게시 맥락 때문에 독립적인 검토가 필요한지 설명해야 하며, 인용된 질문을 실제 상대 요구로 바꿔서는 안 된다. 뜻풀이·인용도 무조건 PASS가 아니다.

테스트 전용 집계에 `readingDeclarationMatchesApprovedFunction`, `expressionReviewWithMatchingReading`, `reasonValidityPendingHumanReview`를 추가했다. 기존 응답·계획·판단 프롬프트·정답·운영 경로는 그대로다. 분리 집계는 비공개 결과 폴더의 `separate-axes-audit.json`에 보존한다. 무료 전체 회귀1,020개 실패0이며, ‘독해 일치+경고’와 ‘PASS+독해 불일치’를 분리하는 테스트2개를 추가했다. 특정 기준에 따른 평가와 사람 검수의 구분은 [OpenAI 공식 평가 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices)을 참고했다.

## 새 판단 계약35회 결과

2026-10-18 승인된 새 추정 상한 $0.50 안에서 GPT-6 Luna 35회 호출을 완료했다. 형식 확인1회, 승인된5조건 × 원문만/고정 독해 제공 ×3회, 오염 독해 대조4회다. 영상·음성·사전·이전 후보 가설·판정 이유·정답 라벨은 전송하지 않았다. 고정 독해는 이전 독립 추출 결과를 재사용했다.

## 진단 요청

요청에는 선택된 후보, 비판 가설, 맥락 사전, 이전 모델 답변, 정답 라벨, 최종 판단 계약을 넣지 않는다. 입력은 원문 ID·시간·텍스트와 중립적인 초점 발화 ID뿐이다. 초점 ID는 읽을 발화를 지정할 뿐 위험 후보라는 뜻은 아니다. 영상·음성도 보내지 않는다. 모델에는 문제나 위험을 찾으라고 하지 않고, 주어진 대화 안에서 발화가 무엇에 답하고 어떤 행위를 하는지만 묻는다.

첫 v1 요청 지침:

```text
각 초점 발화의 대화상 기능과 원문 안의 연결만 기록한다.
질문형 문구가 뜻풀이·정의·인용의 내용으로 언급된 경우와,
현재 듣는 사람에게 실제 질문이나 행동을 요청한 경우를 구별한다.
화자가 자기 행동을 제안한 경우와 듣는 사람에게 행동·정보를 요구한 경우를 구별한다.
연결은 입력에 있는 원문 ID로만 표시한다. 화자 신원, 의도, 동의,
억양, 표정, 실제 행동은 자료에 없으면 추정하지 않는다.
논란·위험·정상 여부나 도덕 평가를 반환하지 않는다.
구분할 수 없으면 UNCLEAR로 반환한다.
```

설계 응답 형태:

```json
{
  "observations": [
    {
      "anchorId": "입력에 있는 초점 발화 ID",
      "function": "DEFINITION_OR_EXPANSION",
      "links": [
        {"segmentId": "입력에 있는 뜻 질문 ID", "relation": "ANSWERS_MEANING_QUESTION"}

      "contentUse": "MENTIONED_PHRASE",
      "evidenceIds": ["입력 원문 ID"]

```

위 JSON은 구조 예시다. 실제 v2는 `response_format=json_schema`, `strict=true`로 필수 필드와 허용 enum을 전달한다. JSON mode와 스키마 준수의 차이는 [OpenAI 공식 문서](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=chat)를 따른다. `function`은 뜻풀이/직접 요청/자기 제안/보고·인용/자기 설명/기타/불명을, `contentUse`는 현재 행위/문구 언급/과거 보고/불명을 구분한다. 서버는 anchor 보존과 원문 ID 범위를 추가 검사한다. 형식 통과가 의미 정답을 보장하지는 않으며 기준 대조와 원문 검토를 별도로 기록한다.
