# 문맥 제한과 미평가 분리 — 2026-10-23

## 수정 이유

114번은 후보 검증 REVIEW_REQUIRED/PASS를 모두 받았지만 문맥 창 제한만으로 두 anchor를 미확인에 넣었다. 115번은 전체 구간을 탐색하고 후보가 없었지만 배치 문맥 제한 때문에 PARTIAL이었다. 제한된 문맥으로 정상 처리한 것과 응답 누락을 구분해야 한다.

## 커버리지 계약 변경

- 창 크기·시간·주변 구간 제한 자체는 처리 실패가 아니다. 후보 엔진은 제한 횟수와 안내를 보존하되, 그 이유만으로 `unassessedSegmentIds`에 추가하지 않는다.
- 응답 누락, 계약 실패, 실제 탐색 누락, 잘림, 예산 제외, 판단 UNCERTAIN, 기존 충돌 처리는 유지한다. 성공 응답을 받았다는 이유로 같은 anchor의 다른 실패를 지우지 않는다.
- 맥락 사전 분석기는 처리 미완료 안내와 문맥 한도 안내를 별도 경로로 반환한다. 실제 후보 예산 제외·응답 누락은 계속 PARTIAL이다.
- 정상 처리에 문맥 제한만 있으면 SUCCESS와 `SPEECH_REVIEW_CONTEXT_LIMITED` 경고를 함께 반환한다. SUCCESS는 안전 보장·문맥 충분성 보장이 아니다.
- 여러 분석기가 같은 단계를 공유해도 제한 경고를 보존한다. 실제 미완료가 함께 있으면 기존 PARTIAL/FAILED 코드가 우선한다.

프롬프트, 사례집, 실제 창 크기, 모델 호출 횟수, 카드 판단·병합 규칙은 바꾸지 않았다. `limited`는 입력 구성 과정의 한도 이력이므로 의미상 필수 문맥이 빠졌다는 판단으로 해석하지 않는다. 모델이 필수 정보 부족으로 UNCERTAIN을 반환하면 계속 미평가로 남는다.

## 검증 범위

`./gradlew test bootJar --offline` 통과: Java 1,206건, 실패·오류·스킵 0. 제한 후보의 PASS·미평가 분리, 제한 경고의 API 코드, 동일 단계 집계 시 경고 보존, 실제 실패 우선, 저장 응답 재생을 포함한다. 입력의 `promptRevision`도 그대로 두어 요청 내용이 바뀌지 않았음을 검사했다.

무료 단위·파이프라인 회귀와 기존 저장 요청/응답 재생으로 확인한다. 재생은 같은 요청 JSON·시스템과 과거 응답을 사용해 카드 생성·fusion·DTO를 통과시키며, 역사적 PARTIAL 중 한도만 원인인 처리 상태의 변경을 명시적으로 검사한다. 모델 정확도 향상이나 새 실제 분석 결과를 뜻하지 않는다.

114·115 자체의 DB 결과를 다시 쓰거나 유료 재분석하지 않는다. 원래 실행 기록은 [전체 전사 결과](전체-저장전사-재분석-114-115.md)에 보존한다.

## 적용

Spring 재시작 후 새 실행부터 적용한다. Python 변경은 없다. `analysis_coverage.context_limited` nullable 컬럼이 추가된다. local/dev의 `ddl-auto=update`는 자동 추가하고, 운영 수동 적용 시 [마이그레이션](migrations/2026-10-23-context-coverage.sql)을 먼저 검토한다. 기존 NULL은 한도 정보 미기록이며 과거 상태를 일괄 SUCCESS로 변경하지 않는다.
