## 무엇을 한 버전으로 묶는가

같은 결과를 재현하려면 사전 JSON만 보관해서는 안 된다. 아래 구성을 함께 고정한다.

| 묶음 | 저장할 내용 |
| --- | --- |
| 데이터 | 사건 연구 원장·범용 패턴·검색용 사례·정상 대조의 schemaVersion 및 내용 해시 |
| 근거 | 원문/출처/검수 상태, 입력 해시, 허용 구간·anchor·후보와 선택된 지칭어 |
| 파이프라인 | 추출 → 후보 탐색 → 근거 선택 → 판단 → 계약 검증 → 묶음/발행, 단계별 활성 설정 |
| 실행 | 코드 커밋, 프롬프트 전문/해시, 모델·reasoning·출력 상한·입출력 계약, 사전 검색/선별 설정 |
| 평가 | 고정 정답/정상 대조 버전, 원응답·요청·감사·채점 해시, 반복별 성공/오류·의미 검수·비용/지연 |
| 승인 | CANDIDATE/STABLE/REJECTED, 승인자·승인 시점·보류 이유, 운영에 실제 반영된 버전 |

토큰/비용 및 원응답처럼 연구용인 자료는 Git 제외 private 디렉터리에 보존한다. Git에는 코드·스키마/검사기·문서·민감정보 없는 버전 정보만 넣는다. API 키나 원댓글/작성자 자료를 기준 버전 manifest에 넣지 않는다.

현재 실행기는 요청·원문·선택 근거·receipt·provider 원응답·Java 감사·채점을 이미 저장한다. **전체 추출/탐색/병합까지 재생한 것은 아니며, STABLE 승격을 자동 관리하는 manifest 검사기는 아직 구현하지 않았다.** 아래는 그 승격 절차와 향후 기록 계약이다.

## 승격 전 확인

1. B/C/D와 승인된 정상 대조를 고정한다. C의 정상 음식 리뷰·단일 메뉴 안내도 별도 입력으로 포함해야 한다. 현재 B 중심 정상 6개만으로 C의 정상 경계까지 검증했다고 하지 않는다.
2. 후보/근거/계약 오류와 실제 PASS·UNCERTAIN을 따로 센다. 원문에 지칭어가 없는 경우와 선택기가 지칭어를 놓친 경우를 구분한다.
3. 고정 B/C/D 각 3회 유효 검토와 정상 대조 반복을 최소 개발 기준으로 삼고, 별도 재실행에서도 같은 경계를 확인한다. 이 반복 수는 통계적 정확도 보증이 아니다.
4. 인용·대상·쟁점 연결·정상 해석 대조를 사람이 확인한다. SAME_ISSUE 또는 assistant 관찰만으로 독립 정답 승인을 만들지 않는다.
5. 전체 실제 영상 경로에서 탐색 누락·중복·시간 표시·병합/발행·취소/실패 처리를 확인한다. 단일 후보 시험만 통과하면 전체 파이프라인 승인으로 승격하지 않는다.
6. 시간·비용은 버전별 조건을 함께 기록한다. 유효 탐지 개선 없이 호출 수가 늘면 그 비용도 판단한다.

전체 승인 후에만 STABLE로 기록한다. 실패 원응답·이전 기준 버전은 보존하고 수정된 결과로 소급 대체하지 않는다. 변경 하나를 시험할 때 나머지 입력·정답·모델·사전은 고정한다.

## 사례가 늘어날 때

새 사건을 연구 원장에 추가 → 기존 패턴에 해당하는지 검수 → 기존 패턴의 적용 조건/정상 경계 보강 또는 새로운 메커니즘만 추가 → 검색용 짧은 사례에 연결 → 새 검토 대상과 정상 대조를 평가 세트에 추가 → 이전 기준과 회귀 비교 → 검수/승격 순서다.

사례 수가 늘었다고 패턴을 하나씩 복제하지 않는다. 댓글은 반응 근거이며 영상 원문이나 검증된 사실로 승격하지 않는다. 사전 예시는 현재 영상의 근거를 대신하지 않는다. 개발에 이미 사용한 사건과 별도 검증 사건은 구분해 데이터 누출·과적합을 점검한다.

안정화 버전의 구조도 영구 불변은 아니다. schema/검색/파이프라인을 바꿀 때는 별도 버전으로 이전하고 기존 회귀 기준을 재검증한다. 현재 후보 상태와 과거 예산은 [실험 기록](AI-분석-실험-기록.md)을 따른다.
