# OoPs?! 기술 차별성 검증안

> 기준 브랜치: `minwook` · 작성일: 2026-10-06 · 상태: 전략 가설, 구현·성능 우위 미검증

> 2026-10-08 최신 현황: 원문 근거 계약·대화 묶음 판정·OCR 영역 선별·로컬 진단은 작업 트리에 반영됐지만, 독립 데이터셋/유사 사례 검색/성능 우위는 검증되지 않았다. ID 9에서 B 누락 유지·D 회귀가 있어 ‘우리만의 정확도 우위’로 홍보하지 않는다. 아래 차별성은 검증할 가설이다. PostHog는 고객의 사용/이탈·검수 유용성 측정을 돕는 후보이지 탐지 정답 생성기가 아니며, HyperFrames를 붙인 것 자체도 기술적 독점 우위가 아니다. [브랜치 비교·도구 적용 검토](main-minwook-비교-및-도구-적용-검토.md)에 고객 검증 연결안과 아직 미구현인 범위를 정리했다.

## 1. 현재 제품에 대한 평가

현재 구조를 “STT와 OCR로 텍스트를 추출하고, GPT로 재분석해 영상 구간에 결과를 표시하는 서비스”라고 설명하면, 기술 중심의 투자 판단을 설득하기 어렵다. 외부 구성요소를 연결해 작동하는 제품을 만든 것은 구현 성과지만, 다른 팀이 쉽게 재현하기 어려운 경쟁력이 있다는 증거는 아직 부족하다.

문제는 STT·OCR처럼 널리 쓰이는 기술을 선택했다는 사실보다, 그 구성요소 위에서 OoPs?!가 어떤 어려운 문제를 독자적으로 해결하고 있는지가 분명하지 않다는 것이다. 결과 병합, 원문 인용 검증, 실패 처리, 파이프라인 정돈은 필요한 기본기다. 그 자체를 투자자가 인정할 핵심 기술이라고 주장하지 않는다.

사용자의 현재 문제의식은 다음과 같이 정리한다.

> “작동하는 서비스는 만들었지만, 흔한 기술로 추출한 텍스트를 GPT에 보내는 구성만으로는 투자할 이유를 설명하기 어렵다. 기능을 더 붙이는 수준을 넘어, 우리가 직접 해결하고 증명할 기술 문제가 필요하다.”

따라서 다음 세 가지를 각각 검증한다.

| 검증 대상 | 현재 판단 | 필요한 증거 |
|---|---|---|
| 구현 가능성 | 업로드·분석·리포트 흐름이 존재함 | 반복 가능한 실제 시연 |
| 제품의 유용성 | 실제 검수 품질·시간 절감은 충분히 검증되지 않음 | 사람이 판정한 사례, 제작자 사용 결과 |
| 지속 가능한 경쟁력 | API 조합만으로는 설명하기 어려움 | 비교 성능, 확보 가능한 고유 데이터, 반복 사용과 개선의 연결 |

이 문서는 현재 투자 가치가 입증됐다는 주장이 아니다. 기술적 차별성을 확보할 수 있는지 확인하기 위한 실험 방향이다.

## 2. 집중할 문제

첫 기술 가설은 **한국어 영상에서 일반적인 평가가 특정 사람·지역·집단에 대한 공격으로 바뀌는 맥락을 찾아내는 능력**이다.

| 발언의 흐름 | 구분해야 할 점 |
|---|---|
| “제 입에는 별로였어요.” | 개인 취향을 설명하는 음식 평가 |
| “이 가격에 이걸 먹는 건 아깝다.” | 특정 상품에 대한 강한 부정 평가, 곧바로 비하로 확정하지 않음 |
| 음식 평가 뒤에 지역 주민의 생활·수준을 낮추는 발언이 이어짐 | 평가 대상이 음식에서 사람·집단으로 확대되는지 확인 |

위 예시는 기준 초안이며 문구별 고정 정답이 아니다. 실제 문맥과 사람의 검토로 판단한다. 과거 논란 영상이라는 이유만으로 영상 전체를 문제 사례로 지정하지 않는다.

기술 문제는 욕설이나 민감 단어의 존재 여부보다 다음 질문에 있다.

- 현재 발언은 무엇을 평가하고 있으며, 앞선 발언과 같은 대상을 가리키는가?
- 개인 경험이나 상품 평가가 사람·집단에 대한 단정으로 확대되는가?
- 문제 표현을 설명·비판하는 인용인가, 현재 대상을 다시 조롱하는 사용인가?
- 판단을 바꾸는 실제 근거는 어느 발언·화면 구간에 있는가?

이 범위를 먼저 검증하고, 은어의 일반·특수 용법이나 다른 검수 유형으로 확장할지는 결과를 보고 결정한다. `~노` 단독 탐지 제외 방침은 유지한다.

## 3. 제안하는 기술 구성

### 단어 사전을 대조 가능한 사례 자료로 확장

문제 표현 목록과 함께 비슷한 표현이 일반적인 평가·인용·설명으로 사용된 사례를 관리한다. 각 사례에는 다음 정보를 둔다.

- 실제 발언과 앞뒤 문맥, 영상 시점, 입력 출처
- 표현의 대상과 대상이 바뀌는 구간
- 사람이 합의한 검토 결정, 그 이유, 의견이 갈린 부분
- 문제 사례인지 일반 사례인지, 어떤 차이를 설명하는 대조 사례인지
- 자료 출처·사용 가능 범위·검토일·기준 버전

논란 발생 여부와 현재 발언의 검토 필요성은 별도 정보로 둔다. 뉴스가 많았다는 이유로 위험의 정답을 만들지 않는다. AI가 만든 합성 사례는 초안이나 학습 보조 자료로 표시하며 실제 품질을 증명하는 평가셋과 구분한다.

### 현재 구간을 문제 용례와 일반 용례 모두에 대조

현재 발언과 유사한 문제 사례만 가져오면 판단이 한쪽으로 기울 수 있다. 일반 사례도 함께 찾아 다음 차이를 비교한다.

- 평가 대상과 대상의 확대 여부
- 개인 경험·취향인지, 집단 전체를 단정하는지
- 실제 조롱·모욕 표현과 이를 뒷받침하는 주변 발언
- 인용·설명 목적과 현재 공격의 구분

모델은 어떤 사례와 비슷한지만 답하지 않고, 현재 원문에서 확인되는 공통점·차이점·부족한 근거를 제시해야 한다. 검색된 사례는 참고 자료이며 현재 구간을 대신하는 증거가 아니다.

### 판단에 필요한 문맥을 선택하고 근거 구간을 연결

바로 앞 한 줄로 대상을 알 수 없으면 앞선 대화에서 지칭 대상을 찾고, 동시간대 OCR을 보조 자료로 확인한다. 문맥 확장에는 입력량과 호출 예산의 상한을 둔다. 판단할 정보가 부족하면 사람의 검토가 필요한 이유를 남긴다.

사전에 없는 표현을 놓치지 않도록 전체 대본의 기본 탐색은 유지한다. 모든 최종 후보는 실제 원문·시점으로 연결하고, 텍스트만으로 억양·표정·의도를 확인했다고 설명하지 않는다.

## 4. 무엇이 차별성이고 무엇이 공개된 방법인가

RAG, 임베딩 검색, 문맥 추가, LLM 분류는 공개된 방법이다. 이를 붙였다는 사실이나 파이프라인 단계 수는 기술 우위의 증거가 아니다.

우리 자산이 될 가능성이 있는 것은 검증된 한국어 영상 사례, 헷갈리는 일반·문제 용례의 대조 자료, 그 차이를 구분하는 판단 방식, 실제 검수 피드백으로 품질을 개선하는 절차다. 자료를 다른 팀도 쉽게 확보할 수 있거나 성능 개선으로 이어지지 않으면 방어력은 약하다. 따라서 데이터의 양만으로 경쟁력을 주장하지 않는다.

문맥에 따른 유해성 판단 변화는 이미 연구된 문제이며, 문맥을 제공했다고 모델 성능이 자동으로 개선되지는 않는다는 결과도 있다. 이 연구는 온라인 대화에 관한 것이므로 한국어 영상에 그대로 일반화하지 않는다. [ACL 연구: Toxicity Detection: Does Context Really Matter?](https://aclanthology.org/2020.acl-main.396/)

문맥을 포함한 검색과 RAG도 공개 구현이 존재한다. 검색 기법 자체와 우리가 축적할 검수 기준·사례·평가 성과를 구분한다. [Anthropic: Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval)

## 5. 파이프라인 개편 전 비교 실험

우선 30개 실제 구간으로 사람의 판정 기준을 맞춘다. 이후 별도 영상에서 평가 사례를 확보하며, 규모는 확보 가능한 자료와 검수 인력에 맞춘다. 텍스트·행동·복합 자료의 수량과 용도는 데이터셋 구축 계획을 따른다.

| 비교 구성 | 확인할 가설 |
|---|---|
| 기본 LLM 검토 | 잘 작성한 프롬프트와 충분한 문맥만으로 해결되는가? |
| 현재 OoPs?! 파이프라인 | 기존 사전·분석기·병합이 실제로 무엇을 개선하는가? |
| 사례 대조를 추가한 구성 | 문제·일반 용례의 대조가 과탐지와 미탐지를 개선하는가? |

같은 STT/OCR, 같은 모델, 같은 평가 기준을 사용한다. 입력·호출 예산 차이를 기록하고, 추가 비용을 허용했을 때의 결과와 비슷한 예산에서의 결과를 구분한다. 비교 기준의 프롬프트를 의도적으로 약하게 만들지 않는다.

사례 검색 자료와 최종 평가 자료는 영상·사례군 단위로 나눠 유사 문장 누출을 줄인다. 사람은 필요한 경우 실제 영상까지 보고 판단하며, 불일치는 기록한다. 모델의 자기 점수를 정답으로 사용하지 않는다.

주요 지표는 유용 판정 비율, 중요 사례 탐지율, 영상 길이당 불필요 알림 수, 원문·시점 연결 정확도, 처리시간·호출 비용이다. 같은 알림 수 또는 검수 부담에서 중요 사례를 더 찾는지도 확인한다. 읽지 못했거나 처리하지 못한 입력을 정상 통과로 집계하지 않는다.

### 결과에 따른 결정

- 기준선 대비 유의미한 개선과 제작자 효용이 확인되면 해당 부분을 중심으로 파이프라인을 개편한다.
- 기본 프롬프트로 비슷한 결과가 나오면 그 부분을 고유 기술로 주장하지 않는다.
- 개선은 있지만 비용·시간 증가가 크면 적용 범위를 어려운 후보로 제한해 다시 비교한다.
- 기술 차이가 작아도 고객이 검수 흐름에 가치를 느끼면 제품·영업 중심 사업 가능성을 따로 평가한다. 기술 중심 투자 논리와 동일하게 설명하지 않는다.

## 6. 다음 작업

실제 자료의 단위·출처·독립 주석·분할·일정은 [논란 데이터셋 구축 계획](논란-데이터셋-구축-계획.md)에 정리한다. 행동·포즈와 긴 영상으로 확장하는 가설은 [행동·포즈 데이터셋과 긴 영상 적용 계획](행동-포즈-데이터셋-및-긴영상-적용-계획.md)을 따른다. 두 계획은 현재 기술 우위가 입증됐다는 의미가 아니다.

1. 현재 파이프라인에서 찾은 사례와 놓친 사례를 구간별로 정리한다.
2. 일반 비평과 사람·집단 공격이 헷갈리는 실제 대조 사례를 확보한다.
3. 사람이 검토 결정과 판단 근거를 맞춘다.
4. 동일한 평가셋으로 세 구성을 비교할 실험 틀을 만든다.
5. 결과를 보고 데이터·판단 방식·파이프라인 중 다음 개발 대상을 정한다.

외부 모델 실험은 기존 API 비용이 발생하므로 자료 준비와 오프라인 검증 이후 범위와 예산을 정해 수행한다. 현재 이 문서의 가설은 코드 구현이나 성능 우위로 확인된 상태가 아니다.

| Whisper·GPT API를 호출하는 것만으로는 기술력이 드러나지 않는다 | 외부 모델이 수행하는 기능과 우리 팀이 만드는 고유한 부분이 불분명함 | 외부 모델 사용을 숨기지 말고, 우리만의 검수 기준·데이터·증거 연결·품질 개선 능력을 분리해 설명 |
| “기술 고도화”가 무엇인지 분명하지 않다 | 투자자가 기대하는 성과와 팀이 생각하는 목표가 다를 수 있음 | 투자 검토자에게 기대하는 구체적 기술·제품 마일스톤을 직접 확인 |
| 제품이 실제로 되는지 확인할 수 있는 프로토타입이 중요하다 | 컨셉 영상·설명서만으로는 입력부터 결과까지의 실현 가능성을 판단하기 어려움 | 영상 업로드부터 시점·원문 근거가 있는 결과까지 한 번에 시연 |
| 투자금이 왜 필요한지, 어디에 쓸지 구체적이어야 한다 | “서비스를 끝까지 만들고 싶다”만으로는 투자 판단에 필요한 계획이 부족함 | 필요한 금액, 집행 항목, 기간, 그 돈으로 달성할 검증 결과를 연결 |
| 고객 확보·유통 역량도 경쟁력이 될 수 있다 | 기술만이 유일한 방어력은 아니며 고객 접근 경로가 강점일 수도 있음 | 크리에이터·제작사별 문제와 도입 의사를 인터뷰로 검증 |
| 특정 성과를 투자 조건으로 삼는 투자자도 있다 | 투자자가 무엇을 증명하면 투자할지 사전에 합의할 수 있음 | 투자자의 판단 기준·마일스톤·검토 시점을 질문하고 기록 |

### 7.2 프로토타입과 구현 경계

- 대표 영상 또는 사용 허가 영상으로 업로드부터 STT/OCR·검토·타임라인 결과까지 재현 가능한 시연을 준비한다. 결과에는 시점·원문·검토 이유와 미처리 범위를 함께 보여준다.
- 외부 STT/OCR/LLM과 팀이 구현한 조율·후보 선별·근거 연결·실패 처리·검수 흐름을 분리해 설명한다. 프로토타입이 존재한다는 사실과 성능 우위는 별개다.
- 30개 실제 파일럿으로 기준을 맞추고, 별도 자료에서 5절의 기준선·현재 파이프라인·사례 대조를 비교한다. 가상 예문은 정답이 아니다. 유형별 표본 수와 실패·미처리·평가 한계도 공개한다.
- 문구는 “논란을 정확히 예측한다”보다 “긴 영상에서 사람이 검토할 구간을 근거와 함께 좁히는 보조 도구”로 맞춘다. 제작자별 개인화·피드백 학습·자체 모델·사람보다 우수한 탐지는 아직 증명되지 않았다.
- 품질 목표는 기준선 측정 뒤 정한다. 후보의 유용성·누락·불필요 알림·근거 연결·처리시간·실패율·비용을 함께 확인하며, 기술 품질과 고객 수요는 따로 검증한다.

### 7.3 고객 문제와 도입 가능성 검증

연예인·대형 제작사만을 고객으로 미리 고정하지 않는다. 크리에이터, MCN, 영상 제작사, 기업 홍보팀 등 후보군별로 실제 게시 전 검수 과정과 문제를 확인한다.

- 최근 영상 검수에서 놓친 문제나 수정에 시간이 많이 든 사례가 있었는지 묻는다.
- 현재 누가 어떤 도구·체크리스트로 검수하고, 어떤 단계에서 시간이 드는지 확인한다.
- 업로드 가능한 영상 유형·길이·민감정보·보관 조건을 확인한다.
- 결과가 어느 수준이어야 사람이 써볼지, 과탐지와 미탐지 중 어떤 실패가 더 큰 비용인지 묻는다.
- 무료 체험 의향만이 아니라 반복 사용, 도입 담당자, 지불 의사와 구매 절차를 확인한다.

인터뷰 결과는 “잠재 고객이 많다”는 주장 대신 대상군별 인터뷰 수, 반복해서 나온 문제, 파일럿 의향, 다음 행동으로 정리한다. 실제 인터뷰 전에 고객 수요가 확인됐다고 발표하지 않는다.

### 7.4 투자자와 기대 마일스톤 확인

후속 멘토링에서 투자 검토자에게 다음을 구체적으로 질문한다.

- 현재 서비스에서 투자를 검토하려면 우선 어떤 가설이 증명되어야 하는가?
- 기술 완성도, 정확도, 실제 사용자, 파일럿 계약 중 어떤 증거를 가장 중요하게 보는가?
- 어느 정도의 표본과 기간이면 그 증거를 판단할 수 있는가?
- 특정 목표를 달성하면 투자 검토를 진행한다는 합의가 가능한가? 가능하다면 목표·판정 방식·시점을 무엇으로 할 것인가?
- 후속 검토 때 원하는 자료는 무엇이며, 투자금의 규모와 사용 계획 중 어떤 형식이 필요한가?

구두 조언을 투자 약속으로 해석하지 않는다. 목표·평가 방식·검토 시점을 문서로 되짚어 오해를 줄인다.

### 7.5 투자 계획서 구성

초기 문서는 완성된 투자 자료가 아니라 가설 검증 계획으로 표시한다. 프로토타입과 고객 검증 결과가 생기면 아래 순서로 구체화한다.

1. 고객과 반복적으로 발생하는 검수 문제
2. 현재 대안과 그 대안이 충분하지 않은 이유
3. 제품 시연: 입력부터 근거가 있는 결과까지
4. 기술 구성: 외부 기술과 자체 구현의 경계
5. 품질·비용·처리시간 비교 결과와 평가 한계
6. 목표 고객, 도입 흐름, 파일럿·사용자 증거
7. 경쟁 대안과 차별화 가설
8. 팀의 역할과 현재 역량, 부족한 역량
9. 투자 요청액, 항목별 사용 계획, 기간, 달성할 마일스톤
10. 주요 위험, 개인정보·영상 보관 정책, 실패 시 계획

투자금 사용은 “개발비” 한 줄로 묶지 않는다. 예를 들어 데이터 라벨링, 사용자 파일럿, 필요한 개발 인력·외부 비용, 보안·법률 검토처럼 실제 견적과 기간을 확인해 구분한다. 지금 확정되지 않은 금액이나 성과는 만들어 넣지 않는다.

### 7.6 진행 순서와 완료 조건

| 순서 | 작업 | 완료 조건 |
|---|---|---|
| 1 | 기술 주장과 현재 구현 경계 정리 | 외부 모델·자체 구현·미검증 가설을 한 장에서 구분 |
| 2 | 영상 검수 프로토타입 시연 준비 | 대표 영상에서 입력부터 원문·타임스탬프가 있는 결과까지 재현 가능 |
| 3 | 소규모 평가셋과 기준선 측정 | 사람 합의 사례, 오탐·미탐·비용·시간이 함께 기록됨 |
| 4 | 고객 인터뷰 및 파일럿 후보 확인 | 대상군별 문제·검수 흐름·도입 장벽·지불 의사 기록 |
| 5 | 투자자 마일스톤 확인 | 투자 검토자가 원하는 증거와 판정 시점을 확인하고 기록 |
| 6 | 투자 계획서와 요청안 작성 | 제품·고객 근거, 필요한 금액, 사용처, 기간, 검증 목표가 연결됨 |

우선 1~3단계를 비용이 거의 들지 않는 범위에서 진행한다. 평가 사례의 라벨링이나 실제 외부 모델 비교에 인력·API 비용이 들 수 있으므로 범위와 예산을 정한 뒤 실행한다. 기술 품질만으로 고객 수요가 증명되지는 않으며, 고객 인터뷰와 파일럿을 별도 검증으로 취급한다.
