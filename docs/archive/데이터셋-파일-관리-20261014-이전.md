
출력의 regression-check/에 같은 준비 파일이 생긴다. 준비/점검 도구는 API를 호출하지 않는다. 13×2×3=78은 평가 항목 수이며 실행 승인·비용 예약이 아니다. 원영상이 없으면 기사 인용 텍스트 시험만 가능하고, 정상 대조는 합성임을 유지한다. 새 3사례의 기대 판단은 아직 null이므로 사람이 현재 입력으로 판단 가능한지부터 확인해야 한다.

관찰 기록의 각 calls 항목에는 unitId/arm/repeat, output/outputHash, selectedExampleIds, referenceHash, 공통 settings, humanReview를 넣는다. raw segment ID는 segment-001부터 입력 순서대로다. output은 run_boundary_comparison.py의 텍스트 창 계약(decision/reason/missingInformation/issues)을 사용한다. humanReview는 status=REVIEWED, reviewerId, 동일 outputHash, targetIssueCorrect/unsupportedInference/duplicateIssue를 포함하며 PASS는 정상 경계를 올바르게 유지했는지 검수한다. 빈 검수·미확정 라벨·잘못된 원문 인용은 성공이 아니다.

plan.settings는 모델·모델 설정·공통 프롬프트 해시·출력 계약 해시를 포함한 **동일 비교 조건의 스냅샷**으로 채우고, baselineReferenceHash/extendedReferenceHash는 비교 기준집 해시로 채운다. 두 기준집 외의 비교 조건을 바꾸지 않는다. 사람이 새 라벨을 확인한 뒤 planHash는 planHash 필드 제외 JSON의 fixed_review_suite.digest로 다시 고정하고 observations.planHash도 맞춘다. 기존 관찰을 새 라벨로 조용히 덮어 평가하지 말고 새 묶음으로 보존한다. 응답/참고 목록은 선언 기록이며 서버 로그 인증을 수행하는 도구가 아니다. 개발 통과도 Java 후보 계약·최종 카드·원영상 시험의 대체가 아니며 운영 승격은 차단 상태로 유지한다.

## 10/11 출처 우선 보강과 비교 정본

`research/source-first-additions/20261011.json`은 기사 출처로 조사한 3개 보충 사례 원장이며, 기존 댓글 카탈로그의 사건/카드/반응 건수에 섞지 않는다. catalog.supplementalResearchFiles가 파일을 참조하고 목록 검사는 누락·범위 밖 경로를 확인한다. 의미/자료 사용 승인은 별도 검수이며 `extend_context_references.py`가 보충 스키마·기존 패턴 연결·정상 대조 표시·HOLDOUT 제외를 검사한다.

비교 정본은 `evaluation/v1/similar-case-reference-final/`의 baseline-runtime.json/extended-runtime.json/provenance.json/routing-input.json/routing-comparison.json이다. 준비 중 출력은 하위 preparation-archives/에 보존했다. 기본 guidelines/runtime.json은 그대로다. --output-dir는 존재하지 않는 datasets 하위 경로만 허용한다.

```sh
python tools/extend_context_references.py \
  --base datasets/controversy/guidelines/runtime.json \
  --additions datasets/controversy/research/source-first-additions/20261011.json \
  --trace datasets/controversy/experiments/request-trace-51.json \
  --output-dir datasets/controversy/evaluation/v1/similar-case-reference-next \
  --audit
```

--audit는 기존 Java 도구로 로컬 참고 선택만 확인하고 모델/검색 API를 호출하지 않는다. Gradle과 Java 17이 필요하다. 이 기록의 제안 인용은 원문 구간 전체와 같으며 부분 인용인 입력은 현재 감사 형식으로 정확한 재생을 주장하지 않도록 거절한다. 새 참고가 선택되지 않으면 모델 재호출로 데이터 보강 효과를 측정하지 않는다. 원장/비교 파일은 Git 제외·private 보관이며 정본이라고 해서 승인 학습 자료가 되는 것은 아니다.

## 최신 분석용 내보내기 — 2026-10-10

`build_review_guidelines.py`는 카드와 세 층 사전의 재구축 결과를 모두 대조한 뒤 공통 패턴/예시집 및 실행용 v4를 내보낸다. 사전 원장·계획·기사 스냅샷이 바뀌면 사전을 먼저 재생성해야 한다. 원장 승인 상태는 변경하지 않는다. 내보낸 파일도 Git 제외/0600이며 다른 서버에는 별도로 안전하게 전달해야 한다. Spring은 시작 시 로드하므로 실행 중 파일 교체만으로 적용되지 않는다. 서버는 원자적으로 교체되는 `runtime.json`만 읽고, 두 별도 파일은 사람이 확인하는 투영본이다. 파일 세 개 전체에 대한 다중 파일 트랜잭션을 보장하는 것은 아니다.

`python3 tools/build_context_dictionary.py --write` → `python3 tools/build_context_dictionary.py --verify` → `python3 tools/build_review_guidelines.py --write`. 기본 실행은 검증만 하고 `--write`가 있을 때에만 파일을 교체한다. 실제 조회/연결/상한 검증은 [현재 분석 흐름](../guides/AI-분석-로직.md)을 따른다.

## 저장 정책

사용자 요청에 따라 `datasets/` 전체와 `uploads/`는 Git에 넣지 않는다. 코드 저장소에는 검증 도구, 가상 테스트, 운영 안내만 둔다. 이미 추적하던 데이터 메타데이터도 추적을 해제했으며 로컬 파일은 보존했다. 기존 Git 이력을 다시 쓰거나 과거 기록을 삭제한 것은 아니다.

새로 저장소를 내려받은 환경에는 데이터 파일이 없다. 검증하려면 별도로 관리한 데이터 사본을 준비하고 `--dataset-root`와 필요한 경우 `--private-root`를 지정한다. 코드의 테스트는 실제 댓글 없이 가상 자료만 사용한다. 로컬 파일 보관은 백업과 별개다. 백업이나 팀 공유 시 개인정보·사용 범위·보관 기한을 별도로 검수한다.

원본 파일명을 바꿔 해시 참조를 깨뜨리거나 중복 수집본을 삭제하지 않았다. 현재 상태 목록에서 사용할 활성 수집본과 중복 제외본을 지정한다. 업로드 폴더의 모든 JSON을 일괄 합치지 않는다.

같은 날 사건 3개를 추가했고 현재 6사건·9카드·30매핑 반응이다. 별도 `replay_draft_cases.py`는 사용자가 `--execute`로 실행할 때만 유료 모델 비교를 수행하는 연구 도구이며 운영 승인 경로를 우회하지 않는다. 결과에 저장되는 사례 해석·모델 출력도 원본과 연결된 파생 자료이므로 수집본의 갱신·삭제 기한을 연장하지 않는다. 자세한 경계와 실행 상태는 공통 카드 문서를 따른다.

후속 작업에서 [범용 작업 기준집](../casebook/범용-논란-기준집.md)을 실제 분석에 연결했다. `build_review_guidelines.py --write`는 전체 공통 카드와 분류 계획의 원본 일치 검사를 거친 후 조건집을 갱신한다. 새 카드는 명시적인 조건 매핑이 없으면 갱신을 통과하지 못한다. 이 연결은 원사례의 승인·학습 상태와 별개이며 조건 버전·출처 카드·정상 해석·필수 근거·누락 정보 경계를 보존한다. 운영에서는 Git 제외 파일을 별도로 제공하고 Spring을 재시작해야 한다.

## 사례 구축 원칙

세 층 파생 사전은 `build_context_dictionary.py --write`로 갱신하고 `--verify`로 공통 카드/계획/스냅샷과 일치하는지 확인한다. 댓글 발췌는 공통 카드 ID를 참조하며 기사 원문 발췌는 해시와 코드 포인트 위치를 검사한다. 출처가 동일한 재인용은 originGroup 후보를 기록하되 독립 근거 수를 자동 산출하지 않는다. 모든 파생 파일과 짧은 스냅샷도 검수·사용 범위·기한을 적용한다. 상세 필드는 [공통 카드의 세 층 정제 단계](../casebook/논란-카드-JSON-구조.md#최신-정제-단계-세-층의-맥락-사전)를 따른다.

알려진 논란 포인트 → 확인 가능한 표현·전후 맥락 → 비판 이유 → 관련 댓글의 보조 근거 → 사람 검수 순서로 구축한다. 지금은 개별 사례를 정제하는 단계다. 연구 가설을 범용 규칙이나 모델 입력으로 자동 승격하지 않는다.

원영상이 없는 경우 보도에 남은 직접 인용과 댓글 반응을 보관할 수 있지만, 인용·관찰·추정을 구분한다. 영상 내용 비판, 게시 시점 비판, 사후 해명 비판도 구분한다. 반론은 참고 자료이며 비판 반응을 취소하는 투표로 사용하지 않는다. 파일 정리가 의미적 연결 검수나 권리 승인을 완료한 것은 아니다.

## 검사

```sh
# 로컬 파일 구조·진행 상태 참조만 검사
python3 tools/review_dataset_catalog.py

# 원문 해시·기한·파일 간 중복·기존 매핑 계약도 검사
python3 tools/review_dataset_catalog.py --private-root uploads/comment-collections

# 실제 데이터와 무관한 목록 검증 테스트
python3 -m unittest discover -s tools/tests -p 'test_review_dataset_catalog.py' -v
```

결과는 건수와 상태만 출력한다. 네트워크 요청·모델 호출·파일 변경·학습·런타임 반영을 실행하지 않는다. 승인 여부와 범용성은 별도 사람 검수 및 다른 사건 평가가 필요하다. 활성 수집본 사이의 중복은 오류로 처리하고, 동일 댓글 행의 제외본은 관계를 검증하되 집계하지 않는다. 보관 기한이 지난 활성 원본은 검사를 통과하지 못한다; 자동 삭제하지는 않는다.
