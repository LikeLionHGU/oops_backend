# 기획 대조와 원출처 우선순위 구현 기록

> 통합일: 2026-10-06 · 상태: 과거 기록, 현재 운영 가이드 아님

2026년 8월 14~17일의 기획 대조와 반영 결과를 보존한다. 당시 미구현·완료 표현, 호출 수·성능·작업량 추정은 현재 기준으로 재검증한 결과가 아니다. 해결 전 설명과 해결 기록이 함께 있으므로 현재 상태 판단에는 사용하지 않는다.

현재 구조·설정은 [서버 아키텍처](../서버-아키텍처.md), AI 현황은 [AI 분석 로직](../AI-분석-로직.md), API는 [API 대조표](../API명세-구현-대조표.md), 운영 대응은 [보안·운영 정책](../보안-운영정책.md)을 따른다.

#### 2. 격차 1 — 참고 자료를 저장하지 않는다 → **해결됨**

> **2026-08-15 구현 완료.** 아래는 문제가 무엇이었고 어떻게 고쳤는지의 기록입니다.
>
> `ReviewReference` 엔티티를 만들어 검토 후보에 연결했고,
> API 응답 `events[].references[]` 로 나갑니다.
> `EntityCheckAnalyzer` 와 `ContextCheckAnalyzer` 가
> LLM 에게 "몇 번 기사를 근거로 썼는지" 를 함께 물어 그 기사만 붙입니다.
> `report-test.html` 에서 바로 확인할 수 있습니다.


##### 기획서

> §14 현재 기획에서 외부 근거는 **핵심 기능**이다.
> 따라서 검색 결과를 AI가 읽고 버리는 구조로 만들면 안 된다.
>
> 참고 자료
>  ├ 자료 제목
>  ├ 제공 기관·매체
>  ├ 주소
>  ├ 게시 날짜
>  └ 관련 내용

##### 현재

뉴스를 검색해서 **LLM에게 주고 버립니다.** 제목·URL·날짜가 어디에도 남지 않습니다.

```java
// EntityCheckAnalyzer
List<NewsItem> news = newsClient.searchRecent(query, 6);
Verdict verdict = verify(today, claim, news);   // ← LLM 에 넣고 끝
```

사용자에게는 LLM이 요약한 한 문장만 갑니다.

```
"영상에서는 2019년이라고 했는데 기사에는 2020년으로 나옵니다."
```

**어느 기사인지 확인할 방법이 없습니다.**

##### 왜 문제인가

기획서의 핵심 주장은 "AI가 판단하지 않고 사람이 판단할 **근거**를 준다"입니다.
그런데 근거를 확인할 수 없으면 결국 AI의 말을 믿으라는 것과 같습니다.

특히 이 도구에서는 **오탐이 반드시 생깁니다.**
`롯데리아 없나?` 를 `롯데리아 싱가포르 2호점 오픈` 기사와 대조한 사례가 있었습니다.
링크가 있었다면 사용자가 30초 만에 "아 무관한 기사네" 하고 넘어갔을 겁니다.
지금은 판단할 방법이 없어 도구 전체를 의심하게 됩니다.

##### 해야 할 일

`ReviewReference` 엔티티를 만들고 검토 후보에 연결합니다.

```
review_reference
  ├ finding_id
  ├ title        기사 제목
  ├ publisher    매체
  ├ url          주소
  ├ published_at 게시일
  └ snippet      관련 대목
```

API 응답의 `events[]` 에 `references[]` 를 추가합니다.
프론트에는 필드 추가라고 미리 알려야 합니다.

**작업량: 반나절 정도. 격차 중 가장 효과가 큽니다.**

#### 3. 격차 2 — 편집 자막을 골라내지 못한다

##### 기획서

> §24 **최우선 1. 편집 자막 추출**
> 실제 편집 자막과 간판·메뉴판·로고 등의 글자를 구분한다.
>
> §8 분류 예: 편집 자막 / 주변 환경 글자 / 고정 로고·워터마크 / 자료 화면 글자 / 분류 불확실

##### 현재

**고정 로고만 걸러냅니다.** 그것도 최근에야 만들었습니다.

```
같은 자리 + 매번 비슷한 글자 → 로고로 보고 제외
```

간판, 메뉴판, 자료 화면 글자는 여전히 "자막"으로 들어갑니다.
그래서 발언↔자막 비교(`caption-mismatch`)를 **꺼 두었습니다.**

기획서가 최우선이라고 한 기능이 지금 동작하지 않습니다.

##### 기획서가 제시한 판단 근거

이미 가진 데이터로 대부분 구현할 수 있습니다.

| 신호 | 지금 있나 | 쓰고 있나 |
|---|---|---|
| 화면 위치 (하단·중앙) | 있음 (OCR 좌표) | 로고 판정에만 |
| 같은 자리에서 글자가 바뀜 | 있음 | 안 씀 |
| 영상 내내 지속 | 있음 | 로고 판정에 씀 |
| 발언 시각과 겹침 | 있음 (STT 타임코드) | **안 씀** |
| 발언 내용과 관련성 | 있음 | **안 씀** |

**발언과의 시간·내용 관계를 안 쓰고 있는 게 가장 큰 누락입니다.**
편집 자막은 말하는 시점에 맞춰 나오고 내용도 발언과 겹칩니다.
간판이나 메뉴판은 그렇지 않습니다.

##### 해야 할 일

OCR 결과에 유형 라벨을 붙입니다.

```
화면 글자
  ├ 위치가 자막 영역인가        (하단 1/3, 중앙 정렬)
  ├ 같은 자리에서 내용이 바뀌는가
  ├ 그 시각에 발언이 있는가
  └ 발언과 글자가 겹치는가      (글자 일치율)
        ↓
  편집 자막 / 환경 글자 / 로고 / 불확실
```

**편집 자막으로 분류된 것만** 발언 비교에 씁니다.
불확실한 것은 비교에서 빼되 내용 검토에는 씁니다.

그다음 `caption-mismatch` 를 다시 켭니다.

**작업량: 하루 정도. 이게 되어야 기획서의 1순위 기능이 살아납니다.**

#### 4. 격차 3 — 분석 수행 상태를 안 보여준다

##### 기획서

> §22 **매우 중요한 기술 원칙이다.**
> "분석했지만 후보가 없었다" 와 "분석 자체에 실패했다" 를 반드시 구분한다.
> 일부 분석기가 실패했는데 "확인할 후보가 없습니다" 라고만 보여줘서는 안 된다.

##### 현재

절반만 되어 있습니다.

**된 것** — 발언도 자막도 못 뽑으면 분석을 실패로 끝내고 사유를 보여줍니다.

**안 된 것** — 개별 분석기가 실패하거나 건너뛴 것은 **로그에만** 남습니다.

```
[pipeline] entity-check 스킵 (조건 불충족)      ← 콘솔에만
[openai] 요청 한도 초과로 포기했습니다           ← 콘솔에만
```

사용자는 이런 경우에도 "확인할 지점 0곳" 을 봅니다.
음성 인식은 됐는데 LLM 호출이 전부 실패한 상황이 실제로 있었습니다.

##### 해야 할 일

`GET /report` 에 분석 상태를 함께 내려줍니다.

```json
"analysisStatus": {
  "stt":          "SUCCESS",
  "ocr":          "SUCCESS",
  "captionMatch": "SKIPPED",
  "entityCheck":  "FAILED",
  "contextCheck": "SUCCESS"
}
```

화면에는 이렇게 보여줍니다.

```
확인할 지점 3곳
⚠ 이름·수치 확인은 실행하지 못했습니다 (요청 한도 초과)
```

**작업량: 반나절. 신뢰와 직결됩니다.**

#### 5. 작은 격차들

##### 5-1. 자료 간 정보가 다를 때

> §3 외부 자료끼리 내용이 다른 경우에는 **"자료 간 정보 차이가 있음"** 으로 보여줄 수 있다.

현재는 `UNVERIFIED_CLAIM`(근거 확인 필요)으로 뭉뚱그립니다.
"근거를 못 찾음" 과 "자료끼리 엇갈림" 은 사용자에게 다른 이야기입니다.
카테고리를 하나 나누면 됩니다. 작업량 작습니다.

##### 5-2. 이름 정리

> §24 현재: RiskFinding, RiskCategory, Severity, RiskScore
> 방향: ReviewCandidate, CandidateType, InternalPriority

기획서도 "코드 이름은 영어로 유지해도 되지만 제품 개념은 검토 후보로 통일"이라고 했습니다.

**사용자에게 보이는 문구는 이미 다 바꿨습니다.** 코드 이름만 남았습니다.
API 필드명(`severity`, `riskTypes`)을 바꾸면 프론트 작업이 깨지므로
**지금은 미루는 게 맞습니다.** 배포 후 여유 있을 때 정리할 항목입니다.

##### 5-3. 화면 변화 기반 OCR

> §20 짧은 간격으로 화면 변화만 확인 → 변화한 구간만 OCR

현재는 고정 간격으로 뽑습니다. 60분 영상이면 12초 간격이라
**짧게 스쳐가는 자막을 놓칠 수 있습니다.**

기획서도 "향후"로 두었고 실측이 필요하다고 했습니다.
지금 하기보다 **놓치는 비율을 먼저 재는 게** 순서입니다.

##### 5-4. 테스트 체계

> §24 목표: AI 품질을 느낌이 아닌 Test Case 로 비교

현재 JUnit 테스트는 서버가 뜨는지 확인하는 것 **1개**뿐입니다.
pytest 는 없습니다.

프롬프트를 고칠 때마다 매번 영상을 돌려 눈으로 확인하고 있는데,
이 과정에서 **오탐 하나를 잡으려다 진짜 탐지를 놓친 일**이 실제로 있었습니다.

대본과 자막을 고정해두고 기대 결과를 적어두는 것만으로도
프롬프트 수정의 영향을 바로 볼 수 있습니다.

순서를 이렇게 제안합니다.

##### ~~1순위 — 참고 자료 저장~~ (완료)

**발표에서 보여줄 것이 명확해졌습니다** — "AI가 이렇게 말했고, 근거는 이 기사입니다".

기획서 1순위지만 작업량이 가장 큽니다.
발언 시각·내용과의 관계를 쓰면 지금 데이터만으로 충분히 됩니다.

#### 7. 한 가지 짚어둘 것

기획서 §21은 초기에 사람의 보조 검수를 허용한다고 했습니다.

> AI 분석 → 검토 후보 생성 → 팀 내부 확인 → 명백한 잘못된 후보 제거 → Creator 에게 전달

**이건 시연 전략으로도 유효합니다.**

지금 오탐이 적지 않게 나옵니다. 발표에서 실시간으로 돌리다 이상한 카드가 뜨면
설명하기 어렵습니다. 미리 돌려본 결과를 쓰거나,
"초기에는 팀이 한 번 검토해서 전달한다"는 운영 방식을 명시하는 게 안전합니다.

기획서도 같은 문단에서 이렇게 못박았습니다.

> 자동화되지 않은 부분을 자동화된 것처럼 사용자에게 설명해서는 안 된다.

| 7 | 검색 결과를 Source Type 으로 분류 후 Ranking | **형태 변경** |
| 8 | 상위 Evidence 만 Verify LLM 에 전달 | 반영 |
| 9 | 자료 충돌 시 임의로 진실 확정 금지 | 반영 |
| 10 | Reference 에 `title/provider/url/publishedAt/sourceType` 반환 | 반영 |
| 11 | Fact Check 에 최근 30일 제한 미사용 | 반영 |
| 12 | Context 와 Fact Evidence 를 별도 Pipeline 으로 | **불필요** |

---

#### 2. 가장 중요한 것 — 11번

**요청서에서 지적한 30일 제한이 실제 버그였습니다.**

`GoogleNewsRssSearchClient` 가 모든 검색에 ` when:30d` 를 붙이는데,
`EntityCheckAnalyzer` 도 그 메서드를 그대로 쓰고 있었습니다.

```
"그 회사는 2019년에 설립됐죠"
  → 최근 30일 기사만 검색
  → 관련 자료 0건
  → "관련 기사 없음 → 건너뜀" 으로 조용히 종료
```

네이버 쪽도 `sort=date` 라 오래된 사실에는 부적합했습니다.

**즉 오래된 사실은 검증을 시도조차 못 하고 있었습니다.**
로그에는 "관련 기사 없음" 으로만 남아서 이상하다는 걸 알아채기 어려웠습니다.

##### 고친 방식

```java
searchRecent(query, n)    // 맥락 참고용. when:30d 유지, 최신순
searchArchive(query, n)   // 사실 확인용. 기간 제한 없음, 정확도순
```

| 분석기 | 쓰는 메서드 | 이유 |
|---|---|---|
| `ContextCheckAnalyzer` | `searchRecent` | "지금 이 주제가 민감한가" — 최근이 맞다 |
| `EntityCheckAnalyzer` | `searchArchive` | "그때 실제로 그랬나" — 기간 제한이 방해된다 |

---

#### 3. 형태를 바꾼 것

##### 3번 · 검색 클라이언트 분리

**요청:** 별도 `EvidenceSearchClient` 인터페이스를 만들어 분리

**한 것:** 기존 `NewsSearchClient` 에 `searchArchive()` 메서드 추가

인터페이스를 새로 파면 구현체를 두 벌 만들어야 합니다.
그런데 구글 RSS 도 네이버도 **같은 API 에 파라미터만 다릅니다.**

```
구글:   when:30d 를 붙이느냐 마느냐
네이버: sort=date 냐 sort=sim 이냐
```

클래스를 나눌 만큼의 차이가 아니라 메서드로 갈랐습니다.
`default` 구현을 둬서 새 구현체가 굳이 나누지 않아도 동작합니다.

**역할 분리라는 목적은 동일하게 달성했습니다.**
나중에 일반 웹 검색을 붙일 때는 `searchArchive` 만 새로 구현하면 됩니다.

##### 7번 · Source 분류

**요청:** 검색 결과를 LLM 으로 분류한 뒤 Ranking

**한 것:** Ranking 은 그대로. **분류는 규칙으로만.**

LLM 분류를 넣으면 호출이 이만큼 늘어납니다.

```
검색 결과 6건 × 주장 6개 = 36회 추가 호출
```

지금 영상 하나에 호출이 **5회**인데 이미 요청 한도에 걸리고 있습니다.
분류에 36회를 쓰면 정작 검증이 못 돕니다. 순서가 뒤바뀝니다.

규칙으로 보는 신호:

| 신호 | 판정 |
|---|---|
| `.go.kr`, `.or.kr`, `.gov` 도메인 / 매체명에 기관 | `OFFICIAL_SOURCE` |
| 제목에 `인터뷰`, `일문일답`, `interview` | `DIRECT_QUOTE_SOURCE` |
| 본문에 인용부호 + `말했다`/`밝혔다`/`said` | `DIRECT_QUOTE_SOURCE` |
| 매체명이 있는 나머지 | `REPUTABLE_MEDIA` |
| 출처를 알 수 없음 | `SECONDARY_SOURCE` |

**확신이 없으면 아래쪽으로 둡니다.** 잘못 올려서 "당사자 자료" 라고
표시하는 편이 더 나쁩니다.

#### 4. 반영하지 않은 것

##### 12번 · 별도 Pipeline

검색은 분리했지만 **분석기를 더 쪼갤 필요는 없었습니다.**
이미 `EntityCheckAnalyzer` 와 `ContextCheckAnalyzer` 로 나뉘어 있고,
각자 다른 검색 메서드를 씁니다. 그 이상 나누면 관리 지점만 늘어납니다.

##### §5 의 `speaker` / `directQuote`

요청서에서도 선택으로 두셨고, **지금 검색 결과로는 채울 데이터가 없습니다.**
뉴스 RSS 는 제목·요약·링크만 주므로 발언자와 원문 인용을 뽑으려면
기사 본문을 가져와 파싱해야 합니다. 그건 §13 의 P1 입니다.

##### §9 의 LLM Source Classifier

위 7번과 같은 이유입니다.

##### §13 의 P1 전체

원문 페이지 Fetch, 본문 Parsing, Quote Attribution.
요청서에서도 나중으로 두신 항목입니다.

---

#### 5. 알아둬야 할 한계

**`PRIMARY_SOURCE` 는 실제로 거의 안 나옵니다.**

지금 검색이 뉴스 RSS 뿐이라 **인터뷰 전문·자서전·공식 홈페이지가
애초에 검색 결과에 없습니다.** 5단계 분류를 붙였지만 현실적으로는
`DIRECT_QUOTE_SOURCE`(인터뷰 기사)와 `REPUTABLE_MEDIA` 두 개로만 갈립니다.

즉 지금 도달한 지점은 이렇습니다.

```
목표:  본인 인터뷰·책을 최종 근거로 삼는다
현재:  본인 말을 인용한 기사를 위로 올린다
```

**나머지 절반은 검색 인프라 문제입니다.**
당사자 자료를 제대로 찾으려면 일반 웹 검색 API(Google / Brave 등)가 필요하고,
새 키와 비용이 붙습니다. 지금 단계에서는 범위 밖으로 뒀습니다.

인터페이스는 열어뒀으므로, 웹 검색을 붙일 때
`searchArchive()` 구현체 하나만 추가하면 나머지 로직은 그대로 씁니다.

---

#### 6. 원칙에 대해 하나 더

요청서에서 가장 중요한 지적은 이 부분이었습니다.

> "당사자의 말이 무조건 사실이다" 가 아니다.
> **Claim 의 성격에 맞는 가장 직접적이고 신뢰 가능한 Source 를 우선한다.**

이걸 코드로 옮겼습니다.

| 주장 성격 | 먼저 보는 자료 |
|---|---|
| `PERSONAL_STATEMENT` — 본인의 생각·의도·경험 | 당사자 자료 → 인터뷰 인용 → 언론 |
| `DATE` · `NUMBER` — 연도·수치 | 공식 자료 → 당사자 자료 → 언론 |
| 그 외 | 공식 자료 → 언론 → 당사자 자료 |

**모든 사실을 당사자 발언으로 확인하려 들면 오히려 틀립니다.**
본인 기억보다 공식 기록이 정확한 경우가 있습니다.

그리고 자료끼리 다른 말을 할 때는 한쪽을 진실로 정하지 않고
"자료에 따라 설명이 다릅니다" 로 남기고 각각 무엇이라 하는지 보여줍니다.
판단은 제작자가 합니다.

---

#### 7. 타깃에 대한 참고

뮤직메카는 음악 정보 채널로, 현재 확정된 타깃과 다릅니다.

```
현재 타깃: 편집을 위임하는 20분 이상 토크·인터뷰 채널
```

**원칙 자체는 채널 종류와 무관하게 맞아서 반영했습니다.**
"주장 성격에 맞는 자료를 우선한다" 는 토크 채널에서도 그대로 유효합니다.

다만 인터뷰 한 건으로 타깃을 넓힐지는 별도 판단이 필요합니다.
이건 기술이 아니라 기획 결정입니다.
