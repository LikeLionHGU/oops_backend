2026년 8월 11~12일의 설명과 운영 경험을 보존한 기록이다. 배포 전이라는 설명, 인증·DB·보관 설정, 비용·성능 수치, 동시 실행 수와 영상 길이 제한은 당시 내용이며 현재 운영 사실이나 실행 권장 사항이 아니다. 특히 DB 삭제 예시는 복구·마이그레이션 절차가 아니므로 운영에서 실행하지 않는다.

현재 구조·설정은 [서버 아키텍처](../서버-아키텍처.md), AI 현황은 [AI 분석 로직](../AI-분석-로직.md), API는 [API 대조표](../API명세-구현-대조표.md), 운영 대응은 [보안·운영 정책](../보안-운영정책.md)을 따른다.

### OOPS — 공개 전 영상 검수 도우미

> 2026년 8월 12일 기준 · 비개발자용 정리

---

#### 한 줄 요약

**편집본 전체를 다시 보는 대신, 다시 확인할 구간만 보세요.**

원본 발언과 편집 자막, 외부 맥락을 비교해 공개 전에 확인할 지점을 시각과 함께 짚어줍니다.

**AI가 삭제 여부를 결정하지 않습니다. 확인할 근거를 제공합니다.**

---

#### 1. 왜 방향을 바꿨나

처음 가설은 이랬습니다.

> 제작자가 영상 속 논란 요소를 놓친다 → AI가 찾아준다 → 업로드 전에 수정한다

현업 인터뷰를 하면서 이 가설이 절반만 맞다는 걸 알게 됐습니다.

**PD와 편집자는 영상을 수십 번 반복해서 봅니다.** 눈에 띄는 문제는 이미 알고 있고,
알면서 일부러 넣은 장면도 있습니다.
"13분 20초에 이런 농담이 있습니다" 같은 알림은 새로운 가치가 없습니다.
"나도 알아, 그래서 넣은 건데"로 끝납니다.

**AI가 도덕 판단을 대신하는 구조도 약합니다.**
"이 발언은 부적절합니다", "논란 가능성 85%" 같은 출력은 제작자의 판단과 충돌합니다.

그래서 문제 정의를 바꿨습니다.

| | |
|---|---|
| **전** | AI가 논란이 될 영상을 찾아준다 |
| **후** | 제작팀이 놓칠 수 있는 **검수 사각지대**를 찾아, 다시 확인할 구간과 근거를 준다 |

---

#### 2. 어떤 사각지대를 찾나

반복해서 영상을 만들다 보면 이런 것들이 남습니다.

1. **익숙해져서 무뎌진다** — 너무 많이 봐서 지나친다
2. **본인이 모르는 맥락이 있다** — 특정 커뮤니티에서 다른 뜻으로 쓰이는 표현
3. **편집자가 의도와 다르게 표현한다** — 출연자는 A라고 했는데 자막은 B
4. **세부에서 오류가 난다** — 이름, 날짜, 숫자

여기만 찾습니다.

---

#### 3. 누구를 위한 것인가

**편집을 다른 사람에게 맡기는, 20분 이상 토크·인터뷰 채널.**

- 본인이 직접 출연하고 편집자가 따로 있음
- 20~60분 분량을 주기적으로 업로드
- 2인 이상 대화, 즉흥 발언이 많음
- 다른 사람·회사·사건을 자주 언급
- 방송사 수준의 검수 팀은 없음

경제·정책·투자 채널은 뺐습니다. 대본 기반이라 대본만 검토해도 대부분 해결되고,
영상 단위로 볼 이유가 약했습니다.

---

#### 4. 어떻게 분석하나

##### 1단계 — 영상에서 재료를 뽑습니다

| 뽑는 것 | 방법 |
|---|---|
| **말한 내용** | 음성 인식 (시각 정보 포함) |
| **화면에 나온 글자** | 이미지 문자 인식 (그 순간 화면 캡처도 함께) |

**여기서 채널 로고를 걸러냅니다.** 화면 구석에 늘 떠 있는 로고가
자막으로 섞여 들어가는 문제가 있었습니다.
같은 자리에 계속 나오면서 내용도 매번 같으면 로고로 보고 뺍니다.

##### 2단계 — 발언과 자막을 각각 훑습니다

**서로 비교하지 않습니다.** 각자 자기 내용만 봅니다.

| 보는 것 | 예 |
|---|---|
| 금지어·개인정보 | 전화번호가 그대로 나옴 |
| 낯선 커뮤니티 표현 | 특정 커뮤니티 말투로 알려진 어미 |
| 특정 대상 평가 | 소개 중인 가게를 깎아내리는 대목 |
| 이름·날짜·숫자 | 실제 기사와 어긋나는 서술 |
| 최근 이슈와 얽힌 주제 | 지금 진행 중인 사건 |

##### 3단계 — 겹치는 것을 하나로 묶습니다

같은 것을 두고 분석기마다 다르게 보고합니다.
"패스트푸드"를 한쪽은 비하로, 다른 쪽은 일반화로 잡는 식입니다.
사용자에게는 같은 지적이므로 카드 하나로 합칩니다.

여러 번 나온 건 **어디어디에 나왔는지** 함께 보여줍니다.

```
(등장: 00:26, 00:35, 00:44)
```

---

#### 5. 결과가 어떻게 나오나

```
01:08   확인 필요
발언: "너무 특색이 없어가지고"
확인 이유: 소개 중인 가게의 메뉴를 평가하는 대목입니다. 당사자가 볼 수 있습니다.
(등장: 01:08, 01:10)

──────────────────────────────
최종 수정 여부는 제작자가 판단하시면 됩니다.
```

**확률 점수나 "부적절합니다" 같은 판정은 내지 않습니다.**
안내 문구도 항목마다 반복하지 않고 맨 아래 한 번만 나옵니다.

---

#### 6. 특히 신경 쓴 것

##### 모르는 맥락을 알려주는 것

편집자가 모든 사회적 이슈를 알기는 어렵습니다.
특정 커뮤니티에서만 다른 뜻으로 쓰이는 표현이 대표적입니다.

여기서 우리가 하는 일은 **"이건 나쁜 표현입니다"가 아니라
"이 표현은 이런 맥락에서 논의된 적이 있습니다"** 입니다.

사전과 AI 양쪽으로 봅니다. AI만으로는 사투리나 일상 표현과 겹치는 것을
애매하다고 그냥 넘어가기 때문입니다.

##### 근거를 같이 주는 것

이름이나 날짜를 확인할 때, 그리고 최근 배경을 알려줄 때는
**AI가 실제로 본 기사를 카드에 같이 붙입니다.**

```
확인 이유: 영상에서는 2019년이라고 했는데 기사에는 2020년으로 나옵니다.

AI가 확인한 자료 2건 — 직접 열어서 확인하세요
· OO그룹 창립 20주년...2020년 설립 후 성장세   한국경제 · 8월 3일
· OO그룹, 설립 6년 만에 매출 1조                 매일경제 · 7월 28일
```

전에는 기사를 검색해서 AI에게 넣고 그냥 버렸습니다.
사용자에게는 "기사에는 2020년으로 나옵니다"라는 문장 하나만 갔습니다.

이 도구는 잘못 잡는 일이 반드시 있습니다.
"여기 롯데리아 없나?"를 "롯데리아 싱가포르 2호점 오픈" 기사와 대조한 적이 있습니다.
링크가 있었다면 30초 만에 무관한 기사라고 넘겼을 겁니다.
없으면 판단할 방법이 없어서 도구 전체를 의심하게 됩니다.

**우리가 하는 일은 판단이 아니라 근거를 주는 것**이라는 원칙과도 맞습니다.
근거를 확인할 수 없으면 결국 AI 말을 믿으라는 것과 같습니다.

##### 잘못 잡는 것을 조심하는 것

"틀렸다"고 했는데 틀리지 않았으면 제작자가 도구 자체를 안 믿게 됩니다.
그래서 사실 확인은 애매하면 통과시키도록 했습니다.

알맹이 없는 설명도 버립니다.
"특정한 맥락에서 사용될 수 있는 표현입니다" 같은 문장은
형식만 갖췄을 뿐 확인할 방법이 없어서 없느니만 못합니다.

#### 7-1. 영상 길이

**90분까지** 받습니다.

화면 인식은 영상이 길어도 **2~3분 안에 끝납니다.**
길이에 비례해 프레임을 늘리면 60분 영상에 900장이 되어 감당이 안 되므로,
장수를 고정하고 간격을 늘립니다. 자막은 몇 초씩 유지되니 대부분 잡힙니다.

다만 **긴 영상은 비용이 큽니다.** 60분이면 1000원 안팎입니다.
시연은 3~5분짜리를 권합니다.

#### 7-2. 실패하면 실패라고 말합니다

음성도 화면 글자도 못 읽으면 분석을 **실패**로 끝냅니다.

그냥 넘어가면 "확인할 지점 없음" 으로 끝나는데,
이건 "검수했더니 괜찮다" 가 아니라 "아무것도 못 봤다" 입니다.
둘을 헷갈리게 하면 안 됩니다.

#### 0. 한눈에

영상 공개 전에 **다시 확인할 구간과 근거**를 타임스탬프로 짚어주는 백엔드입니다.

제작자는 영상을 수십 번 반복해서 봅니다. 눈에 띄는 문제는 이미 알고 있어요.
우리가 찾는 건 반복 작업에서 남는 사각지대입니다 —
편집자가 바꾼 자막, 어긋난 이름·수치, 본인이 모르는 사회적 맥락.

**AI가 판정하지 않습니다.** 확인할 지점과 근거만 제공합니다.
프론트가 쓰는 API는 팀 API 명세(Creator Risk Manager v2.0)를 따르며, 실제 영상으로 검증까지 끝났습니다.

**아직 배포 전이라 로컬에서만 동작합니다.**

---

#### 1. 프로젝트 구성

레포가 두 개입니다.

```
lionlike/
├── oops-backend/     Spring Boot 4 · Java 17 · Gradle   (포트 8080)
└── oops-analysis/    FastAPI · Python 3.11              (포트 8000)
```

##### 왜 나뉘어 있나

음성 인식(Whisper)과 화면 문자 인식(PaddleOCR)이 파이썬 생태계라 분리했습니다.
**서버는 한 대면 됩니다.** 같은 머신에서 HTTP로 통신하고, Python 서버는 외부에 노출하지 않습니다.

```
[프론트]
   │ REST /api/v1 + STOMP WebSocket /ws
[oops-backend]  ─── OpenAI Chat API (리스크 판정)
   │ HTTP localhost:8000  └─ 구글 뉴스 RSS (배경 확인)
[oops-analysis]
   ├─ yt-dlp + ffmpeg   영상 확보, 오디오·프레임 추출
   ├─ OpenAI Whisper    음성 → 타임스탬프 대본
   └─ PaddleOCR         화면 자막 인식 + 프레임 보관
```

---

#### 2. 기술 스택

| 항목 | 버전 | 비고 |
|---|---|---|
| Java | 17 | |
| Spring Boot | 4.0.5 | **Jackson 3** 사용. `com.fasterxml.jackson` 이 아니라 `tools.jackson` |
| Spring Framework | 7.0.6 | |
| Hibernate | 7.2.7 | |
| Gradle | 9.4.1 | wrapper 포함 |
| springdoc-openapi | 3.1.0 | Swagger UI |
| Python | 3.11 | 3.12 이상은 PaddleOCR 설치가 깨짐 |
| PaddleOCR | 2.9.1 | 첫 실행 시 모델 수백 MB 다운로드 |

> **Spring Boot 4 주의점**
> Jackson 3로 올라가면서 패키지가 `com.fasterxml.jackson` → `tools.jackson` 으로 바뀌었습니다.
> `ObjectMapper` 대신 `JsonMapper` 를 씁니다. 검색해서 나오는 예제 대부분이 Jackson 2 기준이라 주의하세요.

##### 테이블

| 엔티티 | 테이블 | 내용 |
|---|---|---|
| `Video` | `video` | 영상 원본 정보, 저장소 키, 상태 |
| `AnalysisJob` | `analysis_job` | 분석 실행 1회. `job_key`(외부 노출 jobId), 진행률, 단계 |
| `TranscriptSegment` | `transcript_segment` | STT 대본 한 줄 (타임코드 포함) |
| `ScreenText` | `screen_text` | OCR 로 읽은 화면 텍스트 한 건 |
| `VideoFrame` | `video_frame` | OCR 에 쓰인 화면 캡처 이미지 |
| `RiskFinding` | `risk_finding` | 탐지된 논란 1건. 프론트에는 TimelineEvent 로 나감 |
| `AnalysisReport` | `analysis_report` | 영상 단위 종합 점수·요약 (내부용, API 미노출) |

`video ↔ analysis_job` 은 1:N 입니다. 재시도하면 `videoId` 는 유지되고 새 job 이 생깁니다.

##### 삭제와 정리

`DELETE /api/v1/videos/{id}` 가 DB 행과 디스크 파일을 함께 지웁니다.

JPA cascade 를 쓰지 않고 `VideoDeletionService` 가 순서를 직접 관리합니다.
`risk_finding`, `screen_text` 가 `video_frame` 을 참조하므로 프레임보다 먼저 지워야 합니다.

`oops.storage.retention-days` 를 0보다 크게 두면
매일 새벽 4시에 그만큼 지난 영상을 자동으로 정리합니다 (`StorageCleanupScheduler`).
로컬은 0(끔), 배포 서버는 7 정도를 권합니다.

##### 파일 저장소

DB가 아니라 디스크에 둡니다. 경로는 `oops.storage.location`(기본 `./uploads`) 기준 상대 경로입니다.

```
uploads/videos/{videoId}/original.mp4     원본 영상
uploads/frames/{videoId}/{timeMs}.jpg     OCR 에 쓰인 화면 캡처
```

절대 경로를 DB에 넣지 않고 `storageKey` 만 저장합니다. S3로 바꿀 때 `StorageService` 만 교체하면 됩니다.

#### 5. 분석 흐름

`AnalysisPipeline` 이 전부 조립합니다.

| 단계 | stage | 하는 일 |
|---|---|---|
| 1 | `STT` | Whisper 로 타임스탬프 대본 생성 |
| 2 | `OCR` | 2초 간격 프레임에서 화면 자막 인식 + 캡처 보관 |
| 3 | `TEXT_RISK`/`OCR`/`MULTIMODAL` | 활성 분석기 순차 실행 |
| 4 | `MULTIMODAL` | 후보 병합 + 우선순위 |
| 5 | `FINALIZING` | 리포트 집계 |

단계마다 `JobProgressService` 를 통해 별도 트랜잭션으로 상태를 커밋하고 WebSocket 으로 발행합니다.

> 파이프라인 본체는 하나의 긴 트랜잭션입니다. 그 안에서 job 을 직접 수정하면
> 커밋 전까지 다른 트랜잭션에 안 보여서 진행률이 0%에 멈춰 있게 됩니다.
> **job 상태 변경은 반드시 `JobProgressService` 를 거치세요.**

##### 분석기 6종

| key | 클래스 | 이벤트 타입 |
|---|---|---|
| `caption-mismatch` | `CaptionMismatchAnalyzer` | CAPTION — **P0** |
| `entity-check` | `EntityCheckAnalyzer` | SPEECH — **P0** |
| `context-check` | `ContextCheckAnalyzer` | SPEECH/CAPTION — **P0** |
| `speech-review` | `SpeechReviewAnalyzer` | SPEECH |
| `screen-text-review` | `ScreenTextReviewAnalyzer` | CAPTION |
| `subtitle`, `screen-text` | 룰 기반 | 안전망 (LLM 불필요) |
| `monetization` | `MonetizationRiskAnalyzer` | 기본 비활성 |

발언과 화면을 각각 **룰 + LLM 두 겹**으로 봅니다.
룰은 키 없이도 도는 안전망이고, 열거할 수 없는 유형은 LLM이 맡습니다.

`caption-mismatch`(발언 vs 자막 대조)는 만들었지만 껐습니다.
자막이 발언과 다른 건 원래 정상이고(예능 자막, 요약 자막), OCR 오인식까지 겹쳐
오탐이 대부분이었습니다. 지금은 발언과 화면을 **독립적으로** 분석하고
같은 시간대에 같은 유형이면 병합합니다.

##### 영상 유형(genre)

타깃은 편집을 위임하는 토크·인터뷰·팟캐스트 채널입니다.
경제·정책·투자는 대본 기반이라 영상 단위로 볼 이유가 약해 제외했습니다.

- `ContentGenre` : TALK_PODCAST / GENERAL
- `GenreDetector` : 대본을 보고 자동 판별 (LLM, 실패 시 키워드 추정)
- 업로드할 때 `genre` 로 직접 지정할 수도 있습니다 (선택 필드)

분석기는 `supports(context)` 에서 `context.genreOrGeneral()` 을 보고
자기가 돌아갈지 결정합니다. 파이프라인은 유형을 모릅니다.

##### 분석기 추가하는 법

```java
@Component
@RequiredArgsConstructor
public class MyAnalyzer implements ContentAnalyzer {
    public String key() { return "my-analyzer"; }
    public String displayName() { return "내 분석"; }
    public boolean supports(AnalysisContext ctx) { return ctx.hasTranscript(); }
    public List<RiskFinding> analyze(AnalysisContext ctx) { ... }
}
```

`application.yml` 의 `oops.analysis.enabled-analyzers` 에 key 를 추가하면 끝입니다.
**파이프라인 코드나 DB 스키마는 건드릴 필요가 없습니다.**

##### 배경 확인 (`context-check`)

이 서비스의 차별점입니다. "재선거" 같은 표현은 그 자체로 무해하지만,
마침 그 사안이 진행 중인 시점이면 반응이 완전히 달라집니다.
LLM은 학습 시점 이후 뉴스를 모르므로 세 단계로 나눴습니다.

1. 대본·자막에서 시사 주제 추출 (LLM)
2. 그 주제로 최근 30일 뉴스 검색 (구글 뉴스 RSS, **키 불필요**)
3. 오늘 날짜 + 기사 목록으로 위험 판정 (LLM)

`NAVER_CLIENT_ID`/`SECRET` 을 넣으면 네이버 뉴스를 우선 사용합니다. 없으면 구글 RSS로 폴백합니다.

##### 후보 병합 (`FindingFusionService`)

분석기 6개가 같은 장면을 중복 보고하므로 정리합니다.

1. 카테고리 묶음이 같고 3초 이내면 한 클러스터
2. 확신도 최고 1건만 대표로 남김
3. 발언·화면 양쪽에서 잡히면 점수 ×1.25 (`crossModal: true`)
4. `확신도(600) + 카테고리 중요도(100) + 교차검증(150) + 중복보고(60)` 으로 우선순위

`events[0]` 이 "가장 먼저 확인할 논란"이 됩니다.

#### 8. 알아둘 함정들

작업하다 실제로 겪은 것들입니다.

**Java HttpClient 는 기본이 HTTP/2 입니다.**
평문 HTTP 서버에 붙을 때 h2c 업그레이드를 시도하는데 uvicorn 이 지원하지 않아 요청이 깨집니다.
`RestClientConfig` 에서 `HTTP_1_1` 로 고정해 뒀습니다. 새 RestClient 를 만들 때도 그렇게 하세요.

**PowerShell 의 `curl` 은 진짜 curl 이 아닙니다.**
`Invoke-WebRequest` 별칭이라 보안 경고가 뜨고, 응답을 ISO-8859-1 로 해석해 한글이 깨집니다.
`curl.exe` 또는 `Invoke-RestMethod` 를 쓰세요.

**`.ps1` 파일은 BOM 이 있어야 합니다.**
Windows PowerShell 5.1 은 BOM 없는 UTF-8 을 시스템 인코딩으로 읽어 한글 주석이 깨집니다.

**UriBuilder 에 인코딩된 값을 넣지 마세요.**
직접 `URLEncoder.encode` 한 값을 넘기면 이중 인코딩됩니다. 뉴스 검색이 항상 0건이던 원인이었습니다.

**코드를 고치면 두 서버 다 재시작해야 합니다.**
Python 과 Spring 은 별개 프로세스입니다. 한쪽만 재시작하면 결과가 그대로라 반영 안 된 걸 눈치채기 어렵습니다.

**실패를 성공으로 보고하지 않게 조심하세요.**
STT 와 OCR 이 모두 실패하면 분석기가 전부 스킵되고
'완료 · 확인할 지점 0곳' 으로 끝납니다.
사용자에게는 "검수했는데 문제없다" 로 읽히지만 실제로는 아무것도 보지 못한 것입니다.

지금은 둘 다 비면 잡을 FAILED 로 바꾸고 사유를 그대로 전달합니다.
새 단계를 추가할 때도 같은 원칙을 지키세요.
**"물어봤는데 없다" 와 "물어보지도 못했다" 는 반드시 구분되어야 합니다.**

**OpenAI 요청 한도(429)를 조심하세요.**
분석기 5개가 각자 여러 번 호출하므로 영상 하나에 수십 번 요청이 나갑니다.
계정 등급이 낮으면 분당 허용량이 적어서 금방 걸립니다.

한도에 걸리면 `OpenAiClient` 가 조용히 빈 결과를 돌려주고,
사용자에게는 "논란 없음" 으로 보입니다. 실제로는 물어보지도 못한 것입니다.
프롬프트 문제로 착각하기 쉬우니, 결과가 갑자기 비면
콘솔에서 `rate_limit_exceeded` 부터 찾아보세요.

지금은 429 를 만나면 안내된 시간만큼 기다렸다 최대 4번까지 재시도합니다.
그래도 계속 걸리면 [rate limits](https://platform.openai.com/account/rate-limits) 에서
계정 등급을 확인하세요. 결제 수단을 등록하면 한도가 올라갑니다.

**PaddleOCR 첫 실행은 몇 분 걸립니다.** 모델을 받느라 멈춘 것처럼 보입니다.

**enum 값을 추가할 때 주의하세요.**
Hibernate 는 `@Enumerated(EnumType.STRING)` 컬럼에 체크 제약을 자동으로 만듭니다.
`ddl-auto: update` 는 이 제약을 갱신하지 않아서, enum 에 값을 추가하면
기존 DB 에서 저장이 거부됩니다. (`Value not permitted for column`)

지금은 모든 enum 컬럼에 `columnDefinition = "varchar(40)"` 을 명시해
제약이 아예 생기지 않도록 해뒀습니다. 새 엔티티를 만들 때도 같은 방식을 쓰세요.

혹시 이 오류를 만나면 로컬 DB 를 지우고 다시 띄우면 됩니다.
```powershell
Remove-Item oops-backend\data -Recurse -Force
```

#### 8-1. 분석이 오래 걸릴 때

시간을 가장 많이 쓰는 곳은 순서대로 이렇습니다.

| 단계 | 2분 영상 기준 | 조절 방법 |
|---|---|---|
| **OCR** | 1~3분 | `oops.analysis-server.ocr-interval-sec` 를 늘린다 (4초 → 6초) |
| LLM 분석기 5종 | 30초~1분 | 분석기를 끄거나 창 크기를 늘린다 |
| STT | 10~20초 | 조절 여지가 거의 없다 |
| 429 재시도 대기 | 최대 30초 | 계정 등급을 올린다 |

파이프라인이 끝나면 콘솔에 내역이 찍힙니다.

```
[pipeline] 소요 내역 — OCR 92초(61%), monetization 18초(12%), STT 12초(8%), ...
```

OCR 프레임 수는 `영상 길이 ÷ 간격` 입니다.
2초 간격이면 2분 영상에 60장, 4초면 30장입니다.
자막은 보통 몇 초씩 유지되므로 간격을 늘려도 대부분 잡힙니다.

#### 10. 남은 작업

##### 배포 (미착수)

지금은 완전히 로컬 전용입니다. 프론트가 접근하려면 서버가 필요합니다.

- 권장 사양: **2 vCPU / 4GB RAM 이상**, 디스크 20GB+
- PaddleOCR 이 메모리를 많이 씁니다. 1GB 티어로는 안 뜹니다
- Python 서버는 `127.0.0.1` 에만 바인딩하고 방화벽에서 8000 을 막을 것
- 도메인은 하나면 충분합니다 (nginx → Spring 8080)

##### 기능

- `CommentAnalyzer` — YouTube Data API v3 `commentThreads.list`
- `PoseAnalyzer` — 프레임 → MediaPipe/YOLO

##### 품질

- OCR 정확도. 한글 자막에 테두리·그림자가 있으면 자주 깨집니다 (`재선거` → `재선커`)
- `RiskRuleEngine`(금지어)과 `CommunitySlangRules`(커뮤니티 은어) 사전이 얇습니다.
  개발 지식 없이 한 줄씩 추가할 수 있으니 팀에서 계속 채우면 좋습니다.
  특히 커뮤니티 은어는 새로 생기고 바뀌므로 주기적으로 봐야 합니다
- 테스트 영상이 2개뿐입니다. 5~10개는 돌려봐야 오탐/미탐 감이 잡힙니다

##### 운영

- **인증이 없습니다.** `videoId` 만 바꾸면 남의 결과를 볼 수 있습니다. `authjwt` 설정 재사용 가능
- ~~업로드 파일 정리 로직이 없어 디스크가 계속 찹니다~~ → 삭제 API + 자동 정리 구현됨
- 마이그레이션 도구(Flyway)가 없습니다. 배포 전에 붙이는 것을 권합니다
- 동시 분석 4개 제한 (`AsyncConfig`)
- 영상 길이 30분 제한 (`oops-analysis/app/config.py`)
