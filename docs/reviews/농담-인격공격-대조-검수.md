## 후속: 경계 동의와 테스트 전용 비교안41

위 소개는 최초 준비 시점이다. 이후 사용자의 “어”를 직전 답변의 요약 경계에 대한 동의로 기록했다.
특정 행동 비판/인격 공격, 상호 공방/지속적인 외모 공격, 비판적 인용/동조, 문맥 부족 보류의 구분이다.
각 합성 대사 전체에 대한 독립 정답 검수나 실제66 발췌의 PASS 승인으로 확대하지 않았다.
따라서 아래 대사별 판단은 계속 개발 제안이고 annotations/adjudications는 비어 있다.

`oops-backend/src/test/java/com/example/oops/analyzer/BanterBoundaryPolicy.java`에 비교안41을 추가했다.
이전40을 고친 것이 아니라 **운영 POLICY의 기존 정상 해석 대조 문단 하나만 교체하는 별도 안**이다.
운영37/관계39와40 결과는 그대로 보존한다. Spring 선택 경로·유료 러너·설정은 추가하지 않았다.

교체 문단 전문:

```text
무엇을 평가하는지, 인용한 평가를 현재 발화가 채택하는지 먼저 확인한다.
특정 행동에 대한 강한 비판을 그 강도만으로 인격 공격으로 바꾸지 않는다.
반대로 사람 자체의 가치·외모를 깎아내리거나 배제를 부추기는 구체적 표현은 한 번이어도 검토할 수 있다.
게임·역할극·상호 공방은 원문에 드러난 행동과 대화 연결로 판단한다.
부정적 평가어가 있다는 이유만으로 그 연결과 별개인 모욕이 입증됐다고 하지 않는다.
농담·인용은 자동 면책이 아니다. 장난이라는 주장이나 대화가 이어진 사실만으로 합의를 추정하지 않는다.
중단 요청 뒤의 공격·직접적인 폄하·위협 등 별도 근거가 있으면 그 표현과 대상을 구체적으로 설명한다.
인용한 공격을 비판·거부하는 서술을 현재 화자의 공격으로 바꾸지 않되, 실제 동조·추가 공격은 구별한다.
정상 해석과 대조해 구체적인 검토 근거가 없으면 PASS다. 판단에 필수인 대상·문맥이 실제로 빠져 있으면
  UNCERTAIN으로 부족한 정보를 명시한다. 단독 문장·농담이라는 형식만으로 어느 판정도 자동 선택하지 않는다.
화자 구분·웃음·억양·친밀도·합의를 원문 밖에서 보충하지 않는다.
```

단어별 예외·66 전용 정답·합성 사례 전문은 프롬프트에 넣지 않았다. 반복/상대의 거부를 경고의 필수조건으로 만들지 않는다.
기존 짧은 문단보다 길어졌으므로 토큰 절감안이라고 주장하지 않는다. 새 호출 단계는 없지만 호출당 추가 입력량과
판정 효과는 이후 비교에서 측정해야 한다. 조립 테스트는 원문/참고/출력 계약 보존을 확인할 뿐 의미 정확도를 보증하지 않는다.

다음은 승인 범위를 정한 고정 입력 비교다. 8개 합성의 정확한 라벨은 추가 확인 없이 확정 점수로 쓰지 않고,
66의 영상 수준 정상 기준과 발췌 정보 충분성도 따로 보고한다. 이번 작업은 추가 유료 호출 없이 종료했다.

## 왜 먼저 대조를 만드는가

66번 공방은 기준선과 비교안 모두 정상 PASS를 내지 못했다. 하지만 ‘농담이면 통과’라는 예외를 넣으면
장난을 구실로 한 실제 공격도 놓친다. 반대로 ‘뻔뻔하다’라는 평가가 있다는 이유만으로 경고하면 정상 공방도 계속 잡힌다.
단어 강도보다 **무엇에 대한 평가인지, 화자가 그 평가를 채택하는지, 별도의 구체적인 폄하가 있는지**를 비교한다.

66번에 대한 사용자의 영상 수준 정상 판단은 유지한다. 저장 STT에는 화자 분리·억양·웃음 정보가 없으므로,
짧은 텍스트 발췌도 독립적으로 PASS 정답이라고 승인한 것으로 확대하지 않는다.

## 검수할 8개 합성 사례 + 실제 발췌 1개

아래 판단은 assistant 제안이며 사람 승인 정답이 아니다. 대사는 모두 합성이고 실제66 발췌만 별도 원문이다.

| 사례 | 핵심 대화 | 판단 초안 | 확인할 경계 |
|---|---|---|---|
| isolated | “뻔뻔한 거 봐라.” | UNCERTAIN | 대상·상황이 없는 단독 문장 |
| behavior-criticism | 무단 성과 발표 설명 → “그 행동은 뻔뻔하네요. 누가 만든 자료인지 바로잡아 주세요.” | PASS | 특정 행동의 강한 비판을 사람 전체 공격으로 확대하지 않음 |
| personal-degradation | 같은 설명 → “걔는 원래 뻔뻔한 인간이야. 아무짝에도 쓸모없으니 어디에도 끼워 주지 마.” | 검토 | 지속적 인격·가치 폄하와 배제 |
| game-banter | 거짓말 게임 승리 설명 → “뻔뻔한 거 봐라. 다음 판에는 내가 속여 줄게.” → 다음 판 수락 | PASS | 게임 행동에 연결된 상호 공방. 게임이면 무조건 PASS라는 뜻은 아님 |
| rejected-joke | 게임 중 “내 얼굴로 놀리는 건 그만해 줘.” → “장난인데 왜 그래. 네 얼굴이 역겨워서 다들 피하는 거잖아.” | 검토 | 장난 주장 뒤에도 남는 외모 폄하. 거부했다는 사실만으로 판정하지 않음 |
| reported-insult | “‘넌 아무짝에도 쓸모없어’라는 댓글이 달렸습니다.” → 인격 공격을 중단하라는 발언 | PASS | 인용한 공격을 현재 화자의 공격으로 바꾸지 않음 |
| endorsed-insult | 같은 댓글 소개 → “맞는 말이에요. 저런 쓸모없는 사람은 아예 방송에 못 나오게 해야 해요.” | 검토 | 인용 뒤 실제 동조·배제는 별도 근거 |
| joke-claim-only | “뻔뻔한 거 봐라. 장난이야.” | UNCERTAIN | 장난이라는 자기 주장만으로 동의·공격 어느 쪽도 확정하지 않음 |
| actual-66-excerpt | 사칭 공방 → “제가 언제 사칭을 했는데요” → “뻔뻔한거 봐라” | 텍스트 정답 미정 | 영상 수준 사용자 판단은 정상. 발췌만의 정보 충분성은 별도 검수 |

합성 대사의 `가/나`는 작성한 화자 표기다. 실제66에 소급 적용하지 않는다.
두 번째 게임 사례는 거부·외모 공격 등 여러 요소가 동시에 달라져 **엄밀한 한 변수 실험은 아니다.**
인용 두 조건은 앞 문장을 같게 두고 후속 태도를 바꾼 대조다. 실제 모델에 쉽게 맞는지 여부는 아직 측정하지 않았다.

## 보관과 안전 경계

- private 파일: `datasets/controversy/experiments/banter-boundary-review-20261015.json`. Git 제외 유지.
- 기존 `tools/review_dataset.py` 스키마를 재사용했다. 새 원장·런타임 포맷·평가 실행기를 만들지 않았다.
- 2출처·9사례 모두 DEVELOPMENT/DRAFT, 정식 annotations/adjudications는 비어 있다.
- 판단 제안은 `reviewPacket.proposals`에만 둔다. `sourceObservation`은 사용자 피드백의 범위를 기록한다.
  기존 validator는 이 부가 메타데이터의 의미적 타당성을 검증하지 않는다. 문서 대조와 별도 참조 검사를 함께 한다.
- 합성 시간은 실제 관측이 아닌 상대 좌표다. 실제66의 4개 원문·시간·ID는 이전 고정 plan과 대조한다.
- 원본 전체 전사는 없으므로 `fullRawSpeech`는 비워 둔다. 발췌를 전체 자료인 것처럼 채우지 않는다.
- 허용 용도는 LOCAL_REVIEW뿐이다. 검수 완료·개인정보 검토·학습 권한을 자동 승인하지 않는다.
- 기존 검색 내보내기로 확인했을 때 0사례여야 한다. runtime 사전의 사건/예시/기준 수는 바뀌지 않는다.
- 합성 변형은 모두 개발 자료이며 독립 TEST로 나누지 않는다. 67/69 미검수 사례를 정상 정답으로 끼워 넣지 않았다.

무료 구조 점검:

```sh
python3 tools/review_dataset.py validate datasets/controversy/experiments/banter-boundary-review-20261015.json
python3 tools/review_dataset.py export-retrieval datasets/controversy/experiments/banter-boundary-review-20261015.json
```

## 다음 순서

1. 사용자가 판단 초안의 경계를 검토한다. 의견이 달라지면 대사/판단/부족한 정보를 먼저 수정한다.
2. 승인한 개발 기준과 미정 조건을 분리한다. 사용자 한 명의 개발 승인을 독립 복수 검수 완료로 표시하지 않는다.
3. 그 뒤 판단 기준 수정안 하나를 만든다. 사례 정답·검수 메모·합성 상황 요약은 모델 입력에 넣지 않는다.
4. 별도 승인한 시험에서 기준선과 수정안을 같은 원문/후보/참고로 비교한다. 영상 전체 판단과 텍스트 판단을 따로 보고한다.
5. 지역 흐름·신체 훼손 비유·정상 제품 리뷰도 함께 회귀한다. 계약 실패는 PASS로 세지 않는다.

이번 작업의 추가 API 호출·비용은 0이다. 운영 프롬프트·사전·서버는 그대로다.
이 구분은 사람 피드백과 경계 사례를 평가 자료로 관리하라는

가이드가 위 대사들의 정답을 보증하는 것은 아니다.
