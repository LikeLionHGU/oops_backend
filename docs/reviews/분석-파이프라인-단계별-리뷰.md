## 1단계: STT 추출

### 범위

- Python: `oops-analysis/app/stt.py`, `config.py`, `main.py`의 `/health`·`/transcribe`
- Java: `oops-backend/.../transcript/*`, `AnalysisServerClient.transcribe`

### 변경

- OpenAI `whisper-1`, `gpt-4o-transcribe-diarize` 경로를 삭제했다. 전사는 Groq `whisper-large-v3`만 지원한다.
- 응답에서 `speaker`, `timestampSource`를 삭제했다. Spring은 두 필드를 읽지 않았다.
- 설정에서 `openai_api_key`, `openai_org_id`, `openai_project_id`, `whisper_model`을 삭제하고 `stt_model` 하나로 합쳤다.
- `SttReviewPlanner`, `/analysis/stt-review-plan` 엔드포인트, 인터셉터 경로를 삭제했다. 계획만 만들고 실행하지 않는 기능이었다.
- `TranscribeResponse.language`를 삭제했다. Spring에서 읽는 곳이 없었다.
- 음성 분할에서 ffmpeg `-ss`를 `-i` 앞으로 옮겼다. 청크마다 파일을 처음부터 읽지 않는다.
- `run.ps1`이 `OPENAI_API_KEY` 대신 `GROQ_API_KEY`를 검사하도록 고쳤다.
- 사실과 다르던 javadoc을 고쳤다.

### 유지 결정

- 청크 전사는 순차로 둔다. 병렬화는 Groq 요청 한도(429) 위험 때문에 보류했다.
- `DummyTranscriptProvider`는 유지한다. 테스트 프로필(`application-test.yml`)이 사용한다.
- `ocr_jobs.py`의 자식 프로세스 환경에서 `OPENAI_API_KEY`를 지우는 처리는 유지한다. 상속된 키를 막는 방어 코드다.

### 검증

- Python 135건 통과.
- Java 1,430건 통과, 실패 0, 오류 0, 기존 스킵 1. 삭제 전 1,438건에서 삭제한 테스트 8건만큼 줄었다.
- Gradle은 JDK 17을 자동으로 찾지 못한다. `-Porg.gradle.java.installations.paths=/opt/homebrew/opt/openjdk@17`을 붙여 실행한다.

### 2단계로 인수인계

- STT 출력 계약: `segments[].startMs/endMs/text`, `title`, `durationSec`. Spring에서는 `TranscriptLine(startMs, endMs, text)`로 변환한 뒤 `TranscriptSegment`로 저장한다.
- 전사 재사용 실행은 `StoredTranscriptProvider`가 SHA-256 스냅샷을 검증한 뒤 쓴다.
- 2단계는 표현 목록 매칭(`expressionOccurrences`)이다. 문서상 판단 흐름과 별개로 기록만 하는 트랙이다. 실제 호출 시점이 판단 단계 앞인지 뒤인지 병렬인지는 아직 확인하지 않았다. `AnalysisPipeline`에서 먼저 확인한다.
- 남은 확인 사항: ruff E701 4건이 `tests/test_processing_failures.py`에 원래부터 있다.
- 1단계에서 찾은 legacy 테스트 후보는 아래 L1-1, L1-2다. 2단계에서도 같은 기준으로 후보를 찾아 표에 더한다.

## legacy 테스트 후보 (7단계 후 논의)
