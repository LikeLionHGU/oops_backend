2026-11-16 시작. 단계마다 최적화와 legacy·미사용 코드 삭제를 진행하고, 다음 단계로 넘어가기 전에 메모와 인수인계를 남긴다.

리뷰 중 확인용으로 새로 만든 스크립트·테스트는 돌린 뒤 지운다. 기존 테스트 중 legacy로 보이는 것은 바로 지우지 않는다. 단계마다 후보로 적어 두고, 7단계를 마친 뒤 [legacy 테스트 후보](#legacy-테스트-후보-7단계-후-논의)에서 하나씩 삭제 여부를 논의한다.

## 1단계: STT 추출

### 범위

- Python: `oops-analysis/app/stt.py`, `config.py`, `main.py`의 `/health`·`/transcribe`
- Java: `oops-backend/.../transcript/*`, `AnalysisServerClient.transcribe`

### 변경

- OpenAI `whisper-1`, `gpt-4o-transcribe-diarize` 경로를 삭제했다. 전사는 Groq `whisper-large-v3`만 지원한다.
- 응답에서 `speaker`, `timestampSource`를 삭제했다. Spring은 두 필드를 읽지 않았다.
- 설정에서 `openai_api_key`, `openai_org_id`, `openai_project_id`, `whisper_model`을 삭제하고 `stt_model` 하나로 합쳤다.
- `SttReviewPlanner`, `/analysis/stt-review-plan` 엔드포인트, 인터셉터 경로를 삭제했다. 계획만 만들고 실행하지 않는 기능이었다.
- `TranscribeResponse.language`를 삭제했다. Spring에서 읽는 곳이 없었다.
- 음성 분할에서 ffmpeg `-ss`를 `-i` 앞으로 옮겼다. 청크마다 파일을 처음부터 읽지 않는다.
- `run.ps1`이 `OPENAI_API_KEY` 대신 `GROQ_API_KEY`를 검사하도록 고쳤다.
- 사실과 다르던 javadoc을 고쳤다.

### 유지 결정

- 청크 전사는 순차로 둔다. 병렬화는 Groq 요청 한도(429) 위험 때문에 보류했다.
- `DummyTranscriptProvider`는 유지한다. 테스트 프로필(`application-test.yml`)이 사용한다.
- `ocr_jobs.py`의 자식 프로세스 환경에서 `OPENAI_API_KEY`를 지우는 처리는 유지한다. 상속된 키를 막는 방어 코드다.

### 검증

- Python 135건 통과.
- Java 1,430건 통과, 실패 0, 오류 0, 기존 스킵 1. 삭제 전 1,438건에서 삭제한 테스트 8건만큼 줄었다.
- Gradle은 JDK 17을 자동으로 찾지 못한다. `-Porg.gradle.java.installations.paths=/opt/homebrew/opt/openjdk@17`을 붙여 실행한다.

### 2단계로 인수인계

- STT 출력 계약: `segments[].startMs/endMs/text`, `title`, `durationSec`. Spring에서는 `TranscriptLine(startMs, endMs, text)`로 변환한 뒤 `TranscriptSegment`로 저장한다.
- 전사 재사용 실행은 `StoredTranscriptProvider`가 SHA-256 스냅샷을 검증한 뒤 쓴다.
- 2단계는 표현 목록 매칭(`expressionOccurrences`)이다. 문서상 판단 흐름과 별개로 기록만 하는 트랙이다. 실제 호출 시점이 판단 단계 앞인지 뒤인지 병렬인지는 아직 확인하지 않았다. `AnalysisPipeline`에서 먼저 확인한다.
- 남은 확인 사항: ruff E701 4건이 `tests/test_processing_failures.py`에 원래부터 있다.
- 1단계에서 찾은 legacy 테스트 후보는 아래 L1-1, L1-2다. 2단계에서도 같은 기준으로 후보를 찾아 표에 더한다.

## 2단계: 표현 목록 매칭

### 범위

- `expression/ExpressionDictionary`, `service/ExpressionService`, `domain/ExpressionOccurrence`, `dto/ExpressionOccurrenceDto`, `repository/ExpressionOccurrenceRepository`
- 사전: `src/main/resources/expression-dictionary.json` (버전 `2026-10-10-user-watchlist-1`, 98개 항목, 별칭 98개)

### 실제 실행 시점

- 판단 단계와 병렬이 아니다. 분석이 끝난 뒤 `AnalysisResultWriter`가 결과를 저장할 때 `ExpressionService.replaceSnapshot`을 호출한다.
- 커버리지 `EXPRESSION_SCAN`은 STT 직후 `AnalysisPipeline`에서 대본 유무만 보고 SUCCESS/FAILED로 기록한다. 실제 매칭은 저장 시점이다. 사전 매칭은 결정적이라 결과는 같지만 기록 시점과 실행 시점이 다르다.
- 리포트에서는 `AnalysisService`가 `expressionOccurrences`로 내보낸다. 카드·점수에는 들어가지 않는다.

### 변경

- `ExpressionDictionary`: 항목마다 정규식을 따로 돌린 뒤 정렬·겹침 제거하던 방식을 별칭 전체를 길이 내림차순으로 묶은 정규식 하나로 바꿨다. 세그먼트당 정규식 실행이 98번에서 1번으로 줄고 정렬·겹침 제거 코드가 사라졌다. 매칭 규칙(경계, 조사·어미 허용 목록, `~노` 금지)은 그대로다.
- 동등성 확인: 기존 구현을 임시 복사한 비교 테스트로 25,880개 입력(별칭×앞뒤 문맥 조합, 무작위 연결 2만 개)에서 hit 13,276건이 모두 같았다. 임시 테스트와 복사본은 삭제했다.
- `ExpressionService`: 호출되지 않던 `replace(video, segments)`(DB ID 기반)와 분기 파라미터를 지우고 `replaceSnapshot` 하나만 남겼다.
- `application-expression-review.yml` 삭제: 분석기 목록이 기본 `application.yml`과 같아져 의미가 없었다. `docs/guides/AI-분석-개선-계획.md`에 삭제 표시를 남겼다.

### 유지 결정

- `EXPRESSION_SCAN` 기록 시점은 바꾸지 않았다. 바꾸려면 커버리지 기록을 결과 저장 쪽으로 옮겨야 해서 3~7단계 흐름과 함께 보는 게 낫다.
- 엔티티에 `dictionaryVersion`, `commonUsageNote`를 행마다 저장하는 구조는 유지한다. 사전이 바뀌어도 과거 결과를 설명할 수 있다.

### 검증

- Java 1,430건 통과, 실패 0, 오류 0, 기존 스킵 1.

### 3단계로 인수인계

- 3단계는 읽기 페이지 분할이다. 핵심 파일: `analyzer/DialogueReadingPage`(96줄), `analyzer/TextReviewBatchPlanner`(113줄), `analyzer/ReviewUnit`(79줄), `analyzer/DialogueReview`(202줄).
- 문서상 계약50(`DialogueReadingPage.plan`)이 이전 primary20/추가문맥16/읽기창48 경로를 대체했다. `TextReviewBatchPlanner`·`ReviewUnit`·`DialogueReview`가 아직 운영 경로에서 쓰이는지, 대체된 경로의 잔재인지 먼저 확인한다.
- `DialoguePageContextSelector`(실험 A0-T), `ContextMechanismRouter`도 `DialogueReadingPage`를 참조한다. 실험 경로는 운영 미연결이라고 문서에 적혀 있으니 운영/실험 구분을 같이 표시한다.
- 2단계에서 새로 찾은 legacy 테스트 후보는 없다. 참고: `ExpressionDictionaryTest`의 두 테스트가 표현 사전이 아니라 `RiskRuleEngine`(자막·화면 개인정보 안전망)도 함께 검사한다. legacy는 아니고 위치만 어색하다.

## 3단계: 읽기 페이지 분할

### 범위

- `analyzer/DialogueReadingPage`(운영 페이지 분할), `analyzer/TextReviewBatchPlanner`(20줄 배치), `analyzer/ReviewUnit`(30초 창), `analyzer/DialogueReview`, `analyzer/CandidateContextWindow`

### 실제 사용 구조

| 코드 | 운영에서 쓰는 곳 | 비고 |
|---|---|---|
| `DialogueReadingPage.plan` | `CandidateReviewEngine.run` (발언 후보 경로) | 계약50. 페이지는 항상 `sharedReadingPage=true` |
| `DialogueReadingPage.windows` | `CandidateContextWindow.conversationUnits` | 페이지 하나를 창 하나로 본다 |
| `TextReviewBatchPlanner.plan`/`withContext` | `TextReviewEngine.run` | 화면 글자(OCR) 검토가 쓴다. 구형 발언 경로도 쓴다 |
| `ReviewUnit` | `TextReviewEngine`, `CandidateContextWindow.discoveryUnits` | OCR 경로에 필요 |
| `TextReviewBatchPlanner.Batch.explicit` | `CandidateReviewEngine.runExperimental` | 실험 A 경로, 운영 미연결 |
| `DialogueReview` | `TextReviewEngine`의 대화 단위 호출 | 구형 발언 경로(`candidate-review-enabled=false`)에서만 켜진다 |

### 결정

- 구형 발언 경로(`candidate-review-enabled=false`일 때 TextReviewEngine 20줄 배치 + DialogueReview)는 삭제하기로 했다. 다만 이 코드를 직접 쓰는 테스트 16개가 있어, 코드와 테스트를 함께 L3-1로 보류했다. 7단계 후 논의에서 같이 지운다.
- `CandidateContextWindow`의 비공유 배치 분기(`discoveryUnits`)는 운영에서 닿지 않는다. 운영 배치는 항상 읽기 페이지(공유)이거나 실험용 명시 창이다. 테스트가 직접 호출해 L3-2로 보류했다.
- `ContextReferenceAudit`(gradle 실행 도구)는 운영과 다른 구형 20/16 배치로 사례 참고 선택을 감사한다. 현재 운영 분할을 반영하지 않는다. L3-3으로 보류했다.

### 유지 결정

- `DialogueReadingPage.fits`는 페이지를 한 줄 늘릴 때마다 요청 JSON을 직렬화해 24,000코드포인트 상한을 확인한다. 페이지당 최대 128줄이라 비용이 작고, 정확한 상한 확인을 대체할 값싼 상한식이 없어 그대로 둔다.
- 2단계 인수인계의 질문(이전 경로 잔재 여부)에 대한 답: `TextReviewBatchPlanner`·`ReviewUnit`은 OCR 검토 때문에 남는다. 잔재는 `DialogueReview`와 SpeechReviewAnalyzer의 비후보 분기다.

### 검증

- 운영 코드 변경이 없어 테스트를 다시 돌리지 않았다. 직전 결과는 Java 1,430건 통과다.

### 4단계로 인수인계

- 4단계는 사례 참고 선택과 후보 탐색이다. 진입점: `CandidateReviewEngine.execute`(1,275줄 파일)의 배치 루프. 배치마다 `ContextMechanismRouter.route`로 참고를 고르고 탐색 요청을 만든다(`CandidateReviewRequestFactory`, `CandidateReviewPrompts`).
- 사례 관련 클래스: `ReviewCaseLibrary`, `ReviewGuidelineLibrary`(546줄), `ContextExampleSelector`, `StructuredContextSearch`, `ContextRelationRetrieval`. 기본 OFF 실험 기능이 많다(`candidate-source-relations-enabled`, `recall-first-discovery-enabled`, `rule-candidate-union-enabled`, `source-understanding-enabled` 등). 기본값과 운영 도달 여부를 먼저 표로 만든다.
- `SpeechReviewAnalyzer`의 `SYSTEM_PROMPT`(유형 정의 포함)는 구형 경로 전용이다. 후보 경로는 `CandidateReviewPrompts`를 쓴다. L3-1에 포함했다.
- `build.gradle`이 820줄을 넘고 실험 실행 태스크가 많다. 4단계에서 실험 도구와 운영 코드를 구분할 때 함께 본다.

## legacy 테스트 후보 (7단계 후 논의)

단계를 진행하며 누적한다. 7단계 전에는 지우지 않는다.

기준: 운영 코드에 없는 로직만 검사하는 테스트, 현재 생산자가 더 이상 보내지 않는 형식을 위한 호환 테스트, 수집되지 않거나 실행되지 않는 테스트.

운영에서 쓰지 않는 코드라도 그 코드를 직접 검사하는 테스트가 있으면, 코드와 테스트를 한 묶음으로 이 표에 올리고 7단계 후에 함께 지운다(3단계에서 사용자 결정).

### 1단계에서 이미 지운 테스트

사용자가 기능 삭제를 승인해 기능과 함께 지웠다.

- Python `test_stt_adapters.py`: `whisper-1` 요청, OpenAI 클라이언트 설정, diarize 응답 파싱, 화자 청크 ID 테스트 4건
