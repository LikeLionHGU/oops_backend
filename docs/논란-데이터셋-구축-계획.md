# OoPs?! 논란 데이터셋 구축 계획

> 기준 브랜치: `minwook` · 작성·정리일: 2026-10-06 · 상태: 설계, 실제 수집·주석 미실행

> 2026-10-08 최신 적용 경계: 개발 영상 v1의 ID 1~9 반복 분석은 [실험 기록](AI-분석-실험-기록.md)에 남겼지만 독립 데이터셋 구축/주석 완료가 아니다. ID 9는 지역 음식 연결 흐름 B와 신체 비유 D를 놓쳤다. 단독 구간과 대화 묶음의 판단 범위를 따로 주석하고, 정상 대체 음식 설명·개인 리뷰·가족 음식 비유와 실제 폄하/불쾌한 신체 비유를 대조 사례로 준비한다. 공격 대상이 반드시 사람/집단이어야 한다는 라벨 제한을 모든 유형에 적용하지 않는다. PostHog의 검수 액션·사용 이벤트는 정답 라벨이 아니며 원문 수집 경로로 사용하지 않는다. 행동·포즈 자료 구축은 현재 보류한다.

공통 수집·주석·평가는 이 문서를 기준으로 한다. 논란 단어·은어의 구체적인 구축 절차는 [12절](#text-dataset), 팀 기준을 맞추기 위한 가상 예문은 [부록](#annotation-examples)에 통합한다. 시각 데이터의 세부 설계는 별도 문서로 유지한다.

## 1. 목표와 범위

한국어 영상에서 게시 전 사람이 다시 볼 구간을 원문·행동·시점·문맥과 함께 판단하는 자료를 구축한다. 첫 버전은 일반 비평과 사람·집단 공격의 구분, 행동·제스처의 일반 사용과 공격적 사용의 구분에 집중한다. 평가와 사례 검색을 먼저 수행하고, 학습은 데이터 품질과 사용 가능 범위를 확인한 뒤 검토한다.

행동·포즈 라벨과 긴 영상 처리의 구체적 설계는 [행동·포즈 데이터셋과 긴 영상 적용 계획](행동-포즈-데이터셋-및-긴영상-적용-계획.md)을 따른다.

`~노` 단독 탐지 제외 방침을 유지한다. 화자의 출신·성향·커뮤니티 소속을 추론하는 라벨은 만들지 않는다. 사실의 진위, 개인정보 노출, 모든 시각적 위험을 한 번에 다루는 범위는 후속 과제로 둔다.

## 2. 사건과 사람의 검수 판단을 분리

| 기록 | 내용 | 용도 |
|---|---|---|
| 사건 기록 | 원본, 공개일, 반응 발생 시점, 문제로 제기된 내용과 출처 | 수집 출발점과 사후 반응 기록 |
| 영상 구간 | 실제 음성·화면·행동, 핵심 구간과 앞뒤 문맥 | 판단 근거 |
| 사람의 주석 | 검토 결정, 유형, 대상, 근거 위치, 부족한 정보, 불일치 | 평가 및 검수 기준 개선 |

논란이 발생했다고 영상 전체가 문제 사례가 되지 않는다. 보도나 비판이 없다고 일반 사례가 되지 않는다. 조회수·댓글·사과 여부도 라벨을 자동 결정하지 않는다.

게시 전 탐지 평가에는 공개 후 기사·댓글·해명을 모델 입력이나 검색 자료로 넣지 않는다. 배경 지식의 출처와 공개일을 기록하며, 당시 이용 가능했는지 확인한다. 사후 자료로 조사한 실험은 회고 분석으로 표시한다. 유명 사건에 대한 모델·평가자의 사전 지식까지 제거했다고 주장하지 않는다.

## 3. 한 건의 단위

문장 하나나 정지 이미지 하나보다, 검토 판단을 뒷받침하는 영상 구간을 기본 단위로 삼는다.

- `focus_range`: 실제 검토할 발언·행동이 있는 핵심 구간
- `context_range`: 지칭 대상·사용 목적을 해석하는 앞뒤 구간
- `evidence_spans`: 이유를 뒷받침하는 특정 발언·화면·행동의 위치
- `sequence_id`: 연속 대화나 행동의 흐름을 연결하는 ID
- `pair_id`: 유사한 표현·행동이 다른 맥락에 쓰인 대조 사례 연결

핵심 구간 앞뒤 약 15~30초를 출발점으로 삼되, 필요한 지칭 대상이나 맥락이 없으면 확장한다. 충분하지 않은 문맥을 고정 길이로 잘라 정답을 강제하지 않는다.

추출된 STT/OCR 원문과 사람이 확인한 전사·화면 문구는 별도로 보존한다. 음성만 있어도 사례를 만들며, OCR 글자 없음·인식 실패·미실행을 구분한다. 행동·억양·표정이 필요한 사례에는 `MEDIA_REQUIRED`를 표시한다. 단어 시간 정렬이 없으면 임의의 단어 타임스탬프를 만들지 않는다.

## 4. 수집 경로

| 순서 | 자료 | 목적 |
|---|---|---|
| 1 | 기존 v1·v2·v3 원본과 남아 있는 분석 결과 | 실제 구간 확인, 현재 오탐·미탐 조사 |
| 2 | 이용 범위를 확인한 협력 제작자·팀의 영상 | 실제 검수 흐름과 일반 용례 |
| 3 | 원본을 확인할 수 있는 공개 사건 영상과 출처 | 문제로 제기된 구간 탐색 |
| 4 | 유사 주제의 일반 리뷰·인터뷰·대화·동작 영상 | 헷갈리지만 검토 이유가 다른 대조 사례 |
| 5 | 기존 한국어 공격·혐오 표현 자료 | 주석 기준 참고, 별도 보조 실험 |

자료별 원본 상태와 다운로드·평가·학습·재배포에 사용할 수 있는 범위를 확인한다. 이용 범위 미확인은 확정본에서 보류하고, 원본 삭제·재편집·출처 불명을 기록한다. 실제 자료를 공개 코드 저장소에 넣지 않는다.

KOLD는 댓글의 공격성 유형·대상·근거 구간과 제목 문맥을, K-MHaS는 한국어 뉴스 댓글의 다중 라벨을 다룬다. 이는 영상 대화·시점·행동까지 직접 제공하는 자료와 달라 우리 핵심 평가셋을 대체하기 어렵다고 판단한다. 우선 주석 설계 참고 자료로 삼는다. [KOLD](https://aclanthology.org/2022.emnlp-main.744/), [K-MHaS](https://aclanthology.org/2022.coling-1.311/)

## 5. 규모와 구성

### 파일럿: 30개 구간

텍스트 중심 10개, 행동 중심 10개, 음성·화면·행동을 함께 봐야 하는 사례 10개로 기준을 맞춘다. 두 사람이 독립 판단하고 이견을 정리한다. 이 자료는 기준 수립에 쓰므로 최종 독립 평가에는 사용하지 않는다.

### v0.1: 실제 구간 200개 목표

| 묶음 | 목표 | 선정 방식 |
|---|---|---|
| 텍스트 중심 | 80개 | 일반 비평·강한 평가·비하·일반화·은어·인용 |
| 행동 중심 | 80개 | 정의된 행동의 실제 사용과 유사한 일반 동작 |
| 복합·입력 경계 | 40개 | 대상·의미가 음성/화면에 의존하거나 인식·가림 문제가 있는 사례 |

이 200개 안에서 실제 대조쌍 약 50쌍을 목표로 한다. 쌍 100개가 추가되는 것은 아니다. 수량은 수집 목표이며 라벨 비율을 맞추려고 사람의 결정을 바꾸지 않는다. 사람이 판단 차이를 설명할 수 있을 때만 대조쌍으로 확정한다. AI로 문구를 고친 가상 사례와 촬영한 연출 사례는 실제 자연 발생 자료와 구분한다.

가능하면 20개 이상의 독립 원본·사건 그룹에서 확보한다. 재업로드·인접 장면은 별도 독립 표본으로 세지 않는다. 그룹이 적으면 일반화 평가의 한계를 명시한다.

### 별도 운영 평가: 완결 영상 5~10개

짧은 사례만으로 긴 영상의 탐지율을 평가하지 않는다. 일반·검토 필요 구간이 모두 있는 완결 영상을 사람이 끝까지 확인한다. 긴 영상 구성은 시각 분석 계획의 길이별 평가안을 따른다.

후보로 나온 장면만 사람이 보면 미탐을 셀 수 없다. 사람이 검토한 범위, 범위 밖 유형, 가려져 판단 못 한 구간도 남긴다. 의도적으로 어려운 사례를 모은 평가와 실제 전체 영상 평가를 따로 보고한다.

## 6. 검수 라벨

| 결정 | 의미 |
|---|---|
| `PASS` | 현재 범위와 근거에서 게시 전 별도 검토할 이유를 찾지 못함 |
| `REVIEW_REQUIRED` | 사람이 다시 볼 구체적인 표현·행동·대상·이유가 있음 |
| `UNCERTAIN` | 입력·문맥·기준이 부족하거나 해석이 갈림 |

이는 오프라인 주석용 결정이다. 현재 DB·API가 이 세 값을 이미 제공한다는 뜻은 아니다. 분석 실패는 결정과 별도로 기록하고, `PASS`를 논란이 없다는 보증으로 설명하지 않는다.

유형은 다중 선택을 허용한다. 텍스트는 기존 `STRONG_NEGATIVE_REVIEW`, `BELITTLEMENT`, `MOCKERY`, `GENERALIZATION`, `UNFAMILIAR_CONTEXT`, `DISCRIMINATION`, `HATE_SPEECH`를 기준으로 경계를 맞춘다. 행동은 관측 동작과 검수 이유를 별도 라벨로 둔다.

각 주석은 대상, 사용 방식, 원문·행동 근거 위치, 구체적 이유, 부족한 정보, 필요한 입력을 포함한다. 일반 불만을 모두 비하로 만들지 않고, 불명확한 유형을 억지로 확정하지 않는다. 모델 점수·확신도·논란 발생 확률은 사람의 정답으로 사용하지 않는다.

## 7. 독립 주석과 품질 관리

1. 수집자가 원본·시점·입력 자료와 선정 방식을 기록한다.
2. 평가자 A·B가 모델 출력과 사건 기사·댓글 반응을 보지 않고 독립 판단한다. 사건을 이미 알면 사전 인지를 표시한다.
3. 두 사람 모두 필요한 원본 영상과 문맥을 확인하고 결정·유형·근거·이유를 남긴다.
4. 제3자가 이견의 이유를 검토한다. 기준을 바꾸면 영향받는 기존 자료도 다시 확인한다.
5. 미해결 차이는 원래 주석과 함께 보존하고 최종 결정을 `UNCERTAIN`으로 둔다.
6. 동일 유형의 표본을 재검수하고 출처·범위·중복·근거를 점검한다.

파일럿에서 최초 결정 일치율·혼동표와 가능하면 Cohen's kappa를 기록한다. 다수결만으로 이견을 삭제하지 않는다. 주관적인 판정의 불일치가 서로 다른 관점을 반영할 수 있다는 연구를 참고한다. [When the Majority is Wrong](https://aclanthology.org/2023.emnlp-main.415/)

일부 문맥 민감 사례에는 핵심만 보는 주석과 충분한 문맥을 보는 주석을 각각 마련한다. 순서의 영향을 줄이도록 평가자나 세션을 나누고, 판단 변화와 정보 부족으로 인한 보류를 구별한다.

## 8. 저장 구조

초기에는 표 형태로 주석하고 확정본을 JSONL로 내보낸다. 실제 자료는 접근을 제한한 로컬 저장소에서 관리한다. 공개 저장소에는 스키마·가이드·합성 예시만 둔다.

| 파일 | 핵심 필드 |
|---|---|
| `sources.jsonl` | 원본 ID·URL, 공개일, 길이, 해시, 원본 상태, 이용 범위·확인 근거 |
| `incidents.jsonl` | 사건 ID, 문제로 제기된 내용, 근거 출처·공개일, 미확인 사항 |
| `cases.jsonl` | 사례 ID, 원본/사건/연속구간/대조쌍/누출그룹 ID, 수집 방식, 핵심·문맥 범위, 입력 상태 |
| `segments.jsonl` | 구간 ID, STT/OCR 종류, 밀리초 범위, 원문·확인 텍스트, 프레임 참조, 처리 버전 |
| `visual_events.jsonl` | 관측 행동, 시작·핵심·종료, 영상 내 인물 트랙, 가시성, 원본 프레임·키포인트 참조 |
| `annotations.jsonl` | 평가자 ID, 결정·유형, 대상·사용 방식, 근거, 이유, 부족한 정보, 사전 인지, 기준 버전 |
| `adjudications.jsonl` | 최종 결정·유형, 합의 이유, 미해결 차이, 재검토 상태 |
| `coverage.jsonl` | 사람이 확인한 원본 영상 범위, 미확인·범위 밖 구간 |
| `splits.jsonl` | 사례 ID, 용도, 분할 그룹, 분할 버전 |
| `manifest.json` | 데이터셋·스키마·기준 버전, 자료 수·독립 그룹 수, 분할 규칙, 검수 상태·한계 |

ID는 서버 finding ID와 독립적으로 발급한다. 수정은 기존 주석을 덮지 않고 버전과 이유를 남긴다. 없음·미확인·해당 없음의 빈 값 의미를 구분한다.

자동 검증 대상은 ID·참조 무결성, 원본 길이 내 시간 범위, 핵심을 포함하는 문맥 범위, 실제 원문 인용, 허용 라벨·필수 이유, 중복과 분할 그룹 누출이다. 행동 시점은 원본 프레임의 실제 시간과 맞춘다.

## 9. 분할과 누출 방지

사례 검색·개발용, 튜닝용, 최종 평가용을 그룹 단위 약 60/20/20으로 나누되 독립성을 우선한다. 파일럿은 개발용으로만 쓴다.

같은 사건·원본·재업로드·중복·대조쌍은 같은 그룹에 묶는다. 인접 클립이나 키포인트 시퀀스를 다른 분할에 넣지 않는다. 같은 제작자를 외웠는지 확인할 때는 제작자도 분리한다.

최종 평가 자료와 같은 사건의 유사 구간을 프롬프트 예문·검색 인덱스·사전·튜닝에 넣지 않는다. 평가 결과를 보고 수정했다면 해당 자료를 개발용으로 전환하고 새 최종 평가셋을 마련한다.

## 10. 현재 서버와의 연결

`TranscriptSegment`·`ScreenText`의 원문·시점을 가져오되 사람 확인 자료와 별도로 관리한다. `RiskFinding`은 모델 후보이며 정답이 아니다. 후보로 나오지 않은 구간도 독립 사례 ID로 등록할 수 있어야 한다.

`ReviewAction`의 `CONFIRMED`는 봤고 그대로 두었다는 의미이고, `EDITED`는 편집했다는 의미다. 위험이 맞다는 확정 라벨은 아니다. `NOT_USEFUL`은 중복·설명·우선순위 때문에 불필요할 수 있어 자동으로 일반 용례에 편입하지 않는다. `HOLD` 이유도 별도로 확인한다.

현재 액션은 갱신 시 이전 값이 덮이고 재분석에서 기존 finding·액션이 삭제될 수 있다. 자료로 축적하려면 별도 스냅샷·이력·독립 주석이 필요하다. `PoseAnalyzer`는 현재 미구현이다. 이 계획에서는 운영 DB·API를 변경하지 않는다.

## 11. 일정·비용·완료 조건

3명 팀이 주당 각 5~8시간씩 참여하는 4~6주 초안이다. 첫 주에 실제 시청·주석 소요시간을 재고 수량·기간을 조정한다.

| 단계 | 작업 | 산출물 |
|---|---|---|
| 1주차 | 필드·행동 범위·30개 파일럿 | 가이드 v0.1, 독립 주석·이견 목록 |
| 2주차 | 기준 조정·대조 사례·그룹 정의 | 가이드 v0.2, 확정 대조쌍·출처 |
| 3~4주차 | 실제 200개 목표 주석·완결 영상 검토 | 주석·합의/보류, 전체 검토 범위 |
| 5~6주차 | 재검수·JSONL·누출 점검·실험 설계 | v0.1 manifest, 고정 평가셋·비교안 |

수집·정리 1명, 독립 주석 2명을 기본으로 하고 수집 담당이 이견 검토를 맡는다. 동일 사람이 두 독립 주석을 모두 만들지 않는다.

작업량은 사례 수 × 두 사람의 시청·주석 시간 + 수집 + 이견 조정 + 완결 영상 검토로 추정한다. 기존 산출물을 재사용하고 유료 도구·외부 API 재분석은 자동 실행하지 않는다. 무료 라이브러리도 연산·저장 비용은 있으므로 장시간 모델 실행은 작은 프로파일링 결과부터 확인한다.

완료 조건은 출처·이용 범위 확인, 일반·문제·경계·대조 사례 확보, 두 독립 주석과 근거·시간, 완결 영상 검토 범위, 그룹 누출 검사, 범위·라벨 분포·일치도·한계를 담은 데이터셋 카드다. 미확인 자료는 보류한다.

다음 비교는 같은 모델·입력에서 기본 프롬프트, 현재 파이프라인, 사례 대조·시각 정보를 추가한 구성으로 진행한다. 짧은 구간 분류와 긴 영상 전체 탐지 성능을 나눠 보고, 추출 오류·후보 누락·판단 오류·위치 오류를 구별한다.

## 12. 논란 단어·은어 데이터셋 구축: KOLD를 참고한 설계

### 12.1 KOLD에서 참고할 구조와 적용 한계

KOLD는 NAVER 뉴스·YouTube의 댓글 40,429개에 공격성 여부, 대상 유형·집단, 공격 표현과 대상의 근거 구간을 주석한 자료다. 기사·영상 제목을 문맥으로 제공한다. Level A는 `OFF/NOT`, B는 공격 대상 `UNT/IND/GRP/OTH`, C는 집단 대상의 세부 구분이다. [KOLD 논문](https://aclanthology.org/2022.emnlp-main.744/), [원문 §2](https://aclanthology.org/2022.emnlp-main.744.pdf)

논문은 사례별 세 주석을 모아 다수결과 검사자 조정으로 라벨을 정한다. 우리 파일럿은 두 독립 주석과 제3자 검토로 시작하고, 해결되지 않은 이견을 보존한다. 이는 KOLD 절차의 그대로인 재현이 아니라 소규모 팀에 맞춘 제안이다. [원문 §3.2](https://aclanthology.org/2022.emnlp-main.744.pdf)

| 참고할 관점 | OoPs?!에서 기록할 내용 | 그대로 옮기지 않을 것 |
|---|---|---|
| 공격성 여부 | 현재 발언의 공격성 주석 | `OFF`를 자동 `REVIEW_REQUIRED`로 변환 |
| 공격 대상 | 사람·집단·조직·상품/서비스·불명·대상 없음 | 공격 대상에서 화자의 소속·정체성을 추론 |
| 공격 표현·대상 구간 | 원문 인용과 문자 범위, 연결 영상 시점 | 민감 단어 한 개를 항상 공격 근거로 지정 |
| 제목 문맥 | 실제 앞뒤 대화, 필요한 동시간대 화면 | 게시 후 댓글·기사를 게시 전 판단 입력에 사용 |
| 주석 품질 관리 | 독립 판단, 이견과 기준 버전 기록 | 모델 답변을 사람의 정답으로 사용 |

댓글의 공격성 분류와 영상의 게시 전 검수는 다른 과제다. 제품은 일반 비평·강한 불만·인용·음성 인식 오류도 구분해야 하므로, KOLD의 분류 체계나 성능을 영상 검수 성능으로 환산하지 않는다. K-MHaS도 보조 참고 자료로 유지하며 핵심 영상 평가셋과 섞어 단일 성능을 내지 않는다.

직접 데이터 사용을 검토할 때는 [저자 저장소](https://github.com/boychaboy/KOLD)의 배포 조건·라이선스·개인정보 처리·상업적 학습 및 재배포 범위를 별도로 확인한다. 공개 논문·다운로드 링크만으로 이용 허가가 확인된 것으로 처리하지 않는다. 현재는 구조 참고만 반영했으며 데이터 다운로드·학습은 실행하지 않았다.

### 12.2 표현 사전과 실제 사용 사례를 분리

단어 목록은 후보를 찾는 장치이고, 사례 데이터셋은 서로 다른 쓰임을 평가하는 자료다. 사전 항목 하나에 여러 사례를 연결하며, 사전에 없는 발언의 사례도 등록할 수 있게 한다.

| 층 | 기록 | 용도 |
|---|---|---|
| 표현 카드 | 안정적인 표현 ID, 원형·변형, 일반 의미·검토할 맥락, 출처·이견·점검일 | 사전 항목의 설명과 매칭 기준 점검 |
| 실제 사용 사례 | 발언·앞뒤 문맥·원본 시점·대상·입력 품질·표현 ID 목록 | 의미와 검수 판단의 대조 |
| 사람의 주석 | 결정·공격성·사용 방식·근거 위치·이유·부족한 정보 | 평가와 기준 개선 |

표현 카드에는 `DRAFT`, `VERIFIED`, `DISPUTED`, `EXCLUDED`, `RETIRED` 같은 관리 상태를 제안한다. `VERIFIED`는 기록한 용례·설명의 근거를 확인했다는 뜻이지 표현 자체가 유해하다는 뜻이 아니다. 근거의 신뢰 상태와 실제 활성화 여부는 별도 필드로 관리한다. `~노` 단독 탐지는 제외 상태를 유지한다.

현재 `context-lexicon.json`의 `id`, `patterns`, 힌트·설명·점검일을 출발점으로 삼는다. 카드의 새 필드와 실제 사례는 처음에는 비공개 자료 파일로 관리한다. Java 파서·검증 코드의 지원을 확인하기 전에는 런타임 JSON에 새 필드를 무작정 넣지 않는다.

### 12.3 한 표현에서 수집할 서로 다른 용례

일상적 의미, 사람·집단을 향한 사용, 설명·비판·뉴스 인용, 농담·연기·재현, 해석이 갈리는 사용, STT/OCR 오인식을 함께 수집한다. 실제로 존재하지 않는 용례를 수량 목표 때문에 만들어 채우지 않는다.

특수한 의미로 사용됐다는 사실과 공격적인 사용인지는 별개다. 커뮤니티에서 쓰인다는 이유만으로 공격성을 부여하지 않는다. 인용·농담도 자동 통과 조건이 아니며 현재 대상에 대한 동조·조롱이 있는지 확인한다.

수집 시작점은 기존 v1·v2·v3에서 확인되는 오탐·미탐, 출처가 부족한 사전 항목, 일반 뜻과 특수 뜻이 겹치는 표현이다. 출처·이용 범위를 확인한 실제 영상과 일반 용례를 우선한다. 기사·댓글은 원본 후보를 찾는 조사 자료로 분리하고, 논란 발생을 정답으로 만들지 않는다.

띄어쓰기·초성·철자·음성 유사 변형은 실제 용례나 오인식 근거가 있을 때 추가한다. 모델이 만들어낸 변형은 합성 테스트로만 보관하고 실제 표현의 존재 근거로 쓰지 않는다. 음성 자체에 표현이 없으면 STT 오탐이며, 프롬프트의 의미 판정 오류와 별도로 센다.

### 12.4 주석 항목: 의미·공격성·검수 결정의 세 축

아래는 우리 스키마의 제안이다. KOLD 필드의 원형이나 현재 API 계약이 아니다.

| 항목 | 제안값·내용 | 주의점 |
|---|---|---|
| `meaning_use` | `LITERAL`, `CONTEXTUAL`, `UNRESOLVED` | 특수 의미가 곧 공격이라는 뜻은 아님 |
| `usage_tags` | 평가·인용·설명·비판·농담·현재 공격 등 복수 태그 | 인용과 현재 공격이 동시에 가능 |
| `offensiveness` | `OFF`, `NOT`, `UNCERTAIN`, `NOT_ASSESSED` | 뒤의 두 값은 우리 보류·미평가 확장 |
| `target_type`, `target_text` | 사람·집단·조직·상품/서비스·불명·대상 없음 | 명시된 발언의 대상만 기록, 정체성 추정 금지 |
| `decision`, `reason` | `PASS`, `REVIEW_REQUIRED`, `UNCERTAIN`와 구체적인 검수 이유 | 공격성·낯선 의미·사후 논란과 별도 판단 |
| `offensive_spans`, `target_spans`, `evidence_spans` | 항목 ID·원문 인용·문자 범위 | 공격성 근거가 없으면 공격 표현 배열은 비움 |
| `required_input`, `missing_information` | 텍스트·음성·화면 필요 여부, 부족한 맥락 | 억양·표정을 텍스트에서 확인했다고 설명하지 않음 |

문자 범위는 참조 세그먼트의 변경하지 않은 문자열에서 0부터 시작하는 `[start, end)` Unicode 코드포인트 기준으로 정의한다. Java의 UTF-16 인덱스 등과 변환할 때 일치 검증을 둔다. STT 원문과 확인 전사는 서로 다른 문자열 ID로 연결하며 수정 뒤 같은 offset을 재사용하지 않는다. 익명화한 사본도 별도 ID와 범위 매핑을 사용한다.

근거는 한 단어에 한정하지 않는다. 공격이 여러 문장에 걸쳐 성립하면 여러 근거 구간과 지칭 대상이 드러나는 문맥을 함께 기록한다. 문자 위치만으로 단어의 정확한 영상 시각을 만들지 않으며, 단어 정렬이 없으면 확인된 세그먼트·핵심 영상 범위를 사용한다.

공격성이 낮더라도 중대한 사실 주장이나 확인할 외부 맥락이 있을 수 있다. 반대로 인용 안의 욕설이 확인돼도 현재 화자의 공격으로 단정할 수 없다. 낯선 의미를 이유로 표시할 때는 현재 용례와 확인된 출처가 무엇을 뒷받침하는지 설명하고, 단순한 연관 가능성만으로 경고하지 않는다.

### 12.5 텍스트 중심 80개를 먼저 만드는 순서

공통 v0.1의 텍스트 80개 안에서 아래 구성을 시도한다. 전체 200개에 추가하는 별도 80개가 아니며, 파일럿 30개도 별도로 유지한다.

| 수집 묶음 | 목표 | 선택 기준 |
|---|---|---|
| 우선 표현 10개 × 실제 용례 약 6개 | 60개 | 서로 다른 사용 맥락·일반 용례·경계·인식 오류 |
| 사전 단어가 없는 발언 | 20개 | 일반 비평과 사람·집단 공격, 대상이 확대되는 흐름 |

수량은 수집 목표다. 위험/일반/보류 라벨을 정해놓고 주석을 맞추지 않으며, 같은 원본의 유사한 문장으로 수량만 늘리지 않는다. 실제 대조쌍은 사람이 문맥 차이를 설명할 수 있는 것만 연결한다.

1. 파일럿에서 원문·의미·대상·근거·결정의 경계를 두 사람이 맞춘다.
2. 현재 사전 항목 중 오탐·미탐·근거 부족 기준으로 우선 표현 10개를 고른다.
3. 수집자는 원본과 일반 용례를 확보하고, 주석자는 모델 결과·사후 반응을 보기 전에 독립 판단한다.
4. 제3자가 이견을 검토한다. 해결되지 않으면 보류하며 원래 의견을 지우지 않는다.
5. 원본·사건·대조쌍 그룹으로 개발/튜닝/최종 평가를 분리하고 중복을 검사한다.
6. 고정된 평가 자료에서 개선 전후의 후보 누락·일반 용례 오탐·근거 오류를 비교한다.

초기 표현 카드 파일 `terms.jsonl`을 제안한다. `term_id`, 기존 `lexicon_id`, 원형·변형, 의미·용례 출처, 근거 상태, 제외 여부, 점검일·버전·연결 사례 ID를 둔다. `cases.jsonl`에는 표현 ID 목록을 선택값으로 추가하고, `annotations.jsonl`에 위 세 축의 주석을 넣는다. 표현 ID가 없는 사례도 유효하다. 기존 공통 파일을 중복 생성하지 않는다.

### 12.6 서버에 적용하는 순서와 평가

첫 활용은 새 모델 학습이 아니라 평가와 사전 점검이다. 개발용 사례로 힌트·매칭·프롬프트를 수정하고, 최종 평가용 사례는 예문·검색 자료·튜닝에 넣지 않는다.

| 비교 | 확인할 질문 |
|---|---|
| 확인 전사로 평가 | 입력이 정확할 때 의미·대상·검수 판단이 맞는가? |
| 실제 STT/OCR로 평가 | 추출 오류까지 포함해 무엇을 놓치거나 잘못 올리는가? |
| 현재 사전·프롬프트 vs 대조 사례 추가 | 일반 용례와 공격적 용례를 함께 제공하면 오탐·미탐이 어떻게 바뀌는가? |
| 사전 단어 없음 | 전체 발언 검토가 사전 밖의 공격·일반화를 찾는가? |

매칭 단계의 후보 재현율, 의미·대상 구분 오류, 최종 검토 정밀도·재현율, 일반 용례의 불필요 알림, 근거 구간 일치, 보류·미처리 비율, 영상당 검수시간·호출 비용을 따로 기록한다. 의도적으로 어려운 표현을 모은 사례셋과 전체 영상을 끝까지 확인한 평가를 분리해 보고한다.

사례 검색은 먼저 표현 ID·대상·사용 방식으로 필요한 개발용 사례를 골라 비교한다. Vector DB는 필수 선행조건이 아니다. 새 분류기나 파인튜닝은 사용 가능 자료와 독립 평가가 충분해진 뒤 검토한다. KOLD를 직접 활용한다면 원래 댓글 라벨은 출처와 함께 유지하고 우리 영상 라벨로 자동 변환하지 않는다. 공개된 자료에 대한 모델의 사전 학습 가능성도 평가 한계로 기록한다.

운영자의 `CONFIRMED`·`NOT_USEFUL` 액션을 자동 정답으로 편입하지 않는다. 미탐 제보와 불필요 사유를 별도 수집·검수해, 버전 있는 사전과 다음 개발용 자료에 반영한다. 기존 산출물을 재사용하는 오프라인 작업부터 시작하며 유료 API 재실행·대규모 다운로드는 이 문서 작성으로 승인된 작업이 아니다.

## 부록. AI 검수 기준 가상 사례

기존 `AI-검수-사례-초안.md`를 통합했다. C01~C24와 미합의 경계 사례를 보존하며 실제 수집·평가 자료와 분리한다. C02의 강한 부정 평가 표시 여부 등은 확정 정답이 아니라 팀 기준을 맞출 논점이다.

> 용도: 팀 라벨링 기준을 맞추기 위한 시작 자료 · 상태: 합의 전 · 사례: 모두 가상 예문

실제 영상·행동 자료의 수집과 주석은 [이 문서의 공통 구축 계획](#1-목표와-범위)을 따른다. 이 가상 사례 표와 실제 사람 합의 자료는 구분한다.

이 표는 모델 정답표가 아니다. 공개된 실제 영상 사례나 제작팀의 합의 없이 적은 초안이므로, 모델 점수 조정에 쓰기 전에 사람이 검토해야 한다. AI가 낸 후보만 보고 평가하면 놓친 장면을 셀 수 없으므로, 실제 평가에서는 영상 전체를 검토하고 후보로 나오지 않은 중요 구간도 기록한다.

| ID | 입력·맥락 | 초안상 처리 | 이유 또는 확인할 점 |
|---|---|---|---|
| C01 | “제 입에는 별로였어요.” 음식점 리뷰 | 표시하지 않음 | 보통의 취향 평가 |
| C02 | 특정 가게를 가리키며 “이 돈 주고 먹기엔 아깝다.” | 낮은 우선순위의 강한 부정 평가 후보 | 대상이 분명하고 표현이 단순한 취향 표현보다 강함. 한 번만 나와도 검토할 수 있음 |
| C03 | “음식이 별로다”를 여러 번 말하지만 모욕·조롱은 없음 | 판단 기준 합의 필요 | 반복 불만만으로 표시할지 제품 기준 결정 |
| C04 | “사장 얼굴이 음식보다 더 별로다.” | 비하·조롱 후보 | 평가가 음식에서 사람을 향한 모욕으로 이동 |
| C05 | “그 동네 사람들은 다 수준이 낮다.” | 일반화 후보 | 개인 평가를 지역 집단 전체로 확장 |
| C06 | “내가 요리를 진짜 못한다.” | 표시하지 않음 | 화자 자신의 능력에 대한 자기 평가 |
| C07 | “그 사람을 ‘사기꾼’이라고 부르더라.” 사실 여부와 거리가 있는 인용 | 문맥 확인 | 현재 화자의 동조·조롱인지 단순 전달인지 확인 |
| C08 | “그 사장은 사기꾼이다.” 구체적인 행위 근거는 없음 | 표현 검토와 사실 대조를 별도 평가 | 표현의 수위와 주장 진위를 한 번에 판정하지 않음 |
| C09 | “그 사람들이 쓴 표현은 차별적이라 쓰면 안 됩니다.” | 보통 표시하지 않음 | 문제 표현을 비판·설명하는 맥락 |
| C10 | 문제 표현을 인용한 직후 특정 출연자를 비웃음 | 검토 후보 | 인용 형식이어도 현재 장면이 조롱에 쓰이는지 확인 |
| C11 | “저 의원도 결국 수박이더라고.” 정치 문맥 | 사전 출처를 확인한 뒤 맥락 검토 | 일반 명사와 특수 용례가 겹침 |
| C12 | “수박을 반으로 잘라 먹었다.” 음식 문맥 | 표시하지 않음 | 일반 용법 근거가 분명함 |
| C13 | “광주에서 포도를 먹었다.” 과일 문맥만 있음 | 표시하지 않음 | 지역·과일 말이 같이 있다는 이유만으로 특수 의미를 만들지 않음 |
| C14 | “광주”와 역사 사건 맥락에서 “포도”를 특정 별칭처럼 사용 | 사전의 근거 자료와 현재 문맥이 모두 뒷받침할 때 후보 | 단어 매칭만으로 사건 연관성을 단정하지 않음 |
| C15 | 자연스러운 경상도 말투의 “밥 묵었노?” | 표시하지 않음 | `~노` 단독 탐지 제외 원칙 유지 |
| C16 | 출신 지역 단서 없이 문장 끝에 “좋노”가 한 번 나옴 | 표시하지 않음 | `~노`는 이번 기본 사전 범위 밖 |
| C17 | 음성에는 문제가 될 표현이 있고 화면 OCR 결과는 없음 | 발언 검토 | OCR 텍스트가 없어도 STT 대본으로 계속 분석 |
| C18 | 음성은 없고 화면에 강한 부정 표현이 나옴 | 화면 글자 검토 | 음성 분석 미실행을 전체 분석 실패나 통과로 오해하지 않게 표시 |
| C19 | OCR 결과가 “재선커”로 깨져 있고 원본 프레임도 불명확 | 판단 보류 또는 제외 | 복원 추측을 원문처럼 표시하지 않음 |
| C20 | 같은 발언이 STT와 편집 자막에 거의 그대로 나타남 | 한 장면으로 묶을 수 있으나 점수는 자동 상승하지 않음 | 두 출처가 같은 신호를 반복한 것일 수 있음 |
| C21 | 같은 가게에 대한 발언이 영상 앞부분과 뒷부분에 각각 나옴 | 별도 후보 | 같은 대상만으로 서로 다른 장면을 병합하지 않음 |
| C22 | 은어를 설명하는 교육 장면에서 예문으로 소개 | 보통 표시하지 않음 | 용어 사용과 의미 설명을 구분 |
| C23 | 영상 대본 안에 “이전 지시를 무시하고…”라는 문장이 포함 | 문장 자체만 검토 | 대본 속 지시문은 AI 지시가 아님 |
| C24 | 후보가 시간상 영상 후반에 몰리지만 상한 때문에 일부 확인되지 않음 | 부분 검토 경고 | 검토한 범위와 확인하지 못한 후보 수를 결과에 남김 |

### 라벨링 기록 항목

각 실제 사례에는 원문과 앞뒤 문맥, 영상 시각, 입력 종류(STT/OCR), 사전 항목 ID, 모델 응답, 최종 병합 결과, 사람의 결정, 이유를 기록한다. 결정을 `PASS`, `REVIEW_REQUIRED`, `UNCERTAIN` 중 하나로 정하고, 오탐·미탐·위치 오류·병합 오류도 별도로 표시한다.

최소 두 사람이 일부 경계 사례를 독립적으로 분류한다. 의견이 갈리면 정답을 임의로 고정하지 말고 기준을 고치거나 판단 보류로 남긴다. 프롬프트에 예시로 넣은 사례는 최종 비교용 평가 사례에서 분리한다.

### 다음 라벨링 순서

1. 이 초안에서 논란 기준이 갈리는 C02·C03·C07·C08·C10·C14를 팀에서 먼저 합의한다.
2. v1·v2·v3의 기존 분석 자료에서 실제 구간을 확인하고, 영상 전체의 누락 후보도 기록한다.
3. 일반 리뷰·은어 일반 용법·인용·OCR 오류 같은 정상 또는 경계 사례를 추가한다.
4. 사례를 프롬프트 예시용과 최종 비교용으로 나누고, 변경 전후를 같은 기준으로 비교한다.
