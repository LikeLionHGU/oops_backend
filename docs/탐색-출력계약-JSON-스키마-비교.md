# 탐색 출력 계약 · JSON/strict 스키마 비교

2026-10-16 · minwook · 새 추정 상한 $0.50과 저장·합성 텍스트의 OpenAI 전송을 사용자 승인받았다. 영상·음성은 전송하지 않았다. 실제 청구액 보장 한도는 아니다.

## 바꾼 변수

이전 [검색 OFF/ON 비교](구조화검색-OFF-ON-정상경계-비교.md)와 달리 **검색은 양쪽 모두 ON**으로 고정했다. 동일 v7 사전·정상 초안 6개·Groq 실제 발췌 2개를 사용하며 판단 프롬프트·모델·추가 라우터/원문 관계 OFF 조건도 유지했다.

JSON 모드와 탐색 DTO 전용 strict 스키마만 바꿔 각 2회, 총 32회 엔진 분석을 실행했다. 첫 반복은 JSON→STRICT, 다음은 STRICT→JSON이다. 별도 합성 상품 설명 1회가 strict 요청에 정상 응답했을 때만 본 비교를 시작했다. 형식 계약은 [OpenAI 공식 문서](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=chat)를 참고했으며 실제 호환 여부는 이번 요청 결과로 확인했다.

이전 계획을 수정하지 않고 새 comparisonFactor=OUTPUT_CONTRACT 계획과 별도 승인 문자열을 사용했다. 검색 카탈로그·사전·판단 계약·출력 스키마 SHA256을 고정했다. 빈 후보 응답이나 판단을 강제로 만들지 않았고, 제공자 실패·예산/사용량 추적 오류 시 중단하도록 했다. 과거 정상 초안은 여전히 검수 전이며 정식 사전에 추가하지 않았다.

## 실행 결과

호환 시험 PASSED 후 32/32 분석을 완료했다. 호환 시험을 포함한 HTTP 46시도와 사용량 46건이 일치했다. 탐색은 전용 출력 형식을 사용했고 검증/복구는 기존 JSON 모드였다. 원문 관계 제안을 반환한 탐색 응답은 양쪽 0건이다.

| 항목 | JSON | STRICT |
|---|---:|---:|
| 본 비교 탐색 응답 | 18 | 18 |
| `truncated` 누락/null | 2 | 0 |
| 정상 초안 SUCCESS·경고 0·미판정 0 | 10/12 | 12/12 |
| 정상 초안 FAILED | 2/12 | 0/12 |
| 정상 초안 경고 수 | 0 | 0 |
| v4 속옷 질문 경고 · 반복 순 | 0·1 | 1·1 |
| v6 집단 전체 표현 경고 · 반복 순 | 0·0 | 0·0 |

별도 호환 시험의 탐색 1건도 필수 Boolean을 반환했다. 표의 탐색 18회에는 포함하지 않는다. JSON 정상 실패는 자기 경험 1회와 사적 질문의 비판적 인용 1회이며 모두 `DISCOVERY_TRUNCATED_REQUIRED`다. 수가 적은 합성 개발 대조이고 반복 2회이므로 오류율 0%나 범용 안정성을 주장하지 않는다.

### 남아 있는 오류

실제 발췌 8회는 모두 PARTIAL이다. strict 형식을 준수해도 다음 의미·원문 범위 문제는 남는다.

- **primary/context 혼동:** JSON/STRICT 각각 1회에서 uncertainSegments에 현재 reviewed/primary 밖의 ID를 넣어 탐색 묶음이 거절됐다. JSON은 뒤 문맥의 ID, STRICT는 앞 배치의 ID였다. 허용 창 문맥을 실제 검토 대상으로 잘못 반환한 문제다.
- **대표 anchor 범위:** `PROPOSAL_ANCHOR_NOT_REVIEWED`는 JSON 2회·STRICT 1회 남았다. 같은 발언이 다른 배치에서 살아날 수 있으므로 건수만 미탐 수로 계산하지 않는다.
- **행위 방향:** STRICT의 v4 한 이유에 ‘보여드릴까요?’라는 제안을 ‘보여 달라’는 흐름으로 설명한 부분이 있다. 동의·강요·화자 신원을 보충하지 말아야 하며, 올바른 형식이라고 이런 이유가 정답이 되지는 않는다.
- **집단 단정 경계:** 양쪽 v6는 주로 뒤의 특정 행위 비판 표현을 대표로 삼고 PASS했다. 원래 ‘진영 모두/전체’의 쟁점 유지와 평가 기준 검수가 여전히 필요하다. 독립 정답 미확정이므로 경고 0을 확정 정상/미탐으로 집계하지 않는다.

## 코드 반영과 다음 순서

필수 Boolean 누락 감소와 해당 정상 대조 보존을 근거로 **탐색 strict 출력을 코드 기본 ON**으로 승격했다. 논란 판단 정확도 향상을 승인한 것은 아니다.

- `STRUCTURED_DISCOVERY_OUTPUT_ENABLED=false`로 기존 JSON 모드를 명시 선택할 수 있다. Spring 재시작 후 반영되며 이 작업에서 서버 재시작·AWS 배포·실제 `.env` 변경은 하지 않았다.
- 검증·복구·라우팅·이미지와 과거 명시적 2인자 클라이언트는 기존 모드를 유지한다. 다른 모델·제공자는 재확인한다. 미지원 시 JSON 모드로 자동 재전송하지 않는다.
- 다음은 primary/context ID 반환 계약 → 요청/제안·주체/대상 보존 → 집단 단정 경계 검수다. 누락/범위 오류를 조용히 삭제하거나 원문을 추측 교정하지 않는다.
- 추가 모델 시험은 새 승인 범위에서 수행한다. 현재 정상 대조는 개발 초안이며 별도 영상·정상 사례 검증도 필요하다.

위 실험의 출력 스키마와 구별되는 `candidate_discovery_scoped_v2`를 반영했다. 판단 정책·원문·검색·창 크기는 유지하고 탐색의 범위 안내와 반환 가능 ID만 바꿨다. 이전 실험 결과를 이 변경의 검증 결과로 재사용하지 않는다.

`JsonSchemaOutput.discoveryIdScope`를 명시한 DTO만 요청 JSON에서 ID를 읽어 스키마의 primaryId/rawId 공유 정의에 enum을 넣는다. [공식 구조화 출력 문서](https://developers.openai.com/api/docs/guides/structured-outputs)의 enum 계약을 사용한다. 본문을 추가 복제하거나 보조 문맥을 지우지 않으며, 매 요청 새 트리를 사용해 다른 배치의 허용 ID가 섞이지 않는다. 실제 요청과 typed replay는 같은 생성 경로다.

스키마만으로 `anchor/uncertain ⊆ 실제 reviewed`나 같은 허용 창의 근거 연결을 보장하지 못하므로 기존 서버 검증은 유지했다. 범위가 맞아도 원문의 ‘제안’을 ‘요구’로 바꾸는 해석 오류는 여전히 별도 문제다.

## ID 범위 단독 실호출 비교 · 2026-10-16

새 추정 상한 **$0.50 및 저장·합성 텍스트/선택된 사전 참고의 OpenAI 전송**을 승인받아 완료했다. 영상·음성은 보내지 않았다. 양쪽 strict 출력·현재 프롬프트·검색 ON·사전·모델을 동일하게 고정하고, ID enum 제한만 UNSCOPED/SCOPED로 분리했다. 이전 프롬프트와 비교한 실험은 아니다.

실제 발췌 2개와 기존 정상 초안 6개를 각 2회, 총 32회 분석했다. 순서는 UNSCOPED→SCOPED / SCOPED→UNSCOPED로 교차했다. SCOPED 합성 상품 설명 호환 시험 1회가 통과한 뒤 진행했다. 테스트 전용 UnscopedDiscovery DTO만 동적 enum을 생략하며 Spring에는 연결하지 않았다. 모의 전송에서 두 요청이 enum 외에는 같은지 확인하고, 실제 호출별 출력 형식 해시와 범위 ON/OFF를 기록했다.

이번에는 제한을 빼도 범위 오류가 나오지 않아 **제한 추가의 감소 효과는 입증하지 못했다.** 양쪽 프롬프트에 같은 범위 안내를 사용했다는 점과 반복 2회의 작은 개발 표본을 고려한다. ID 제약을 의미 판단의 중립적 변화라고 가정해서도 안 된다. SCOPED는 v6에서 추가 후보를 만들어 검증 호출과 시간이 늘었다. 경고 0만으로 두 경로의 안정성이 같다고 해석하지 않는다.

v4의 최종 검증 실패는 UNSCOPED `TARGET_EVIDENCE_REQUIRED` 1건, SCOPED `TARGET_MENTION_RELATION` 1건이었다. 모든 v4 실행에는 문맥 제한 후보도 남았다. v6 SCOPED의 후보는 검증에서 PASS했으나 각 반복 2개 후보의 `contextLimited=true` 때문에 미판정을 보존해 PARTIAL이었다. 출력 ID 오류나 제공자 실패로 분류하지 않는다. v6 독립 정답도 확정하지 않는다.

### 다음 · 원문 행위·대상 방향 보존

이전 STRICT 반복 1에서 원문 `살짝 보여드릴까요?`와 탐색의 ‘보여주겠다는 제안’이 실제 검증 입력에도 모두 있었다. 최종 이유만 ‘보여 달라’로 변했다. 이 건은 원문이 중간에 잘려 사라진 것이 아니라 검증 생성 단계의 재해석 오류다. 이번 비교에서는 그 정확한 문구 변화는 재현되지 않았지만, 보여주겠다고 말한 주체와 공개 대상/대화 상대를 혼동하는 설명·대상 계약 실패가 남았다.

해당 실제 전사에는 앞서 ‘오펜무가 뭐예요?’도 있다. 뒤의 표현이 직접 사적 질문인지 용어를 풀어 말한 것인지 구분할 필요가 있지만, 화자 정보가 없는 전사만으로 어느 쪽이라고 새 정답을 확정하지 않는다.

새 `utterance-direction-boundaries.json`에 자기 공개 제안/타인에게 요청/용어 풀이/비판적 인용/화자 미확정/거절 존재를 나눠 합성 관계 초안 6개를 추가했다. 최종 PASS/경고 정답은 부여하지 않았고 사전에도 승격하지 않았다. 무료 테스트는 잘못된 후보 가설·인용이 있어도 원문·순서·시간·ID가 검증 요청까지 보존되고 관계 라벨이 모델 입력에 섞이지 않는지만 확인한다. 모델이 의미를 올바르게 판단한다는 테스트가 아니다.

다음 비교는 검증 지침의 최소 보강을 우선한다. ‘누가 무엇을 누구에게 제안/요청했는지 보존하고, 질문·용어 풀이·인용·거절·실제 공개를 서로 바꾸지 말며, 화자/동의/실제 실행은 확인된 원문 범위만 적는다’는 방향이다. 제안이면 자동 정상, 요청이면 자동 경고라는 단어 규칙은 만들지 않는다. 새로운 유료 비교는 별도 계획과 승인을 받는다.
