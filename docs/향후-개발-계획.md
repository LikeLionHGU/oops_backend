# OoPs?! 향후 개발 계획

> 기준: `minwook` 작업 트리 · 최신 우선순위: 2026-10-10, 개정 26/기준집 v4. 표현 트랙은 설계이며 코드·API·프론트는 미구현이다.

이 계획은 현재 데모를 깨뜨리지 않으면서 운영 안정성, 분석 품질, 확장성을 순서대로 높이기 위한 로드맵이다. 비용이 발생하는 인프라는 실제 측정값과 사용자 규모가 확인된 뒤 도입한다.

사업·투자 관점에서 기술 차별성, 프로토타입, 고객 검증, 투자자와 합의할 마일스톤을 구체화하는 과제는 [교수님 피드백 기반 개선안](기술-차별성-검증안.md#mentoring)을 따른다. AI 품질 평가의 세부 기준은 [AI 분석 개선 계획](AI-분석-개선-계획.md)을 참고한다.

## 다음 작업의 최신 순서

1. **개정 26 대조 평가:** ID 32는 B/C/D 3개, ID 33은 D 1개였다. 후보별 선택·ID 오류 복구·발견/PASS/보류/실패·호출/원가를 새 실행과 정상 대조에서 비교한다. Java 427개/도구 Python 95개 통과는 계약 검증이지 범용 정확도 보증이 아니다.
2. **표현 트랙과 관측 보완:** [표현 자체 탐지 설계](표현-탐지-및-선택-필터-설계.md)를 기준으로 검수된 단어 목록 → STT 로컬 적중 → 별도 저장/DTO/집계 순서로 구현한다. 프론트 필터는 연결 계약만 먼저 확정하며 전면 프론트 작업은 보류한다. 기존 맥락 검수와 위험 카드 집계는 유지한다. 실행 버전·선별 예시·실패 원인·원가/단계 지연을 추적하며 로컬 진단/MD를 영구 이력 대체로 보지 않는다.
3. **main과 안전하게 통합:** 배포 CORS·RPM/TPM 호출 제어·YouTube 리포트/재생·원본 만료 표시·후보 병합 보강을 보존한다. 두 브랜치의 변경을 선택적으로 통합하고 호환 테스트 후 서버 반영한다.
4. **고객 검증 계측:** PostHog는 우선 명시적 이벤트로 업로드→분석→리포트→사람 검수의 전환을 측정한다. 세션 리플레이는 민감 화면 차단·수집 동의·예산 설정 검증 후 별도로 켠다. SDK/외부 전송은 아직 없다.
5. **공개 운영 전 인증·소유권:** 기존 로그인 설계를 구현해 모든 미디어/리포트에 접근 검사를 넣는다. 단, 로그인 전에 동의한 내부 테스트용 이벤트 계측을 설계하는 것은 가능하다.
6. **편집 기능은 보류:** HyperFrames는 향후 사람이 승인한 수정안의 짧은 미리보기/렌더 실험부터 검토한다. 행동·포즈 분석, 자동 삭제·자동 수정, 전면 편집툴 전환은 이번 우선순위에 넣지 않는다.

기존 단계별 상세안은 아래에 보존한다. 위 최신 순서가 현재 작업 우선순위이며, 도구별 담당/비용/보안/완료 조건은 [비교·도구 적용 검토](main-minwook-비교-및-도구-적용-검토.md)에 모았다.

## 현재 구현을 기준으로 한 출발점

로드맵의 전제는 현재 `minwook` 브랜치의 실제 실행 방식이다.

```text
사용자 요청
  ↓
Spring Boot API 서버
  ├─ 영상·작업 상태를 DB에 저장
  ├─ 로컬 파일 저장소(./uploads)에 원본 저장
  └─ Spring 비동기 Executor에 분석 작업 등록
        ↓
      Python FastAPI(oops-analysis, 기본 http://localhost:8000)
        ├─ /probe       영상 길이 확인
        ├─ /transcribe STT와 타임스탬프 대본 생성
        └─ /ocr        프레임 추출과 OCR
              ↓
      Spring Boot
        ├─ 룰·맥락·엔티티·외부 근거 분석
        ├─ OpenAI 호출
        ├─ 후보 병합·우선순위 계산
        └─ 리포트와 진행 상태 저장
```

현재는 메시지 브로커가 있는 영속 큐가 아니라 Spring 프로세스 내부의 `ThreadPoolTaskExecutor`를 사용한다. 기본 설정은 동시 실행 1~2개, 대기열 50개이며, Python 서버는 Spring과 별도 프로세스로 실행된다. 따라서 Python Worker만 늘려도 Spring의 작업 대기열·DB·OpenAI 호출 한도는 그대로 병목으로 남는다.

또한 기본 설정에서 업로드 원본은 `./uploads`에 저장된다. 원본만 먼저 정리하는 `source-retention-hours`는 기본 24시간이며 완료·실패 영상에 대해 원본 파일만 삭제한다. 전체 자료를 정리하는 `retention-days`는 기본 0으로 꺼져 있어 대본·리포트·프레임과 DB 기록은 남는다. 운영 프로필에서 두 설정의 실제 값을 확인하고, 원본 만료 뒤 재분석·영상 재생이 불가능해지는 점을 고려해 사용자 안내와 보관 정책을 맞춰야 한다.

## 1. 우선순위 요약

| 우선순위 | 목표 | 핵심 작업 |
|---|---|---|
| 지금 | 데모 안정성 | 상태 확인, 요청 제한, 추적 ID, 실패·보관 정책, 테스트 데이터 정리 |
| 다음 | 운영 준비 | 사용자 인증·소유권, 멱등성, 큐 포화 응답, 로그·메트릭, 원본 저장 정책 |
| 이후 | 확장성 | Object Storage, 운영 DB, 영속 작업 큐, 분석 Worker 분리, 자동 확장 |
| 장기 | 품질·사업화 | 라벨 데이터셋, 피드백 루프, 모델 선택 최적화, 비용·SLA 관리 |

순서를 바꾸지 않는 것이 중요하다. 먼저 “현재 작업이 어디에서 얼마나 걸리는지”를 측정하고, 그 다음 중복·권한·실패 처리를 고친 뒤, 그래도 병목이 남을 때 인프라를 분리한다. 측정 없이 Python 서버나 Executor 수만 늘리면 외부 AI 한도와 메모리 사용량이 먼저 악화될 수 있다.

## 2. 1단계: 현재 데모 안정화

### 이미 반영된 항목

- 업로드·YouTube 등록·재시도 요청 제한
- `X-Request-Id` 기반 장애 추적
- 비동기 분석 로그에 요청 ID 전파
- Spring Boot와 Python 분석 서버 상태를 확인하는 Health API
- Python Health 확인용 2초 timeout 분리
- 분석 Executor 풀 크기 외부 설정화
- 원본 영상과 전체 산출물의 보관 기간 설정
- Python 분석 단계별 실패 처리와 분석 범위·경고 기록
- 취소 상태의 완료 덮어쓰기 방지와 취소 후 결과 트랜잭션 롤백
- 분석 대기열 포화 시 작업을 실패 상태와 안내 문구로 정리
- YouTube URL 도메인 제한과 Python 파일·프레임 경로 제한

### 계속 확인할 항목

- 대표 영상(v1, v2, v3) 재분석 결과가 의도한 논란 구간을 찾는지 확인
- STT만 가능한 환경과 OCR까지 가능한 환경의 결과 차이 기록
- 분석 실패 후 재시도할 때 중복 데이터가 생기지 않는지 확인
- 서버 재시작 후 진행 중 작업이 어떻게 복구되는지 테스트

### 1단계 완료 기준

- 대표 영상으로 업로드부터 리포트까지 한 번 재현할 수 있다.
- STT 실패, OCR 미설치, OpenAI 키 없음, 분석 서버 중단을 서로 다른 상태로 확인할 수 있다.
- 작업이 실패했을 때 `jobId`와 `X-Request-Id`로 원인을 찾을 수 있다.
- 운영에서 사용할 원본·산출물 보관 기간과 삭제 대상이 문서와 설정에 일치한다.
- 같은 영상의 중복 실행, 취소, 재시작 후 `PENDING`·`PROCESSING` 작업 처리가 테스트로 고정되어 있다.

## 3. 2단계: 비용 없이 먼저 할 수 있는 개선

다음 항목은 외부 유료 인프라 없이 코드와 테스트 중심으로 진행할 수 있다.

1. **인증·소유권 설계**: 사용자별 영상 접근 규칙과 로그인 주체를 먼저 확정한다.
2. **멱등성 키**: 같은 업로드 요청이 재전송되어도 영상과 분석 작업이 중복 생성되지 않게 한다.
3. **작업 큐 입장 제한**: 서버가 감당할 수 있는 동시 분석 수를 넘으면 즉시 대기 또는 안내 응답을 준다.
4. **구조화 로그**: `requestId`, `videoId`, `jobId`, `analyzer`, `stage`, 소요시간을 공통 필드로 기록한다.
5. **부하 테스트**: k6 또는 Siege로 업로드·상태 조회·리포트 조회를 구분해 측정한다. 실제 OpenAI 호출은 모킹한다.
6. **분석 회귀 테스트**: 실제 사례를 개인정보 제거 후 고정 테스트셋으로 만들고 탐지 결과 변화를 비교한다.
7. **로그 민감정보 제거**: API 키, 원문 영상 내용, 불필요한 개인정보가 로그에 남지 않게 점검한다.
8. **재시도 정책 정리**: 일시적 네트워크 오류, 외부 API 한도, 잘못된 영상 파일을 서로 다른 결과로 처리한다.

### 비용 없는 개선의 구현 순서

1. `requestId`·`videoId`·`jobId`·`stage`를 모든 주요 로그에 남긴다.
2. 업로드·재시도 요청에 멱등성 키를 받고, 중복 작업 생성 여부를 DB 제약조건으로 방어한다.
3. Executor 대기열이 가득 찼을 때 무한 대기처럼 보이지 않도록 명확한 `대기 중` 또는 `일시적으로 처리 불가` 응답을 정의한다.
4. 분석 단계별 소요시간과 실패 원인을 저장하고, 실제 영상 길이별 기준값을 만든다.
5. 외부 AI 호출은 모킹한 부하 테스트로 API 서버와 작업 상태 조회의 한계를 먼저 측정한다.
6. 그 결과를 기준으로 동시 분석 수와 대기열 크기를 조정한다.

## 4. 3단계: 운영 인프라 분리

다음 조건 중 하나라도 반복되면 구조 분리를 검토한다.

- 업로드가 몰릴 때 API 응답까지 느려진다.
- 분석 대기열이 계속 쌓인다.
- 한 영상의 OCR/STT가 다른 사용자의 요청을 지연시킨다.
- 로컬 디스크가 부족하거나 서버 교체가 어려워진다.
- 서버 장애 후 진행 중 작업과 결과를 복구하기 어렵다.

목표 구조는 다음과 같다.

```text
API 서버
  ├─ 운영 DB: 사용자·영상·작업·리포트
  ├─ Object Storage: 원본·프레임·산출물
  └─ 작업 큐: 분석 요청·재시도·상태
        ├─ STT Worker
        ├─ OCR Worker
        └─ LLM/근거 Worker
```

권장 도입 순서는 Object Storage → 운영 DB → 작업 큐 → Worker 분리 → 자동 확장이다. Docker와 Kubernetes/EKS는 Worker 분리 이후 운영 복잡도와 비용을 비교해 선택한다.

### 분리할 때 지켜야 할 경계

| 경계 | API 서버가 담당할 일 | Worker가 담당할 일 |
|---|---|---|
| 요청 | 업로드 접수, 권한 확인, 작업 생성, 상태 응답 | 직접 담당하지 않음 |
| 분석 | 작업을 큐에 넣고 즉시 응답 | STT·OCR·LLM 실행과 단계별 상태 갱신 |
| 파일 | 업로드 완료와 접근 권한 관리 | 필요한 입력을 읽고 중간 산출물 저장 |
| 실패 | 재시도 요청과 사용자 메시지 제공 | 일시 오류 재시도, 영구 오류 종료 |
| 결과 | 리포트 조회와 검토 액션 저장 | 분석 결과를 job 버전에 연결해 저장 |

Worker를 분리할 때도 분석 결과를 메모리에만 두면 안 된다. 작업을 받은 사실, 현재 단계, 재시도 횟수, 결과 버전을 DB 또는 영속 큐에 남겨야 서버가 재시작되어도 “없어진 작업”과 “아직 처리 중인 작업”을 구분할 수 있다.

### 인프라 전환 완료 기준

- API 서버를 재시작해도 접수된 작업이 유실되지 않는다.
- Worker를 여러 대 실행해도 같은 `jobId`가 동시에 두 번 처리되지 않는다.
- Worker 한 대를 중단해도 작업이 재시도되거나 명확한 실패로 남는다.
- 원본 파일과 산출물의 위치가 특정 서버의 로컬 디스크에 종속되지 않는다.
- 대기시간, 처리시간, 실패율, 재시도 횟수를 사용자·영상·분석 단계별로 확인할 수 있다.

## 5. AI 품질·비용 로드맵

실제 자료의 구축은 [논란 데이터셋 구축 계획](논란-데이터셋-구축-계획.md), 시각적 행동과 긴 영상의 연구 범위는 [행동·포즈 데이터셋과 긴 영상 적용 계획](행동-포즈-데이터셋-및-긴영상-적용-계획.md)을 따른다. 시각 분석은 현재 미구현이며, 데이터·오프라인 비교 결과를 보고 운영 연결을 결정한다.

현재 AI 개발의 상세 순서는 [AI 분석 개선 계획](AI-분석-개선-계획.md)을 따른다. 판단 기준·평가 자료 → 사전 품질·매칭 → 프롬프트·근거 검증 → 결과·병합·분석 범위 → 선택 기능·버전·종합 비교 순서로 진행한다. 사실 대조의 기본 활성화 여부는 표현 검토와 별도 평가한 뒤 결정한다. 가상 예문으로 시작하는 [AI 검수 사례 초안](논란-데이터셋-구축-계획.md#annotation-examples)은 실제 검증셋이 아니다.

| 단계 | 할 일 | 판단 기준 |
|---|---|---|
| 1 | 영상·표현별 정답 라벨 수집 | 정탐·오탐·미탐을 구분할 수 있는가 |
| 2 | 룰·저비용 모델 기준선 측정 | 영상당 시간·호출 수·비용·정밀도 |
| 3 | 어려운 후보만 고성능 모델로 재검토 | 품질 증가가 추가 비용을 정당화하는가 |
| 4 | 결과 캐시·중복 분석 방지 | 영상/대본/프롬프트 버전이 같을 때 안전한가 |
| 5 | 사용자 피드백 반영 | 실제 검수 시간을 줄였는가 |

고성능 모델을 모든 영상에 적용하는 방식은 비용과 처리량을 먼저 확인해야 한다. 현재는 룰 기반 결과와 저비용 LLM 결과를 기준선으로 삼고, 어려운 사건·맥락 후보에만 실험적으로 적용하는 방향이 적합하다.

## 6. 측정해야 할 지표

### 서버 지표

- 업로드 API p50/p95 응답시간
- 상태 조회 API p50/p95 응답시간
- 분석 대기시간과 실제 분석시간
- 동시 분석 수와 큐 대기 길이
- CPU·메모리·디스크 사용량
- Python 서버 재시작 횟수와 실패율

### AI 지표

- STT 성공률
- OCR 성공률과 OCR 텍스트의 유효성
- 분석기별 실행 성공률
- 정밀도·재현율·오탐·미탐
- 영상 1개당 OpenAI 호출 횟수와 비용
- 사용자 피드백 후 재검토가 필요한 비율

### 보관·보안 지표

- 원본 영상 평균 보관시간
- 저장소 사용량 증가량
- 인증되지 않은 접근 시도
- 요청 제한 초과 횟수
- 장애 발생부터 원인 파악까지 걸린 시간

### 지표를 해석하는 순서

1. 업로드 API가 느린지, 분석 작업이 큐에서 오래 기다리는지, Worker가 실제로 오래 걸리는지 나눈다.
2. STT·OCR·LLM·뉴스 검색 중 어느 단계가 전체 시간과 비용을 차지하는지 비교한다.
3. 실패율을 전체 영상 기준과 단계별 기준으로 나눈다. “분석 실패 5%”만으로는 Python 장애인지 외부 API 장애인지 알 수 없다.
4. 평균값만 보지 말고 p95와 최장 처리시간을 함께 본다. 영상 길이가 긴 서비스에서는 일부 긴 영상이 사용자 경험을 결정한다.

초기에는 목표값을 임의로 정하기보다 대표 영상 10~20개의 기준선을 만든다. 이후 영상 길이 구간별로 `업로드 응답시간`, `큐 대기시간`, `분석시간`, `영상당 비용`의 목표 범위를 정한다.

## 7. 멘토링 때 추가로 확인할 질문

- 현재 규모에서 API 서버와 분석 Worker를 분리해야 하는 기준을 어떤 지표로 정하는가?
- 영상 원본·프레임·리포트 중 어떤 데이터를 얼마 동안 보관하는 것이 일반적인가?
- 작업 큐를 도입할 때 재시도와 중복 실행을 어떻게 설계하는가?
- 외부 AI API가 느리거나 중단되었을 때 사용자에게 어느 수준까지 진행 상황을 보여주는가?
- 실제 장애에서 로그, 메트릭, 알림 중 무엇을 먼저 확인하는가?
- 영상 접근 권한과 다운로드 URL을 어떤 방식으로 보호하는가?

## 8. 기획서 반영 개발 단계

기획서의 아이디어를 현재 프로젝트에 적용할 때는 다음 순서가 적합하다.

### Phase 0 — 논란 정의와 데이터셋 설계

- `Surface Signal`, `Context Interpretation`, `Content Label`, `Risk Mechanism`을 구분한다.
- `PASS`, `REVIEW_REQUIRED`, `UNCERTAIN`의 의미와 사용자 문구를 정한다.
- Positive, Negative, Hard Negative, Ambiguous 사례를 수집한다.
- annotation guideline과 평가용 JSON 구조를 만든다.

### Phase 1 — STT 기반 맥락 검수

- 현재 STT 타임스탬프에 앞뒤 대화 Window를 연결한다.
- 은어·밈·과거 사건 표현을 Signal로 찾고, 곧바로 위험 판정하지 않는다.
- 현재의 `SubtitleAnalyzer`, `ContextLexiconAnalyzer`, `SpeechReviewAnalyzer`를 이 구조에 맞춰 평가한다.
- 영상에서 검토할 시간 구간과 판단 근거를 사용자에게 보여준다.

### Phase 2 — 유사 사례와 동적 맥락

- 검증된 Controversy Event를 검색 가능한 형태로 관리한다.
- 필요한 후보에만 인물·사건·표현 기반 뉴스 검색을 수행한다.
- 검색 출처와 기준일을 리포트에 남긴다.
- Vector DB와 Embedding은 데이터 규모와 검색 품질을 측정한 뒤 도입한다.

### Phase 3 — 제한적인 Vision 확장

- 오프라인 실험에서는 STT/OCR 후보의 전후 구간을 확대 확인하는 구성과, 말이 없어도 실행되는 저비용 시각 후보 탐색을 비교한다.
- 상세 영상 모델은 텍스트 또는 시각 후보 주변에 제한한다. STT/OCR 후보만을 필수 진입 조건으로 삼지 않는다.
- 짧은·무음·정지 제스처의 후보 누락을 먼저 측정하며, 관측 행동과 공격적인 사용 맥락의 판단을 분리한다.
- 전체 프레임을 고성능 Vision 모델에 보내는 방식은 비용·처리시간 측정 전에는 사용하지 않는다.

### Phase 4 — Human-in-the-Loop와 멀티모달 판단

- 사용자 피드백을 수집하고 사람이 검증한 데이터만 평가셋에 반영한다.
- 텍스트, 프레임, 유사 사례, 동적 사회 맥락을 하나의 검토 이벤트로 통합한다.
- `Risk Mechanism`과 근거를 함께 제공해 사람이 최종 판단할 수 있게 한다.

### 단계별 선행조건과 완료 기준

| 단계 | 먼저 준비할 것 | 완료로 볼 수 있는 상태 |
|---|---|---|
| Phase 0 | 용어·라벨·annotation guideline | 같은 사례를 두 사람이 비슷하게 분류한다 |
| Phase 1 | STT 타임스탬프와 검토 이벤트 구조 | 후보 구간·앞뒤 문맥·근거를 리포트에서 확인한다 |
| Phase 2 | 출처·발행일·기준일을 가진 이벤트 데이터 | 검색 결과가 없을 때도 “근거 없음”과 “안전함”을 구분한다 |
| Phase 3 | 원본 시점·전체 저비용 탐색·후보 상세 확인·비용 측정 | 무음 행동의 후보 누락까지 평가하고 고비용 모델은 필요한 구간에 제한한다 |
| Phase 4 | 검토 액션과 데이터 정제 정책 | 사용자 피드백이 평가셋과 다음 버전 개선에 연결된다 |

선행조건이 준비되지 않은 상태에서 다음 단계를 동시에 진행하면, 기능은 많아지지만 어떤 입력으로 어떤 판단을 했는지 설명하기 어려워진다. 특히 Phase 2의 검색 결과와 Phase 3의 Vision 결과는 근거의 출처와 실패 상태를 함께 저장할 수 있을 때만 도입한다.

## 9. 기획서에서 바로 도입하지 않을 항목

다음 항목은 방향성은 타당하지만, 현재 데모에 바로 넣으면 운영 복잡도와 비용이 커질 수 있다.

- S3/R2 직접 업로드와 비공개 Object Storage
- Redis/SQS 기반 영속 작업 큐
- Vector DB와 Embedding 검색
- 전체 영상에 대한 Vision LLM 분석
- 별도 행동·자세·물체 탐지 모델
- 자체 모델 학습과 Fine-tuning

각 항목은 사용자 수, 큐 대기시간, 저장소 사용량, 영상당 비용, 평가셋 성능을 확인한 뒤 단계적으로 결정한다.

### 당장 하지 않을 이유가 명확한 항목

- **Python 서버만 여러 대로 늘리기**: Spring 내부 Executor와 로컬 파일 경로를 공유하지 않으면 오히려 작업이 실패할 수 있고, 공유하더라도 DB·OpenAI 한도가 병목으로 남는다.
- **Executor 동시성만 높이기**: 영상 한 편이 여러 외부 호출을 만들기 때문에 스레드 수가 곧 처리량이 아니다. CPU·메모리·외부 API 한도를 함께 측정해야 한다.
- **전체 영상을 매번 고성능 모델에 보내기**: 후보 선별과 캐시가 없는 상태에서는 비용과 처리시간이 선형으로 늘어난다.
- **검색 결과를 곧바로 논란 판정으로 사용하기**: 검색은 참고 근거이지 사실 판정 자체가 아니므로 출처와 문맥 확인 단계가 필요하다.
- **오탐을 줄이려고 표현 사전만 계속 늘리기**: 사전이 커질수록 후보는 늘지만, 사투리·인용·일반 설명을 구분하지 않으면 사용자 검토 부담이 커진다.

## 10. 품질 목표 지표

Accuracy 하나만으로 서비스 품질을 판단하지 않는다. 다음 지표를 영상 단위와 후보 이벤트 단위로 함께 기록한다.

- Precision, Recall
- False Positive Rate, False Negative Rate
- 영상당 평균 Alert 수
- `REVIEW_REQUIRED` 비율
- 심각한 위험 누락 비율
- 사람과 AI의 판단 일치율
- 30분 영상 1개당 평균 검수 시간

특히 이 서비스에서는 “30분 영상 하나를 검토할 때 사용자가 실제로 확인해야 하는 구간이 몇 개인가”가 핵심 제품 지표다.
