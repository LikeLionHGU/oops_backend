# OoPs?! 향후 개발 계획

> 기준 브랜치: `minwook` · 기준일: 2026-10-06

이 계획은 현재 데모를 깨뜨리지 않으면서 운영 안정성, 분석 품질, 확장성을 순서대로 높이기 위한 로드맵이다. 비용이 발생하는 인프라는 실제 측정값과 사용자 규모가 확인된 뒤 도입한다.

## 1. 우선순위 요약

| 우선순위 | 목표 | 핵심 작업 |
|---|---|---|
| 지금 | 데모 안정성 | 상태 확인, 요청 제한, 추적 ID, 실패·보관 정책, 테스트 데이터 정리 |
| 다음 | 운영 준비 | 사용자 인증·소유권, 멱등성, 부하 테스트, 로그·메트릭, 원본 저장 정책 |
| 이후 | 확장성 | Object Storage, 운영 DB, 작업 큐, 분석 Worker 분리, 자동 확장 |
| 장기 | 품질·사업화 | 라벨 데이터셋, 피드백 루프, 모델 선택 최적화, 비용·SLA 관리 |

## 2. 1단계: 현재 데모 안정화

### 이미 반영된 항목

- 업로드·YouTube 등록·재시도 요청 제한
- `X-Request-Id` 기반 장애 추적
- Spring Boot와 Python 분석 서버 상태를 확인하는 Health API
- 분석 Executor 풀 크기 외부 설정화
- 원본 영상과 전체 산출물의 보관 기간 설정
- Python 분석 단계별 실패 처리와 분석 범위·경고 기록

### 계속 확인할 항목

- 대표 영상(v1, v2, v3) 재분석 결과가 의도한 논란 구간을 찾는지 확인
- STT만 가능한 환경과 OCR까지 가능한 환경의 결과 차이 기록
- 분석 실패 후 재시도할 때 중복 데이터가 생기지 않는지 확인
- 서버 재시작 후 진행 중 작업이 어떻게 복구되는지 테스트

## 3. 2단계: 비용 없이 먼저 할 수 있는 개선

다음 항목은 외부 유료 인프라 없이 코드와 테스트 중심으로 진행할 수 있다.

1. **인증·소유권 설계**: 사용자별 영상 접근 규칙과 로그인 주체를 먼저 확정한다.
2. **멱등성 키**: 같은 업로드 요청이 재전송되어도 영상과 분석 작업이 중복 생성되지 않게 한다.
3. **작업 큐 입장 제한**: 서버가 감당할 수 있는 동시 분석 수를 넘으면 즉시 대기 또는 안내 응답을 준다.
4. **구조화 로그**: `requestId`, `videoId`, `jobId`, `analyzer`, `stage`, 소요시간을 공통 필드로 기록한다.
5. **부하 테스트**: k6 또는 Siege로 업로드·상태 조회·리포트 조회를 구분해 측정한다. 실제 OpenAI 호출은 모킹한다.
6. **분석 회귀 테스트**: 실제 사례를 개인정보 제거 후 고정 테스트셋으로 만들고 탐지 결과 변화를 비교한다.
7. **로그 민감정보 제거**: API 키, 원문 영상 내용, 불필요한 개인정보가 로그에 남지 않게 점검한다.
8. **재시도 정책 정리**: 일시적 네트워크 오류, 외부 API 한도, 잘못된 영상 파일을 서로 다른 결과로 처리한다.

## 4. 3단계: 운영 인프라 분리

다음 조건 중 하나라도 반복되면 구조 분리를 검토한다.

- 업로드가 몰릴 때 API 응답까지 느려진다.
- 분석 대기열이 계속 쌓인다.
- 한 영상의 OCR/STT가 다른 사용자의 요청을 지연시킨다.
- 로컬 디스크가 부족하거나 서버 교체가 어려워진다.
- 서버 장애 후 진행 중 작업과 결과를 복구하기 어렵다.

목표 구조는 다음과 같다.

```text
API 서버
  ├─ 운영 DB: 사용자·영상·작업·리포트
  ├─ Object Storage: 원본·프레임·산출물
  └─ 작업 큐: 분석 요청·재시도·상태
        ├─ STT Worker
        ├─ OCR Worker
        └─ LLM/근거 Worker
```

권장 도입 순서는 Object Storage → 운영 DB → 작업 큐 → Worker 분리 → 자동 확장이다. Docker와 Kubernetes/EKS는 Worker 분리 이후 운영 복잡도와 비용을 비교해 선택한다.

## 5. AI 품질·비용 로드맵

| 단계 | 할 일 | 판단 기준 |
|---|---|---|
| 1 | 영상·표현별 정답 라벨 수집 | 정탐·오탐·미탐을 구분할 수 있는가 |
| 2 | 룰·저비용 모델 기준선 측정 | 영상당 시간·호출 수·비용·정밀도 |
| 3 | 어려운 후보만 고성능 모델로 재검토 | 품질 증가가 추가 비용을 정당화하는가 |
| 4 | 결과 캐시·중복 분석 방지 | 영상/대본/프롬프트 버전이 같을 때 안전한가 |
| 5 | 사용자 피드백 반영 | 실제 검수 시간을 줄였는가 |

고성능 모델을 모든 영상에 적용하는 방식은 비용과 처리량을 먼저 확인해야 한다. 현재는 룰 기반 결과와 저비용 LLM 결과를 기준선으로 삼고, 어려운 사건·맥락 후보에만 실험적으로 적용하는 방향이 적합하다.

## 6. 측정해야 할 지표

### 서버 지표

- 업로드 API p50/p95 응답시간
- 상태 조회 API p50/p95 응답시간
- 분석 대기시간과 실제 분석시간
- 동시 분석 수와 큐 대기 길이
- CPU·메모리·디스크 사용량
- Python 서버 재시작 횟수와 실패율

### AI 지표

- STT 성공률
- OCR 성공률과 OCR 텍스트의 유효성
- 분석기별 실행 성공률
- 정밀도·재현율·오탐·미탐
- 영상 1개당 OpenAI 호출 횟수와 비용
- 사용자 피드백 후 재검토가 필요한 비율

### 보관·보안 지표

- 원본 영상 평균 보관시간
- 저장소 사용량 증가량
- 인증되지 않은 접근 시도
- 요청 제한 초과 횟수
- 장애 발생부터 원인 파악까지 걸린 시간

## 7. 멘토링 때 추가로 확인할 질문

- 현재 규모에서 API 서버와 분석 Worker를 분리해야 하는 기준을 어떤 지표로 정하는가?
- 영상 원본·프레임·리포트 중 어떤 데이터를 얼마 동안 보관하는 것이 일반적인가?
- 작업 큐를 도입할 때 재시도와 중복 실행을 어떻게 설계하는가?
- 외부 AI API가 느리거나 중단되었을 때 사용자에게 어느 수준까지 진행 상황을 보여주는가?
- 실제 장애에서 로그, 메트릭, 알림 중 무엇을 먼저 확인하는가?
- 영상 접근 권한과 다운로드 URL을 어떤 방식으로 보호하는가?

## 8. 기획서 반영 개발 단계

기획서의 아이디어를 현재 프로젝트에 적용할 때는 다음 순서가 적합하다.

### Phase 0 — 논란 정의와 데이터셋 설계

- `Surface Signal`, `Context Interpretation`, `Content Label`, `Risk Mechanism`을 구분한다.
- `PASS`, `REVIEW_REQUIRED`, `UNCERTAIN`의 의미와 사용자 문구를 정한다.
- Positive, Negative, Hard Negative, Ambiguous 사례를 수집한다.
- annotation guideline과 평가용 JSON 구조를 만든다.

### Phase 1 — STT 기반 맥락 검수

- 현재 STT 타임스탬프에 앞뒤 대화 Window를 연결한다.
- 은어·밈·과거 사건 표현을 Signal로 찾고, 곧바로 위험 판정하지 않는다.
- 현재의 `SubtitleAnalyzer`, `ContextLexiconAnalyzer`, `SpeechReviewAnalyzer`를 이 구조에 맞춰 평가한다.
- 영상에서 검토할 시간 구간과 판단 근거를 사용자에게 보여준다.

### Phase 2 — 유사 사례와 동적 맥락

- 검증된 Controversy Event를 검색 가능한 형태로 관리한다.
- 필요한 후보에만 인물·사건·표현 기반 뉴스 검색을 수행한다.
- 검색 출처와 기준일을 리포트에 남긴다.
- Vector DB와 Embedding은 데이터 규모와 검색 품질을 측정한 뒤 도입한다.

### Phase 3 — 제한적인 Vision 확장

- STT/OCR 후보의 전후 구간만 프레임을 확대 추출한다.
- 말과 화면 행동이 일치하는지 확인하는 보조 분석부터 시작한다.
- 이후에야 독립적인 움직임·자세·물체 탐지를 검토한다.
- 전체 프레임을 고성능 Vision 모델에 보내는 방식은 비용·처리시간 측정 전에는 사용하지 않는다.

### Phase 4 — Human-in-the-Loop와 멀티모달 판단

- 사용자 피드백을 수집하고 사람이 검증한 데이터만 평가셋에 반영한다.
- 텍스트, 프레임, 유사 사례, 동적 사회 맥락을 하나의 검토 이벤트로 통합한다.
- `Risk Mechanism`과 근거를 함께 제공해 사람이 최종 판단할 수 있게 한다.

## 9. 기획서에서 바로 도입하지 않을 항목

다음 항목은 방향성은 타당하지만, 현재 데모에 바로 넣으면 운영 복잡도와 비용이 커질 수 있다.

- S3/R2 직업 업로드와 비공개 Object Storage
- Redis/SQS 기반 영속 작업 큐
- Vector DB와 Embedding 검색
- 전체 영상에 대한 Vision LLM 분석
- 별도 행동·자세·물체 탐지 모델
- 자체 모델 학습과 Fine-tuning

각 항목은 사용자 수, 큐 대기시간, 저장소 사용량, 영상당 비용, 평가셋 성능을 확인한 뒤 단계적으로 결정한다.

## 10. 품질 목표 지표

Accuracy 하나만으로 서비스 품질을 판단하지 않는다. 다음 지표를 영상 단위와 후보 이벤트 단위로 함께 기록한다.

- Precision, Recall
- False Positive Rate, False Negative Rate
- 영상당 평균 Alert 수
- `REVIEW_REQUIRED` 비율
- 심각한 위험 누락 비율
- 사람과 AI의 판단 일치율
- 30분 영상 1개당 평균 검수 시간

특히 이 서비스에서는 “30분 영상 하나를 검토할 때 사용자가 실제로 확인해야 하는 구간이 몇 개인가”가 핵심 제품 지표다.
