# 탐색 축과 최종 검토 근거 분리

2026-10-17 · minwook · `final-review-basis-text-v1` · **무료 870개·후속 4안 실호출 112회 완료, 기본 OFF 유지**.

## 바꾸는 이유

[행위·대상 지침 비교](탐색-출력계약-JSON-스키마-비교.md)의 수정안은 운영에 채택하지 않았다. 진단에서는 대상 없는 동일한 SEXUAL 검토 응답이 탐색 축에 따라 통과/거절되는 것을 재현했다. 이번 변경은 탐색의 분류 가설을 최종 판단 계약과 분리한다. 이것이 실제 의미 오류를 줄인다는 인과관계는 아직 검증하지 않았다.

[OpenAI 공식 프롬프트 지침](https://developers.openai.com/api/docs/guides/prompting)의 단계적 적용·회귀 검증 방식을 참고해 선택 기능으로 구현했다. 미채택된 행위 방향 지침 6문장을 기본 프롬프트에 추가하지 않았다.

## 달라지는 구조

| 정보 | 역할 | 유지/변경 |
|---|---|---|
| 탐색 `proposal.axis` | 읽기 창·허용 근거 범위 선택 | 그대로 보존 |
| 검증 `reviewBasis` | 최종 검토 이유가 대상 평가인지 표현 자체인지 명시 | 텍스트 검증 ON에서 추가 |
| 기존 `assessment` | PASS/REVIEW_REQUIRED/UNCERTAIN·분류·대상·근거 | 기존 형식 보존 |

`reviewBasis`는 assessment 내부가 아니라 각 `verifications` 항목의 필드다. 아래는 새 필드만 보여주는 부분 객체이며 전체 응답 예시는 아니다.

```json
{
  "candidateId": "candidate-1",
  "reviewBasis": {
    "axis": "EXPRESSION_CONTENT",
    "reason": "인용한 표현 자체에 독립적인 검토 사유가 있습니다.",
    "evidenceIds": ["stt-1"]
  }
}
```

REVIEW_REQUIRED일 때 세 필드를 모두 요구한다. reason은 300자 이내, evidenceIds는 중복 없이 허용 raw이면서 현재 assessment.evidence에도 인용한 ID여야 한다. anchor ID를 포함하고 원문 구간 수를 넘길 수 없다. 이것은 최소 원문 연결 검사이지 이유의 의미를 자동으로 입증하는 검사는 아니다.

PASS/UNCERTAIN은 `reviewBasis=null`이며 기존 대조 해석·누락 정보·원문 검증을 유지한다. PASS의 대조 조건을 없애기 위해 새 축을 쓰지 못한다.

## 우회 방지

- **TARGET_TREATMENT:** 최종 대상 평가를 선택했으면 실제 target과 기존 TARGET/CONTEXT 지칭·관계 계약이 필수다. GRAPHIC_METAPHOR도 이 최종 축을 명시했다면 대상을 생략할 수 없다.
- **EXPRESSION_CONTENT:** 우선 GRAPHIC_METAPHOR/SEXUAL/PRIVACY/VIOLENCE만 허용한다. 독립적인 표현·공개 내용의 검토 이유를 설명해야 하고 대상 필드 및 TARGET 역할 인용은 금지한다.
- 비하·조롱·집단 일반화·차별·혐오·상품 평가 속 모욕을 표현 자체로 바꿔 통과시키지 못한다. 이번 허용 목록은 제한적인 실험 범위이며 전체 분류 체계의 최종 결론이 아니다.
- SEXUAL 같은 허용 분류라도 단어·사생활 질문·자발적 제안 자체가 경고 근거는 아니다. 특정인을 대상화한다는 이유를 독립적인 표현 문제로 바꾸는 것은 지침상 금지한다. 다만 그 의미 정합성까지 결정적으로 검증하는 구현은 아니다.
- 필드 누락·모르는 축·인용하지 않은 ID·필드 간 충돌은 거절한다. 누락을 탐색 축으로 자동 보충하거나 실패를 PASS로 바꾸지 않는다.

검증할 때만 임시 유효 축으로 기존 검증기를 호출하며 원래 후보는 변경하지 않는다. 최종 축이 바뀌어도 읽기 창을 확장·축소하거나 원문·시간·anchor·기존 근거·참고 사전을 바꾸지 않는다. 필요한 문맥이 없다면 새 정보로 메우지 않고 UNCERTAIN을 반환해야 한다.

## 연결과 호환

`FINAL_REVIEW_BASIS_ENABLED=false`가 기본값이다. Spring의 `SpeechReviewAnalyzer` → `CandidateReviewEngine` 텍스트 검증·복구에만 연결했다. 화면/프레임 검증은 기존 계약을 유지한다.

OFF에서는 기존 프롬프트·요청과 2인자 `Verification` 생성자, 과거 JSON을 유지한다. 요청하지 않은 `reviewBasis`가 반환되면 `UNEXPECTED_REVIEW_BASIS`로 거절한다. ON에서 경고 응답에 필드가 없으면 `REVIEW_BASIS_REQUIRED`로 미판정을 남기며 기존 계약으로 되돌리지 않는다.

기존 대상 오류 복구도 동일한 새 지침과 계약 버전을 사용한다. 복구에서 축을 다시 선택할 수 있지만 원문·허용 후보·참고는 그대로다. 새 basis 필드 오류는 자동 복구 대상으로 추가하지 않아 호출·비용이 조용히 증가하지 않는다. 기존 복구 예산은 유지한다.

진단 `candidatePipeline.evidenceCounts[].reviewBasis`에 탐색 축·반환 축·basis 제공 여부·ID 수·계약 통과 여부만 남긴다. 원문/이유는 이 메타데이터에 저장하지 않는다. 요청 기록 기능이 켜져 있으면 기존 보존 정책에 따라 실제 요청/응답을 별도로 확인한다. 공개 카드 API의 필드는 변경하지 않았다.

### 원문과 판단 변화

- **실제 166 질문:** 기존은 2회 모두 경고·통과, 새 계약은 2회 모두 PASS·통과다. 새 응답은 모욕·대상화·강압의 구체적 근거가 부족하다고 설명했다. 원문에 앞선 줄임말 뜻풀이도 있으므로 어느 쪽이 정답인지는 별도 검수해야 한다. 이를 오탐 해결 또는 미탐 증가로 확정하지 않는다.
- **실제 178 자기 공개 제안:** 기존은 경고 2회(1회 대상 지칭 계약 탈락), 새 계약은 경고/대상 인용 누락 1회와 PASS 1회다. 자기 제안을 타인 공개 요구로 직접 뒤집은 문장은 확인하지 않았지만, 듣는 사람을 성적 대상화의 대상으로 삼는 논리는 여전히 검수해야 한다. 새 판단도 반복 안정적이지 않다.
- **서버 장애 안내 정상 초안:** 새 계약도 2회 모두 PASS이나 첫 응답의 대조 설명이 null이라 검증에 탈락했다. 중간에 ‘양쪽 모두 계약 통과’라고 안내한 집계는 이 최종 수치로 정정한다. 누락을 자동 정상 처리하지 않았다.
- **화자 불명 관계 초안:** 양쪽 모두 PASS지만 기존은 대조 설명 누락 2회, 새 계약은 2회 통과다. 국소적인 출력 완결성 개선이지 판단 개선의 증거는 아니다.
- **거절 후 주제 전환 초안:** 양쪽 모두 거절·중단을 보존했고 실제 공개나 동의를 만들지 않았다. 양쪽 2회차는 target을 ‘질문을 받은 상대’로 쓰고 EXPLICIT targetMention을 ‘당신’으로 써 기존 지칭 계약에 탈락했다. 의미상 타당한 재표현과 계약 불일치의 경계는 별도 점검한다.

## 후속 · 계약/판단 가드 2×2 분리 계획 준비


가드가 있는 두 안은 같은 블록을 ‘대상 필드 형식 예시’ 직전에 넣는다. 없는 두 안에서는 해당 블록을 제거한다. 각 계약을 고정하면 가드 유무만 다르고, 각 가드 조건을 고정하면 basis 필드·최종 축 계약과 그 검증기만 다르도록 구성했다. raw·후보·anchor·시간·참고는 동일하다. 새 계약 두 안에만 실제 요청과 같은 `verificationContract` 메타데이터를 넣는다.
