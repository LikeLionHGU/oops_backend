# 논란 맥락 사전: 저장·검색·메커니즘 라우팅 현황

2026-10-15 · minwook. 과거 설계의8개 메커니즘, 현재 공통 판단6유형, 이번 파일럿 검색 키3개는 목적과 시점이 다르다.

## 1. 메커니즘 필터는 어디까지 왔나

| 항목 | 작업 전 | 이번 결과 |
|---|---|---|
| 사건 원장 | 32사건·38발언, 대부분 사건 요약 | 원장·승인 상태 그대로 보존 |
| 참조 단위 | 메뉴 평가와 신체 비유가 한 사례에 혼합 | 피식대학 원장3항목을 참조 단위4개로 분리 |
| 검색 문구 | 실행v4는 해석·공통 판단 조건까지 색인에 포함 | v6 미리보기는 retrievalView로 별도 고정 |
| 메커니즘 라우팅 | 대분류 mechanismIds만 저장, 우선순위 경로 없음 | routingKeys와 선택적 소프트 우선순위 overload 구현 |
| LLM 자동 분류 | 문서상 설계 | **미구현·미실행** |
| 후보별 참고 | 발견 배치 참고를 고정, candidateReference 미호출 | **명시적 v6일 때만** 후보 근거로 한 번 재선택하고 검증/복구까지 고정 |
| 운영 반영 | 기본v4 | 기본runtime 유지, v6는 미리보기만 생성 |

새 LLM/임베딩 호출·벡터DB·모델 변경·서버 재시작은 없다. 수동 힌트 테스트는 자동 분류의 성공이 아니다.

## 2. 왜 저장 단위를 나눴나

38예시 중37개는 한 문단 flow, 원문 구간은1개 항목, 명시적 비판 가설은2개뿐이었다.
원장에 연결된 reactions/evidence.sources/documents는 비어 있어 다른 연구 파일의 댓글·링크를 연결 완료로 볼 수 없었다.
빌드는 통과하므로 미연결보다는 내용·검색 단위가 병목이다. 요약을 자동으로 원문으로 복원하지 않는다.

| 새 단위 필드 | 역할 |
|---|---|
| parentCaseId / familyId | 연구 원장의 발언·사건으로 돌아가는 연결 |
| source | 로컬 정본 원문·해시·출처 종류 |
| utteranceIds / roles | 원문 ID·상황/평가 역할. 역할별로 재정렬하지 않고 실제 순서를 유지 |
| interpretation / boundary | 작성한 비판 연결과 한계. 전사와 분리 |
| normalContrasts | 합성 개발 대조임을 표시. 실제 정상 영상·독립 정답 승인과 구별 |
| retrievalText | 검색 전용 문구. 해석을 고쳐도 자동 변경하지 않음 |
| routingKeys | 검색용 연결 구조. 위험 판정이나 공통6유형 자체가 아님 |

파일럿 키는 local-life-devaluation(2단위), service-choice-devaluation(1), graphic-body-metaphor(1)다.
완전한 분류 목록이 아니며 싱글턴의 한계도 남는다. 같은 사건의4단위를 독립 사건4개로 세지 않는다.

## 4. 실제 분석 연결과 필터의 안전 경계

- 기본v4: 발견 배치 → 어휘 사례 선택 → 후보 발견 → 배치 참고 고정 → 검증/복구. 기존 동작 유지.
- 명시적v6: 발견 배치 → 후보 발견 → 검증된 후보의 원문 근거로 단위 참고를 한 번 선택 → snapshot 고정 → 검증/복구.
- 검증할 때마다 참고를 바꾸거나 원문 창을 확대하지 않는다. 기존 승인 사례 참고도 함께 보존한다.
- 세부 routingKeys 힌트를 받으면 해당 단위를 어휘 겹침 없이도 우선 후보로 올릴 수 있다.
  다른 어휘 후보를 제거하는 하드 필터는 아니다. 미지/빈 힌트는 어휘 검색으로 돌아가고 빈 원문은 예시를 만들지 않는다.
- family 제외·채널·최대2예시·예시 전체3000자·전체payload6000자 제한은 유지한다.
- **생산 파이프라인은 아직 힌트를 공급하지 않는다.** 자동 분류 호출·프롬프트·설정은 없다.
  v6 후보별 재선택과 수동 힌트 회귀를 자동 메커니즘 분류 구현으로 표시하지 않는다.
- normalContrasts는 합성 대조라는 지침을 v6에만 붙이고 현재 영상 근거나 정상 판정을 대신하지 못하게 한다.

## 5. 무료 검증 결과

H2 저장 STT를 읽기 전용으로 읽고 수동 고정 후보를 실제 엔진의 mock discovery에 넣었다.
이것은 모델 탐색/판정이 아니라 참고 선택·요청 조립 검사다. 실제4조건의 raw JSON과 기본 경로의 참고 JSON은
이전 plan과 동치다. 프로세스별 JSON 키 순서 차이로 전체 문자열은 달라 과거 요청 바이트 replay라고 하지 않는다.

## 6. 다음 단계와 확장 기준

1. DRAFT 단위4개의 원문·해석·정상 대조 검토. 학습/독립 정답 승인이 아니다.
2. 기존35개를 같은 방식으로 점진 정제. source 없이 요약에서 발언을 만들지 않는다.
3. 세부 검색 키와 공통6개 판단 기준의 역할·축 정합성 검토. 키 수를 판정 유형 수로 늘리지 않는다.
4. 다른 소재·가까운 정상 대조로 분류/검색/최종 판단을 따로 평가한다.
5. 승인한 범위에서 LLM 분류 연결. 영상 전체의 넓은 키로 모든 후보를 같은 사례로 몰지 않도록 배치/후보 범위를 설계한다.
   긴 영상도 무조건 추가1회라고 비용을 단정하지 않는다.
6. 실모델·정상 회귀 뒤 별도 publish/운영 반영. 이번에는 배포/재시작하지 않았다.

현재 archive1MiB/최대1000예시와 요청 예산이 있으므로500사례를 무조건 수용한다고 보장하지 않는다.
원장과 단위는 파일별로 늘리되 한도에 닿으면 인덱스와 조회를 분리한다. 모든 사례를 모델에 보내는 방식으로 확장하지 않는다.
