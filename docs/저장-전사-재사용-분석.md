# 저장 전사 재사용 분석 — 2026-10-23

## 전사는 영상별로 저장되는가

서비스의 기본 저장소는 DB의 `transcript_segment`다. 각 행은 `video_id`, `start_ms`, `end_ms`, `text`를 갖는다. `GET /api/v1/videos/{id}/transcript`로 해당 영상의 전사를 조회한다.

같은 videoId의 실패/취소 재시도는 기존 결과 저장 경로에서 전사를 교체할 수 있다. 따라서 모든 job 버전의 전사가 DB에 자동 보존되는 구조는 아니다. 실험 폴더의 `transcript-99.json` 같은 파일은 별도 수집한 스냅샷이며, 모든 영상의 JSON 파일이 자동 생성되는 것은 아니다.

## 새 로컬 API

`POST /api/v1/videos/{sourceVideoId}/analysis/replay-transcript`

- `local` 프로필에서만 등록된다.
- 명시적 loopback 서버 바인딩·loopback peer만 허용한다. 프록시 헤더와 외부 Origin을 거절한다.
- `Content-Type: application/json`이 필요하다. 요청 본문에 전사나 임의 파일 경로를 받지 않는다.
- 완료 상태의 원본 영상과 비어 있지 않은 저장 전사가 필요하다.
- 원본 Video 잠금 안에서 전사를 읽고, 새 videoId의 전사 행으로 복사한다.
- 동일 시작 시간은 기존 행 ID 순서로 정렬한다. 공백·문구·시간을 교정하지 않는다.
- 신규 Video에 `transcriptSourceVideoId`와 `transcriptSnapshotSha256`을 보관한다. 해시는 순서·시간·UTF-8 원문을 길이 구분해 계산한다.
- 새 video/job을 기존 bounded admission에 등록한다. 커밋된 전사만 작업자가 읽는다.
- 원본 전사·리포트·검수 상태·미디어는 변경하지 않는다. 복사본에 원본 storageKey를 공유하지 않는다.

생성 응답은 `sourceVideoId`, 새 `videoId`, `jobId`, `status`, `transcriptSegments`, `transcriptSha256`을 반환한다. 대기열이 가득 차면 생성된 실행은 기존 admission 규칙에 따라 FAILED가 될 수 있다.

## 재사용 실행의 경로

새 Video의 자기 소유 전사 → `StoredTranscriptProvider` 무결성 확인 → 기존 텍스트 분석기 → fusion → 결과 writer → 기존 status/report API.

재사용 provider가 실패하면 외부 STT로 폴백하지 않는다. 원본 전사가 나중에 삭제돼도 새 Video의 복사본으로 실행한다. 결과 writer가 복사본 전사를 교체할 때도 동일 원문·시간으로 새 객체를 저장한다.

STT는 새 인식이 아니라 저장 전사를 사용했다는 coverage 메시지를 남긴다. 전체 OCR이 전역 ON이어도 이 실행에서는 OFF이며 선택적 프레임 검토도 차단한다. 영상 길이에 따른 새 STT 비용 추정은0이다. 텍스트 AI 분석 비용은 별도로 발생한다.

이는 전체 **저장 전사** 분석이지 원음·영상 재검수나 새 STT 품질 검증이 아니다. UPLOAD 원본의 복사 실행은 storageKey가 없어 스트리밍할 수 없다. YOUTUBE 원본은 기존 URL 메타데이터를 보존하지만 다운로드·음성 추출에 사용하지 않는다.

## 조회와 실행 예시

조회는 모델 호출을 발생시키지 않는다.

```bash
curl -sS http://127.0.0.1:8080/api/v1/videos/99/transcript
```

아래 POST는 **새 유료 텍스트 분석을 시작한다**. 서버 재시작·전송/예산 승인 후에만 수행한다. 구현 과정에서는 실제 실행하지 않았다.

```bash
curl -sS -X POST http://127.0.0.1:8080/api/v1/videos/99/analysis/replay-transcript \
  -H 'Content-Type: application/json' -d '{}'
```

응답의 새 videoId로 조회한다. 예시의 NEW_VIDEO_ID를 실제 응답 값으로 바꾼다.

```bash
curl -sS http://127.0.0.1:8080/api/v1/videos/NEW_VIDEO_ID/status
curl -sS http://127.0.0.1:8080/api/v1/videos/NEW_VIDEO_ID/transcript
curl -sS http://127.0.0.1:8080/api/v1/videos/NEW_VIDEO_ID/report
```

여러 영상은 한 편이 완료된 뒤15초 간격을 둔다. 기존 `/analysis/retry`는 완료된 분석을 재실행하는 API로 바꾸지 않았다. 일반 retry의 기존 worker health 사전 확인도 유지한다.

## 적용·검증 범위

현재 실행 중인 서버는 임의로 종료/재시작하지 않았다. Spring을 재시작해야 새 API와 provider가 적용된다. Video에 nullable 출처 ID·해시 컬럼2개를 추가했으며 로컬 `ddl-auto:update` 환경의 재시작에서 반영된다. 운영 배포에는 해당 스키마 변경을 별도 검토·적용해야 한다.

무료 검증은 DB 복사/원본 보존, 단일 커넥션에서 커밋 후 작업자의 스냅샷 가시성, provider 우선 선택·STT 미호출, 해시 불일치 중단, OCR/프레임 차단, 로컬 프로필/접근 제한을 확인한다. 실제99/109 재분석·API 리포트 신규 저장은 아직 실행하지 않았다.

테스트 DB에서는 실제 결과 writer로 복사 전사를 저장하고, 기존 AnalysisService의 리포트·전사 조회까지 확인했다. 이 시험의 분석 결과는 무료 테스트용 빈 결과이며 AI 정확도·실제99/109의 분석 결과를 의미하지 않는다.
