## 1. 개발 범위와 현재 상태

기존 개선 항목은 품질과 안정성의 기본기다. 기술적 경쟁력을 증명하기 위한 별도 가설과 비교 실험은 [기술 차별성 검증안](기술-차별성-검증안.md)을 따른다. 2026-10-08 합의에 따라 공통 문맥 입력과 중간 평가를 분리하는 개편을 진행한다. 배심원 구성과 최종 판단 정책의 기본 활성화는 실제 비교 결과로 결정한다. 상세 범위와 상태는 [9절](#pipeline-redesign)을 따른다.

| 영역 | 기존 동작 기준 | 이번 계획 |
|---|---|---|

현재 코드의 주요 변경 지점은 `SpeechReviewAnalyzer`, `ScreenTextReviewAnalyzer`, `ContextLexiconAnalyzer`, `ContextValidator`, `ContextLexicon`, `FindingFusionService`다. 기본 분석 설정과 사실 대조 기능은 유지하며, 표현 분석 전용 비교 profile만 추가했다.

### 1차 반영 내용

- 일반 용법 힌트 하나만으로 사전 후보를 버리지 않고, 특수 맥락 신호와 함께 평가한다. 일상 용례만 있는 후보는 추가 문맥 호출 없이 제외한다.
- 후보가 24개를 넘으면 영상 시간대에 걸쳐 선택하고, 미검토 수를 부분 분석 경고로 남긴다. 주변 STT/OCR 문맥은 입력 종류별로 분리한다.
- 발언·화면 검토는 원문에 실제 존재하는 짧은 인용을 응답하도록 하고 서버에서 검증한다. 허용되지 않은 유형과 대상을 요구하는데 대상이 없는 결과는 저장하지 않는다.
- 보통의 부정 리뷰와 비하를 구분하고, `STRONG_NEGATIVE_REVIEW`는 낮은 우선순위(점수 상한 0.39)로 별도 표시한다.
- 문맥 검증은 현재 요청 묶음에 포함된 후보 ID만 받으며, 애매함·인용·일반 용례 기준을 프롬프트에서 정리했다.
- 결과 병합은 시간과 유형 호환성을 함께 요구하며, 같은 대상명만으로 다른 장면을 합치거나 서로 다른 유형을 합치지 않는다. STT와 OCR이 겹쳐도 점수 보너스를 주지 않는다.
- 변경된 기준을 설명하는 24개 합성 검수 사례, 회귀 테스트, 기본 동작을 바꾸지 않는 `expression-review` profile을 추가했다.

이 변경은 코드 경로와 데이터 검증을 개선한 1차분이며 실제 검수 정확도 향상을 입증한 것은 아니다. API 소비 화면이 새 enum을 어떤 방식으로 표시하는지, 실제 사례에서 놓침과 과탐지가 어떻게 변하는지 확인해야 한다.

## 2. 먼저 고정할 판단 기준

### 2.1 표현의 발견과 표시 결정을 분리

사전이나 룰이 발견한 표현은 내부 후보다. 사용자에게 표시하려면 현재 사용 맥락에서 무엇을 확인해야 하는지 설명할 수 있어야 한다. 단순히 특정 커뮤니티에서 사용된 적이 있거나 정치·지역·사건을 언급했다는 이유만으로 표시하지 않는다. 화자의 지역·성향·커뮤니티 소속은 추론하지 않는다.

`~노` 어미는 단독 탐지에서 계속 제외한다. 이를 다시 사전에 넣거나 방언 판별을 이번 개발의 선행조건으로 삼지 않는다.

### 2.2 부정 평가도 검토하지만, 문구별 고정 판정을 피한다

다음 예시는 사람이 라벨링할 때의 기준 초안이다. 같은 문구도 앞뒤 문맥에 따라 결과가 달라질 수 있다.

| 발언과 상황 | 판단 초안 | 이유 |
|---|---|---|
| 음식 리뷰에서 “제 입에는 별로였어요” | 일반적으로 표시하지 않음 | 개인 취향 평가이며 공격을 뒷받침하는 맥락이 없음 |
| 특정 가게 리뷰에서 “돈이 아깝다” | 맥락 검토 | 강한 불만일 수 있으므로 반복되는 조롱·비난의 대상·주변 표현 확인 |
| “돈이 아깝다” 주변에 모욕적인 비유·반복 조롱이 이어짐 | 표현 수위 검토 후보 | 단순 만족도 평가보다 강한 공격으로 읽힐 구체적 근거가 있음 |
| 음식 평가가 지역 주민 전체를 깎아내리는 말로 이어짐 | 일반화·비하 검토 후보 | 평가 대상이 음식에서 집단으로 확대됨 |
| “그 사람이 사기꾼이다”를 사실처럼 말함 | 표현 검토 후보, 사실 대조는 별도 | 특정인에 대한 중대한 주장이며 진위는 표현 검토만으로 결정할 수 없음 |
| 비판·교육 목적으로 문제 표현을 인용함 | 보통 제외, 맥락 확인 | 인용 여부와 현재 사용 의도를 함께 확인 |
| 문제 표현을 인용하며 특정인을 다시 조롱함 | 검토 후보 가능 | 인용이라는 형식만으로 현재 공격이 사라지지는 않음 |

“별로다”라는 한 단어를 일괄 제외하지 않고, “돈이 아깝다”를 일괄 경고하지 않는다. 대상의 식별 가능성, 평가의 강도, 모욕·조롱의 구체적 표현, 집단 일반화, 주변 발언의 반복을 판단 근거로 사용한다. 한 문장이라도 구체적인 대상에 대한 표현 강도가 높으면 수위 검토 후보가 될 수 있으며, 반복 조롱은 이를 뒷받침하는 추가 근거다. 텍스트만으로 억양·표정·의도를 확인했다고 설명하지 않는다.

### 2.3 결과 결정과 점수의 의미

- `PASS`: 충분히 검토한 입력에서 표시할 근거를 찾지 못함. 평가 사례의 결정값으로 사용하며, 모든 정상 문장을 DB에 저장하지는 않는다.
- `REVIEW_REQUIRED`: 제작자가 확인할 구체적인 표현과 이유가 있음.
- `UNCERTAIN`: OCR·STT 오류나 부족한 맥락 때문에 해석을 결정하기 어려움. 어떤 정보가 부족한지 함께 남김.

분석 실패·미실행은 위 결정과 별도의 실행 상태다. 읽지 못한 영상을 `PASS`로 처리하지 않는다. 막연한 “논란일 수도 있다”는 문장은 `UNCERTAIN` 결과로도 올리지 않는다.

`score`와 최종 우선순위는 논란 발생 확률이 아니다. 모델이 반환한 자기 확신 점수도 확률처럼 사용하지 않는다. 구현에서는 강한 부정 평가를 `STRONG_NEGATIVE_REVIEW`로 분류하고, 기존 severity 경계에 맞춰 최대 0.39로 제한해 낮은 우선순위로 보여준다. 이 값은 보정된 확률이 아니라 초기 정책 상한이며, 실제 라벨 사례로 적절성을 검토한다. API 소비 화면이 새 enum을 동적으로 표시하는지 별도로 확인한다.

## 3. 논란 사전 설계

### 3.1 단어 수보다 항목의 검증 가능성을 높인다

현재 JSON 파일을 유지한다. 새 속성은 Java 파서와 검증 코드를 먼저 확장한 다음 추가한다. 기존 항목은 새 필드가 없어도 읽을 수 있도록 하되, 출처·예문이 없는 항목은 점검 대상으로 구분한다.

| 정보 | 역할 |
|---|---|
| 기존 `id`, `patterns`, `regex` | 안정적인 항목 ID와 실제로 매칭할 표현 |
| 기존 `contextHints`, `suppressHints` | 특수 용법·일반 용법을 판단하는 참고 신호 |
| 기존 `triggerMode`, `needsContext`, `reason`, `reviewedAt` | 검토 방식과 사용자 설명, 점검일 |
| 제안 `riskExamples` | 검토할 가치가 있는 앞뒤 맥락과 이유 |
| 제안 `safeExamples` | 일상 용법·인용·설명 등 헷갈리지만 보통 제외할 예시 |
| 제안 `sources` | 의미·사례를 확인한 원자료 URL, 제목, 날짜, 어떤 주장을 뒷받침하는지 |
| 제안 `evidenceStatus` | 검증됨·이견 있음·근거 부족 등 사전 설명의 근거 상태 |

검증되지 않은 의미·기원은 모델이 만들어 채우지 않는다. 근거 부족 항목은 경고 문구를 약하게 쓰는 것으로 해결하지 않고, 활성 탐지에 사용할 수 있는지 먼저 재검토한다. 정치적 표현의 수를 맞추는 것보다 항목마다 동일한 근거 기준을 적용하는 것이 우선이다.

### 3.2 후보를 버리는 조건을 보완한다

`suppressHints`는 일반 용법을 지지하는 신호로 취급한다. 특수 용법 신호도 함께 있거나 앞뒤 문맥이 충돌하면 바로 제거하지 않고 문맥 확인에 전달한다. 반대로 의미가 명확한 일반 용법은 기존처럼 추가 호출 없이 제외할 수 있다.

단어 경계와 조사·띄어쓰기 변형을 확인하고, 한 문장 안의 각 매칭 위치를 보존한다. 짧은 부분 문자열이 다른 단어 안에서 우연히 일치하지 않도록 예외를 테스트한다. STT의 음성 유사 변형은 실제 오인식 사례가 있을 때 추가하고, 임의의 넓은 정규식으로 의미를 복원하지 않는다.

`needsContext: false`인 표현도 인용·설명일 수 있다. 룰 결과를 최종 판정으로 보지 않고 내부 후보로 생성해, 이미 실행되는 전체 검토 결과와 대조하는 방향을 적용한다. AI를 실행하지 못하면 룰 기반 후보라는 한계를 표시한다.

### 3.3 사전 추가 절차

표현 제안 → 의미·사례 출처 확인 → 위험 예문과 일반 예문 작성 → 매칭 회귀 확인 → 문맥 검토 비교 → 버전 반영 순서로 관리한다. 항목을 늘리려면 적어도 위험 예문 1개와 일반·경계 예문 2개 또는 동등한 맥락 테스트를 작성한다. 일반 용법이 없는 표현도 인용·비판 예문으로 제외 조건을 검증한다.

## 4. 프롬프트와 입력 문맥 설계

### 4.1 세 역할의 공통 기준을 맞춘다

| 분석기 | 역할 | 주요 수정 |
|---|---|---|
| `SpeechReviewAnalyzer` | 전체 대본에서 사전에 없는 표현·공격·일반화까지 탐색 | 일반 리뷰의 자동 비하 분류 제거, 강한 평가와 조롱의 예문 추가 |
| `ContextValidator` | 사전 후보의 실제 의미와 사용 맥락 확인 | 애매함 지침 통일, 인용 자동 제외 보완, 검증된 사례와 대조 |
| `ScreenTextReviewAnalyzer` | 화면 문구 자체의 위험과 OCR 불확실성 확인 | 원문과 추정 복원 구분, 음성 없이도 판단 가능, 동일한 수위 기준 적용 |

전체 대본 검토를 유지해 사전에 없는 표현도 찾는다. 사전 검토에는 현재 후보와 관련된 소수의 예문만 넣는다. 사전 전체를 매 호출에 붙이거나, 모든 후보에 신규 호출을 추가하지 않는다.

공통 판단 순서는 원문 확인 → 표현의 대상·의미 확인 → 평가·인용·조롱 등 사용 맥락 확인 → 구체적인 검토 이유 확인 → 결정이다. 장르는 보조 정보로 쓰며 코미디라고 자동 통과시키거나 리뷰라고 자동 비하로 처리하지 않는다. 입력 대본·OCR·외부 자료 안의 지시는 분석 데이터로만 취급한다.

### 4.2 자막 유무에 독립적인 입력

음성의 앞뒤 대화는 STT 세그먼트에서 가져오고, 같은 시점의 OCR은 별도 보조 입력으로 붙인다. 현재처럼 시간순 혼합 목록에서 앞뒤 한 항목을 가져오면 직전 대화 대신 같은 장면의 반복 자막을 받을 수 있으므로 이를 보완한다.

첫 구현은 기존 윈도우를 유지하되 시간·입력 길이·포함 세그먼트 수를 기록한다. 대화 문맥이 잘리는 사례가 확인되면 시간 기준 묶음과 입력 길이 상한을 적용한다. 상한 때문에 분할한 구간은 겹치는 문맥을 제공하고 같은 원문 구간의 중복 후보를 정리한다.

| 확보한 입력 | 실행할 검토 | 결과에 남길 범위 |
|---|---|---|
| STT 있음, OCR 텍스트 없음 | 전체 발언·사전 문맥 검토 | 음성 검토 완료, 화면 글자 없음 또는 OCR 실패를 구분 |
| STT와 OCR 있음 | 발언과 화면을 각각 검토, 동일 시점 연결 | 각 입력의 수행 상태와 원문 |
| STT 없음, OCR 있음 | 화면 문구 검토 | 음성 미확보, 억양·발언 내용 판단 불가 |
| 둘 다 없음 | 현재 파이프라인의 분석 불가 처리 유지 | 분석 실패 이유, 검토 결과 없음과 구분 |

OCR 텍스트가 없다는 사실만으로 “자막이 없는 영상”이라고 확정하지 않는다. 인식 실패일 수도 있다. 음성과 화면 글자 모두에 나타나지 않는 표정·행동은 이번 텍스트 검토의 분석 범위에 포함하지 않는다.

### 4.3 응답에 실제 근거를 요구한다

LLM 내부 응답에는 입력 항목 ID, 실제 인용 문구, 결정, 유형, 대상(선택), 구체적인 이유, 부족한 정보를 요구한다. `ContextValidator` 응답의 ID는 해당 요청 묶음에 속하는지 검증한다. 창 내부 번호가 유효하더라도 인용 문구가 해당 원문에 없으면 저장하지 않고 검증 실패 수를 기록한다.

인용은 원문과 일치시켜 확인하고, OCR 복원 문구는 별도 추정값으로 보존한다. 검증 실패는 “위험 없음”으로 집계하지 않는다. 이 검증은 제공된 텍스트와 결과의 일치를 확인하며 STT가 실제 음성을 정확히 옮겼다는 보증은 아니다.

불필요한 대상명을 만들어내지 않도록 대상은 선택값으로 둔다. 대상이 없으면 이름을 이용한 병합을 적용하지 않고, 유형에 맞는 실질적인 검토 이유가 있는지 확인한다. 허용되지 않은 결정·유형과 누락 필드를 범용 카테고리로 자동 보정하지 않는다.

## 5. 결과 정리와 분석 범위

병합은 시간상 같은 장면인지, 유형이 호환되는지, 실제 지적 내용이 같은지를 함께 확인한다. 대상명은 보조 조건이다. 같은 대상을 여러 번 언급한 후보는 표시상 묶을 수 있지만 각 원문·시각·유형·이유를 보존해야 한다. 해당 정보를 보존하기 전에는 멀리 떨어진 구간을 하나의 finding으로 합치지 않는다.

발언이 화면 자막에 그대로 반복되어도 점수를 자동으로 1.25배 올리지 않는 방향으로 수정한다. “양쪽에서 확인됨”은 관측 정보로 남기고, 우선순위는 구체적인 표현·근거·검토 결정으로 계산한다. 판단 보류 후보가 중복 개수 때문에 높은 위험으로 바뀌지 않도록 한다.

사전 후보 최대 24개는 비용 상한으로 유지할 수 있지만, 상한 전 전체 후보 수와 선정·미검토 수를 센다. 먼저 중복을 제거하고 시간대와 항목별 편중을 줄인 뒤 한도 안에서 선택한다. 제외한 후보를 안전하다고 판단한 것으로 처리하지 않는다. 전체 대본 검토가 수행되었는지와 사전 전용 검토가 일부 제한되었는지는 별도로 기록한다.

기존 `AnalysisCoverage`의 성공·실패·스킵 구조는 재사용한다. 일부만 처리한 경우를 담을 상태와 검토 수·누락 수는 추가 설계가 필요하다. 리포트와 `TimelineEventDto`에는 필요한 필드를 추가하는 방식으로 연결하고 기존 API 필드의 의미를 갑자기 바꾸지 않는다. DB 변경은 기존 데이터의 기본값·마이그레이션·되돌리기를 포함한다.

분석 결과에는 사용한 모델 ID, 프롬프트·사전·판정 기준 버전, 입력 해시를 남기는 방향으로 확장한다. 후보별 분석기 출처도 보존해 사전 문제인지 프롬프트 문제인지 비교한다.

## 6. 사실 대조 기능의 경계

표현 수위와 사실의 진위는 별도 판단이다. “돈이 아깝다”는 의견이므로 기사와 대조하지 않는다. 특정인에 대한 범죄 주장·사건 날짜·수치처럼 검증 가능한 주장만 사실 대조 후보가 된다. 표현 검토는 해당 발언이 가진 공개 전 검토 필요성을 설명할 수 있지만 진위를 확정하지 않는다.

기본 실행 설정은 기존 동작을 유지한다. 표현 검토만 비교할 수 있도록 `expression-review` Spring profile 구성을 추가한다. 이 profile은 `entity-check`와 `context-check`를 제외해 표현 검토 단독 결과를 비교한다. 기본 profile이나 현재 배포 설정은 바뀌지 않는다. 외부 검색 실패가 표현 검토를 중단시키지 않아야 한다.

사실 대조의 기본 활성화 여부는 다음을 확인한 뒤 결정한다.

- 주장과 직접 관련된 출처 및 원문 근거를 결과에 연결할 수 있는가?
- 발언 시점과 자료 시점이 다를 때 그 차이를 설명하는가?
- 검색 결과 없음·근거 부족·검색 실패·상충하는 자료를 구분하는가?
- 표현 검토만 제공할 때보다 유용한 후보가 늘고, 추가 오탐·지연·호출 비용을 감당할 수 있는가?

이 기준을 통과하기 전에는 “기사에 없음”을 오류 판정의 근거로 쓰지 않는다. 사전 항목의 의미를 사람이 출처로 검증하는 작업은 런타임 사실 대조 기능과 별개로 계속 수행한다.

## 7. 평가와 검증

라벨링 시작을 위한 가상 사례와 기준 초안은 [데이터셋 문서의 가상 사례 부록](논란-데이터셋-구축-계획.md#annotation-examples)에 통합했다. 이는 사람이 합의한 정답 데이터가 아니다. 구체적인 수집·독립 주석·분할은 [논란 데이터셋 구축 계획](논란-데이터셋-구축-계획.md)을 따른다. 30개 파일럿으로 기준을 맞춘 뒤 텍스트·행동·복합 입력을 포함한 실제 구간 200개를 목표로 한다. 자막 없음, 일반 비평, 강한 불만, 반복 조롱, 집단 일반화, 은어의 일반 용법, 인용·비판, STT/OCR 오류를 포함한다. v1·v2·v3은 사용 가능한 기존 산출물을 확인해 활용하고, 알려진 논란 구간이라는 이유만으로 영상 전체를 정답으로 지정하지 않는다. 시각 분석과 긴 영상 평가의 추가 설계는 [행동·포즈 데이터셋과 긴 영상 적용 계획](행동-포즈-데이터셋-및-긴영상-적용-계획.md)에 둔다.

사례마다 원문·앞뒤 문맥·입력 출처·시각·사람의 결정·유형·이유를 기록한다. 실제 영상이 필요한 판정과 텍스트만으로 가능한 판정을 구분한다. 두 사람이 먼저 독립적으로 분류하고 불일치 사례를 합의하거나 판단 보류로 남긴다. 모호한 사례를 억지로 정답 하나에 맞추지 않는다.

프롬프트에 사용할 예문과 최종 비교용 평가 사례를 분리한다. 같은 영상·유사 문구를 양쪽에 나누어 평가 성능이 부풀려지지 않도록 영상 또는 사례군 단위로 분리한다. 모의 응답 검증은 코드 경로를 확인할 뿐 모델의 정밀도·재현율을 입증하지 않는다.

| 평가 대상 | 확인할 것 |
|---|---|
| 의미·수위 판단 | 표시 후보의 유용성, 일반 용법 오탐, 중요한 위험 누락, 판단 보류의 적절성 |
| 근거·구간 연결 | 원문 일치, 실제 구간과 연결 여부, 잘못된 ID·유형 거부 |
| 병합 | 다른 시점·다른 문제 보존, 반복 자막 중복 제거, 점수 과대 증가 방지 |
| 입력·실패 | STT만/OCR만/둘 다 없음, 일부 LLM 실패, 후보 한도 초과 |
| 비용·재현 | 호출 수·입력량·분석시간, 사용 버전·입력 해시 |

출시 판단은 현재 기준선과 비교한다. 일반 용법과 부정 리뷰의 불필요한 표시가 줄어야 하고, 합의된 중요 위험 사례의 탐지가 악화되지 않아야 한다. 사례 수와 유형별 결과를 함께 공개하고 소규모 평가를 전체 서비스 정확도로 설명하지 않는다. 실제 모델 비교가 아직 없으면 해당 항목은 검증 대기로 남긴다.

## 8. 구현 순서와 완료 조건

각 묶음은 별도 커밋으로 검토할 수 있게 진행한다. 날짜를 먼저 고정하기보다 완료 조건을 충족한 뒤 다음 단계로 넘어간다.

| 순서 | 구현 묶음 | 주로 수정할 곳 | 완료 조건 |
|---|---|---|---|
| 1 | 판단 기준·평가 자료 | 이 문서, 평가용 fixture·가이드 | 30개 파일럿에서 기준 합의, 개선 전 기준선과 비교 방법 준비 |
| 2 | 사전 품질·매칭 보완 | `context-lexicon.json`, `ContextLexiconEntry`, `ContextLexicon`, 사전 테스트 | 출처·예문 기반 항목 점검, 충돌 힌트·부분 문자열·인용·`~노` 회귀 확인 |
| 3 | 공통 판단·프롬프트·근거 검증 | 세 LLM 분석기와 `ContextValidator`, 내부 응답 모델 | 강한 평가와 일반 리뷰 기준 통일, 모의 응답에서 잘못된 근거·ID 거부, 자막 없는 입력 처리 확인 |
| 4 | 결과 모델·병합·범위 | `RiskFinding`, `FindingFusionService`, `AnalysisCoverage`, DTO·리포트 | 판단 보류 및 근거 보존, 부당 병합·점수 상승 방지, 후보 누락 표시, API 호환 검증 |
| 5 | 구성·버전·종합 비교 | 분석 설정, 실행 기록, 평가 결과 | 표현 검토와 사실 대조를 개별 실행·비교 가능, 버전 추적, 보류 평가셋 결과 확인 |

단계 3의 결정값은 내부 응답에서 먼저 다루고, 단계 4에서 DB와 API로 연결한다. 연결 전에는 내부 판단 보류를 기존 위험 카테고리로 임의 저장하지 않는다. 근거 검증 실패나 부분 실행 상태도 누락되지 않도록 단계 3~4의 연결 검증을 수행한다.

단계 5의 실모델 비교는 기존 산출물 재사용과 코드 검증을 끝낸 뒤 필요한 구간으로 제한한다. 프롬프트·사전 변경만으로 실제 품질이 좋아졌다고 선언하지 않는다. 이전 설정과 버전을 함께 보관해 문제가 생기면 이전 분석 구성으로 되돌릴 수 있게 한다.

9절의 공통 입력·중간 평가 기반, 사전 경로 문맥 연결, 전체 발언·화면 평가 연결을 구현하고 오프라인 검증했다. 다음 코드 작업은 분석기 간 충돌·최종 병합이며, 동시에 24개 합성 사례를 기준 논의에 활용하고 30개 실제 텍스트 구간은 사람이 라벨링한다. 포즈·행동 분석은 보류한다. 사전 항목과 점수 상한 변경, 비용이 드는 실모델 비교는 사람의 기준과 예산을 확인한 뒤 진행한다.

## 9. 정확도 중심 파이프라인 개편 (2026-10-08)

### 9.1 목표와 비목표

추출 오류·발견 오류·의미 판단 오류·위치 오류를 분리해서 측정할 수 있는 구조를 만든다. 사용자에게 표시하는 최종 후보와 각 평가자의 중간 판단을 분리한다. 이는 정확도 향상을 검증할 기반이지 향상 자체의 증명은 아니다.

- 기존 AWS 배포와 Spring·Python 경계는 이번 구현에서 유지한다. Rails 8 전환은 별도 비교 과제다.
- 포즈·행동 분석, 신규 유료 인프라, 유료 API 재실행은 이번 범위에서 제외한다.
- GPT-6 Luna·gpt-transcribe는 앞선 비용표의 비교 기준이다. 이번 개편만으로 실제 기본 모델·STT 응답 형식을 변경하지 않는다.
- `~노` 단독 탐지 제외와 자막 없는 영상의 STT 검토를 유지한다.
- 강한 상품 비평을 낮은 우선순위로 알리는 기존 정책은 유지한다. 그것을 공격 경고와 분리하거나 제외할지는 실제 주석 기준을 합의한 뒤 바꾼다.

### 9.2 목표 흐름

STT·OCR 추출 → 공통 문맥 입력 → 전체 구간 평가 → 근거 검증·충돌 해결 → 최종 후보 병합 → 검수 리포트.

공통 입력은 구간 ID·원문·출처·시점·OCR 신뢰도와 시간상 연결된 여러 앞뒤 발언·자막을 보존한다. OCR과 STT가 같은 문구를 담았다고 독립된 위험 근거로 계산하지 않는다. 화자·지칭 대상은 확인 가능한 경우만 추가하고 추정으로 채우지 않는다. 원문과 추정 수정문은 별도 자료로 관리한다.

목표는 통합 평가와 문화·언어/사실·보도/맥락·오탐 배심원이 같은 입력 계약을 사용하는 것이다. 배심원은 전체 입력을 배치로 독립 검토하며, 단어 매칭 또는 다른 배심원의 후보가 있어야 실행되는 구조로 제한하지 않는다. 공통 표현 카드·사례는 단일 기준으로 관리하고 배심원별로 필요한 부분만 제공한다. 현재는 기존 발언·화면 평가 두 경로를 공통 입력에 연결했다. 긴 영상의 시간·원문량 기반 배치, 겹침과 미평가 ID 기록은 9.7절에 반영했으며, 실제 토큰 계산·선택적 문맥 확장·배심원 실행은 후속 단계다.

### 9.3 중간 결과와 근거 계약

평가자별 실행 상태(`SUCCESS`, `FAILED`, `NOT_ASSESSED`)와 결정(`PASS`, `REVIEW_REQUIRED`, `UNCERTAIN`)을 분리한다. 빈 응답이나 실행 실패를 `PASS`로 변환하지 않는다. 평가 결과에는 평가한 구간 ID, 결정, 이유, 부족한 정보, 원문 인용의 구간 ID·문자 범위를 기록한다. 문자 범위는 변경하지 않은 원문에 대한 Unicode 코드포인트 `[start, end)` 기준이다.

최종 후보 생성 전에 실제 구간·인용 위치·원문 일치를 검증한다. 원문 일치는 텍스트 연결만 증명하고 음성 인식의 정확성이나 해석의 타당성을 증명하지 않는다. 서로 다른 해석은 중복으로 지우지 않고 충돌로 남긴다. 점수가 높거나 배심원 수가 많다는 이유만으로 대표 판단을 확정하지 않는다.

재분석 실행별 결과·모델·프롬프트·사전 버전과 검수 이력 보존은 후속 DB 설계에 포함한다. 현재 영상별 덮어쓰기 구조가 이미 해결된 것으로 설명하지 않는다.

### 9.4 구현 단계와 전환 조건

| 단계 | 작업 | 상태·전환 조건 |
|---|---|---|
| A | 공통 시점별 입력, 중간 평가 자료형, 원문 범위 검증 | 기반 구현·오프라인 검증 완료; 중간 평가 자료형의 LLM·DB 연결은 아직 없음 |
| B | 기존 맥락 사전 경로에 여러 줄 문맥 연결 | 기존 분석기에 연결·모의 응답 검증 완료; 실모델 정확도 비교는 대기 |
| C | 전체 발언·화면 평가의 공통 배치와 중간 결과 연결 | 코드 연결·오프라인 검증 완료; 실모델·운영 검증 대기, 중간 결과는 DB 미저장 |
| D | 근거 재검증·충돌 해결·판단 후 병합 | 서로 다른 판단·등장 시점 보존; 판정 정책은 사람 기준과 비교 |
| E | 실행별 저장·평가 도구·통합/배심원 비교 | 실제 라벨과 개발/최종 평가 분리; 비용·지연·오탐·미탐 함께 측정 |

단계 A의 자료형만 추가했다고 전체 분석기가 새 평가 계약을 사용하는 것은 아니다. 단계 B의 문맥 확장도 실제 정확도 향상을 입증하지 않는다. 단계 C~E 전환 전에는 기존 프론트 결과 계약과 모델 기본값을 유지한다. 각 단계의 검증·제약과 남은 작업을 이 절에 기록한다.

### 9.5 평가 원칙

사람이 확인한 전사와 실제 STT 입력을 비교해 추출·판단 오류를 구별한다. 같은 원본·사건의 유사 구간을 개발과 최종 평가에 나눠 넣지 않는다. 일반 비평·방언·인용·민감 표현의 일반 용례·입력 오류를 포함한다. 최종 평가는 불필요한 경고 수를 비슷하게 유지했을 때 중요한 구간을 더 찾는지와 원문·시점 정확성을 확인한다. 경고하지 않은 구간도 표본 재검토하며, 24개 합성 사례나 모의 API 테스트를 실제 탐지 성능으로 발표하지 않는다.

### 9.6 첫 반영과 검증 결과 (A·B)

`minwook` 브랜치에서 다음을 반영했다.

- `ReviewInput`: 변경하지 않은 원문·시점·STT/OCR 출처·OCR 신뢰도를 불변 스냅샷으로 묶는다. 저장된 구간은 DB ID를 사용하며, 저장 전 입력의 인덱스 기반 ID는 해당 스냅샷에서만 유효하다. 재분석 실행을 넘나드는 ID로 사용하지 않는다.
- `AnalysisContext`: 기존 네 인자 생성자를 유지하며 공통 입력을 한 번 생성한다. STT만 있는 영상과 OCR만 있는 입력을 지원한다.
- `ContextLexiconAnalyzer`: 같은 출처의 앞뒤 문맥은 시간 간격 15초 이내, 다른 출처는 겹치거나 간격 2초 이내 구간을 연결한다. 앞/뒤/다른 출처 그룹별 최대 8구간·원문 4,000코드포인트를 선택하며, 원문 구간 자체는 자르지 않는다. 가까운 구간을 우선 선택하고 시간순으로 전달한다. 한도를 초과하면 기존 분석 범위 안내에 문맥 제한을 남긴다.
- `ReviewEvaluation`·`ReviewEvidenceValidator`: 실행 상태와 결정 분리, 평가한 ID·이유·부족한 정보·원문 범위 계약을 추가했다. 존재하지 않거나 평가하지 않은 ID, 범위를 벗어난 인용, 원문과 다른 인용, 실패 상태의 판정을 거부한다. 빈 결과를 `PASS`로 만들지 않는다. 이 검증기는 아직 최종 후보 저장 경로에 연결하지 않았다.

맥락 사전의 후보 상한 24개, 요청 묶음 크기, 응답 형식, 표시 정책은 유지했다. 여러 줄을 보내므로 입력 토큰과 실제 호출 비용은 증가할 수 있다. 코드포인트 상한은 토큰 상한이 아니며 정확한 비용·지연은 실모델 비교에서 측정해야 한다. 기존 일반 용례 힌트 필터도 유지하므로 이번 반영이 전체 입력의 독립 평가를 구현한 것은 아니다.

Java 17 toolchain과 캐시된 Gradle 9.4.1로 오프라인 테스트를 실행했다. 전체 **72개 통과**, 그중 새 테스트 **15개**다. 여러 발언·동시 자막의 실제 요청 전달, STT만/OCR만 입력, 문맥 한도 안내, 원문·시점 유지, emoji를 포함한 코드포인트 범위와 잘못된 근거 거부를 확인했다. 유료 API 호출·운영 배포·모델 교체·포즈 분석은 수행하지 않았다.

이후 단계 C의 연결 결과는 9.7절에 기록한다. A·B의 테스트는 코드 동작 검증이며 실제 영상에서 오탐·미탐이 감소했다는 증거가 아니다.

### 9.7 전체 발언·화면 평가 연결 (C)

`SpeechReviewAnalyzer`와 `ScreenTextReviewAnalyzer`를 `TextReviewEngine`에 연결했다. 사전 후보 유무와 관계없이 각 출처의 비어 있지 않은 전체 원문을 시간순으로 검토한다. 모델 기본값과 외부 API 응답 DTO·DB 스키마는 변경하지 않았다. **LLM 내부 응답은 기존 `findings/index`에서 `evaluations/segmentId/decision`으로 변경했으므로 예전 모의 응답·재생용 fixture를 그대로 사용하면 미판정으로 처리된다.**

| 항목 | 반영 내용 |
|---|---|
| 공통 배치 | 평가 대상 최대 20구간·12,000코드포인트·시간 범위 120초. 발언은 3구간, 화면은 2구간 겹침을 유지하며 다음 배치가 반드시 전진하도록 구성 |
| 주변 문맥 | 기존 공통 창을 이용해 다른 출처와 배치 경계의 발언·자막을 연결. 배치 전체에서 최대 16구간·8,000코드포인트, 개별 창의 한도도 적용. 이미 대상에 포함된 구간은 한도 적용 전에 제외 |
| 입력 계약 | 장르와 ID·원문·출처·시점·OCR 신뢰도를 JSON으로 전달. `primary`는 평가 대상, `context`는 보조 정보로 구분 |
| 결정 | 모든 대상 ID에 `PASS`·`REVIEW_REQUIRED`·`UNCERTAIN`을 요청. 빈 결과·잘못된 ID·빠진 판정은 통과로 변환하지 않음 |
| 근거 | 원문의 정확한 연속 인용에서 서버가 코드포인트 범위를 계산하고 기존 검증기로 확인. 공백·문장부호를 지운 유사 문자열은 새 경로에서 허용하지 않음 |
| 후보 생성 | 유효한 `REVIEW_REQUIRED`만 기존 `RiskFinding`으로 변환. 허용 유형·구체적인 사유·강한 부정 리뷰의 대상 및 점수 상한 0.39를 유지 |
| 보류·충돌 | `UNCERTAIN`은 부족한 정보와 함께 내부 결과에 남기고 자동 위험 카드로 만들지 않음. 같은 ID의 결정이 배치 내부나 겹침에서 달라지면 양쪽 관측을 보존하고 해당 경로의 후보 출력을 보류 |
| 실행 범위 | 미판정·충돌 ID, 응답 검증 실패·빈 응답·문맥 제한을 내부 실행 결과에 기록. 기존 `coverage`와 `warnings`에는 개수와 실행 상태를 전달 |

단일 원문 구간만으로 배치 상한을 초과하는 경우에는 원문을 자르거나 건너뛰지 않고 단독 요청하며 제한 초과를 알린다. 시간·코드포인트 상한은 토큰 한도나 요청 비용의 보장이 아니다. 모든 구간의 명시적 결정을 받으므로 이전 후보 전용 응답보다 출력 토큰이 늘 수 있고, 원문량·시간 기준으로 분할되면 호출 수도 증가할 수 있다.

원문 인용이 반복되면 서버는 첫 일치 위치를 기록한다. 이는 모델이 별도 지정한 세부 위치나 단어별 음성 타임스탬프가 아니다. STT 정확성·대상 해석·진위는 이 검증만으로 증명하지 않는다. OCR 추정 `reading`은 중간 결과에서 원문과 분리하며, 기존 화면 호환을 위해 최종 `captionText`의 “해석” 표기는 유지한다.

새 경로는 유효한 일부 결과가 있으면 `PARTIAL`, 모두 미판정이면 `FAILED`를 기록한다. 보류·충돌·문맥 제한도 분석 범위 안내에 남긴다. 파이프라인이 중간 실행 결과를 한 번 소비하고 예외·취소 시에도 잔여 결과를 정리한다. **중간 판정과 ID 목록은 현재 실행 메모리에만 있고 DB·기존 공개 API에 구간별로 저장·노출되지 않는다.** 재시작 이후 검수 이력으로 사용할 수 없으며, 실행별 저장은 E 단계다.

공식 [OpenAI Structured Outputs 문서](https://developers.openai.com/api/docs/guides/structured-outputs)에 따르면 JSON mode는 특정 스키마 준수를 보장하지 않는다. 이번 구현은 기존 `json_object` 호출을 유지하되 서버 검증을 연결했다. `json_schema` 기반 제약, 거절·출력 제한의 별도 분류는 후속 보완이며 이번 변경만으로 모델 응답 계약이 항상 지켜진다고 설명하지 않는다.

이번 단계의 새 테스트 **24개**, 이전 테스트 포함 **96개가 오프라인으로 통과**했다. 발언·화면의 명시적 통과/검토/보류, 잘못된 ID·인용·유형·결정, 응답 누락·전체 실패, 시간·문자량 배치, 겹침 충돌 보존, 동일 시점의 별도 원문, OCR 복원 분리와 실제 파이프라인의 성공/부분/실패 상태 기록을 확인했다. 유료 모델 실행·배포·포즈 분석은 수행하지 않았다.

남은 D 작업은 **서로 다른 분석기**의 해석 충돌 해결과 최종 `FindingFusionService`의 중복·판단 보류 처리다. 현재 같은 경로의 충돌 후보를 보류해도 다른 룰·사전 분석기에서 나온 후보까지 함께 보류하는 것은 아니다. 정확한 구간 연결·판정 정책·엄격한 인용 때문에 생기는 누락은 사람 라벨이 있는 실영상으로 비교해야 한다. 실제 정확도 향상·운영 응답 호환·비용·지연 검증은 아직 대기다.

### 9.8 OCR 영역 보존과 편집 텍스트 선별

간판·메뉴판을 편집 자막으로 취급하는 입력 문제가 확인되어, 최종 병합 작업보다 입력 출처 분리를 먼저 반영했다. 편집 기능·HyperFrames·자막 파일 업로드는 이번 구현에 포함하지 않았다.

Python `/ocr`는 `items` 목록을 유지하되 `formatVersion: regions-v1`로 **영역별** 원문·인식 신뢰도·정규화 좌표(`boxX/boxY/boxWidth/boxHeight`)·관측 ID·관측 수·같은 위치의 문구 변화 수를 반환한다. 한 프레임의 글자를 문장으로 합치지 않고 반복 위치의 글자를 워터마크라는 이유만으로 삭제하지 않는다. 기존 저신뢰도·너무 짧은 인식 결과 제외는 유지한다.

같은 원문·겹치는 위치(IoU 0.6 이상)가 연속 관측될 때만 하나의 구간으로 연결한다. 빈 프레임·시간 간격 단절·다른 위치는 연결하지 않는다. 좌표·프레임 크기를 모르면 텍스트는 보존하고 위치 추적을 하지 않는다. 좌표는 첫 관측 기준이며 장면 움직임·스타일·실제 자막 레이어를 복원한 것은 아니다. 프레임 크기는 Pillow 또는 기존 OCR 의존성 OpenCV로 읽는다. 기존 프레임 샘플링 간격·300프레임 상한 때문에 짧게 등장한 자막이 누락될 가능성은 그대로 남아 있다.

Spring은 좌표·관측 정보·역할·역할 판단 이유를 `ScreenText`에 저장한다. STT가 준비된 파이프라인에서 다음 **잠정 규칙**으로 역할을 분류한다. OCR 신뢰도를 자막 확률로 해석하지 않으며 위치 하나만으로 결정하지 않는다.

| 역할 | 현재 규칙·처리 |
|---|---|
| `EDITORIAL` | 가로형 영역과 같은 시간대 STT의 충분한 길이 문구 일치, 또는 가로형·넓은 영역에서 여러 문구가 교체되는 패턴. 편집 텍스트 추정으로 자막 표현 검토에 전달 |
| `BACKGROUND` | 현재는 명확한 구독·좋아요 등 UI 문구와 링크 안내에 한정. 보조 문맥으로 보존하며 개인정보 룰은 유지 |
| `UNCERTAIN` | 위치 없음, 구버전 응답, 근거가 부족한 간판·메뉴·단발성 강조 문구 등. 삭제하지 않지만 자막 표현 검토의 단독 대상에서 제외 |

간판·메뉴판을 모두 정확하게 `BACKGROUND`로 판별하는 구현은 아니다. 대부분은 `UNCERTAIN`으로 남는다. STT와 다른 강조·설명 자막은 위치 변화 패턴으로 일부 선택하지만, 한 번만 등장하는 중요한 자막을 놓칠 수 있다. 문구 교체가 많은 배경 화면도 편집 텍스트로 잘못 선택될 수 있다. 실제 자막 역할 분류의 정밀도·재현율은 아직 검증하지 않았다.

화면 LLM의 `primary`에는 편집 텍스트 추정만 넣는다. 배경·불확실 영역은 역할 표시를 붙여 제한된 주변 `context`로 제공하고, 제외 수·미판정 ID를 남긴다. 모두 제외된 경우에도 화면 검토를 안전·완전 성공으로 처리하지 않고 `PARTIAL`로 알린다. 화면 표현 룰·은어 사전·맥락 검색의 직접 입력도 같은 선택 기준을 적용한다. 개인정보 정규식은 역할과 관계없이 검사한다. 이 검사는 모든 개인정보 유형을 잡는다는 보장은 아니다.

새 메타데이터의 DB 저장은 구현했지만 기존 `/screen-texts` 공개 DTO는 유지했으므로 프론트에서 영역·역할 목록을 직접 표시하는 기능은 아직 없다. 자막 파일을 제공하는 경로 역시 후속 과제다. 새 Spring은 예전 Python 응답도 읽을 수 있으나 좌표 없는 결과는 불확실로 분류해 자동 자막 검토에서 제외한다. **실제 선별을 쓰려면 Spring과 Python을 함께 업데이트해야 한다.** 기존 저장 자료에 편집 자막 역할을 임의로 소급 지정하지 않는다.

DB에는 9개 nullable 컬럼을 추가한다. 운영 DB를 변경하거나 배포하지 않았으며, 수동 MySQL 절차는 [영역 컬럼 추가 SQL](migrations/2026-10-08-ocr-regions.sql)에 남겼다. 현재 dev/local의 `ddl-auto=update`가 이미 컬럼을 만들었는지 확인한 뒤 중복 실행을 피한다. 운영 백업·컬럼 점검 후 적용하며, 되돌릴 때는 Spring/Python 코드를 함께 복원하고 추가 컬럼과 원문은 보존한다. H2 신규 스키마 왕복 테스트만으로 운영 MySQL 마이그레이션을 검증했다고 설명하지 않는다.

Java **107개**, Python **22개** 오프라인 테스트를 통과했다. 영역 분리·연속 연결·단절·좌표 없음·UI 보존, 역할 선별·시간 대조·개인정보 경로, 구/신 OCR 응답 파싱, 프레임 재사용, H2 좌표·역할 저장을 확인했다. Python 테스트 의존성은 별도 임시 가상환경에 설치했고 PaddleOCR 모델 다운로드·실영상 추론·유료 API 호출·운영 DB 변경은 하지 않았다.

다음 검증은 실제 영상의 프레임과 STT를 함께 사람이 분류하는 것이다. 간판·메뉴가 제외되는 비율뿐 아니라 발언 자막·강조 자막의 누락을 측정하고, 같은 영상의 프레임은 개발/최종 평가에 나눠 넣지 않는다. 표본에서 임계값을 정한 뒤 별도 영상으로 확인한다. OCR 오류·역할 분류 오류·LLM 판단 오류를 구분해 기록한다.

### 9.9 v1 로컬 리포트에서 발견한 누락·뉴스 연관 오탐 보완 (2026-10-08)

사용자가 실행한 90초 v1 결과는 작업 상태가 `COMPLETED`였지만 발언 53구간 중 유효 판정 5·미판정 48·응답 검증 실패 5건이었다. 이벤트 8개 중 매장 유무 질문과 관련 없는 브랜드 뉴스, 일반 음식 이야기와 건강 연구를 연결한 경고가 있었다. 실제 영상 전체의 정답을 주석한 것은 아니므로 확정 정확도·오탐률로 환산하지 않는다.

**코드 반영 범위:**

- 정상 구간도 명시적인 PASS를 반환하도록 공통 계약을 강화하고 `requiredSegmentIds`·`minimumDecisionCount`를 입력에 추가했다. 질문·일반 감정·미완성 발언·불명 단어에 대한 반례를 명시했다. 모델·API·STT 설정은 바꾸지 않았다.
- 비어 있지 않은 응답에서 판정이 빠졌거나 검증에 실패한 구간만 재검토한다. 분석기 실행당 최대 6개 추가 배치, 배치당 최대 8구간, 구간당 최대 한 번이다. 앞뒤·다른 출처 문맥은 기존 제한을 유지한다. 이미 중첩 배치에서 판정된 구간과 충돌 구간은 제외한다.
- 호출 실패·빈 응답은 자동 PASS로 만들지 않고 미판정으로 남긴다. 네트워크 실패의 재시도는 기존 클라이언트가 담당하며 여기서 추가 중첩하지 않는다. 추가 배치 한도는 의미 검토 호출 기준이며 클라이언트 내부 전송 재시도 횟수까지 합친 HTTP 요청 한도는 아니다.
- 로그에 요청·수락·미판정 수, 알려진 미판정 ID, 실패 종류(결정 enum·원문 불일치·누락 근거·카테고리/사유 등), 실제 재검토 호출 수·복구 수를 기록한다. 원문·모델 응답 전문·키는 기록하지 않는다. 최종 경고에는 재검토·복구 요약을 추가한다. 복구에는 중첩된 최초 배치에서 정상 판정을 확보한 경우도 포함된다.
- `context-check`는 주제를 실제 줄에 연결한 뒤 해당 줄과 앞뒤 10초의 원문을 최대 9줄·4,000코드포인트 범위로 전달한다. 초과한 anchor는 이 경로에서 제외하며 프레임 엔티티·저장 경로는 전송하지 않는다. 추출 모델의 context는 추정임을 표시한다.
- 뉴스 경고는 DIRECT_EVENT/CONTEXTUAL_EVENT 연결, 원문·선택한 기사 제목 또는 요약의 정확한 인용, 공통 사건 단서, 구체적인 연결 이유, 유효한 기사 번호를 요구한다. MERE_MENTION/UNRELATED·브랜드명만 같은 경우·없는 인용·잘못된 출처를 거부한다. 출처가 없을 때 임의로 검색 첫 기사를 붙이는 기존 fallback을 이 경로에서는 사용하지 않는다.
- 본문을 읽지 않은 제목·요약 기반 배경 경고는 점수 0.69 이하로 제한하여 단독 HIGH로 표시하지 않는다. 기사 사실을 검증한 것으로 설명하지 않으며 이유에도 제목·요약 기준임을 표시한다. 사실 확인 분석기와는 별도다.

이 보호 장치가 의미 판단의 정확성을 보장하지는 않는다. 모델이 사건 단서를 잘못 연결하거나 서로 다른 사건의 비슷한 표현을 같은 것으로 볼 수 있고, 직접 인용이 없는 암시·패러프레이즈는 놓칠 수 있다. 논란 탐지를 고유명사나 고정 단어 목록만으로 결정하도록 변경한 것은 아니다.

실행 이력·중간 평가 원문은 여전히 DB에 저장하지 않는다. `COMPLETED`는 종료 상태이고 warnings의 PARTIAL/FAILED와 미판정 수를 함께 보여야 한다. 처음 응답의 오류·문맥 제한·UNCERTAIN이 남으면 복구 후에도 PARTIAL일 수 있다. 배경·불확실 OCR 제외는 재검토로 자동 승격하지 않는다.

회귀 테스트는 누락만 재검토·정상 PASS 복구·재검토 한도·중첩 복구 시 중복 호출 방지, 브랜드/음식 단순 일치 거부, 실제 사건 인용 허용·점수 제한, 잘못된 출처·인용·NaN 거부, 프레임 경로 미전송을 오프라인 mock으로 검증한다. 실제 v1 재분석·외부 유료 호출·운영 DB 변경·배포는 수행하지 않는다. 재검토에 따라 비용·시간이 증가할 수 있어 v1/v2/v3의 경고 수뿐 아니라 미판정 수와 실제 놓친 위험도 같이 비교해야 한다.

변경 후 Java 117개 테스트가 통과했다(실패·오류 0). 실제 모델 응답에서 같은 결과가 나온다는 보장은 아니며 실행 중인 로컬 Spring 재시작 후 v1 재분석으로 확인해야 한다. 이번 변경에는 DB 스키마 변경과 Python 수정이 없다.

프롬프트와 출력 계약을 명확히 하고 회귀 평가를 함께 유지하는 방향은 [OpenAI 공식 프롬프트 지침](https://developers.openai.com/api/docs/guides/prompt-engineering)을 참고했다. 이 문서가 우리 서비스의 탐지 품질을 인증하는 것은 아니다.

### 9.10 v1에서 찾아야 할 실제 검토 구간의 기준 초안 (2026-10-08)

사용자의 요청에 따라 일반적인 '위험할 수 있다'는 추측보다 실제 비판받은 발언·대화의 근거를 개발 평가의 출발점으로 삼는다. 로컬 videoId=2의 STT 전체와 2024년 당시 보도를 대조했다. 아래는 **회고 개발용 잠정 주석**이며 원본 90초 영상을 사람이 음성·장면까지 확인한 확정 정답이 아니다. 시간은 업로드한 편집본의 STT 기준이다. 전체 원본에 있던 다른 발언을 이 편집본의 누락으로 세지 않는다.

당시 [매경이코노미 보도(2024-05-17)](https://www.mk.co.kr/news/business/11018177)는 지역과 주민을 낮춰 보는 언행, 현지 음식·식당을 깎아내리는 평가, 가게가 식별되는 상황에 대한 비판을 소개했다. **당시 ID 2 결과의 문제:** A는 리포트에 없다. B는 브랜드 이름·발언 조각을 강한 부정 평가로 잡아 대상을 잘못 연결한다. C는 메뉴 관련 후보가 있지만 반복 폄하 문맥에 대한 근거 설명이 부족하다. D는 후보는 있으나 UNFAMILIAR_CONTEXT와 막연한 불쾌감 설명으로 의미를 잘못 분류한다. 따라서 당시 경고 13개를 핵심 4개 발견 성공으로 계산하지 않는다. 현재 ID 9의 상태와는 구분한다.

**단독 경고로 잡지 않을 대조 사례:** `롯데리아 없나?`, `근데 좀`, `코미디언으로서 한계를 느꼈다`, 음식의 일반적인 건강 설명. `산나물 먹기 싫잖아`는 단독 취향 표현과 지역 폄하의 보조 문맥을 구분한다. `반산두종`처럼 전사가 불명확한 구간은 청취 확인 전 의미·원문을 추정해 확정하지 않는다. 같은 음식 비교라도 맛·재료를 설명하는 일반 리뷰, 같은 국가 언급이라도 실제 위치 질문·중립적인 건축 비교를 별도 대조 사례로 둔다.

평가는 다음처럼 진행한다.

1. 원본 편집본을 사람이 확인해 실제 발언·대상·가게 식별 정보·검토 문맥 범위를 확정한다. STT 원문과 사람이 확인한 전사를 분리하고 필요한 경우 MEDIA_REQUIRED로 표시한다.
2. A~D를 단어 사전이 아니라 **개발용 문맥 사례**로 저장한다. 인용 위치에 연결된 후보가 실제 조롱·폄하·비하적 비유를 설명할 때만 발견 성공으로 센다. '당사자가 볼 수 있다'는 이유만으로는 성공이 아니다.
3. B처럼 긴 문맥 범위는 근거를 읽는 범위와 카드가 표시하는 핵심 발언 범위를 분리한다. 34~61.5초 전체를 자동 삭제 구간으로 간주하지 않는다. 같은 근거의 STT/OCR 카드 수로 성능을 부풀리지 않는다.
4. 발견한 핵심 사례 수, 잘못된 대상·유형·근거, 불필요한 경고 수, 미판정·보류를 따로 기록한다. 이 영상에서 핵심 4묶음을 놓치지 않는 것을 목표로 하되 개별 점수·유형은 주석 확정 후 정한다.
5. 동일·유사 정상 표현과 다른 지역·음식 영상으로 오탐을 함께 평가한다. v1은 이미 보고 프롬프트에 사용한 개발 자료이므로 독립 테스트셋으로 주장하지 않는다.

당시 기사·사과·공개 후 댓글은 주석자가 비판의 이유를 조사하는 자료일 뿐, 게시 전 탐지의 런타임 정답 힌트로 주입하지 않는다. 지역명·브랜드명·할머니 등의 단어를 사전에 등록해 무조건 경고하는 변경은 하지 않는다. 현재 평가는 STT와 보도의 대조 단계이며 이 기준만으로 런타임 코드를 추가 수정한 것은 아니다.

### 9.11 대화 단위 읽기·복수 근거·대상 연결 1차 구현 (2026-10-08)

9.10의 핵심 사례를 단어 목록으로 하드코딩하지 않고, 여러 발언을 근거로 반환할 수 있도록 발언·편집 텍스트 공통 엔진을 확장했다. `minwook`의 로컬 코드에 반영하며 배포·서버 재시작·유료 모델 호출은 하지 않는다. 포즈·편집 기능·로그인·모델 교체는 이번 범위가 아니다.

#### 원본 구간과 분석용 읽기 창의 분리

`ReviewUnit`은 primary 구간 각각을 대표 anchor로 하는 **겹치는 읽기 창**이다. 원본 STT/OCR의 문자열·시간·ID는 합치거나 수정하지 않는다. 입력 JSON의 `reviewUnits`에는 anchor ID, 포함 구간 ID, 문맥 시간 범위와 제한 여부를 전달한다. 원문은 기존 primary/context에 한 번씩 전달한다.

- 같은 출처의 인접 구간을 읽되 최대 30초·32구간·4,000 Unicode code point로 제한한다. 인접 시간 간격이 5초보다 크면 창 확장을 멈춘다. 이 값들은 검증 전 초기 휴리스틱이며 의미·화자·장면 경계를 보장하지 않는다.
- 단독 발언이 상한을 초과하면 원문을 잘라 버리지 않고 제한 상태로 남긴다. 배치·주변 문맥 제한도 읽기 창에 전달한다.
- 원본 구간 전체를 primary로 검토하는 기존 경로를 유지한다. 특정 키워드가 있는 발언만 창으로 만드는 것이 아니다.
- OCR 역할 분류는 유지한다. 배경·출처 불확실 OCR은 자동 검토 primary로 승격하지 않고, 근접 문맥으로만 사용할 수 있다.
- 대표 anchor는 실제 검토 표현이 있는 primary 구간이어야 한다. 같은 대화의 보조 발언은 별도 경고가 없으면 명시적인 PASS로 검토 여부를 기록한다. PASS는 해당 발언이 대화 맥락과 무관하거나 절대 안전하다는 뜻이 아니다.

긴 문맥을 정확히 의미 단위로 나누는 모델이나 화자 분리기를 구현한 것은 아니다. 30초를 넘는 이야기·대상을 멀리서 소개하는 발언·촘촘한 대화는 문맥이 잘릴 수 있다. 창 확장·분할 정책은 별도 영상으로 검증한 뒤 조정한다.

#### 복수 원문 근거와 대상 계약

LLM 결정에 `evidence[]`를 추가했다. 각 인용은 원본 `segmentId`, 연속 `quote`, 역할 `PRIMARY/TARGET/CONTEXT`를 반환하고 위치는 서버가 원문에서 Unicode code-point 범위로 계산한다. 같은 인용이 반복되면 최초 위치를 사용한다. 시간은 원본 구간 범위이며 인용 단어만의 정밀 시간은 아니다.

| 필드 | 검증·활용 |
|---|---|
| PRIMARY | 실제 검토 표현. 대표 anchor의 원문 인용을 반드시 포함 |
| TARGET | 검토 대상 연결에 필요한 실제 발언·화면 인용 |
| CONTEXT | 의미를 이해하기 위한 보조 발언 |
| targetType | PERSON/GROUP/REGION/RESIDENT_GROUP/BUSINESS/PRODUCT/WORK/OTHER |
| targetRelation | EXPLICIT 또는 CONTEXTUAL. 후자는 문맥 추론임을 표시 |
| targetReason | 원문 대상과 검토 표현이 어떻게 연결되는지 설명 |
| alternativeInterpretation | 가능한 정상 해석. 없으면 null, 억지 정상 해석 생성 금지 |

최대 12개 인용을 허용하며 같은 역할의 동일 인용 중복, 원문에 없는 인용, 제공하지 않은 ID, 해당 읽기 창 밖의 같은 출처 인용, 대표 anchor가 아닌 PRIMARY를 거부한다. 다른 출처는 anchor와 2초 이내에 근접하고 실제 입력에 제공된 경우만 보조 근거로 허용한다. 대상이 있는 REVIEW_REQUIRED는 TARGET 인용·유효 대상 유형·관계·구체적 연결 이유가 없으면 유효 판정으로 인정하지 않는다. 단순 브랜드 언급을 공격 대상으로 바꾸지 않도록 지침을 보강했다.

`ReviewEvaluation.suppliedSegmentIds`와 `reviewedSegmentIds`를 분리했다. 문맥을 받거나 근거로 참조했다고 그 발언을 검토 완료로 세지 않는다. 잘못된 인용·대상 계약은 기존 제한된 누락 재검토 경로로 보내고, 끝내 복구되지 않으면 미판정으로 남긴다. 기존 단일 evidenceText 응답은 대상 없는 결정에서 호환되지만 대상 있는 경고는 새 대상 근거 계약이 필요하다.

검증은 **인용의 실재와 연결 형식**을 확인한다. 실제로 그 대상을 낮춰 말했는지, 정상 리뷰인지, 모델이 TARGET 인용을 잘못 해석했는지까지 결정적으로 증명하지는 못한다. 모델이 지침을 어겨 서로 다른 anchor에 같은 사건을 중복 경고하는 문제도 완전히 해결한 것은 아니다.

#### 기존 리포트·저장 호환

DB 스키마와 공개 DTO는 변경하지 않았다. 카드 시간·본문은 대표 anchor를 유지하며, 문맥을 읽은 전체 범위를 자동 삭제 구간으로 표시하지 않는다. 문맥 추론 대상, 최대 4개의 보조 인용·시간·출처 역할, 대조 해석은 기존 reason에 표시한다. reason은 기존 1,000자 컬럼을 넘지 않게 생략 표시하고 대상은 200자 제한을 검증한다. 구조화된 전체 근거·대상 연결·대조 해석은 실행 중 내부 평가에 보존하지만 DB에 별도 영속 저장하지 않으므로 재현·감사 API는 후속 과제다.

발언·화면 시스템 지침의 '판정하지 않는다'를 **도덕적 판결·논란 확률을 선언하지 않되 재검토 필요 여부는 분류한다**로 명확히 했다. 민감 주제의 단순 언급·개인 감정을 위험으로 만들지 않고, 일반 모욕적 비유를 UNFAMILIAR_CONTEXT로 대체하지 않도록 보강했다. `~노` 단독 제외, 일반 취향 표현 제외, 강한 특정 대상 리뷰의 낮은 우선순위 정책은 유지한다. 이 계약 명확화와 회귀 평가 방향은 [OpenAI 공식 프롬프트 지침](https://developers.openai.com/api/docs/guides/prompt-engineering)을 참고했다.

추가 LLM 분석 단계를 넣지 않았으므로 정상 응답의 호출 단계 수는 그대로다. 다만 읽기 창 ID·복수 인용·대상 설명 때문에 토큰과 응답 시간이 증가할 수 있고, 계약 불이행 시 기존 재검토 호출이 늘 수 있다. 비용 감소·속도 개선을 주장하지 않는다.

#### 검증과 다음 단계

오프라인 테스트는 읽기 창 제한·원문 보존·동일 대화의 복수 인용·대상 연결·보조 인용과 판정 범위 분리·잘못된 원문/ID/역할/대상 계약·멀리 떨어진 근거 거부·정상 질문/취향/자기 감정의 명시적 PASS·이모지 위치·실제 JSON 역직렬화·기존 DB 설명 길이를 확인한다. 응답을 mock으로 제공하는 계약 테스트이며 **실모델이 v1의 핵심 4묶음을 정확히 찾는다는 검증이 아니다**.

변경 후 전체 Java 테스트 133개가 통과했다(실패·오류·건너뜀 0). Gradle wrapper JAR가 없어 설치된 Gradle 9.4.1과 Java 17로 오프라인 실행했다. Python·DB·서버 프로세스는 변경하지 않았다.

다음 순서는 다음과 같다.

1. 사람이 원본을 확인해 9.10의 사례와 정상 대조 사례를 확정한다. 현재 v1은 개발 자료로만 사용한다.
2. 사용자가 로컬 Spring을 재시작한 뒤 새 업로드로 결과를 비교한다. 기존 COMPLETED 영상의 리포트는 자동 갱신되지 않는다. 핵심 사례별 대상·유형·근거·시간, 미판정, 불필요한 카드, 토큰·시간을 함께 확인한다.
3. 별도 영상·정상 리뷰의 독립 평가를 확보한 뒤 문맥 패턴 사전을 추가한다. 은어 사전을 단어별 금지 목록으로 확장하는 방식은 피한다.
4. 실제 오탐이 남는 후보에 한해 재검증기를 추가한다. 이번 구현은 별도의 2차 모델 검증·배심원·엄격 JSON Schema 전환을 포함하지 않는다.

### 9.12 v4 회귀 결과와 Luna 우선 교체 (2026-10-08)

videoId=4의 실제 리포트는 대상 53구간 중 유효 판정 35·미판정 18, 응답 검증 실패 40·판정 충돌 2, 최종 카드 5개를 기록했다. 생성된 카드는 짧은 응답·발언 조각에 대한 막연한 UNFAMILIAR_CONTEXT 설명이고, 9.10의 핵심 네 묶음은 올바른 근거와 대상으로 발견되지 않았다. 이전 videoId=2의 유효 판정 52·미판정 1보다 악화했으므로 9.11의 변경을 품질 개선으로 확정하지 않는다. 이 40건은 검증 시도별 오류 수이며 서로 다른 40구간이나 외부 호출 실패 40건을 뜻하지 않는다. 세부 검증 실패 유형은 실행 로그가 필요하다.

사용자가 멘토링 모델 교체를 먼저 요청했고, 타임스탬프 차이를 설명한 뒤 **Luna부터 적용하고 STT 시간 정렬은 별도 설계**하는 방식을 선택했다.

- Spring 텍스트 판단 기본 모델은 `gpt-6-luna`로 변경했다. 공통 클라이언트의 모든 텍스트 분석기에 적용되며 분석기별 별도 모델·배심원을 추가하지 않는다.
- 기존 비추론 경로와 비교하기 위해 `reasoning_effort=none`을 명시한다. `OPENAI_REASONING_EFFORT`로 low/medium/high/xhigh/max를 선택하면 temperature를 전송하지 않는다. endpoint는 기존 Chat Completions, JSON mode와 분석기 프롬프트·출력 계약은 유지한다.
- 거부·length/content_filter 중단·빈 응답을 호출 실패로 추적한다. 중단된 JSON을 정상 판정으로 소비하지 않는다.
- Standard 기준 기본 비용 추정 단가를 입력 $0.10 / 캐시 입력 $0.01 / 출력 $0.50(각 100만 토큰)로 갱신했다. 환경 변수로 다른 모델을 선택하면 단가도 함께 지정해야 한다. 추정 로그는 실제 청구액이 아니며 캐시 쓰기·별도 티어·지역 가산 등을 완전하게 반영하지 않는다.
- Python STT 코드·기본 모델·음성 분당 추정 단가는 변경하지 않았다. `gpt-transcribe`는 기존 `verbose_json/timestamp_granularities` 계약을 그대로 사용할 수 없어 모델명만 교체하지 않는다. 후속 설계에서 시간 정밀도·정렬 검증·추가 호출 비용을 비교한다.

호환성 기준은 [OpenAI GPT-6 Luna 모델 문서](https://developers.openai.com/api/docs/models/gpt-6-luna), [GPT-6 마이그레이션 지침](https://developers.openai.com/api/docs/guides/latest-model#update-api-and-model-parameters), [파일 음성 전사 지침](https://developers.openai.com/api/docs/guides/speech-to-text#timestamps)을 확인했다. 모델 변경만으로 이전의 막연한 이유·대상 연결·계약 실패가 해결된다고 주장하지 않는다.

모의 HTTP 요청으로 실제 모델·추론 파라미터·JSON 형식·사용량 파싱·거부/중단 처리를 검증했고 당시 전체 Java 138개 테스트가 통과했다(실패·오류·건너뜀 0). 실제 외부 호출·키 확인·서버 재시작·배포는 수행하지 않았다. 이후 ID 5의 실제 Luna 사용은 사용자가 확인했다.

### 9.13. ID별 실험 기록과 누락 원인 진단

ID 8 이후 같은 호출의 명시적 대화 묶음 판정 계약을 추가했다. 구간 판정과 별도로 묶음 연결 관계·판정·근거를 검증하고 유효 후보를 기존 리포트에 반영한다. 누락은 미판정/PARTIAL로 추적하며 별도 호출은 추가하지 않았다. 기본 활성, false 설정으로 이전 계약에 롤백 가능하다. [실험 기록 12절](AI-분석-실험-기록.md)에 Java 195개 계약/회귀 테스트, 13절에 실제 ID 9 결과를 정리했다. 53구간 모두 판정됐지만 묶음 5개 중 1개는 UNIT_LINKAGE_REQUIRED로 탈락했다. B는 유효 묶음 PASS, D는 구간 PASS로 누락되어 품질 향상은 입증되지 않았다.

ID 7 이후 대화 흐름 단계에서 방향별 bounded 읽기 창, 배치 경계 문맥 보완, 발언 우선 문맥 선별과 대상 연결 판단 지침을 추가했다. 인용은 같은 출처 근거 전체가 하나의 창에 포함되어야 한다. 당시 Java 175개 테스트가 통과했고 ID 8은 C/D 근거 일부 보완·B 누락 유지였다. 구현은 [실험 기록 10절](AI-분석-실험-기록.md), 실제 결과는 11절을 따른다. 토큰·비용 비교는 로그가 없어 미확인이다.

ID 6 실제 진단 결과와 이후 출력 계약 명확화는 [실험 기록 7~8절](AI-분석-실험-기록.md)에 추가했다. 대상 enum 허용값과 대표 인용 필드 일치를 프롬프트에 명시했으며 검증은 유지한다. 계약 회귀 테스트 포함 Java 165개가 통과했고 실제 탐지 품질 변화는 다음 실행 대기 상태다. 대화 흐름 판단 개선과는 분리된 단계다.

최종 목표·ID 1~5의 변경/개선/회귀·정상 대조 기준·후속 기록 양식은 [AI 분석 실험 기록](AI-분석-실험-기록.md)에 모았다. ID 5는 ID 4보다 판정 범위와 시간은 개선됐지만 핵심 A/B/C는 여전히 카드에 없다. 내부 판정이 소실된 과거 실행에서 이를 PASS나 보류로 추정하지 않는다.

ID 6부터 공통 텍스트 검토 엔진의 구간별 최종 상태·유효 이유·부족한 정보·근거 ID/역할·검증 탈락 코드·재검토 이력을 로컬 진단 API로 확인했다. 진단 도입 자체는 모델·판정 기준을 바꾸지 않았지만 이후 계약/프롬프트 변경은 ID별 기록을 따른다. 정상 판정, 정보 부족, 후보 검증 탈락을 구분한 후 개선 방향을 결정한다.

기본 비활성, local 프로필에서 활성화하며 공개 접근·운영 사용을 금한다. 진단은 최근 20개 영상/1시간/분석기별 400구간/판정·탈락 각 4개로 제한하고 DB 커밋 후 게시한다. 영상 삭제 시 커밋 후 함께 제거한다. 원문·거부된 모델 인용은 저장하지 않지만 유효 이유 등에도 개인정보가 있을 수 있으므로 실행자가 127.0.0.1에 바인딩해야 한다. 컨트롤러가 접속 IP/소유권을 검사하는 것은 아니다. 묶음 진단 상세는 최대 200개로 제한한다. 재시작 시 사라지는 임시 진단이며 영구 실험 기록은 MD에 별도로 남긴다.
