## 14. 승격 게이트와 복원 리허설

`tools/release_gate.py`는 로컬 JSON 비교기다. 모델을 부르거나 runtime을 덮어쓰거나 실제 서버에 배포하지 않는다.

비교 입력은 다음을 서로 해시로 고정해야 한다.

- **Suite:** 사전 동결된 입력·사람 승인 정답, source/evaluation group, 카테고리, 입력 해시, 관련 참고 ID 검수. suite 자체와 기준선·후보 실행의 해시가 같아야 한다.
- **Criteria:** suite 동결 뒤 실행 전에 잠근 전체 기준. 전체와 카테고리별로 미탐, 오탐, 불확실, 미평가, 계약 실패, 근거 오류/미검수, 중복, 관련 참고 미회수·기존 관련 참고 밀림, 예산 위반, 최대 비용을 따로 정한다.
- **Runs:** 기준선·후보가 각 suite의 모든 케이스를 정확히 한 번씩 포함하고, 케이스별 원본·입력 해시가 동결 suite와 일치해야 한다. `REVIEW_REQUIRED`는 `COMPLETED` 및 `REVIEWED_VALID` 근거만 허용한다. 각 실행은 코드·모델·프롬프트·정책·runtime·설정·검색 구성요소에 속한 실제 파일 경로/해시를 매핑하며, 구성요소별 지문은 manifest에서 계산한다. 검색 실험은 실제 bundle을 검증한 상태에서 검색 구성요소만 바뀌고 경로-구성요소 매핑은 같아야 한다.
- **승격 승인:** 결과가 `READY_FOR_HUMAN_REVIEW`여도 자동 승격하지 않는다. 기준선·후보의 실제 bundle 디렉터리가 manifest와 파일 집합·SHA까지 정확히 일치하고, 격리 임시 디렉터리 rollback rehearsal가 PASS이며, 수동 승인이 suite 해시·criteria 해시·기준선 실행 해시·후보 실행 해시·후보 bundle 해시 모두와 일치할 때만 `deploymentEligible=true`가 된다. 실행 해시는 JSON object의 canonical SHA-256이다. 승인 JSON에 `PASS`만 적거나 평가셋/실행 결과를 바꾼 뒤 과거 승인을 재사용해도 eligibility가 열리지 않는다. 이 도구는 실제 배포를 실행하지 않는다.

카테고리 실패는 전체 평균으로 상쇄하지 않는다. 같은 기준선보다 품질 지표가 나빠지면 별도로 실패시킨다. `UNCERTAIN`, `NOT_EVALUATED`, `CONTRACT_FAILURE`는 성공이나 PASS로 세지 않는다. 비용은 두 실행에서 동일한 산정기준(`PROVIDER_REPORTED` 또는 사전 고정 추정치)을 써야 한다. 사람 승인 상태와 sourceGroup 확인은 입력된 검수 메타데이터에 대한 일관성 검사이지, 사람 신원·원본 영상·라벨 진실성을 암호학적으로 인증하지는 않는다.

비교 준비가 된 이후 명령 모양:

```sh
python3 tools/release_gate.py compare \
  --suite <frozen-independent-suite.json> \
  --baseline <baseline-run.json> \
  --candidate <candidate-run.json> \
  --criteria <prelocked-criteria.json> \
  --baseline-bundle-dir <baseline-bundle> \
  --candidate-bundle-dir <candidate-bundle> \
  --rollback-rehearsal \
  --approval <optional-human-promotion-approval.json>
```

실제 bundle을 확인하지 않는 비교는 결과를 `READY_FOR_HUMAN_REVIEW`로 낼 수 있어도 eligibility는 항상 false다. 실제 bundle 디렉터리를 제공하면 manifest에 나열된 파일만 있어야 하고, 파일 내용 SHA와 정규화 bundle SHA가 실행 기록과 일치해야 한다. 심볼릭 링크·민감 경로·누락/추가 파일은 거부한다.

이 변경부터 실행기록은 `release-evaluation-run-2` 계약을 사용한다. 이전 v1 기록은 입력 지문과 파일별 구성요소 귀속을 증명하지 못하므로 새 검증 비교에 그대로 재사용하지 않는다.

`rollback-rehearsal`은 baseline/candidate bundle의 서로 다른 파일 manifest를 별도 임시 디렉터리에 차례로 적용하고, baseline 파일 집합을 복원한 뒤 SHA가 같은지 확인한다. 실제 프로젝트·서버·배포 디렉터리는 변경하지 않는다. manifest 형식은 다음과 같다.

```json
{
  "baselinePaths": ["runtime.json", "application.yml"],
  "candidatePaths": ["runtime.json", "application.yml", "new-config.json"]
}
```

```sh
python3 tools/release_gate.py rollback-rehearsal \
  --baseline-dir <baseline-bundle> \
  --candidate-dir <candidate-bundle> \
  --manifests <baseline-candidate-paths.json>
```

현재는 이 도구를 실제 배포 산출물에 실행하지 않았다. 테스트 fixture에서 경로 탈출·비밀 파일·링크·추가/변경 파일 거절, 파일 구성이 다른 candidate 적용 후 baseline 복원을 확인했다. 그러므로 “운영 롤백 완료”가 아니라 **오프라인 리허설 기능 구현 및 합성 검증**이다.

## 15. 검색 알고리즘 비교와 적용 경계

현재 production selector는 세 요소를 한 점수로 숨기지 않는다.

- **LEXICAL:** NFKC 정규화 뒤 한국어 문자 3-gram 겹침과 문서 빈도 기반 점수. 사전 전체 크기/빈도가 바뀌면 기존 사례 순위에도 영향을 줄 수 있다.
- **STRUCTURED:** `context-search-profiles.json`의 작성된 query/reference 조건으로 개념 확장. 현재 `structured-context-search-enabled` 기본값은 `true`이며 판정 호출을 추가하지 않는다.
- **RELATION / ROUTING:** 역할별 관계 유사도와 mechanism routing은 각각 실험 설정으로 분리돼 있다. `candidate-source-relations-enabled`와 `mechanism-routing-enabled` 기본값은 `false`다.
- **SEMANTIC:** 의미 순위 비교 실험이 존재하지만 현재 운영 검색 경로로 승격된 상태는 아니다.

이 작업에서 기본값·검색식·공용 프롬프트를 변경하지 않았다. 기존 `CasebookImpactAudit`, `ContextFitAdoptionGateTest`, structured/role ablation 테스트를 유지한다. 특히 기존 적용 게이트는 현 개발 자산에서 이득이 확인되지 않으면 채택하지 않는다. 이 테스트들은 검색의 구조·참고 선택 변화를 보며, 모델 최종 판단의 의미 정확도를 증명하지는 않는다.

새 비교는 `release_gate.py`의 `SEARCH_ABLATION`으로 동일한 suite/정답/모델/프롬프트/정책/runtime/설정을 고정하고 retrieval 지문만 바꾼다. manifest에는 구성요소별 실제 파일과 SHA가 있어야 하며, 두 실제 bundle 디렉터리가 없으면 검색 ablation은 거절한다. suite에는 각 query의 사람 검수 `expectedRelevantReferenceIds`가 필요하다. 비교 결과는 아래를 전체·카테고리별로 보존한다.

- 관련 참고 미회수와 baseline에서 candidate로 옮길 때 밀린 관련 참고
- 무관 참고 유입과 payload 상한 초과
- 최종 미탐/오탐, 불확실·미평가·계약 실패, 근거 오류·미검수, 중복
- 비용 및 비용 산정 방식

개발 평가에 쓴 동일 사건 자료는 독립 평가에 세지 않는다. 현재 레지스트리에 query별로 승인된 관련 참고 ID가 충분히 연결돼 있지 않고, verified independent source group도 없다. 따라서 아직 알고리즘 간 실제 품질 비교를 실행하지 않았고 어떤 검색 옵션도 새로 승격하지 않았다.

### 검색 미회수와 사례집 부족을 구분

검색 결과가 없다는 사실만으로 “사례집에 기준이 부족하다”고 결론 내리지 않는다. 최소한 아래 원인을 분리해 기록한다. 이 분류는 조사 메모용이며 서버의 공식 상태 코드가 아니다.

| 관측 | 우선 확인할 원인 | 사례집 부족으로 바로 결론 가능한가 |
|---|---|---|
| 짧은 요약만 입력했고 실제 발언·문맥은 미확인 | 질의가 영상의 실제 표현과 다를 수 있음 | 아니오 |
| 후보 질의에 쟁점 표현·대상·평가 연결이 없음 | 탐색 출력 또는 질의 구성 | 아니오 |
| 관련 사례가 일치 목록에 없음 | 채널·제외 family·규칙·검색 view·정규화 확인 | 아직 아님 |
| 관련 사례는 일치했지만 최종 선택에 없음 | 순위·상위 개수·payload 예산·다른 참고의 밀림 | 아니오, 검색 선택 문제 |
| 참고가 선택됐지만 모델 요청에서 빠짐 | 투영·파이프라인 연결 문제 | 아니오 |
| 관련 참고가 요청에 들어갔는데 최종 판단이 어긋남 | 현재 원문 근거·판단 경계·모델 단계 | 아니오, 검색 부재가 아님 |
| 같은 사건의 참고 하나만 검색됨 | 동일 family 자기회수 | 범용 전이 증거가 아님 |

새 메커니즘/사례의 검색 공백이라고 부르려면 실제 질의 원문 또는 그 한계를 밝힌 입력을 고정하고, 검색 자원·코드 해시·채널·제외 family·순위·예산을 확인해야 한다. 같은 사건 자료를 제외한 뒤 다른 출처의 참고가 검색되는지 따로 본다. 입력이 뉴스 요약이면 이 결과는 뉴스 요약 질의의 검색 결과이지, 원영상 탐지의 검색 결과가 아니다.

2026-10-26에 비공개 연구 자료를 이용한 오프라인 selector 관측이 기록되었다. 당시 결과는 gold 라벨이나 품질 평가가 아니었고 런타임도 변경하지 않았다. 권리 검토 후 해당 출처가 포함된 입력과 결과는 격리했으므로 세부 질의·회수 결과를 재현하거나 성능 근거로 사용하지 않는다. 기록은 로컬 비공개 `datasets/controversy/research/cross-case-practice-standard-review-20261026.json`에 보존한다.

2026-10-27 권리 재점검에서 YTN 페이지의 AI 데이터 사용 제한 안내를 확인했다. 따라서 해당 페이지의 발췌·요약·검색 질의·검색 결과를 AI 검색, 모델 입력, 평가 또는 학습에 다시 사용하지 않는다. 기존 연구 기록은 감사 이력 보존을 위해 삭제하지 않았지만 `QUARANTINED_SOURCE_RIGHTS_BLOCKED`로 격리했고, 이전 검색 결과도 재현·성능 근거로 재사용하지 않는다. 출처 URL·발행사·게시일·제한 상태와 기존 발췌의 격리 여부를 `datasets/controversy/research/source-provenance/<source-c>.json`에 기록했다. 기존 별도 위키트리/디시인사이드 스냅샷과 KBS 자료는 YTN 자료와 분리된 채 그대로 둔다. 런타임 사전·판단 프롬프트는 변경하지 않았다.

기존 비공개 연구 레코드의 `candidateProjection`은 출처 분리 실험을 기록한 이력이다. 다만 YTN의 AI 사용 제한 확인 후 이 레코드 전체를 권리 검토 전까지 격리했다. 그 안의 인용·요약·검색 질의·인메모리 후보는 더 이상 selector ablation이나 모델 payload에 사용하지 않는다. `SourceExcerptRetrievalBaselineTest`는 이 한 연구 레코드의 오프라인 재생 전에만 provenance를 검사한다. 과거 결과는 당시의 역사적 기록일 뿐, 현재 재생 가능한 기준선이나 모델 품질 증거가 아니다.

2026-10-27에는 이와 별도로 `tools/build_incident_dataset.py`가 v7 context-unit 입력을 compile하기 전에 source-use 정책을 검사하도록 연결했다. 기준선 이전에 존재하던 29개 context-unit의 정확한 `id + unit schema version + source kind/path/SHA-256`은 `tools/context_unit_source_lock.json`에 고정되어 있다. 이 항목은 현재 빌드의 재현성 보존용 **동결 legacy 입력**이며 권리 허가를 뜻하지 않는다. schema version을 낮추거나 source identity를 바꾸면 예외를 상속하지 않는다.

새 출처는 unit의 `sourceProvenance`에서 메타데이터 경로·SHA-256·source ID·`RUNTIME_RETRIEVAL` 용도를 연결해야 한다. 메타데이터 계약은 `source-provenance-metadata-2`이며, 이 runtime 경로의 실제 사용인 `RUNTIME_RETRIEVAL`, `RETRIEVAL_INDEXING`, `MODEL_INPUT`을 모두 명시적으로 허용해야 한다. 그중 하나라도 차단되어 있으면 허용 목록보다 차단을 우선한다. 신규 transcript unit은 `context-reference-unit-3`만 허용하고, 선택한 transcript 행·원본 파일 해시·사람의 개발 경계 승인 레코드까지 일치해야 한다. 검토 증빙 `source-use-review-2`에도 동일한 artifact 경로·SHA-256과 전체 사용 목적을 넣어 자료가 바뀌면 기존 증빙을 재사용할 수 없게 한다. 경로 이탈·심볼릭 링크·누락·해시 불일치·격리·차단 상태는 fail-closed다. YTN의 현재 `BLOCKED_PENDING_PERMISSION` 메타데이터는 이 허용 조건을 충족하지 않아 새 unit 연결이 거부된다.

provenance metadata·검토 증빙은 build manifest의 `inputHashes`에, context-unit lock은 `sourceUsePolicySha256`에 기록된다. 별도로 Git 제외 경로의 `datasets/controversy/definitions/incident-source-lock.json`은 현재 로컬 incident 32건의 정확한 파일 해시를 고정한다. incident 추가·수정·삭제는 runtime 빌드에서 `INCIDENT_SOURCE_REVIEW_REQUIRED`로 거부된다. 이는 무검토 신규 사례가 incident 경로를 통해 runtime에 들어가는 우회를 닫기 위한 임시 fail-closed 조치다. 새 사례 등록·수정은 현재 막히며, 향후 별도의 증빙 연계 입수 절차가 생기기 전까지 이 잠금 파일을 임의 갱신하지 않는다. 잠금 해시는 build manifest의 `incidentSourcePolicySha256`에 기록된다. 게시 중 정책 해시나 입력이 달라지거나 사후 검증이 실패하면 직전 runtime과 manifest를 복원한다.

> 현재 작업 트리 보충: 위 문단의 등록 차단 설명은 당시 기록이다. `tools/incident_intake.py`에는 검토 증빙과 미리보기 해시를 확인하는 별도 입수 경로가 있다. 미리보기는 읽기 전용이지만 `--apply`는 사례·잠금·runtime·manifest 등을 변경하므로 별도 검토 후 실행한다. 코드 존재만으로 실제 사례가 승인·등록되었거나 권리가 확인되었다는 뜻은 아니다.

이 검사는 **기본 incident 빌더와 context-unit 경로**에만 적용된다. 직접 runtime 파일 교체·별도 연구 파이프라인까지 막는 전역 통제는 아니다. 기존 동결 입력은 권리 허가를 뜻하지 않는다. 메타데이터·검토 증빙의 사실성과 법적 효력도 사람이 확인해야 하며, 이 코드는 법률 판단이나 사용 권한을 만들어내지 않는다.

`SourceExcerptRetrievalBaselineTest`의 provenance 게이트는 정책 JSON과 detached SHA-256 일치, YTN sourceId, 고정된 연구 파일명·SHA-256, `RETRIEVAL` 범위를 가진 명시적 재사용 결정, 증빙 파일의 존재·SHA-256이 모두 맞아야만 열린다. 격리 상태이거나 `blockedUses`에 retrieval이 있으면 allow 필드와 충돌하더라도 차단한다. 허가 필드만 채우거나 증빙·연구 파일이 바뀌면 재생은 차단된다. 증빙 파일의 실제 법적 효력은 사람이 확인해야 하며, 이 테스트는 법률 판단이나 전역 접근 제어가 아니다. 미허가·누락·손상 시에는 fail-closed로 건너뛰거나 차단한다. 가드는 모델 품질을 검증하지 않으며 런타임·프롬프트 변경도 하지 않는다.

아래 명령은 현재 권리 상태에서 역사적 재생 테스트를 건너뛰며, provenance 정책 검증만 실행한다.

```sh
cd oops-backend
OOPS_CASEBOOK_AUDIT_RUNTIME=../datasets/controversy/guidelines/runtime.json \
OOPS_CASEBOOK_AUDIT_RECORD=../datasets/controversy/research/cross-case-practice-standard-review-20261026.json \
  ./gradlew test --tests com.example.oops.analyzer.SourceExcerptRetrievalBaselineTest
```

2026-10-26 selector 결과는 권리 제한 확인 전의 역사적 관측치로 남아 있으며, 이 문서에서는 수치나 질의 내용을 재사용하지 않는다. 비공개 연구 파일은 Git 제외 상태를 유지하고, YTN 자료의 권리 검토가 해결되기 전까지 selector 재생·모델 입력·평가에 쓰지 않는다. 추후 서면 허가를 받으면 허용된 처리 범위와 증빙을 먼저 provenance metadata에 기록한 뒤 별도 검토한다. 허가를 받지 못하면 제한이 없는 대체 출처로 새 연구 기록을 만든다.

### 사례 추가 전후의 성공 기준

사례 추가는 그 사례 자체를 다시 찾는지보다, **다른 출처의 유사한 검토 흐름과 가까운 정상 경계를 함께 구분하는지**로 평가한다.

1. 비교 전에 입력·사람 검수 결정·출처 family·기대 관련 참고 ID를 동결한다. 후보 사례의 같은 family는 일반화 평가에서 제외한다.
2. 기준선/후보에서 사례 자산만 바꾸고 모델·프롬프트·판단 기준·검색 설정·입력은 고정한다.
3. 관련 참고 회수, 다른 출처에서의 회수, 무관 참고 유입, 기존 관련 참고 밀림, payload를 기록한다. 최종 판단까지 비교한다면 검토 대상의 누락과 정상 경계의 과탐도 함께 본다.
4. 자기회수만 늘거나 정상 입력에 참고가 들어온 것만으로 개선이라고 하지 않는다. 검색 회수 개선과 최종 판단 개선을 각각 보고한다. 작은 개발 비교는 해당 표본에서 관찰된 결과로만 표시하고 일반 정확도 수치로 확대하지 않는다.

첫 단계는 무료 오프라인 진단이며, 최종 판단의 모델 비교·외부 전송은 필요한 입력, 비용 추정, 새 승인을 별도로 확인한 뒤 수행한다.

## 16. 사례 확장과 독립 영상 평가

품질 감사에서 runtime은 **64개 참고 예시 / 6개 기준**이다. 이 중 맥락 unit으로 이관된 것은 29개, legacy 유지 항목은 **35개**다. legacy 35개는 31개 `familyId` 작업 묶음으로 정리되며 4개 묶음이 각각 2항목, 나머지 27개가 단일 항목이다. `familyId`는 검수 작업을 모으는 이름일 뿐 검증된 영상/source group으로 간주하지 않는다.

각 legacy 항목은 현 시점 모두 `UNCLASSIFIED_REQUIRES_HUMAN_REVIEW`다. 분류 후보는 중복, 새 표현, 새 경계, 정책 충돌, 새 메커니즘, 출처 부족 보류다. 도구는 이를 자동 추측하지 않는다. 출처·승인·문맥 연결을 확인한 뒤 사람이 이 중 하나를 정해야 한다. 이 triage 보고서는 기본 inventory에 포함되며 runtime/사례/정답을 수정하지 않는다.

```sh
python3 tools/audit_context_casebook.py \
  --output datasets/controversy/experiments/legacy-triage-<새이름>
```

출력은 Git 제외 실험 폴더에 쓰인다. 기존 폴더를 덮지 않는다. 그룹 ID를 source independence나 데이터셋 라벨로 승격하지 않는다.

### 원영상이 없는 사례의 증거 범위

원영상 확보는 논란 맥락 사례를 기록하기 위한 필수 조건이 아니다. 대신 자료 유형에 맞게 주장 범위를 제한한다. 이 구분은 사례의 위험도나 진실성을 수치화하는 점수가 아니라, 해당 자료가 뒷받침할 수 있는 주장의 한계다. 저장 필드와 기사 인용·상황 요약·해석 분리는 [공통 논란 카드 JSON](../casebook/논란-카드-JSON-구조.md)을 따른다.

| 근거 수준 | 보관·사용 | 주장할 수 없는 것 |
|---|---|---|
| 원영상/원음 또는 신뢰 가능한 원문 전사를 직접 확인 | 확인된 인용·전후 문맥을 기록하고, 별도 사람 검수 뒤 해당 자료에 대한 개발/평가 입력으로 사용 가능 | 한 구간 확인만으로 영상 전체의 정답·범용 성능을 보증하지 않음 |
| 뉴스의 직접 인용·보도된 반응·기자 설명만 확인 | `reportedQuotes`, 출처가 있는 `textContext`, 해석 종류와 미확인 정보를 분리. 사람 검수 후 보도 발췌에 대한 개발 참고로 사용 가능 | 이를 원영상 전사·정확한 시점·화자 억양·전체 문맥의 사실로 바꾸지 않음. 원영상 기준 독립 평가로 세지 않음 |
| 나무위키 등 2차 요약만 확인 | 사례 발견용 단서와 인용된 출처 목록을 기록. 가능한 경우 원출처를 따라 확인하고, 못 찾으면 보류·미확인 상태 유지 | 출처 없는 문장을 직접 인용·검증된 반응·확정된 논란 원인으로 취급하지 않음 |

뉴스·위키에 원영상이 없더라도, 출처 발언과 보도된 상황에서 일반화할 맥락을 사람이 검수해 연구 사례로 남길 수 있다. 단, 보도 인용과 해석을 분리하고 정상 대조·자료 한계를 기록한다. 이 단계의 사례는 자동으로 runtime, 독립 gold, 학습 자료가 되지 않는다. 뉴스의 비판 해설과 댓글 반응도 각각 작성자 해석·보도된 반응으로 귀속하며 전체 시청자 합의로 일반화하지 않는다.

독립 영상 평가를 시작하려면 최소한 다음을 채워야 한다.

1. 개발/기존 검수 영상과 겹치지 않는 실제 source group 및 원본·전사 출처 해시를 확인한다.
2. 모델 결과를 보기 전에 영상별 판단과 관련 참고 ID를 사람 검수하고 suite/criteria를 동결한다.
3. 검토 대상뿐 아니라 가까운 정상 대조를 같은 메커니즘·출처 기준으로 포함한다.
4. 같은 영상에서 나온 클립·전사·파생 문장을 한 source/evaluation group으로 묶어 train/dev/holdout 누출을 막는다.
5. 그 자료로 개발을 시작하면 holdout에서 제외하고, 새 미사용 출처를 다시 확보한다.

현재 고정 suite는 독립 gold가 아니고 source group으로 확인된 독립 영상은 **0개**다. 그래서 코드가 실행된다는 이유로 16번 전체를 완료 처리하지 않는다. 영상 찾기·원음 검수·정답 라벨링·정책 승인·유료 모델 비교는 이번 변경에서 수행하지 않았다.
