### 10/10 기본 경로 변경: 외부 검색 선택 실행

일반 업로드 분석은 논란 맥락과 표현 원문 검수에 집중한다. `entity-check`(가격·중량·출시일 등 사실 주장 대조)와 `context-check`(최근 뉴스 배경 검색)는 기본 실행 목록에서 제외했다. 기존 구현·DB·응답 타입·과거 리포트는 유지한다. 비활성 단계는 기존 coverage 정책의 NOT_ENABLED이며 성공/PASS나 실패 경고로 표시하지 않는다. 음성 프롬프트 개정은 28 그대로다.

기존 외부 검색을 시험할 때만 `--spring.profiles.active=local,external-review`로 실행한다. 서버 전체 설정이며 사용자별/요청별 스위치가 아니다. 이 프로필은 핵심 분석기와 두 검색 분석기를 함께 지정한다. Spring 목록은 병합이 아니라 교체되므로 환경·명령행·다른 프로필에서 enabled-analyzers를 재정의하면 실제 활성 목록을 확인해야 한다. 뉴스 키가 없어도 RSS 경로가 있어 키 제거로 비활성화를 대신하지 않는다.

선택 프로필은 아직 기존 전체 원문 기반 검색이다. 후속의 **판단에 꼭 필요한 후보만 외부 맥락 확인**과 구분한다. 검색 실패·촬영 날짜 누락·불일치 자료는 논란/거짓으로 변환하지 않는다. 외부 검색 호출은 줄지만 실제 시간·비용 절감량은 다음 실영상으로 측정해야 한다.

### 10/10 검증된 논란 흐름 병합 — implemented

병합 개정은 `2026-10-10-validated-flow-fusion-2`다. 실행 개정 29는 핵심 anchor 인용 누락을 기존 단일 후보 재탐색 대상으로 추가했으며 프롬프트 본문·모델·참고 사전·기존 호출 한도는 변경하지 않았다. 검증을 통과해 finding으로 변환되는 지점에서 anchor, 대상 유형, PRIMARY/TARGET/CONTEXT 인용의 원문 ID·출처·시간·quote를 저장한다. 탐색 가설·PASS·UNCERTAIN에는 저장 카드가 없으며 reason 문자열을 파싱해 근거를 만들지 않는다.

- 같은 anchor: 동일 category·출처 타입·대상 유형·정확한 PRIMARY 인용이 필요하다. TARGET이 있으면 표시 대상명 대신 동일 원문 ID/시간의 서로 포함되는 TARGET 인용을 양방향 대조한다. 추가로 일치하지 않는 대상 인용이 있으면 이 경로로 합치지 않는다. TARGET이 양쪽 모두 없을 때만 기존 대상명 비교를 유지한다.
- REGION의 가까운 장소 지칭(여기/이곳/그곳/저기/저곳)은 양쪽 TARGET 모두 anchor 시작의 ±3초 안에 있고 정확히 공유하는 CONTEXT 원문 구간이 2개 이상일 때 동일 anchor 지원으로 합칠 수 있다. 시간 인접만으로 합치지 않으며 대상 유형이 다르면 분리한다. 이는 지칭 대상의 의미 동치를 보장하지 않는 제한적 휴리스틱이다. 서로 다른 장소를 지칭하는 대조 영상 검증이 추가로 필요하다.
- 다른 anchor: 동일 category·출처 타입·대상 유형, 대상명 문자 비교 0.85 이상, 60초 이내, 한 anchor의 PRIMARY가 다른 후보의 CONTEXT로 정확히 인용됨, 공통 CONTEXT 원문 구간 2개 이상을 모두 요구한다. 문자 비교는 의미 이해가 아니며 단독 허가 조건이 아니다. 인용이 조금 다르면 놓칠 수 있는 보수적 1차 정책이다.
- 묶음의 모든 구성원과 조건을 대조한다. 시간 창 겹침·같은 단어·같은 유형만으로 합치거나 A-B/B-C의 연쇄로 서로 다른 A-C까지 합치지 않는다.
- 기존 메타데이터 없는 분석기는 인접 3초 안의 정확히 같은 원문·호환 유형·대상 비교가 맞는 반복만 병합한다. 이전 대상명만/원문 글자 유사도만 허용하던 경로는 제거했다. STT/OCR 출처 차이는 새 검증 흐름 병합에서 강제 연결하지 않는다.
- 대표는 기존 점수/설명 구체성 순서를 유지한다. 점수를 올리지 않고 관련 인용을 보존하며 카드 범위는 anchor 처음~끝으로 넓힌다. contextBefore/After는 넓어진 범위가 아닌 대표 anchor 기준이다. 실제 전체 발언의 의미를 합성한 새 설명은 만들지 않는다.

리포트의 새 `supportCount`는 병합된 분석 finding 수, `relatedEvidence`는 인용 역할·원문·시간 목록이다. 새 `occurrences`는 고유 음성 원문 anchor 수(음성 없는 경우 원문 시간·문구 단위)다. 서로 다른 문장을 묶은 anchor 수이지 같은 발언 반복 횟수나 논란 수는 아니다. 같은 anchor 텍스트/이미지 2지원은 occurrences=1/supportCount=2다. 예전 저장 행은 occurrenceCount=null로 이전 mergedCount 표시를 유지하며 relatedEvidence는 빈 배열이다. 기존 필드는 유지하고 새 필드만 추가했다. 엄격한 프론트 스키마가 있으면 추가 필드 허용 여부를 확인한다.

DB의 risk_finding에 nullable `occurrence_count`(integer), `validated_support_json`(text) 두 컬럼을 추가한다. local/dev는 기존 Hibernate update 정책으로 반영한다. 운영의 스키마 관리 방식은 확인하지 않았고 배포/운영 DB 변경은 하지 않았다. 자동 갱신이 아닌 환경에서는 이 두 추가 컬럼을 별도 이관하고 백업·조회 검증 후 배포해야 한다. 기존 행의 임의 재해석/덮어쓰기와 유료 모델 호출은 없다.

핵심 발언 인용이 없는 탐색 후보(`PROPOSAL_ANCHOR_EVIDENCE_REQUIRED`)는 원문을 코드로 덧붙이지 않고 허용 창 안에서 재탐색한다. anchor·축·원문 인용을 다시 검증하고 이후 독립 판정까지 통과해야 발행한다. 탐색 복구 최대 1회/영상, 텍스트·이미지 복구 합산 최대 2회는 유지한다. 기존에 복구하지 않던 누락 후보가 해당되면 호출 1회가 추가될 수 있으며, 복구 실패/한도 소진은 미확인으로 남긴다.

### 10/10 코드리뷰 적용: 별도 표현 탐지

기존 맥락 검수와 별도로 STT → 표현 사전 로컬 매칭 → 원문 위치/구간 시간 → expression_occurrence 저장 경로를 구현했다. 욕설과 사용자 지정 논쟁 표현 98개 표기는 재미·인용·일상 용례여도 등장 사실을 보존한다. 맥락 검토 필요와 동일한 판정이 아니며 expressionOccurrences로 별도 반환한다. `~노` 단독 제외는 유지한다.

프론트 필터는 미구현이다. 표현은 기존 events·점수·검수 집계에 포함하지 않으며 원문/맥락 검증을 통과한 위협·차별 카드는 계속 표시한다. 추가 모델 호출은 0회다. 기존 키워드 기반 위험 카드는 제거하고 개인정보 패턴만 로컬 안전망으로 유지한다. 결과/완료 상태는 같은 트랜잭션에서 저장하며 완료 알림은 커밋 후 발행한다. STT/OCR 오류를 분리하고 같은 단계의 경고 요약을 함께 보존한다. 분석기별 promptRevisions도 진단에 추가했다. [상세 계약·배포 경계](표현-탐지-및-선택-필터-설계.md)를 따른다.

### 개정 28: 탐색 범위와 검증 범위 연결

대상·맥락 후보는 탐색부터 targetWindows(최대 60초/48구간/6,000 code point)를 쓰고 표현 자체 후보는 windows(기존 30초/32구간/4,000 code point)를 쓴다. 두 창 모두 배치에서 이미 제공한 raw의 ID만 참조한다. 5초를 넘는 침묵을 연결하지 않으며 창 여러 개를 합친 인용은 거부한다. raw 본문은 한 번만 전달하지만 추가 창 ID 목록과 프롬프트로 입력 토큰은 늘 수 있다.

대상 검증 문맥은 유효 후보의 첫~마지막 인용과 그 사이 원문을 보존한 뒤 60초 한도 안에서 앞뒤를 보충한다. 넓은 탐색 창의 우연한 앞쪽 끝을 모두 고정해 뒤 연결이 밀려나지 않도록 했다. 텍스트 검증에도 proposedEvidence를 전달하고 질문 anchor 하나만 떼어 판단하지 않도록 한다. 모델 가설은 증거가 아니며 원문과 정상 해석을 다시 대조해야 한다.

PROPOSAL_EVIDENCE_SHAPE/PROPOSAL_WINDOW_MISMATCH만 고정 anchor/axis의 단일 후보로 재탐색한다. 영상당 최대 1회이며 기존 텍스트·이미지 재검증과 합산 최대 2회를 공유한다. 허구 ID·없는 원문·축/anchor 변경은 거부한다. 재탐색 결과는 자동 카드가 아니고 별도 검증을 통과해야 한다. proposal=null/재실패/예산 제외는 미확인으로 남는다.

discoveryCalls는 재탐색을 포함한 탐색 호출 수, discoveryRepairCalls는 그 안의 재탐색 수다. repairCalls는 텍스트·이미지 재검증 시도 수, verificationCalls는 실제 검증 호출 수다. repairs의 PROPOSAL_* 초기 코드로 탐색 복구를 구분한다. 전체 복구 예산은 discoveryRepairCalls+repairCalls≤2다.

### 후보별 참고 유지와 근거 계약 재검증

발언 검증/이미지 후보는 이미 원문 일치를 확인한 후보 인용으로 예시를 우선 검색하고 그 후보의 허용 문맥으로 보조한다. 같은 참고 입력의 후보만 최대 4개씩 묶고 합집합 문맥으로 예시를 다시 고르지 않는다. 예시 적중이 동일한 결정을 강제하지는 않는다.

텍스트·이미지 검증의 DECISION_UNKNOWN_EVIDENCE_ID, TARGET_REQUIRED, TARGET_EVIDENCE_REQUIRED, TARGET_CONTEXT_EVIDENCE_REQUIRED만 같은 후보·원문·참고 입력으로 후보당 1회 재검증한다. 위 탐색 복구와 영상당 최대 2회 예산을 공유한다. 서버에서 ID/대상/인용을 치환하거나 이전 응답을 수정하도록 요구하지 않는다. 원문·발행 검증은 유지하며 PASS/UNCERTAIN도 허용한다. 이미지 후보는 같은 시점으로 프레임을 재추출하고 관찰·이미지 계약도 다시 검증한다. 텍스트 경로로 우회하지 않는다. 재추출 실패를 포함한 복구 실패/예산 제외는 미확인이다. 허구 인용·API 실패에는 복구 호출을 하지 않는다.

탐색은 각 창의 평가와 후속 설명을 함께 재점검한다. 선택권·서비스·생활 조건을 낮추는 실제 연결과 정상 메뉴 불만·판매 조건 안내를 구별한다. 특정 벤치마크 강제 후보 규칙은 없다. 잘못된 제안은 원문에 존재하는 anchor/시간/axis와 PROPOSAL_* 실패 코드를 진단에 보존한다. 허구 원문이나 잘못된 인용은 저장하지 않는다.

참고별 묶음 분리와 복구로 전체 호출·비용이 늘 수 있다. 참고 입력 상한은 그대로다. 이미지 재추출 실패는 추가 모델 호출 없이 종료될 수 있다. ID 37은 개정 27에서 B 관련 흐름/C/D, 동일 전사의 ID 38은 C/D만 발행했다. B의 탐색 형식/범위 실패와 이미지 PASS를 구분한다. 개정 28 실영상 효과는 대기 중이다. [실험 기록](AI-분석-실험-기록.md)을 따른다.

### 개정 25에서 달라진 기반

- 연구 사전을 검증 후 `guidelines/patterns.json`(공통 패턴), `guidelines/context-examples.json`(예시집), `guidelines/runtime.json` v4(원자적 실행 묶음)로 내보낸다. 서버는 마지막 실행 묶음 하나만 읽어 서로 다른 파일 버전의 혼합을 막는다.
- 사례가 늘어도 공통 패턴 입력은 사례 수에 비례하여 늘지 않는다. 예시는 요청 원문에서 로컬 문자 유사도로 최대 2개 선별하며, 각각의 흐름·비판 이유·자료 한계를 통째로 유지한다. 사건 전체 반응·반론·공개 시점 반응은 콘텐츠 예시에서 제외한다. 공개 시점 민감성은 별도 현재 사건 대조가 필요하다.
- 무검증 링크나 댓글 원문 대신 무결성이 확인된 기사 해석/보도 반응의 짧은 발췌만 유형과 함께 전달한다. 작성자·원문 댓글·수집 ID는 모델 입력에서 제외한다.
- 발언 탐색 배치·검증 묶음·이미지 후보 및 OCR 요청 배치마다 원문을 기준으로 예시를 다시 선별한다. OCR 배경 문구는 검색 질의에서 제외하고 STT/OCR을 강제로 연결하지 않는다.
- `contextDictionarySha256`과 요청별 `contextSelections`로 예시 선택 및 입력 크기를 추적한다. 검색 실패를 안전 판정으로 바꾸지 않으며, 예시가 없어도 공통 기준으로 원문 전체를 탐색한다. 근거 검증은 유지한다.
- 장르 제한·제작자가 아는 문제 제외라는 낡은 설명을 정리하고 전체 장면 미지원과 선택적 프레임 지원을 구분했다.

추가 에이전트/임베딩/유료 검색 호출은 없다. 참고 JSON 상한은 8,000→6,000 code point, 선택 예시 배열의 합산 크기는 최대 3,000으로 제한한다. 상한을 넘는 예시는 잘라서 전달하지 않고 제외한다. 저장 v1 전사의 탐색 창 3개에서 참고 JSON은 기존 5,913→평균 3,608.3 code point로 약 39% 감소했다. 전체 프롬프트·토큰·청구 비용 감소율이나 정확도 향상이 아니다. 참고와 현재 증거를 분리하는 원칙은 [OpenAI 공식 안내](https://developers.openai.com/api/docs/guides/prompt-engineering), 검색과 판단을 별도로 평가하는 경계는 [정확도 최적화 안내](https://developers.openai.com/api/docs/guides/optimizing-llm-accuracy)를 참고했다.

### 실행과 다음 개편 순서

사례 추가/수정 시 카드 재구축/검증 후 `python3 tools/build_context_dictionary.py --write` → `python3 tools/build_context_dictionary.py --verify` → `python3 tools/build_review_guidelines.py --write`로 재생성한다. 원장·계획·스냅샷 불일치와 기한 만료는 내보내기를 차단한다. 데이터는 Git 제외이므로 코드 배포만으로 다른 서버에 사전이 전달되지는 않는다. 기준집은 Spring 시작 시 로드하여 실행 중 서버에는 재시작이 필요하다.

1. Spring 재시작 후 다음 업로드에서 개정 28/기준집 v4/후보별 선택/discoveryRepairCalls·repairCalls·repairs·PROPOSAL_*를 확인하고 ID 37/38과 B·C·D 및 실패를 비교한다. 정상 리뷰와 같은 영상 반복 실행도 필요하며 개정 28 실영상 효과는 미검증이다.
2. B가 탐색 범위·형식에서 탈락하는지, 문맥을 본 뒤 PASS인지 구별한다. 자료가 전달됐다는 이유만으로 카드 발행을 강제하지 않는다.
3. 문자 기반 검색의 표현 변화 누락을 측정하고 필요할 때 의미 검색을 검토한다. 현재는 로컬 검색이지 벡터 검색·파인튜닝·그래프 추론이 아니다.
4. 측정 후 사실/최근 사건을 선택 실행으로 분리하고 중복 호출을 정리한다. 비교 실험용 이전 분석 경로는 회귀·롤백에 필요하여 아직 삭제하지 않는다.

### 최종 방향: 하나의 큰 논란 맥락 마인드맵

사람이 보는 전체 지도에는 패턴·논란 포인트·반응을 연결하고, AI에는 현재 원문과 관련된 작은 부분만 제공한다. 이번 구현은 패턴↔예시 연결의 기반이다. 패턴 간 포함/동시 등장/적용 조건/정상 경계/출처 지원 같은 관계 유형이나 그래프 UI·자동 인과 추론은 아직 없다. 같은 단어의 등장과 같은 논란 메커니즘을 구분하고, 사람 검수 전 연결은 가설로 유지해야 한다. 반응의 인기·다수결로 관계를 정답화하지 않는다. 실제 정상 대조 예시는 여전히 0개이며 현재 정상 경계 문구를 정상 영상 데이터라고 부르지 않는다.

## 현재 판단 기준: ID 15 이후

최신 선언 버전은 `2026-10-08-judgment-policy-2`다. 아래 이전 버전·단계별 설명보다 이 절과 [실험 기록 26~27절](AI-분석-실험-기록.md)이 우선한다. 코드 반영, 실영상 검증 대기 상태다.

1. **무엇을 검토하는가:** 대상의 열등함·초라함을 묘사하는 폄하, 표현 자체의 구체적인 신체 훼손 비유·위협·성적 모욕·비공개 개인정보 노출, 별도 근거 확인이 필요한 주장/특수 의미를 구분한다. 부정적인 단어·지역명·브랜드명·방언 자체는 경고 근거가 아니다.
2. **정상 리뷰와 구분:** 맛·가격·기능 불만과 강한 비판·단정적인 표현 자체는 경고하지 않는다. 실제 대상·상황·평가 관계에서 조롱·모욕으로 이어지는 추가 문맥을 설명해야 한다. 농담·인용은 면책이 아니며, 단순 가능성을 상상해 후보를 만들지 않는다.
3. **근거에 따른 결정:** 실제 표현, 대상 또는 표현 자체의 문제, 필요한 문맥 연결, 정상 해석과 구별되는 이유로 판단한다. 구체적 검토 근거는 REVIEW_REQUIRED, 현재 근거 없음은 PASS, 필수 원문/대상/문맥 누락은 UNCERTAIN이다. PASS는 안전 보증이 아니다.

판단은 `ReviewJudgmentPolicy`로 발언·묶음·화면 글자에 공유한다. 출처별 유형/한계와 `TextReviewEngine`의 JSON·인용·허용 창 규칙은 별도 절이다. 출력 API/enum·검증 로직·점수 상한·호출 구조는 바꾸지 않았다. 분리란 요청/API를 늘린 것이 아니라 같은 시스템 메시지의 책임을 상수와 제목으로 구분한 것이다.

**C 카드 유지 자체가 목표는 아니다.** '메뉴가 의미 없다'를 단정적이라는 이유만으로 노출했다면 새 기준에서 PASS가 될 수 있다. 원본 영상과 사람 평가로 정상 리뷰인지 누적 조롱인지 확인하고 오탐/누락을 함께 평가한다. 범용 정책이며 v1 정답을 넣지 않는다.

### Signal과 Risk를 분리한다

민감한 단어·은어·밈·제스처가 발견되었다는 사실은 `Signal`일 뿐, 곧바로 `Risk`라는 뜻은 아니다.

```text
Signal 발견
  ↓
앞뒤 발언·화면·장르·대화 상황 확인
  ↓
현재 사용 의도와 사회적 맥락 해석
  ↓
검토 가치가 있는 Risk인지 판단
```

예를 들어 `~노` 같은 일반적인 문장 끝 어미는 경상도 사투리와 구분하기 어렵고 화자의 영상에서 반복적으로 나타날 수 있으므로, 현재 기본 사전에서는 단독 탐지 대상에서 제외한다. 향후 별도 데이터셋으로 충분히 검증되기 전까지는 지역 방언 오탐을 줄이는 것을 우선한다. 이전 `CommunitySlangRules` 직접 카드 경로는 제거했다. 표현 등장은 독립 목록으로, 맥락 판단은 검증 경로로 분리한다.

### 사람의 정체성을 추론하지 않는다

화자의 출신 지역·정치 성향·커뮤니티 이용 여부를 추측해서는 안 된다. 영상과 대본 안에서 실제로 확인되는 언어적·시각적 맥락만 사용한다. 출신 지역을 알면 표현의 의미를 자동으로 결정할 수 있다는 식의 규칙도 만들지 않는다.

### 애매함을 결과로 허용한다

현재 리포트는 여러 `finding`과 분석 범위를 제공한다. 발언·화면 LLM 검토의 내부 응답은 다음 세 결정을 사용하며, 구간별 결정의 DB 저장·공개 API 노출은 후속 과제다.

| 내부 구현 결정 | 의미 |
|---|---|
| `PASS` | 현재 근거로는 별도 검토가 필요한 위험을 찾지 못함 |
| `REVIEW_REQUIRED` | 게시 전 사람이 확인할 가치가 있는 후보 |
| `UNCERTAIN` | 정보가 부족하거나 분석기 간 판단이 엇갈림 |

`PASS`는 “절대 논란이 되지 않는다”는 보증이 아니며, `UNCERTAIN`은 실패가 아니라 정보 부족을 명시한 결과다. 현재는 보류를 자동 위험 카드로 만들지 않고 분석 범위 안내에 기록한다. 구간별 사람 검수 화면과 영속 저장은 아직 구현하지 않았다.

### 의미 있는 정밀도를 우선한다

30분 영상에서 후보를 수십 개 보여주는 것보다, 실제 검토할 가치가 있는 소수의 구간을 근거와 함께 보여주는 것이 서비스 목적에 맞다. 따라서 후보를 넓게 찾는 단계와 최종 사용자에게 표시할 단계를 분리하고, 최종적으로는 `Review Required Rate`, 영상당 평균 Alert 수, 심각한 위험 누락 비율을 함께 관리한다.

## 3. 분석기 역할

| 구분 | 현재 역할 |

| `SubtitleAnalyzer` | STT 개인정보 노출 패턴만 확인. 욕설/은어 등장은 별도 표현 트랙 |

| `ExpressionService` / `ExpressionDictionary` | STT 욕설·확인 표현 등장을 별도 저장/API로 반환. 이전 CommunitySlangRules 직접 카드 경로 제거 |
| `ContextLexiconAnalyzer` | 단어 하나만 보지 않고 앞뒤 맥락과 함께 판단 |
| `SpeechReviewAnalyzer` | 전체 STT를 공통 배치로 검토하고 원문 근거·명시적 결정을 검증 |
| `ScreenTextReviewAnalyzer` | 전체 OCR을 공통 배치로 검토하며 원문과 추정 복원을 분리 |
| `ContextCheckAnalyzer` | 사건·논란의 시점과 맥락을 외부 자료와 비교 |
| `EntityCheckAnalyzer` | 인물·사건 등 고유명사와 뉴스 근거를 확인 |
| `MonetizationRiskAnalyzer` | 광고·수익화 관점에서 검토가 필요한 표현을 표시 |
| `CaptionMismatchAnalyzer` | 발언과 화면 자막의 불일치 가능성을 표시 |
| `FindingFusionService` | 여러 분석기의 결과를 하나의 리포트로 통합 |

분석기 활성화 여부는 `application.yml`의 `oops.analysis.enabled-analyzers`에서 조절한다. Spring의 OpenAI 키가 없으면 이에 의존하는 텍스트·맥락 분석기는 건너뛸 수 있지만, Python STT는 별도 `oops-analysis` 설정의 OpenAI 키가 필요하다. Python 쪽 키가 없거나 STT가 실패하고 OCR에서도 텍스트를 얻지 못하면 파이프라인은 완료가 아니라 실패할 수 있다. 뉴스 키가 없을 때는 Google News RSS가 기본 제공자로 사용되므로 뉴스 분석이 자동으로 꺼지는 것은 아니다.

### 현재 기본 활성화 범위

| 상태 | 분석기 |
|---|---|
| 기본 활성화 | `subtitle`, `speech-review`, `context-lexicon`, `screen-text`, `screen-text-review` |
| 선택 프로필 `external-review` | 기본 분석기 + `entity-check`, `context-check` (기존 외부 검색 경로) |
| 기본 비활성화 | `entity-check`, `context-check`, `caption-mismatch`, `monetization`, `comment`, `pose` |

따라서 현재 결과는 음성 대본과 OCR 화면 텍스트 중심이다. 행동·제스처·댓글 여론·자막과 발언의 불일치를 실제로 분석한다고 설명해서는 안 된다. 해당 기능은 코드에 분석기 형태가 일부 존재하더라도 기본 파이프라인에 포함되지 않은 별도 확장 영역이다.

### 10/8 공통 텍스트 검토 연결

두 LLM 검토기는 `ReviewInput` → `TextReviewBatchPlanner` → `TextReviewEngine`을 공유한다. 사전 후보가 없어도 전체 비어 있지 않은 발언과 **편집 텍스트로 추정된 OCR 영역**을 검토하고, 다른 출처와 앞뒤 구간은 제한된 보조 문맥으로 전달한다. 배경·출처 불확실 글자는 보존하되 자막 표현 검토의 단독 대상에서 제외하고 제외 수를 알린다. 개인정보 룰은 모든 역할에 유지한다. 유효한 `REVIEW_REQUIRED`만 기존 후보로 변환하며 누락·실패·보류·충돌은 통과로 바꾸지 않는다. 원문 인용은 코드포인트 범위로 검증하고 OCR 복원 문구는 별도로 남긴다.

중간 결과는 실행 메모리에만 존재한다. 기존 `coverage/warnings`에는 요약 상태를 저장하며, 분석기 간 충돌 해결·실행 이력·배심원 실행은 아직 구현하지 않았다. 배치 한도·비용 영향·96개 오프라인 테스트와 미검증 항목은 [개선 계획](AI-분석-개선-계획.md#pipeline-redesign)의 9.7절을 참고한다.

v1 로컬 검증 후 누락 구간 한정 재검토를 추가했다(분석기당 최대 6배치·배치당 8구간·구간당 한 번). 빈 응답·충돌·제외된 OCR을 PASS로 바꾸지 않는다. 뉴스 배경 경고에는 실제 발언과 기사 인용·사건 연결·유효 출처를 요구하고, 제목·요약 기반 점수는 0.69 이하로 제한한다. 브랜드명 단순 일치만으로 경고를 만들지 않도록 보완했으며 실제 영상 품질 재평가는 남아 있다. 세부 정책과 한계는 개선 계획 9.9절에 기록한다.

## 4. 룰 기반 분석과 LLM 분석을 함께 쓰는 이유

룰 기반 분석은 빠르고 비용이 없으며 같은 입력에 같은 결과를 내기 쉽다. 반면 표현의 앞뒤 맥락이나 풍자·비유·사건 연결을 이해하는 데 한계가 있다.

LLM 분석은 맥락 이해에 유리하지만 비용·지연·응답 변동성이 있고, STT/OCR이 잘못 읽은 문장을 그대로 믿을 위험이 있다. 따라서 현재 구조는 다음처럼 역할을 나눈다.

```text
룰 기반: 확실한 후보를 빠르게 수집
       +
LLM 기반: 후보의 의도·맥락·심각도를 보완
       +
외부 근거: 사건·최신성에 대한 참고자료 제공
       ↓
검토용 리포트
```

리포트의 `finding`은 확정 판결이 아니라 “이 시점을 확인해볼 필요가 있다”는 후보이다. 근거가 부족하거나 분석 자체가 실행되지 않은 경우에는 `coverage`와 `warnings`로 구분해서 표시해야 한다.

## 검토 이벤트의 목표 구조

문장 하나를 곧바로 `논란`으로 저장하지 않고, 다음 단계의 이벤트로 저장하는 방향이 적합하다.

```text
Surface Signal
  ↓
Context Interpretation
  ↓
Risk Mechanism
  ↓
Final Review Decision
```

예시는 다음과 같다.

```json
{
  "startTime": 193.2,
  "endTime": 201.8,
  "surfaceSignals": ["PAST_EVENT_REFERENCE"],
  "contextInterpretations": ["DIRECT_REFERENCE_TO_SUBJECT"],
  "contentLabels": ["PAST_CONTROVERSY_REFERENCE"],
  "riskMechanisms": ["RESURFACING_PRIOR_CONTROVERSY", "SECONDARY_HARM"],
  "decision": "REVIEW_REQUIRED",
  "evidence": "과거 논란을 당사자에게 다시 설명하도록 요구하는 장면"
}
```

위 JSON은 현재 DB 스키마에 그대로 적용된 계약이 아니라, 향후 분석 결과를 확장할 때의 목표 형태다.

### Content Label과 Risk Mechanism

`Content Label`은 발언이나 행동이 무엇을 하고 있는지 나타내고, `Risk Mechanism`은 왜 게시 후 문제가 될 수 있는지를 나타낸다.

| Content Label 예시 | Risk Mechanism 예시 |
|---|---|
| `PAST_CONTROVERSY_REFERENCE` | `RESURFACING_PRIOR_CONTROVERSY` |
| `PRIVATE_MATTER` | `PRIVACY_INTRUSION` |
| `RUMOR_REPETITION` | `RUMOR_AMPLIFICATION` |
| `COMMUNITY_REFERENCE` | `COMMUNITY_ASSOCIATION_RISK` |
| `MOCKERY` | `HUMILIATION` |
| `AGGRESSIVE_BEHAVIOR` | `PHYSICAL_INAPPROPRIATENESS` |
| `PERSONAL_QUESTION` | `POWER_IMBALANCE`, `SECONDARY_HARM` |

이렇게 분리하면 같은 발언이라도 실제 위험 원인이 무엇인지 설명할 수 있고, 사용자에게 단순한 금지어 목록보다 설득력 있는 근거를 제공할 수 있다.

## 5. 비용과 처리량을 제한하는 현재 방식

- 기본 OpenAI 모델은 설정으로 교체할 수 있고, 데모에서는 비교적 저렴한 모델을 우선 사용한다.
- 영상 최대 길이와 OCR 최대 프레임 수를 환경변수로 제한한다.
- OCR 프레임은 일정 간격으로 추출하며, 긴 영상에서는 최대 프레임 수를 넘지 않도록 간격을 늘린다.
- OpenAI 호출 사이에 제한을 두고, 외부 API의 `Retry-After` 안내를 반영한다.
- 업로드·등록·재시도 API에는 IP 기준 요청 제한을 적용했다.
- Python OCR이 실패해도 STT 분석까지 전체 작업이 실패하지 않도록 단계별 실패를 분리한다.

## 6. 현재 품질상의 한계

1. STT는 발음, 고유명사, 은어를 잘못 인식할 수 있다. 자막이 없는 경우에도 음성 STT로 발언 검토를 수행하지만, STT가 놓친 표현은 후속 프롬프트만으로 복구할 수 없다.
2. OCR은 글꼴·배경·움직임에 따라 자막을 누락하거나 비슷한 글자로 읽을 수 있다.
3. 영상에 실제로 말하지 않은 편집 자막과 화면 속 일반 텍스트가 아직 완벽하게 분리되지 않는다.
4. 은어 목록을 늘리는 것만으로는 부족하며, 표현별로 “어떤 맥락에서 위험한가”를 함께 관리해야 한다.
5. 뉴스 검색 결과가 없거나 최신 사건인 경우, `finding 없음`과 `근거를 찾지 못함`을 혼동하면 안 된다.
6. 현재 데이터셋과 정량 평가셋이 작아 재현율·정밀도를 충분히 비교하기 어렵다.

### 구현상 특히 주의할 지점

1. **점수는 확률이 아니다.** 현재 `score`는 모델의 실제 확률이 아니라 분석기와 Fusion 로직이 계산한 확인 우선순위에 가깝다. `0.8`을 “80% 확률로 논란”이라고 설명하면 안 된다.
2. **애매한 결과가 영속 검수 이력으로 저장되지 않는다.** 공통 텍스트 검토에는 `UNCERTAIN`이 구현돼 있으나 공개 리포트는 보류를 별도 카드로 저장하지 않고 coverage 안내에 반영한다. 사전 `AMBIGUOUS` 처리와 공통 검토의 보류 계약도 동일하지 않다. 로컬 임시 진단을 사용자별 영구 이력으로 오해하지 않는다.
3. **후보 한도는 일부 구간을 확인하지 못하게 한다.** 맥락 사전은 최대 24개를 시간대별로 고르고, 초과 수를 `PARTIAL` 경고로 기록한다. STT·OCR LLM 분석도 윈도우 단위 호출이며 각 호출 실패는 coverage로 확인해야 한다.
4. **룰 매칭은 문맥보다 빠르다.** 현재 일부 룰은 문자열 포함 여부를 먼저 보기 때문에 인용·부정·자기 경험·일반 설명도 후보가 될 수 있다. 확실한 비하 표현과 일반적인 민감 주제 신호를 같은 방식으로 다루면 오탐률이 높아진다.
5. **뉴스 검색은 근거의 품질이 일정하지 않다.** 검색 결과가 최신이거나 원출처라는 보장이 없으며, 검색 결과가 없다는 사실도 안전하다는 근거가 아니다. 기사 발행일·출처 유형·주장과의 직접 관련성을 별도로 기록해야 한다.
6. **교차 검증이 항상 독립 근거는 아니다.** 같은 발언이 화면 자막에 그대로 반복되면 STT와 OCR 양쪽에서 잡힐 수 있다. 가까운 시점의 호환되는 후보는 병합하되, 출처 수나 중복 수만으로 점수를 올리지 않는다.
7. **프롬프트 버전과 분석기 버전이 결과에 남지 않는다.** 같은 영상을 다시 분석했을 때 모델·프롬프트·사전이 달라진 것인지 결과가 달라진 것인지 비교하기 어렵다.

## 7. 품질을 높이는 방법

멘토링에서 제안된 방향을 현재 서비스에 적용하면 다음 순서가 적합하다.

1. 실제 영상에서 탐지 후보를 모아 `정탐`, `오탐`, `미탐`, `판단 불가`로 라벨링한다.
2. 은어·논란 표현은 단어 목록이 아니라 예문, 위험 맥락, 예외 맥락과 함께 저장한다.
3. 같은 영상에 대해 STT/OCR 원문, 분석기 결과, 최종 사용자 피드백을 연결한다.
4. 모델을 바꾸기 전에 영상별 분석시간, 호출 횟수, 비용, 정밀도·재현율을 비교한다.
5. 강한 모델은 모든 영상에 적용하지 않고, 룰과 저비용 모델이 판단하기 어려운 후보에만 실험적으로 적용한다.
6. 같은 영상 재분석 시 재사용할 수 있는 결과와 다시 계산해야 하는 결과를 분리한다.

### Hard Negative를 반드시 함께 만든다

맥락 의존 표현의 논란 사례만 모으면 모델이 다음과 같은 잘못된 규칙을 배울 수 있다.

```text
특정 표현 발견 = 위험
```

따라서 다음 사례를 함께 수집해야 한다.

- 자연스러운 지역 방언
- 다른 사람의 발언을 인용하는 장면
- 표현의 의미를 설명하는 교육적 장면
- 과거 사건을 객관적으로 설명하는 장면
- 밈·패러디를 비판적으로 소개하는 장면

초기에는 Positive 사례 하나당 Hard Negative를 2~3개 정도 확보하는 것을 실험 기준으로 삼을 수 있다. 실제 비율은 평가셋의 결과를 보며 조정한다.

### 대화 Window를 기준으로 판단한다

현재 STT 세그먼트의 앞뒤 문장을 연결해 분석하는 방향을 유지한다. 목표 데이터 구조에는 발화자, 시작·종료 시간, 현재 발언, 이전 발언, 이후 발언이 포함되어야 한다.

문장 단위 분석만으로는 인용인지, 질문인지, 당사자에게 직접 요구하는 말인지 구분하기 어렵다. 발화자 정보가 없는 영상에서는 이를 추정하지 말고 `UNCERTAIN` 또는 검토 후보로 남긴다.

## 8. AI 로직 개선 우선순위

### 1순위: 결과 의미와 평가 기준 고정

모델을 더 좋은 것으로 바꾸기 전에 결과의 의미부터 고정한다.

```text
Signal 발견
  ↓
Context 분석
  ↓
Risk Mechanism 추출
  ↓
검토 결정
  ├─ PASS
  ├─ REVIEW_REQUIRED
  └─ UNCERTAIN
```

현재 DB의 `score`는 이 결정과 분리해 “화면에 먼저 보여줄 우선순위”로 정의하는 것이 좋다.

| 필드 | 의미 |
|---|---|
| `decision` | 사람이 확인해야 하는지에 대한 결과 |
| `confidence` | 모델이 자신의 해석을 얼마나 확신하는지 |
| `priority` | 여러 후보 중 사용자에게 먼저 보여줄 순서 |
| `evidence` | 판단에 사용한 발언·화면·외부 자료 |
| `coverage` | 실제로 분석된 입력 범위와 빠진 단계 |

### 2순위: Hard Negative 기반 회귀 테스트

다음 사례를 고정 테스트셋으로 만들고 변경 때마다 비교한다.

- 자연스러운 사투리와 일상 표현
- 단순 인용·설명·뉴스 전달
- 자기 자신을 대상으로 한 표현
- 일반적인 정치·사회 주제 언급
- OCR이 깨진 자막
- 같은 장면을 STT와 OCR이 동시에 읽은 사례
- 실제로 검토가 필요한 과거 논란·루머·개인정보 사례

각 사례에는 `정상`, `검토 필요`, `판단 불가`를 사람이 라벨링한다. 모델이 후보를 많이 내는 것보다 정상 사례를 불필요하게 올리지 않는지 먼저 확인해야 한다.

### 3순위: 후보 수와 비용을 단계적으로 제한

현재 구조를 다음처럼 다듬는 것이 좋다.

```text
전체 STT/OCR
  ├─ 모든 구간에 저비용 맥락 검토를 유지
  └─ 룰·사전으로 후보 구간을 추가 수집
          ↓
      중복 제거·우선순위화
          ↓ 확인이 더 필요한 구간만
      뉴스 검색·추가 LLM 검토
          ↓
      최종 검토 이벤트
```

룰에 걸린 구간만 LLM으로 보내는 방식은 사전에 없는 표현이나 어휘만으로 드러나지 않는 위험을 놓칠 수 있다. 따라서 전체 대본을 살피는 저비용 검토와 룰 기반 후보 수집을 함께 유지하고, 뉴스 검색이나 더 비싼 추가 검토를 우선순위가 높은 후보에 한정한다. 같은 입력의 결과를 재사용할 때는 영상·STT/OCR 결과 해시와 분석기·프롬프트 버전을 함께 확인해야 한다.

### 4순위: 분석 범위와 실패를 사용자에게 공개

다음 상황은 `finding 없음`과 구분해야 한다.

- OpenAI 키가 없어 LLM 분석을 실행하지 못함
- OCR 모델이 없어 화면 분석을 실행하지 못함
- 외부 뉴스 검색이 실패함
- 최대 후보 수를 넘어 일부 후보를 보지 않음
- OCR 결과가 비어 있어 화면을 제대로 읽었는지 알 수 없음

사용자 화면에는 최소한 다음을 보여주는 것이 좋다.

```text
STT: 완료
OCR: 완료 / 텍스트 없음 / 실패
맥락 분석: 완료 / 일부 실패
뉴스 확인: 실행 안 함 / 검색 결과 없음 / 완료
```

## 9. 분석기별 개선 방향

| 분석기 | 현재 한계 | 다음 개선 |
|---|---|---|
| `SubtitleAnalyzer` | 문자열 포함 기반 오탐 | 단어 경계·부정·인용·반복성 고려 |
| `ContextLexiconAnalyzer` | 사전·힌트 품질에 의존 | Hard Negative와 표현별 예외 맥락 관리 |
| `SpeechReviewAnalyzer` | 20줄 고정 Window, 호출 수 증가 | 시간 기반 Window·후보 우선 호출·프롬프트 버전 관리 |
| `ScreenTextAnalyzer` | 편집 자막과 간판·로고 구분 한계 | 영역·지속시간·반복 패턴으로 편집 자막 분리 |
| `ScreenTextReviewAnalyzer` | OCR 오류를 LLM이 추정 | OCR 신뢰도와 원본 프레임을 함께 사용 |
| `ContextCheckAnalyzer` | 뉴스 품질·최신성 편차 | 출처 유형·발행일·검색 기준일 기록 |
| `EntityCheckAnalyzer` | 검색 결과와 주장 연결이 어려울 수 있음 | 주장 단위 근거·반대 근거·원출처 분리 |
| `FindingFusionService` | 같은 신호의 교차 검증을 과대평가 가능 | 동일 원문·동일 프레임 여부를 확인한 뒤 보정 |

## 10. 평가 지표와 출시 기준

분석기 전체를 하나의 정확도로 평가하지 말고, 유형별로 따로 측정한다.

| 지표 | 의미 |
|---|---|
| Precision | 표시한 후보 중 실제로 검토할 가치가 있는 비율 |
| Recall | 사람이 라벨링한 중요 후보를 찾아낸 비율 |
| False Positive Rate | 정상 장면을 불필요하게 올린 비율 |
| False Negative Rate | 중요한 장면을 놓친 비율 |
| Review Required Rate | 영상당 사람 검토가 필요한 후보 비율 |
| 평균 Alert 수 | 영상 한 편에서 표시되는 최종 후보 개수 |
| Human-AI Agreement | 사람 검수자와 AI 판단의 일치율 |
| 영상당 비용 | STT·LLM·뉴스 검색에 사용한 실제 비용 |

데모 단계에서는 Recall을 무리하게 높이기보다, 대표 영상에서 사용자가 감당할 수 있는 Alert 수와 근거의 품질을 우선 확인한다. 운영 전에는 최소한 다음 질문에 답할 수 있어야 한다.

- 30분 영상에서 최종 후보가 평균 몇 개인가?
- 그중 사람이 “검토할 가치가 있다”고 판단한 비율은 얼마인가?
- 정상적인 사투리·인용·설명 장면의 오탐률은 얼마인가?
- 분석 실패나 미실행 단계가 사용자에게 명확히 표시되는가?
- 같은 영상을 재분석했을 때 왜 결과가 달라졌는지 설명할 수 있는가?

## 11. 앞으로 고려할 입력 확장

- 사용자가 가진 `.srt`, `.vtt` 자막 파일을 직접 받는 기능
- 편집 자막과 일반 화면 텍스트를 분리하는 OCR 영역·시간 연속성 규칙
- 영상 해시와 STT/OCR 결과 해시를 활용한 중복 분석 방지
- 분석기별 버전과 프롬프트 버전을 저장해 결과 재현
- 사용자 피드백을 다음 룰·평가 데이터셋으로 연결

위 항목은 품질 향상 방향이며, 현재 `minwook` 브랜치에 모두 구현된 기능은 아니다.

## 12. 외부 근거와 유사 사례 검색

### Dynamic Social Context

사회적 의미는 새로운 사건과 함께 바뀔 수 있으므로, 고정된 프롬프트만으로 현재 맥락을 모두 판단한다고 가정하지 않는다. 다만 모든 문장을 검색하면 비용과 지연이 커지므로 다음처럼 후보 이후에 제한적으로 검색한다.

```text
Signal 후보
  ↓
인물·사건·표현 Entity 추출
  ↓
정말 필요한 후보만 뉴스·공개 자료 검색
  ↓
출처가 있는 Context를 LLM에 제공
```

뉴스나 검색 결과는 판단의 근거 후보이지 사실 확정 자체가 아니다. 출처, 기준일, 관련성을 함께 저장하고 검색 결과가 없을 때는 `근거 없음`과 `위험 없음`을 구분한다.

### Controversy Dataset과 유사 사례 검색

검증된 이벤트 데이터가 충분히 쌓이면 문장 전체를 매번 프롬프트에 넣는 대신, 현재 후보와 유사한 Positive·Hard Negative 사례를 찾아 LLM 판단에 참고자료로 제공할 수 있다. Vector DB와 Embedding은 이 단계에서 검토할 기술이며, 현재 프로젝트에 구현되어 있지는 않다.

## 13. 멀티모달 분석 확장

현재는 Python에서 STT와 OCR을 만들고 Spring Boot에서 텍스트·맥락 분석을 수행한다. 이후에는 텍스트 후보의 타임스탬프를 이용해 필요한 구간만 영상으로 확대 분석하는 방식이 적합하다.

```text
STT/OCR 후보
  ↓
해당 시점 전후 짧은 구간 선택
  ↓
프레임을 더 촘촘하게 추출
  ↓
행동·제스처·상황 확인
```

말이 없어도 발생하는 시각 사건은 STT/OCR 후보만으로 찾을 수 없다. 후속 오프라인 실험에서는 전체 영상의 저비용 시각 탐색을 독립적으로 수행하고, 텍스트 또는 시각 후보 주변에서만 고비용 상세 확인을 비교한다. 초기 행동 범위·샘플링·가림·짧은 사건의 누락 평가는 [행동·포즈·긴 영상 계획](행동-포즈-데이터셋-및-긴영상-적용-계획.md)을 따른다. 현재 `pose`는 미구현이며 이 문단은 운영 기능이 아니다.

## 14. 사람 검토와 피드백

사용자는 각 후보에 대해 다음 피드백을 남길 수 있어야 한다.

- 정확한 탐지
- 문제 없음
- 카테고리 수정
- 위험 수준 수정
- AI가 놓친 구간 추가

이 피드백은 즉시 모델 학습에 넣는 것이 아니라, 검수된 데이터셋으로 분류·검토한 뒤 룰, 프롬프트, 평가셋 개선에 사용한다. 이를 통해 `AI 예측 → 사람 검토 → 검증 데이터 → 품질 개선`의 순환을 만든다.
