# OoPs?! AI 분석 로직

> 기준: `minwook` 작업 트리 · 최신 확인: 2026-10-08, ID 9 · 코드 반영, 로컬 개발 영상 검증 진행·독립 평가/운영 검증 대기

사전·프롬프트 개선, 자막 없는 영상의 입력 처리, 부정 평가의 수위 판단, 사실 대조의 선택 실행에 대한 다음 개발안은 [AI 분석 개선 계획](AI-분석-개선-계획.md)에 정리한다. 실제 용례·KOLD 참고 주석·평가 기준은 [논란 데이터셋 구축 계획](논란-데이터셋-구축-계획.md#text-dataset)을 따른다. 데이터셋 문서로 통합한 [가상 검수 사례 부록](논란-데이터셋-구축-계획.md#annotation-examples)은 팀 검토 전의 출발 자료이며 검증 데이터로 간주하지 않는다.

OoPs?!의 목적은 영상을 자동으로 삭제하거나 최종 판결하는 것이 아니라, 영상 속 발언·화면 문구·맥락에서 검토가 필요한 지점을 시간 정보와 근거를 붙여 보여주는 것이다.

10/8 대화 단위 검토 1차 변경: 원본 구간을 유지한 `ReviewUnit` 읽기 창과 복수 PRIMARY/TARGET/CONTEXT 인용, 대상 유형·문맥 연결 이유를 발언/편집 텍스트 검토에 추가했다. 제공 문맥과 실제 판정 구간은 별도로 추적하며, 공개 DTO·DB 스키마는 유지한다. 제한·호환·실모델 검증 절차는 [개선 계획 9.11절](AI-분석-개선-계획.md)을 따른다. 별도 후보 재검증기와 문맥 패턴 사전은 아직 추가하지 않았다.

## 핵심 판단 원칙

ID 8 이후 발언 분석 기본 경로는 구간 `evaluations`와 대화 묶음 `unitEvaluations`를 같은 호출에서 함께 받는다. 최대 6개 bounded 묶음의 대상 연결·정상 해석·보류를 명시적으로 검증하며, 유효 묶음 후보는 기존 리포트 경로로 전달한다. 구간 PASS와 묶음 후보는 다른 판단 범위이고 근거 구간을 일괄 위험으로 바꾸지 않는다. 묶음 누락은 PARTIAL이며 그 이유만으로 추가 재호출하지 않는다. 구현·비용 한계·롤백 설정·검증은 [실험 기록 12절](AI-분석-실험-기록.md)에 정리했다.

**ID 9 결과:** 구간 53/53 유효, 묶음 5개 요청 중 4개 유효·1개 계약 탈락, 메뉴 평가 카드 1개다. B의 지역 음식 흐름은 묶음에서도 PASS, D의 신체 비유는 특정 인물/집단 모욕 근거가 없다는 이유로 구간 PASS가 되어 이전 탐지가 사라졌다. 묶음 관측은 가능해졌지만 품질 개선은 입증되지 않았다. 다음은 공격 대상 유무와 불쾌한 비유의 검토 필요성을 분리하고 정상 대조 사례로 검증한다. [실험 기록 13절](AI-분석-실험-기록.md)을 최신 결과로 사용한다.

### Signal과 Risk를 분리한다

민감한 단어·은어·밈·제스처가 발견되었다는 사실은 `Signal`일 뿐, 곧바로 `Risk`라는 뜻은 아니다.

```text
Signal 발견
  ↓
앞뒤 발언·화면·장르·대화 상황 확인
  ↓
현재 사용 의도와 사회적 맥락 해석
  ↓
검토 가치가 있는 Risk인지 판단
```

예를 들어 `~노` 같은 일반적인 문장 끝 어미는 경상도 사투리와 구분하기 어렵고 화자의 영상에서 반복적으로 나타날 수 있으므로, 현재 기본 사전에서는 단독 탐지 대상에서 제외한다. 향후 별도 데이터셋으로 충분히 검증되기 전까지는 지역 방언 오탐을 줄이는 것을 우선한다. `CommunitySlangRules`도 최종 판정기가 아니라 검증된 표현 후보를 만드는 장치로 취급한다.

### 사람의 정체성을 추론하지 않는다

화자의 출신 지역·정치 성향·커뮤니티 이용 여부를 추측해서는 안 된다. 영상과 대본 안에서 실제로 확인되는 언어적·시각적 맥락만 사용한다. 출신 지역을 알면 표현의 의미를 자동으로 결정할 수 있다는 식의 규칙도 만들지 않는다.

### 애매함을 결과로 허용한다

현재 리포트는 여러 `finding`과 분석 범위를 제공한다. 발언·화면 LLM 검토의 내부 응답은 다음 세 결정을 사용하며, 구간별 결정의 DB 저장·공개 API 노출은 후속 과제다.

| 내부 구현 결정 | 의미 |
|---|---|
| `PASS` | 현재 근거로는 별도 검토가 필요한 위험을 찾지 못함 |
| `REVIEW_REQUIRED` | 게시 전 사람이 확인할 가치가 있는 후보 |
| `UNCERTAIN` | 정보가 부족하거나 분석기 간 판단이 엇갈림 |

`PASS`는 “절대 논란이 되지 않는다”는 보증이 아니며, `UNCERTAIN`은 실패가 아니라 정보 부족을 명시한 결과다. 현재는 보류를 자동 위험 카드로 만들지 않고 분석 범위 안내에 기록한다. 구간별 사람 검수 화면과 영속 저장은 아직 구현하지 않았다.

### 의미 있는 정밀도를 우선한다

30분 영상에서 후보를 수십 개 보여주는 것보다, 실제 검토할 가치가 있는 소수의 구간을 근거와 함께 보여주는 것이 서비스 목적에 맞다. 따라서 후보를 넓게 찾는 단계와 최종 사용자에게 표시할 단계를 분리하고, 최종적으로는 `Review Required Rate`, 영상당 평균 Alert 수, 심각한 위험 누락 비율을 함께 관리한다.

현재는 사용자가 별도의 자막 파일을 업로드해 분석하는 기능은 구현되어 있지 않다. 영상에서 직접 얻은 STT와 OCR이 기본 입력이다.

  ├─ 선택적 외부 분석

## 3. 분석기 역할

| 구분 | 현재 역할 |
|---|---|
| `SubtitleAnalyzer` | STT 문장에서 룰 기반 위험 표현을 찾음 |
| `ScreenTextAnalyzer` | OCR 화면 텍스트에서 위험 표현을 찾음 |
| `CommunitySlangRules` | 커뮤니티 은어·표현 변형을 빠르게 탐지 |
| `ContextLexiconAnalyzer` | 단어 하나만 보지 않고 앞뒤 맥락과 함께 판단 |
| `SpeechReviewAnalyzer` | 전체 STT를 공통 배치로 검토하고 원문 근거·명시적 결정을 검증 |
| `ScreenTextReviewAnalyzer` | 전체 OCR을 공통 배치로 검토하며 원문과 추정 복원을 분리 |
| `ContextCheckAnalyzer` | 사건·논란의 시점과 맥락을 외부 자료와 비교 |
| `EntityCheckAnalyzer` | 인물·사건 등 고유명사와 뉴스 근거를 확인 |
| `MonetizationRiskAnalyzer` | 광고·수익화 관점에서 검토가 필요한 표현을 표시 |
| `CaptionMismatchAnalyzer` | 발언과 화면 자막의 불일치 가능성을 표시 |
| `FindingFusionService` | 여러 분석기의 결과를 하나의 리포트로 통합 |

분석기 활성화 여부는 `application.yml`의 `oops.analysis.enabled-analyzers`에서 조절한다. Spring의 OpenAI 키가 없으면 이에 의존하는 텍스트·맥락 분석기는 건너뛸 수 있지만, Python STT는 별도 `oops-analysis` 설정의 OpenAI 키가 필요하다. Python 쪽 키가 없거나 STT가 실패하고 OCR에서도 텍스트를 얻지 못하면 파이프라인은 완료가 아니라 실패할 수 있다. 뉴스 키가 없을 때는 Google News RSS가 기본 제공자로 사용되므로 뉴스 분석이 자동으로 꺼지는 것은 아니다.

### 현재 기본 활성화 범위

| 상태 | 분석기 |
|---|---|
| 기본 활성화 | `subtitle`, `speech-review`, `context-lexicon`, `screen-text`, `screen-text-review`, `entity-check`, `context-check` |
| 기본 비활성화 | `caption-mismatch`, `monetization`, `comment`, `pose` |

따라서 현재 결과는 음성 대본과 OCR 화면 텍스트 중심이다. 행동·제스처·댓글 여론·자막과 발언의 불일치를 실제로 분석한다고 설명해서는 안 된다. 해당 기능은 코드에 분석기 형태가 일부 존재하더라도 기본 파이프라인에 포함되지 않은 별도 확장 영역이다.

### 10/8 공통 텍스트 검토 연결

두 LLM 검토기는 `ReviewInput` → `TextReviewBatchPlanner` → `TextReviewEngine`을 공유한다. 사전 후보가 없어도 전체 비어 있지 않은 발언과 **편집 텍스트로 추정된 OCR 영역**을 검토하고, 다른 출처와 앞뒤 구간은 제한된 보조 문맥으로 전달한다. 배경·출처 불확실 글자는 보존하되 자막 표현 검토의 단독 대상에서 제외하고 제외 수를 알린다. 개인정보 룰은 모든 역할에 유지한다. 유효한 `REVIEW_REQUIRED`만 기존 후보로 변환하며 누락·실패·보류·충돌은 통과로 바꾸지 않는다. 원문 인용은 코드포인트 범위로 검증하고 OCR 복원 문구는 별도로 남긴다.

중간 결과는 실행 메모리에만 존재한다. 기존 `coverage/warnings`에는 요약 상태를 저장하며, 분석기 간 충돌 해결·실행 이력·배심원 실행은 아직 구현하지 않았다. 배치 한도·비용 영향·96개 오프라인 테스트와 미검증 항목은 [개선 계획](AI-분석-개선-계획.md#pipeline-redesign)의 9.7절을 참고한다.

v1 로컬 검증 후 누락 구간 한정 재검토를 추가했다(분석기당 최대 6배치·배치당 8구간·구간당 한 번). 빈 응답·충돌·제외된 OCR을 PASS로 바꾸지 않는다. 뉴스 배경 경고에는 실제 발언과 기사 인용·사건 연결·유효 출처를 요구하고, 제목·요약 기반 점수는 0.69 이하로 제한한다. 브랜드명 단순 일치만으로 경고를 만들지 않도록 보완했으며 실제 영상 품질 재평가는 남아 있다. 세부 정책과 한계는 개선 계획 9.9절에 기록한다.

## 4. 룰 기반 분석과 LLM 분석을 함께 쓰는 이유

룰 기반 분석은 빠르고 비용이 없으며 같은 입력에 같은 결과를 내기 쉽다. 반면 표현의 앞뒤 맥락이나 풍자·비유·사건 연결을 이해하는 데 한계가 있다.

LLM 분석은 맥락 이해에 유리하지만 비용·지연·응답 변동성이 있고, STT/OCR이 잘못 읽은 문장을 그대로 믿을 위험이 있다. 따라서 현재 구조는 다음처럼 역할을 나눈다.

```text
룰 기반: 확실한 후보를 빠르게 수집
       +
LLM 기반: 후보의 의도·맥락·심각도를 보완
       +
외부 근거: 사건·최신성에 대한 참고자료 제공
       ↓
검토용 리포트
```

리포트의 `finding`은 확정 판결이 아니라 “이 시점을 확인해볼 필요가 있다”는 후보이다. 근거가 부족하거나 분석 자체가 실행되지 않은 경우에는 `coverage`와 `warnings`로 구분해서 표시해야 한다.

## 검토 이벤트의 목표 구조

문장 하나를 곧바로 `논란`으로 저장하지 않고, 다음 단계의 이벤트로 저장하는 방향이 적합하다.

```text
Surface Signal
  ↓
Context Interpretation
  ↓
Risk Mechanism
  ↓
Final Review Decision
```

예시는 다음과 같다.

```json
{
  "startTime": 193.2,
  "endTime": 201.8,
  "surfaceSignals": ["PAST_EVENT_REFERENCE"],
  "contextInterpretations": ["DIRECT_REFERENCE_TO_SUBJECT"],
  "contentLabels": ["PAST_CONTROVERSY_REFERENCE"],
  "riskMechanisms": ["RESURFACING_PRIOR_CONTROVERSY", "SECONDARY_HARM"],
  "decision": "REVIEW_REQUIRED",
  "evidence": "과거 논란을 당사자에게 다시 설명하도록 요구하는 장면"
}
```

위 JSON은 현재 DB 스키마에 그대로 적용된 계약이 아니라, 향후 분석 결과를 확장할 때의 목표 형태다.

### Content Label과 Risk Mechanism

`Content Label`은 발언이나 행동이 무엇을 하고 있는지 나타내고, `Risk Mechanism`은 왜 게시 후 문제가 될 수 있는지를 나타낸다.

| Content Label 예시 | Risk Mechanism 예시 |
|---|---|
| `PAST_CONTROVERSY_REFERENCE` | `RESURFACING_PRIOR_CONTROVERSY` |
| `PRIVATE_MATTER` | `PRIVACY_INTRUSION` |
| `RUMOR_REPETITION` | `RUMOR_AMPLIFICATION` |
| `COMMUNITY_REFERENCE` | `COMMUNITY_ASSOCIATION_RISK` |
| `MOCKERY` | `HUMILIATION` |
| `AGGRESSIVE_BEHAVIOR` | `PHYSICAL_INAPPROPRIATENESS` |
| `PERSONAL_QUESTION` | `POWER_IMBALANCE`, `SECONDARY_HARM` |

이렇게 분리하면 같은 발언이라도 실제 위험 원인이 무엇인지 설명할 수 있고, 사용자에게 단순한 금지어 목록보다 설득력 있는 근거를 제공할 수 있다.

## 5. 비용과 처리량을 제한하는 현재 방식

- 기본 OpenAI 모델은 설정으로 교체할 수 있고, 데모에서는 비교적 저렴한 모델을 우선 사용한다.
- 영상 최대 길이와 OCR 최대 프레임 수를 환경변수로 제한한다.
- OCR 프레임은 일정 간격으로 추출하며, 긴 영상에서는 최대 프레임 수를 넘지 않도록 간격을 늘린다.
- OpenAI 호출 사이에 제한을 두고, 외부 API의 `Retry-After` 안내를 반영한다.
- 업로드·등록·재시도 API에는 IP 기준 요청 제한을 적용했다.
- Python OCR이 실패해도 STT 분석까지 전체 작업이 실패하지 않도록 단계별 실패를 분리한다.

## 6. 현재 품질상의 한계

1. STT는 발음, 고유명사, 은어를 잘못 인식할 수 있다. 자막이 없는 경우에도 음성 STT로 발언 검토를 수행하지만, STT가 놓친 표현은 후속 프롬프트만으로 복구할 수 없다.
2. OCR은 글꼴·배경·움직임에 따라 자막을 누락하거나 비슷한 글자로 읽을 수 있다.
3. 영상에 실제로 말하지 않은 편집 자막과 화면 속 일반 텍스트가 아직 완벽하게 분리되지 않는다.
4. 은어 목록을 늘리는 것만으로는 부족하며, 표현별로 “어떤 맥락에서 위험한가”를 함께 관리해야 한다.
5. 뉴스 검색 결과가 없거나 최신 사건인 경우, `finding 없음`과 `근거를 찾지 못함`을 혼동하면 안 된다.
6. 현재 데이터셋과 정량 평가셋이 작아 재현율·정밀도를 충분히 비교하기 어렵다.

### 구현상 특히 주의할 지점

1. **점수는 확률이 아니다.** 현재 `score`는 모델의 실제 확률이 아니라 분석기와 Fusion 로직이 계산한 확인 우선순위에 가깝다. `0.8`을 “80% 확률로 논란”이라고 설명하면 안 된다.
2. **애매한 결과가 영속 검수 이력으로 저장되지 않는다.** 공통 텍스트 검토에는 `UNCERTAIN`이 구현돼 있으나 공개 리포트는 보류를 별도 카드로 저장하지 않고 coverage 안내에 반영한다. 사전 `AMBIGUOUS` 처리와 공통 검토의 보류 계약도 동일하지 않다. 로컬 임시 진단을 사용자별 영구 이력으로 오해하지 않는다.
3. **후보 한도는 일부 구간을 확인하지 못하게 한다.** 맥락 사전은 최대 24개를 시간대별로 고르고, 초과 수를 `PARTIAL` 경고로 기록한다. STT·OCR LLM 분석도 윈도우 단위 호출이며 각 호출 실패는 coverage로 확인해야 한다.
4. **룰 매칭은 문맥보다 빠르다.** 현재 일부 룰은 문자열 포함 여부를 먼저 보기 때문에 인용·부정·자기 경험·일반 설명도 후보가 될 수 있다. 확실한 비하 표현과 일반적인 민감 주제 신호를 같은 방식으로 다루면 오탐률이 높아진다.
5. **뉴스 검색은 근거의 품질이 일정하지 않다.** 검색 결과가 최신이거나 원출처라는 보장이 없으며, 검색 결과가 없다는 사실도 안전하다는 근거가 아니다. 기사 발행일·출처 유형·주장과의 직접 관련성을 별도로 기록해야 한다.
6. **교차 검증이 항상 독립 근거는 아니다.** 같은 발언이 화면 자막에 그대로 반복되면 STT와 OCR 양쪽에서 잡힐 수 있다. 가까운 시점의 호환되는 후보는 병합하되, 출처 수나 중복 수만으로 점수를 올리지 않는다.
7. **프롬프트 버전과 분석기 버전이 결과에 남지 않는다.** 같은 영상을 다시 분석했을 때 모델·프롬프트·사전이 달라진 것인지 결과가 달라진 것인지 비교하기 어렵다.

## 7. 품질을 높이는 방법

멘토링에서 제안된 방향을 현재 서비스에 적용하면 다음 순서가 적합하다.

1. 실제 영상에서 탐지 후보를 모아 `정탐`, `오탐`, `미탐`, `판단 불가`로 라벨링한다.
2. 은어·논란 표현은 단어 목록이 아니라 예문, 위험 맥락, 예외 맥락과 함께 저장한다.
3. 같은 영상에 대해 STT/OCR 원문, 분석기 결과, 최종 사용자 피드백을 연결한다.
4. 모델을 바꾸기 전에 영상별 분석시간, 호출 횟수, 비용, 정밀도·재현율을 비교한다.
5. 강한 모델은 모든 영상에 적용하지 않고, 룰과 저비용 모델이 판단하기 어려운 후보에만 실험적으로 적용한다.
6. 같은 영상 재분석 시 재사용할 수 있는 결과와 다시 계산해야 하는 결과를 분리한다.

### Hard Negative를 반드시 함께 만든다

맥락 의존 표현의 논란 사례만 모으면 모델이 다음과 같은 잘못된 규칙을 배울 수 있다.

```text
특정 표현 발견 = 위험
```

따라서 다음 사례를 함께 수집해야 한다.

- 자연스러운 지역 방언
- 다른 사람의 발언을 인용하는 장면
- 표현의 의미를 설명하는 교육적 장면
- 과거 사건을 객관적으로 설명하는 장면
- 밈·패러디를 비판적으로 소개하는 장면

초기에는 Positive 사례 하나당 Hard Negative를 2~3개 정도 확보하는 것을 실험 기준으로 삼을 수 있다. 실제 비율은 평가셋의 결과를 보며 조정한다.

### 대화 Window를 기준으로 판단한다

현재 STT 세그먼트의 앞뒤 문장을 연결해 분석하는 방향을 유지한다. 목표 데이터 구조에는 발화자, 시작·종료 시간, 현재 발언, 이전 발언, 이후 발언이 포함되어야 한다.

문장 단위 분석만으로는 인용인지, 질문인지, 당사자에게 직접 요구하는 말인지 구분하기 어렵다. 발화자 정보가 없는 영상에서는 이를 추정하지 말고 `UNCERTAIN` 또는 검토 후보로 남긴다.

## 8. AI 로직 개선 우선순위

### 1순위: 결과 의미와 평가 기준 고정

모델을 더 좋은 것으로 바꾸기 전에 결과의 의미부터 고정한다.

```text
Signal 발견
  ↓
Context 분석
  ↓
Risk Mechanism 추출
  ↓
검토 결정
  ├─ PASS
  ├─ REVIEW_REQUIRED
  └─ UNCERTAIN
```

현재 DB의 `score`는 이 결정과 분리해 “화면에 먼저 보여줄 우선순위”로 정의하는 것이 좋다.

| 필드 | 의미 |
|---|---|
| `decision` | 사람이 확인해야 하는지에 대한 결과 |
| `confidence` | 모델이 자신의 해석을 얼마나 확신하는지 |
| `priority` | 여러 후보 중 사용자에게 먼저 보여줄 순서 |
| `evidence` | 판단에 사용한 발언·화면·외부 자료 |
| `coverage` | 실제로 분석된 입력 범위와 빠진 단계 |

### 2순위: Hard Negative 기반 회귀 테스트

다음 사례를 고정 테스트셋으로 만들고 변경 때마다 비교한다.

- 자연스러운 사투리와 일상 표현
- 단순 인용·설명·뉴스 전달
- 자기 자신을 대상으로 한 표현
- 일반적인 정치·사회 주제 언급
- OCR이 깨진 자막
- 같은 장면을 STT와 OCR이 동시에 읽은 사례
- 실제로 검토가 필요한 과거 논란·루머·개인정보 사례

각 사례에는 `정상`, `검토 필요`, `판단 불가`를 사람이 라벨링한다. 모델이 후보를 많이 내는 것보다 정상 사례를 불필요하게 올리지 않는지 먼저 확인해야 한다.

### 3순위: 후보 수와 비용을 단계적으로 제한

현재 구조를 다음처럼 다듬는 것이 좋다.

```text
전체 STT/OCR
  ├─ 모든 구간에 저비용 맥락 검토를 유지
  └─ 룰·사전으로 후보 구간을 추가 수집
          ↓
      중복 제거·우선순위화
          ↓ 확인이 더 필요한 구간만
      뉴스 검색·추가 LLM 검토
          ↓
      최종 검토 이벤트
```

룰에 걸린 구간만 LLM으로 보내는 방식은 사전에 없는 표현이나 어휘만으로 드러나지 않는 위험을 놓칠 수 있다. 따라서 전체 대본을 살피는 저비용 검토와 룰 기반 후보 수집을 함께 유지하고, 뉴스 검색이나 더 비싼 추가 검토를 우선순위가 높은 후보에 한정한다. 같은 입력의 결과를 재사용할 때는 영상·STT/OCR 결과 해시와 분석기·프롬프트 버전을 함께 확인해야 한다.

### 4순위: 분석 범위와 실패를 사용자에게 공개

다음 상황은 `finding 없음`과 구분해야 한다.

- OpenAI 키가 없어 LLM 분석을 실행하지 못함
- OCR 모델이 없어 화면 분석을 실행하지 못함
- 외부 뉴스 검색이 실패함
- 최대 후보 수를 넘어 일부 후보를 보지 않음
- OCR 결과가 비어 있어 화면을 제대로 읽었는지 알 수 없음

사용자 화면에는 최소한 다음을 보여주는 것이 좋다.

```text
STT: 완료
OCR: 완료 / 텍스트 없음 / 실패
맥락 분석: 완료 / 일부 실패
뉴스 확인: 실행 안 함 / 검색 결과 없음 / 완료
```

## 9. 분석기별 개선 방향

| 분석기 | 현재 한계 | 다음 개선 |
|---|---|---|
| `SubtitleAnalyzer` | 문자열 포함 기반 오탐 | 단어 경계·부정·인용·반복성 고려 |
| `ContextLexiconAnalyzer` | 사전·힌트 품질에 의존 | Hard Negative와 표현별 예외 맥락 관리 |
| `SpeechReviewAnalyzer` | 20줄 고정 Window, 호출 수 증가 | 시간 기반 Window·후보 우선 호출·프롬프트 버전 관리 |
| `ScreenTextAnalyzer` | 편집 자막과 간판·로고 구분 한계 | 영역·지속시간·반복 패턴으로 편집 자막 분리 |
| `ScreenTextReviewAnalyzer` | OCR 오류를 LLM이 추정 | OCR 신뢰도와 원본 프레임을 함께 사용 |
| `ContextCheckAnalyzer` | 뉴스 품질·최신성 편차 | 출처 유형·발행일·검색 기준일 기록 |
| `EntityCheckAnalyzer` | 검색 결과와 주장 연결이 어려울 수 있음 | 주장 단위 근거·반대 근거·원출처 분리 |
| `FindingFusionService` | 같은 신호의 교차 검증을 과대평가 가능 | 동일 원문·동일 프레임 여부를 확인한 뒤 보정 |

## 10. 평가 지표와 출시 기준

분석기 전체를 하나의 정확도로 평가하지 말고, 유형별로 따로 측정한다.

| 지표 | 의미 |
|---|---|
| Precision | 표시한 후보 중 실제로 검토할 가치가 있는 비율 |
| Recall | 사람이 라벨링한 중요 후보를 찾아낸 비율 |
| False Positive Rate | 정상 장면을 불필요하게 올린 비율 |
| False Negative Rate | 중요한 장면을 놓친 비율 |
| Review Required Rate | 영상당 사람 검토가 필요한 후보 비율 |
| 평균 Alert 수 | 영상 한 편에서 표시되는 최종 후보 개수 |
| Human-AI Agreement | 사람 검수자와 AI 판단의 일치율 |
| 영상당 비용 | STT·LLM·뉴스 검색에 사용한 실제 비용 |

데모 단계에서는 Recall을 무리하게 높이기보다, 대표 영상에서 사용자가 감당할 수 있는 Alert 수와 근거의 품질을 우선 확인한다. 운영 전에는 최소한 다음 질문에 답할 수 있어야 한다.

- 30분 영상에서 최종 후보가 평균 몇 개인가?
- 그중 사람이 “검토할 가치가 있다”고 판단한 비율은 얼마인가?
- 정상적인 사투리·인용·설명 장면의 오탐률은 얼마인가?
- 분석 실패나 미실행 단계가 사용자에게 명확히 표시되는가?
- 같은 영상을 재분석했을 때 왜 결과가 달라졌는지 설명할 수 있는가?

## 11. 앞으로 고려할 입력 확장

- 사용자가 가진 `.srt`, `.vtt` 자막 파일을 직접 받는 기능
- 편집 자막과 일반 화면 텍스트를 분리하는 OCR 영역·시간 연속성 규칙
- 영상 해시와 STT/OCR 결과 해시를 활용한 중복 분석 방지
- 분석기별 버전과 프롬프트 버전을 저장해 결과 재현
- 사용자 피드백을 다음 룰·평가 데이터셋으로 연결

위 항목은 품질 향상 방향이며, 현재 `minwook` 브랜치에 모두 구현된 기능은 아니다.

## 12. 외부 근거와 유사 사례 검색

### Dynamic Social Context

사회적 의미는 새로운 사건과 함께 바뀔 수 있으므로, 고정된 프롬프트만으로 현재 맥락을 모두 판단한다고 가정하지 않는다. 다만 모든 문장을 검색하면 비용과 지연이 커지므로 다음처럼 후보 이후에 제한적으로 검색한다.

```text
Signal 후보
  ↓
인물·사건·표현 Entity 추출
  ↓
정말 필요한 후보만 뉴스·공개 자료 검색
  ↓
출처가 있는 Context를 LLM에 제공
```

뉴스나 검색 결과는 판단의 근거 후보이지 사실 확정 자체가 아니다. 출처, 기준일, 관련성을 함께 저장하고 검색 결과가 없을 때는 `근거 없음`과 `위험 없음`을 구분한다.

### Controversy Dataset과 유사 사례 검색

검증된 이벤트 데이터가 충분히 쌓이면 문장 전체를 매번 프롬프트에 넣는 대신, 현재 후보와 유사한 Positive·Hard Negative 사례를 찾아 LLM 판단에 참고자료로 제공할 수 있다. Vector DB와 Embedding은 이 단계에서 검토할 기술이며, 현재 프로젝트에 구현되어 있지는 않다.

## 13. 멀티모달 분석 확장

현재는 Python에서 STT와 OCR을 만들고 Spring Boot에서 텍스트·맥락 분석을 수행한다. 이후에는 텍스트 후보의 타임스탬프를 이용해 필요한 구간만 영상으로 확대 분석하는 방식이 적합하다.

```text
STT/OCR 후보
  ↓
해당 시점 전후 짧은 구간 선택
  ↓
프레임을 더 촘촘하게 추출
  ↓
행동·제스처·상황 확인
```

말이 없어도 발생하는 시각 사건은 STT/OCR 후보만으로 찾을 수 없다. 후속 오프라인 실험에서는 전체 영상의 저비용 시각 탐색을 독립적으로 수행하고, 텍스트 또는 시각 후보 주변에서만 고비용 상세 확인을 비교한다. 초기 행동 범위·샘플링·가림·짧은 사건의 누락 평가는 [행동·포즈·긴 영상 계획](행동-포즈-데이터셋-및-긴영상-적용-계획.md)을 따른다. 현재 `pose`는 미구현이며 이 문단은 운영 기능이 아니다.

## 14. 사람 검토와 피드백

사용자는 각 후보에 대해 다음 피드백을 남길 수 있어야 한다.

- 정확한 탐지
- 문제 없음
- 카테고리 수정
- 위험 수준 수정
- AI가 놓친 구간 추가

이 피드백은 즉시 모델 학습에 넣는 것이 아니라, 검수된 데이터셋으로 분류·검토한 뒤 룰, 프롬프트, 평가셋 개선에 사용한다. 이를 통해 `AI 예측 → 사람 검토 → 검증 데이터 → 품질 개선`의 순환을 만든다.
