# OoPs?! AI 분석 로직

> 기준 브랜치: `minwook` · 기준일: 2026-10-06

OoPs?!의 목적은 영상을 자동으로 삭제하거나 최종 판결하는 것이 아니라, 영상 속 발언·화면 문구·맥락에서 검토가 필요한 지점을 시간 정보와 근거를 붙여 보여주는 것이다.

## 1. 입력 데이터

| 입력 | 생성 주체 | 활용 |
|---|---|---|
| 영상 메타데이터 | Spring Boot / FFmpeg 계열 처리 | 길이 제한, 타임라인 기준 |
| STT 대본 | Python → Whisper | 발언 내용과 발언 시점 분석 |
| 화면 텍스트 | Python → PaddleOCR | 편집 자막·화면 문구 분석 |
| 장르 | 사용자 입력 또는 장르 감지 | 장르별 판단 기준 보정 |
| 뉴스·검색 결과 | Google News RSS / Naver | 특정 사건·인물·논란의 최신성 확인 |

현재는 사용자가 별도의 자막 파일을 업로드해 분석하는 기능은 구현되어 있지 않다. 영상에서 직접 얻은 STT와 OCR이 기본 입력이다.

## 2. 전체 분석 파이프라인

```text
영상
  │
  ├─ 길이·파일 검증
  │
  ├─ Python 전처리
  │    ├─ 오디오 추출 → Whisper STT → 타임스탬프 대본
  │    └─ 프레임 추출 → PaddleOCR → 화면 텍스트
  │
  ├─ Spring Boot 1차 분석
  │    ├─ 확실한 표현·위험 키워드 룰
  │    ├─ 은어·맥락 사전
  │    ├─ 자막과 화면 텍스트 분석
  │    └─ 장르·수익화 위험 분석
  │
  ├─ 선택적 외부 분석
  │    ├─ OpenAI 발언 검토
  │    ├─ OpenAI 화면 텍스트 검토
  │    ├─ 맥락·사건 확인
  │    └─ 뉴스 근거 검색
  │
  ├─ FindingFusionService
  │    └─ 중복 제거·우선순위·심각도 조정
  │
  └─ 리포트·타임라인·분석 범위·경고 저장
```

## 3. 분석기 역할

| 구분 | 현재 역할 |
|---|---|
| `SubtitleAnalyzer` | STT 문장에서 룰 기반 위험 표현을 찾음 |
| `ScreenTextAnalyzer` | OCR 화면 텍스트에서 위험 표현을 찾음 |
| `CommunitySlangRules` | 커뮤니티 은어·표현 변형을 빠르게 탐지 |
| `ContextLexiconAnalyzer` | 단어 하나만 보지 않고 앞뒤 맥락과 함께 판단 |
| `SpeechReviewAnalyzer` | STT 발언을 OpenAI에 보내 의도와 위험도를 검토 |
| `ScreenTextReviewAnalyzer` | OCR 오인식을 고려해 화면 문구를 OpenAI로 검토 |
| `ContextCheckAnalyzer` | 사건·논란의 시점과 맥락을 외부 자료와 비교 |
| `EntityCheckAnalyzer` | 인물·사건 등 고유명사와 뉴스 근거를 확인 |
| `MonetizationRiskAnalyzer` | 광고·수익화 관점에서 검토가 필요한 표현을 표시 |
| `CaptionMismatchAnalyzer` | 발언과 화면 자막의 불일치 가능성을 표시 |
| `FindingFusionService` | 여러 분석기의 결과를 하나의 리포트로 통합 |

분석기 활성화 여부는 `application.yml`의 `oops.analysis.enabled-analyzers`에서 조절한다. OpenAI나 뉴스 키가 없으면 관련 분석기는 건너뛰고, 가능한 룰 기반 결과를 남기는 방식이다.

## 4. 룰 기반 분석과 LLM 분석을 함께 쓰는 이유

룰 기반 분석은 빠르고 비용이 없으며 같은 입력에 같은 결과를 내기 쉽다. 반면 표현의 앞뒤 맥락이나 풍자·비유·사건 연결을 이해하는 데 한계가 있다.

LLM 분석은 맥락 이해에 유리하지만 비용·지연·응답 변동성이 있고, STT/OCR이 잘못 읽은 문장을 그대로 믿을 위험이 있다. 따라서 현재 구조는 다음처럼 역할을 나눈다.

```text
룰 기반: 확실한 후보를 빠르게 수집
       +
LLM 기반: 후보의 의도·맥락·심각도를 보완
       +
외부 근거: 사건·최신성에 대한 참고자료 제공
       ↓
검토용 리포트
```

리포트의 `finding`은 확정 판결이 아니라 “이 시점을 확인해볼 필요가 있다”는 후보이다. 근거가 부족하거나 분석 자체가 실행되지 않은 경우에는 `coverage`와 `warnings`로 구분해서 표시해야 한다.

## 5. 비용과 처리량을 제한하는 현재 방식

- 기본 OpenAI 모델은 설정으로 교체할 수 있고, 데모에서는 비교적 저렴한 모델을 우선 사용한다.
- 영상 최대 길이와 OCR 최대 프레임 수를 환경변수로 제한한다.
- OCR 프레임은 일정 간격으로 추출하며, 긴 영상에서는 최대 프레임 수를 넘지 않도록 간격을 늘린다.
- OpenAI 호출 사이에 제한을 두고, 외부 API의 `Retry-After` 안내를 반영한다.
- 업로드·등록·재시도 API에는 IP 기준 요청 제한을 적용했다.
- Python OCR이 실패해도 STT 분석까지 전체 작업이 실패하지 않도록 단계별 실패를 분리한다.

## 6. 현재 품질상의 한계

1. STT는 발음, 고유명사, 은어를 잘못 인식할 수 있다.
2. OCR은 글꼴·배경·움직임에 따라 자막을 누락하거나 비슷한 글자로 읽을 수 있다.
3. 영상에 실제로 말하지 않은 편집 자막과 화면 속 일반 텍스트가 아직 완벽하게 분리되지 않는다.
4. 은어 목록을 늘리는 것만으로는 부족하며, 표현별로 “어떤 맥락에서 위험한가”를 함께 관리해야 한다.
5. 뉴스 검색 결과가 없거나 최신 사건인 경우, `finding 없음`과 `근거를 찾지 못함`을 혼동하면 안 된다.
6. 현재 데이터셋과 정량 평가셋이 작아 재현율·정밀도를 충분히 비교하기 어렵다.

## 7. 품질을 높이는 방법

멘토링에서 제안된 방향을 현재 서비스에 적용하면 다음 순서가 적합하다.

1. 실제 영상에서 탐지 후보를 모아 `정탐`, `오탐`, `미탐`, `판단 불가`로 라벨링한다.
2. 은어·논란 표현은 단어 목록이 아니라 예문, 위험 맥락, 예외 맥락과 함께 저장한다.
3. 같은 영상에 대해 STT/OCR 원문, 분석기 결과, 최종 사용자 피드백을 연결한다.
4. 모델을 바꾸기 전에 영상별 분석시간, 호출 횟수, 비용, 정밀도·재현율을 비교한다.
5. 강한 모델은 모든 영상에 적용하지 않고, 룰과 저비용 모델이 판단하기 어려운 후보에만 실험적으로 적용한다.
6. 같은 영상 재분석 시 재사용할 수 있는 결과와 다시 계산해야 하는 결과를 분리한다.

## 8. 앞으로 고려할 입력 확장

- 사용자가 가진 `.srt`, `.vtt` 자막 파일을 직접 받는 기능
- 편집 자막과 일반 화면 텍스트를 분리하는 OCR 영역·시간 연속성 규칙
- 영상 해시와 STT/OCR 결과 해시를 활용한 중복 분석 방지
- 분석기별 버전과 프롬프트 버전을 저장해 결과 재현
- 사용자 피드백을 다음 룰·평가 데이터셋으로 연결

위 항목은 품질 향상 방향이며, 현재 `minwook` 브랜치에 모두 구현된 기능은 아니다.
