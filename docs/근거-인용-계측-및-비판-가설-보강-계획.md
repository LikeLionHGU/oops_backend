당시 EVIDENCE_BUDGET_EXCEEDED는 유효 형태의 9~12개 인용에만 부여됐다.

## 이번 구현: 검증 응답의 고정 개수 상한 해제

```yaml
oops:
  analysis:
    candidate-review-evidence-limit: ${CANDIDATE_REVIEW_EVIDENCE_LIMIT:0}
```

0은 발언 후보 검증 응답의 고정 8개/12개 제한을 해제한다. 허용된 현재 원문 구간과
PRIMARY/TARGET/CONTEXT 역할 조합의 범위에서 검증한다. 따라서 자연 상한은 제공된 구간 수의
3배이고 동일 구간·역할의 중복은 허용되지 않는다. 역할이 다르면 같은 줄을 두 번 쓸 수 있다.
원문 ID·허용 창·역할·원문 일치·PRIMARY·대상 연결·반대 해석 검증은 유지한다.
프롬프트도 해당 설정에 맞춰 고정 8개 요구를 해제한다.

8로 설정하면 이전 검증 인용 상한을 다시 사용할 수 있다. 과거 계약 비교용 run/validate
오버로드는 명시적으로 기존 8개 경로를 유지하며 Spring의 실제 발언 분석은 위 설정을 전달한다.
탐색 제안의 8개 제한, 비후보 텍스트 분석의 12개 계약, 후보/문맥/요청 크기 상한은 변경하지 않았다.
이 작업은 검증 단계의 오류를 관측하려는 변경이며 전체 탐지 정확도 개선을 입증하지 않는다.

새 분석 후 진단에서 확인한다:

```sh
curl -s "http://127.0.0.1:8080/api/v1/videos/${VIDEO_ID}/analysis/diagnostics" \
  | jq '.data.snapshot.analyzers[] | select(.evaluatorId=="speech-review") | .candidatePipeline.evidenceCounts'
```

각 항목에는 candidateId, attempt(INITIAL/REPAIR), evidenceCount(응답 객체 수),
uniqueSegments(고유 원문 ID), uniqueSegmentRoles(고유 ID/역할), duplicateRoleEntries,
invalidEntries, configuredLimit, validationFailure를 남긴다. 원문이나 API 키는 계측 필드에
저장하지 않는다. 응답 부재의 count는 null이며 0개 응답과 구별한다. 과거 진단의 evidenceCounts는
비어 있는 목록으로 읽으며 숫자를 사후 생성하지 않는다. 설정은 Spring 재시작 뒤 새 분석에 적용된다.

이번에는 모델 호출 없이 가상 응답으로 13개 허용, 중복 거절, 최초/복구 개수 보존과 과거 JSON
호환을 검증했다. 54번의 모델 원응답을 재실행·복원한 시험은 아니다.

## criticismHypotheses의 목적과 입력 형식 — 아직 미구현

각 사건의 발언 흐름에 실제 표현과 비판 해석을 따로 저장한다. 댓글은 선택 보강이며 댓글이 없어도
알려진 사건에 대한 해석을 기록할 수 있다. 현재 compile 경로는 댓글에 연결된 reasonHypotheses 및
audienceReception의 이유만 criticismHypotheses로 내보내므로 기사/개발 기준의 이유를 위한 별도 입력이
필요하다. 기존 reactionId 필드에 가짜 댓글 ID를 만들어 넣지 않는다.

계획은 incident-2의 statements에 선택 필드 criticismHypotheses를 추가하고 객체로 보관하는 것이다.
기존 legacyCard.controversy.reasonHypotheses(댓글 연결용)는 유지한다. 입력 스키마·마이그레이션·
추가 도구·컴파일러를 함께 수정해야 하며 저장만 하고 빌드가 무시하는 필드를 만들지 않는다.

아래는 형식 설계 예시이며 검수된 실제 데이터나 출처 확인 완료 표시가 아니다.

```json
{
  "id": "hypothesis-local-options",
  "text": "매장 부재와 대체 음식을 연결하며 지역 생활의 선택지를 하찮게 취급한다는 비판 해석이다.",
  "basis": "USER_REVIEWED_DEVELOPMENT_EXPECTATION",
  "status": "DRAFT",
  "evidenceRefs": [],
  "sourceRefs": [],
  "supportingReactionIds": [],
  "requiredCurrentEvidence": [
    "장소·생활 선택지를 가리키는 실제 원문",
    "그 선택지를 낮추는 평가·비교와 앞뒤 연결"
  ],
  "normalContrast": [
    "가게가 없어 집에서 대체 음식을 만든다는 설명만으로 경고하지 않는다."
  ],
  "missingContext": ["화자·억양·장면은 별도 근거 없이는 확인되지 않는다."]
}
```

evidenceRefs는 해당 발언의 실제 segmentId 또는 reportedQuoteId를 참조한다. sourceRefs는
sourceId와 근거 위치·자료 종류를 참조하고 원문 확인/보도 인용/해석을 구분한다. 기사/댓글 기반
가설은 연결 출처가 있어야 하며, 개발 기대 기준은 USER_REVIEWED_DEVELOPMENT_EXPECTATION으로
표시해 실제 여론이나 원음 확인 자료처럼 승격하지 않는다. supportingReactionIds는 존재하는
댓글만 참조하며 없으면 빈 배열이다. 상태는 사람 의미 검수와 별개로 기록한다.

## 런타임 전달 방식

사건의 구조화된 객체는 원장에 보존하고 분석 요청에는 짧은 문자열 배열로 투영한다.
현재 Java context.criticismHypotheses 계약(최대 16개, 각 350코드포인트)을 유지한다.
가설 본문 + 필수 연결 + 정상 대조를 350자 안에 명시적으로 작성하고 초과는 빌드에서 거절한다.
잘라내거나 근거 없는 모델 요약으로 내용을 축약하지 않는다. 출처 ID와 원문은 원장에 남긴다.
별도 compactReferenceText 필드 또는 결정적인 문구 조립 규칙을 정해 같은 입력이 같은 출력을
만들도록 한다. 댓글 이유는 직접 매핑된 CONTENT 반응만 합치고 중복 문구를 제거한다.
반론·사건 전체 감정·사후 대응을 영상 내용의 직접 비판 근거로 바꾸지 않는다.

예시(적용을 위한 초안):

- B: "매장 부재를 주민의 생활 선택지와 연결해 대체 음식을 열등하게 취급한다는 비판 가설. 단순 매장 부재·대체 메뉴 설명과 구별한다. 현재 원문에 낮추는 평가와 연결 근거가 필요하다."
- C: "메뉴에 의미가 없다는 평가와 주는 대로 먹어야 한다는 말을 연결해 식당의 메뉴·선택을 하찮게 취급한다는 비판 가설. 특색·가격 불만이나 단일 메뉴 안내만으로 경고하지 않는다."
- D: "음식 맛을 사람의 살을 뜯는 구체적 신체 훼손 이미지에 빗댄 표현 자체의 검토 가설. 할머니 맛이라는 추억 표현만으로는 적용하지 않고 실제 폭력·노인 전체 공격으로 확대하지 않는다."

가설은 새 영상에서 같은 결론을 강제하지 않는다. 현재 영상의 실제 원문이 필수 연결을
뒷받침하는지 확인하고 제공 자료가 부족하면 보류한다. 저장 형식을 B 전용 판정 규칙으로 만들지 않는다.

## 적용 순서와 비교

1. 먼저 이번 인용 계측 버전으로 새 영상 ID를 확인해 개수 제한 해제 효과를 기록한다.
2. 사건 원장에서 B/C/D를 독립 발언 흐름으로 나누고 기존 승인된 개발 기대 기준을 명시한다.
3. 비판 가설 입력 스키마와 컴파일 투영을 구현하고 원본/해석/정상 경계를 검수한다.
4. build --write/--verify로 반영한 뒤 진단의 실제 선택 ID와 요청에 포함된 가설을 확인한다.
5. 같은 저장 STT·후보와 정상 대조로 가설 보강 전후를 비교한다. 인용 제한 변화와 사전 보강을
   동시에 바꾼 한 번의 결과로 각각의 효과를 주장하지 않는다.

전체 영상/별도 정상 대조의 범용 평가와 v1 짜깁기 클립의 개발 재현을 구분한다.
다음 모델 시험은 새 실행이며 별도 비용이 든다. 이번 변경은 서버 재시작·업로드·유료 호출을
자동 실행하지 않았고 현재 ID 54 리포트도 변경하지 않았다.
