## 서버 구성

| 구성 | 담당 |
|---|---|
| Spring Boot 4 / Java 17 · 8080 | 업로드, 작업 상태, 분석 순서, OpenAI 판단 요청, 근거 검증, DB·리포트 |
| Python FastAPI · 8000 | 영상 준비, Groq STT, OCR, 선택 구간 프레임 추출 |
| Groq Whisper Large v3 | 음성을 구간 시작·끝 시간이 있는 대본으로 전사 |
| OpenAI GPT-6 Luna | 발언·화면 문구의 후보 탐색과 검증 |
| PaddleOCR | 로컬 프레임의 글자와 영역 추출 |

`oops-backend/`와 `oops-analysis/`는 별도 프로세스다. 같은 머신에서 실행할 때 Spring의 `./uploads`와 Python의 `../oops-backend/uploads`가 같은 실제 저장소를 가리켜야 한다. 로컬 DB는 H2 파일 모드이고 재시작 후에도 기록이 남는다.

## 현재 분석 흐름

```text
영상 파일 / YouTube URL → 작업 접수 → Python STT ──┐
외부 스크립트 / 저장 전사 재사용 → 전사 스냅샷 ─────┤
                                                    ↓
시간순 읽기 창 → 관련 사례 검색 → AI 후보 탐색
→ 후보별 원문·문맥과 참고 재선택 → AI 검증 → 서버 근거·계약 검사
→ 검토 대상 finding → 보수적 중복 병합 → 리포트 저장 → 사람 검수
```

기본 후보 엔진은 `2026-10-23-candidate-repair-contract-48`이다. 설정된 분석기는 순차 실행하며 여러 페르소나가 병렬 투표하는 구조는 아니다. 전체 OCR은 기본 OFF, 필요한 후보의 프레임 확인은 별도 경로다. 스크립트·저장 전사 입력은 STT/OCR/프레임을 재호출하지 않는다.

`PASS`, 후보 미생성, 정보 부족, 계약 실패, 예산상 미평가는 구분한다. 사례집은 판단 참고이며 과거 라벨이 새 영상의 판정을 강제하지 않는다. 아래 날짜별 수치와 실험은 당시 조건의 기록이지 현재 버전의 성능 보장이 아니다. 최신 검증 상태는 아래 전용 절과 [문서 안내](docs/README.md)를 먼저 확인한다.

영상 등록 → 길이 확인 → STT → 표현 등장 목록 저장 → 맥락 사전 참고와 발언 후보 탐색 → 원문·대상·문맥 검증/필요 후보 장면 확인 → 병합 → 리포트와 사람의 검수 결정. 전체 OCR은 기본 미실행이며 `FULL_SCREEN_OCR_ENABLED=true` 서버 선택 시 기존 경로로 실행한다.

- STT는 기존 OpenAI Whisper와 같은 음성 추출·10분 분할·구간 타임스탬프 계약을 사용한다. 단어별 시간은 현재 요청하지 않는다.
- OCR에는 간판·메뉴판도 잡힐 수 있다. 편집 자막·배경 글자·불확실 영역을 구분하며 자막이 반드시 있다고 가정하지 않는다.
- 욕설·논쟁 표현의 등장은 별도 트랙이다. 적중만으로 맥락 경고를 확정하지 않는다.
- 가격·날짜 등 사실 대조와 최근 뉴스 검색은 기본 분석에서 제외했다. 기존 검색을 시험하는 서버 프로필은 `external-review`다.
- 일부 후보는 선택 프레임 검증을 사용할 수 있다. 전체 영상의 말투·표정·억양을 이해하는 기능이나 포즈 분석을 완료한 상태는 아니다.
- 경고 0개와 정상 통과는 다르다. 수행 범위·실패·미판정도 함께 확인한다.

## 로컬 실행

먼저 Java 17, Python 환경, `ffmpeg`·`ffprobe`를 준비한다. 아래 명령은 저장소 루트에서 시작한다. 이미 설정 파일이 있으면 예제 파일로 덮어쓰지 않는다.

### Python 분석 서버 — 터미널 1

최초 설치:

```bash
cd oops-analysis
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

처음에만 `.env.example`을 `.env`로 복사한 뒤 입력한다. 키는 저장소나 채팅에 올리지 않는다.

```env
GROQ_API_KEY=발급받은_Groq_키
STT_MODEL=whisper-large-v3
MEDIA_STORAGE_ROOT=../oops-backend/uploads
```

```bash
ANALYSIS_PROFILE=local python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

모델·키 설정은 Python 프로세스 재시작 후 반영된다. OpenAI STT로 되돌릴 때는 `STT_MODEL=whisper-1`과 Python용 `OPENAI_API_KEY`를 설정한다. 자동 제공자 fallback은 없다. OCR을 제외한 설치·Windows 안내는 [Python README](oops-analysis/README.md)를 따른다.

로컬 실행에서는 Spring `local` 프로필이 업로드 파일·요청·저장 검증의 용량 상한을 해제하고, Python `ANALYSIS_PROFILE=local`이 영상 길이 상한을 해제한다. 변경 후 두 서버를 재시작해야 한다. 비로컬 설정의 기본 상한은 500MiB·90분이며, 운영에 로컬 무제한 설정을 사용하지 않는다. 디스크·메모리·외부 API 한도, 처리 타임아웃과 OCR 프레임 예산은 유지되므로 긴 영상의 완전한 분석을 보장하지 않는다. 영상 길이에 따라 API 비용도 증가한다.

### Spring 백엔드 — 터미널 2

`oops-backend` 디렉터리에서 OpenAI 키를 환경변수 또는 `application-secret.yml`에 설정한다. Spring은 Python의 `.env`를 자동으로 읽지 않는다.

macOS zsh 예시:

```zsh
cd oops-backend
read -s "OPENAI_API_KEY?OpenAI API 키 입력: "
export OPENAI_API_KEY
echo
export JAVA_HOME=/opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk/Contents/Home
export PATH="$JAVA_HOME/bin:$PATH"
export FULL_SCREEN_OCR_ENABLED=false
bash ./gradlew bootRun --args='--spring.profiles.active=local --server.address=127.0.0.1'
```

Java 경로는 설치 환경에 맞춰 조정한다. 상세 설정은 [Spring README](oops-backend/README.md)를 참고한다. `bootRun`은 서버가 실행되는 동안 끝나지 않는 것이 정상이다.

```bash
curl http://127.0.0.1:8080/api/v1/videos/VIDEO_ID/transcript
```

새 모델은 기존 완료 리포트를 자동으로 바꾸지 않는다. 완료 영상으로 다시 비교하려면 새로 업로드한다. `analysis/retry`는 실패·취소 상태에서만 사용할 수 있다. 업로드는 전사와 분석 API 호출·비용을 발생시킨다.

## 사전과 데이터

검수 입력JSON 하나로 [사례 등록·보강 도구](docs/casebook/데이터셋-파일-관리.md#단일-검수-입력-도구--2026-10-24)를 사용할 수 있다. `python3 tools/casebook_intake.py 입력.json`은 쓰기 없는 계획이고,`--check-retrieval`은 무료 Java 검색 확인이다. 실제 적용은 검토한 planSha256을 지정한 `--apply`로만 가능하며 출처·승인·빌드·검색을 재검증한다. 정보 부족은 HOLD로 기록만 하고 사전에 넣지 않는다. 모델/API 호출·자동 학습은 없다.

| 파일 | 역할 |
|---|---|
| `datasets/controversy/guidelines/runtime.json` | 생성된 로컬 v7 실행 사전. 64개 참고·6개 공통 기준(10/25 승인5건 모두 반영,새 로더 재시작·유료 묶음 검증 대기) |
| `oops-backend/src/main/resources/context-lexicon.json` | 표현의 맥락 확인용 사전 |
| `oops-backend/src/main/resources/expression-dictionary.json` | 욕설·논쟁 표현의 별도 등장 목록 |

맥락 사전은 사건별 원장과 공통 정의에서 빌드한다. `runtime.json`을 직접 편집하지 않는다. 현재 예시 선택은 문자 검색 + v7 로컬 개념 조합 보완이며 기본 최대 3개다. [구조화 검색](docs/casebook/맥락사전-구조화검색-보완.md)은 별도 API 호출 없이 사적 신체 정보 질문·집단 전체 평가 참고를 회수한다. 의미 검색이나 논란 판정은 아니며 `STRUCTURED_CONTEXT_SEARCH_ENABLED=false`로 이전 검색을 재현한다. LLM 검색 키 분류·원문 관계 추가 기능은 별도로 기본 OFF다.

`datasets/**`는 Git 제외다. **코드를 pull하거나 빌드해도 비공개 사전이 자동 배포되지 않는다.** 실행 서버에 별도로 제공하고 Spring을 재시작해야 한다. [데이터셋 파일 관리](docs/casebook/데이터셋-파일-관리.md)와 [v7 승격 기록](docs/casebook/v7-기본사전-승격.md)을 따른다.

### 정본 데이터와 docs의 차이

현재 자산은 실제 논란 사건뿐 아니라 사람이 승인한 정상·검토 경계를 포함하는 **콘텐츠 검수 맥락 사례집**이다. 기존 사건 ID는 출처 추적을 위해 유지한다.

| 위치 | 역할 |
|---|---|
| `datasets/controversy/incidents/`, `context-units/` | 사건 원장·작성한 맥락 참조 단위 |
| `datasets/controversy/context-sources/`, `context-relations/` | 원문·출처·승인 연결 및 검색 관계 프로필 |
| `datasets/controversy/definitions/` | 공통 기준·빌드·검색 설정 |
| `datasets/controversy/guidelines/runtime.json` | 빌더가 생성하고 Spring이 로드하는 실제 분석 참고 |
| `docs/*보강*`, `docs/*분석결과*` 등 | 왜 추가했는지, 사용자가 무엇을 승인했는지, 무엇을 검증했는지 설명하는 변경·검수 기록 |

**docs는 실행 사전이나 데이터 정본이 아니며 AI가 docs 전체를 읽지 않는다.** 승인과 적용 경계를 사람이 추적하고 과거 결정을 반복하지 않기 위해 기록한다. 정본 JSON과 생성 사전이 실제 자산이고 문서는 설명이다. 문서만 수정해도 분석 사전이 갱신되는 것은 아니다. 원문·식별 정보·원시 응답의 정본은 Git 제외 데이터 영역에 보관하고, 문서에는 필요한 검수 근거와 연결만 남긴다.

정본 수정 후 저장소 루트에서 `python3 tools/build_incident_dataset.py --write`와 `--verify`로 생성·일치를 확인한다. runtime은 직접 편집하지 않는다. 빌드 후 Spring 재시작·로드 개수·해시 확인까지가 반영 절차다.

### 최신 확인 상태 — 2026-10-24

- 로컬 사전은57참고·6기준이다.125 검수 후 정상2개를 추가하고 기존 자랑 응수·동료 비유의 적용 조건을 보강했다. 기존 사건 원장32개는 유지하고,성씨·놀림의 정보 부족1개는 추가하지 않았다. [보강 근거·파일 해시](docs/reviews/팟캐스트-검수와-사례보강.md#최신-사례집-보강--57참고-빌드-2026-10-24)를 따른다.
- 최신 소개 경계 보강과 읽기 전용 카드 공유 근거 표시에서 Java 전체1,232개·관련 Python40개와27subtest를 통과했다. 사전은57개를 유지하며 소개1개만 내용이 바뀌었다. 최종 모델 판단 개선을 검증한 결과는 아니다.
- 후속125번은 새55참고 해시·관련6경계 회수를 확인한 저장 텍스트1회 재분석이다. 정상4흐름 중 소개는 후보 미생성·옷은PASS로 경고가 사라졌고,정자 수 응수·동료 비유 경고는 남았다. 검토2흐름은 유지되지만 개인 대상 해석·중복도 남아 전체 품질 개선은 미확인이다. [최신 비교](docs/reviews/팟캐스트-검수와-사례보강.md#최신-확인--125번-저장-텍스트-재분석-2026-10-24)를 따른다. 검색 성공은 최종 판정 개선이나 범용 정확도 입증이 아니다.
- 최신126번은57참고 해시·실제 선택을 확인한1회 재분석이다. 정자 수 응수·동료 비유·자격지심 경력 대화는PASS로 바뀌었고 옷PASS도 유지됐다. 이름 대목은카드없음(명시적 PASS 미확인),소개 경고는 재발했다. 총9→5카드·검토2흐름 탐지는 유지되지만 중복·개인 대상 해석·PARTIAL이 남는다. [상세 결과와 한계](docs/reviews/팟캐스트-검수와-사례보강.md#최신-실제-비교--126번57참고-2026-10-24)를 따른다.
- 스크립트 입력과 저장 전사 재사용은 원본을 보존하고 새 ID로 분석한다. [스크립트 입력](docs/guides/텍스트입력과-전사재사용.md#record-1)·[저장 전사 재사용](docs/guides/텍스트입력과-전사재사용.md#record-2)을 참고한다. 사용자 스크립트는 원음·화자·정확한 종료 시각이 검증된 전사가 아니다.
- 후속으로 소개 사례의 정상/실제 배제 경계를 보강하고 `relatedFindingEvidence` 응답을 추가했다. 공유 근거만 표시하며 카드·판정·대상·점수·검수 상태를 합치지 않는다. Spring 재시작 후 기존126 조회로 적용을 확인해야 한다. 규칙 외부화·조기 중복 제거·정규화·가중치 변경은 보류,공용 프롬프트·후보 창·검증기는 그대로다. 성씨 쟁점은 정보 부족으로 유지하며 추가 유료 반복은 자동 진행하지 않는다.
